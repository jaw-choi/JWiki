오전 요약

1. 포인터, new/delete, 메모리 누수의 본질
    

- std::string도 내부적으로는 문자 데이터를 가리키는 포인터(주소)를 관리합니다. 결국 핵심은 주소를 누가 들고 있느냐입니다.
    
- new는 힙에 메모리를 할당하고 시작 주소를 반환합니다.
    
- 반환된 주소를 포인터 변수에 받지 않으면, 힙에 공간은 생겼는데 그 주소를 아무도 모르는 상태가 됩니다. 이게 대표적인 메모리 유실(누수) 패턴입니다.
    
- 포인터 변수 p(스택에 존재)와 new로 만든 객체(힙에 존재)는 별개이며, 대입으로 연결되어야 합니다.
    
- 함수가 끝나면 스택의 지역 변수(포인터 포함)는 사라질 수 있는데, 힙 객체를 가리키는 포인터가 사라지면 힙 객체는 남아도 접근 불가가 되어 누수가 됩니다.
    
- delete는 해당 주소로 가서 메모리를 해제합니다. 내부적으로는 결국 OS(커널)의 메모리 관리 루틴으로 이어집니다.
    
- new/delete는 반드시 쌍으로 관리해야 합니다.
    
- 배열 할당(new[])과 단일 할당(new)에 따라 해제도 delete[] / delete로 맞춰야 합니다.
    

2. 값 복사 vs 주소 복사
    

- int 같은 값 타입은 대입 시 값이 복사됩니다. 원본을 바꿔도 복사본은 영향이 없습니다.
    
- 포인터/참조는 결국 주소가 복사됩니다. 완전한 “복사 없음”은 불가능하고, 최소화의 의미는 큰 데이터 대신 주소만 주고받는다는 뜻입니다.
    

3. 메모리 영역(세그먼트) 큰 그림
    

- 프로그램 메모리는 크게 코드 영역, 데이터 영역, 힙, 스택으로 나눠서 이해합니다.
    
- 코드 영역: 컴파일된 명령어(실행 코드)
    
- 데이터 영역: 전역 변수, static 변수 등 프로그램 시작부터 종료까지 유지되는 것
    
- 힙: 런타임(실행 중) 동적 할당 영역
    
- 스택: 함수 호출 프레임(매개변수, 지역변수 등) 쌓이는 영역, LIFO 구조
    

4. RAM, 저장장치, 가상 메모리 개념
    

- 결국 물리적으로는 RAM 하나를 OS가 효율적으로 나눠 쓰는 관점입니다.
    
- RAM이 부족하면 OS가 디스크(SSD/HDD)를 일부 메모리처럼 쓰는 가상 메모리(스왑/페이지)를 사용해 버팁니다.
    
- 그래서 RAM이 부족해도 어느 정도까지는 프로그램이 돌아가지만, 디스크를 끌어 쓰면 느려질 수 있습니다.
    
- 그래도 한계(디스크/주소 공간/정책 등)를 넘으면 new 같은 할당이 실패할 수 있습니다.
    

5. 게임에서의 현실적인 메모리 관리 흐름(요즘 트렌드 강조)
    

- 동적 할당/해제는 비용이 있어 성능에 불리할 수 있습니다.
    
- 그래서 요즘 대형 게임/엔진은 자주 쓰는 큰 메모리를 시작 시 크게 잡아두고, 해제를 자주 하지 않고 재사용하는 방식(풀링, 커스텀 할당자, 아레나 등)이 흔합니다.
    
- 과거: 잘게 할당하고 빨리 해제하는 패턴을 미덕으로 보던 시대가 있었음
    
- 최근: 메모리를 더 쓰더라도 할당/해제 빈도를 줄여 프레임 안정성을 확보하는 경향이 강함
    

6. 직렬화(Serialization)와 파싱(Parsing)
    

- 직렬화: 메모리의 객체/상태를 다른 시스템으로 보낼 수 있는 형태로 바꾸는 행위(파일 저장, 네트워크 전송, 에디터↔런타임 상태 전달 등)
    
- 역직렬화: 그 데이터를 다시 객체로 복원하는 행위
    
- 파싱: 저장된 포맷을 해석하는 과정 자체를 의미하며, 직렬화 시스템의 구성 요소로 들어갈 때가 많습니다. 범위는 직렬화가 더 큽니다.
    
- 엔진에서 플레이/정지 시 상태를 스냅샷처럼 저장했다가 복구하는 것도 직렬화 시스템으로 이해할 수 있습니다.
    
- Unity의 SerializeField, Unreal의 UPROPERTY 같은 에디터 노출/저장 연계도 직렬화 맥락으로 연결됩니다.
    

7. 객체지향(OOP)에서 클래스와 객체, 그리고 역사/의도
    

- 클래스 자체를 객체라고 단정하면 면접에서 꼬리 질문에 취약해질 수 있습니다. 클래스는 객체를 만들기 위한 설계 단위로 보는 편이 안전합니다.
    
- 객체지향은 절차지향으로 풀기 어려운 복잡성을 다루기 위해 나온 문제 해결 패러다임입니다.
    
- 역사 흐름(요지)
    
    - Simula: 클래스/상속 개념의 초기 도입
        
    - Smalltalk(앨런 케이): 메시지 기반 객체 개념을 강하게 밀어붙임
        
    - C++: C 사용자들이 자연스럽게 넘어오도록 문법 친화성을 확보하며 보급
        
    - Java/C#: 객체지향을 실용적으로 정제하면서 대중화
        
- 앨런 케이 관점의 핵심은 변수 숨기기 자체가 목적이라기보다, 객체 간 소통에서 상대가 알 필요 없는 내부는 감추고 필요한 메시지만 주고받게 하자는 방향입니다. public 메서드를 메시지로 보고 소통하자는 관점입니다.
    

8. 객체지향 만능론이 아니라, 실전 중심 태도
    

- 객체지향은 한때 정답처럼 여겨졌지만, 성능과 데이터 접근 효율 문제로 데이터 중심 설계(DOD, data-driven)가 강하게 도전한 시기도 있었습니다.
    
- 다만 데이터 중심은 사람이 유지·확장하기 어렵고 개발 속도가 느려지는 비용이 있어, 현실에서는 절충/부분 적용으로 자리 잡는 경우가 많습니다.
    
- 결론적으로 업계는 이론 선행보다 구현과 검증이 앞서는 경우가 많고, 일정 수준 전까지는 구현 경험을 통해 감을 쌓는 것이 유리하다는 메시지였습니다.

## 2. 왜 필요한가? (Why)

## 3. 핵심 개념 (What)

- **L"" 리터럴:** C++에서 wide character 문자열을 직접 정의하는 방법이다. 예를 들어, `L"hello world"`는 wide character 문자열을 나타낸다.

## 4. 동작 과정 (How)

3.  컴파일러는 TEXT 매크로 또는 L"" 리터럴을 만나면 해당 문자열을 wide character로 변환한다.

# [C++] new와 delete, 메모리 누수

## 1. 한 줄 요약
C++에서 `new`로 할당된 메모리는 반드시 `delete`로 해제해야 하며, 그렇지 않으면 메모리 누수가 발생한다. Unreal Engine에서는 자체 메모리 관리 시스템을 사용하므로 `new`와 `delete`를 직접 사용하는 것을 지양해야 한다.

## 2. 왜 필요한가? (Why)
- 메모리 누수는 프로그램의 성능 저하 및 시스템 불안정으로 이어질 수 있다.
- `new`와 `delete`를 올바르게 사용하지 않으면 메모리 누수가 발생하기 쉽다.
- Unreal Engine에서는 자체 메모리 관리 시스템을 통해 메모리 누수를 방지하고 효율적인 메모리 관리를 제공한다.

## 3. 핵심 개념 (What)
- **메모리 누수:** `new`로 할당된 메모리를 `delete`로 해제하지 않아 해당 메모리를 더 이상 사용할 수 없게 되는 현상.
- **`new` 연산자:** 힙(heap) 영역에 메모리를 동적으로 할당하는 연산자.
- **`delete` 연산자:** `new`로 할당된 메모리를 해제하여 시스템에 반환하는 연산자.
- **스마트 포인터:** 메모리 관리를 자동으로 처리해주는 클래스 템플릿. `std::unique_ptr`, `std::shared_ptr` 등이 있다.

## 4. 동작 과정 (How)
1.  `new` 연산자를 사용하여 힙 영역에 메모리를 할당한다.
2.  할당된 메모리의 주소를 포인터 변수에 저장한다.
3.  더 이상 해당 메모리가 필요하지 않으면 `delete` 연산자를 사용하여 메모리를 해제한다.
4.  스마트 포인터를 사용하면 메모리 해제를 자동으로 처리할 수 있다.

## 5. 장단점 / 트레이드오프
- 장점:
  - `new`와 `delete`를 직접 사용하면 메모리 관리에 대한 높은 자유도를 가질 수 있다.
  - 스마트 포인터를 사용하면 메모리 누수를 방지하고 코드를 간결하게 유지할 수 있다.
- 단점:
  - `new`와 `delete`를 직접 사용할 경우 메모리 누수 발생 가능성이 높다.
  - 스마트 포인터는 약간의 성능 오버헤드가 있을 수 있다.

## 6. 자주 나오는 질문 / 오해
- Q: Unreal Engine에서는 `new`와 `delete`를 사용하면 안 되나요?
- A: Unreal Engine에서는 자체 메모리 관리 시스템을 사용하므로 `new`와 `delete`를 직접 사용하는 것을 지양해야 합니다. 대신 Unreal Engine에서 제공하는 스마트 포인터나 메모리 관리 기능을 사용하는 것이 좋습니다.

# [CS] 메모리 구조: 스택, 힙, 데이터, 코드 영역

## 1. 한 줄 요약
프로그램의 메모리는 크게 스택, 힙, 데이터, 코드 영역으로 나뉘며, 각 영역은 서로 다른 용도로 사용된다.

## 2. 왜 필요한가? (Why)
- 메모리 구조를 이해하면 프로그램의 동작 방식과 성능을 최적화하는 데 도움이 된다.
- 각 영역의 특징을 알면 메모리 관련 오류를 쉽게 해결할 수 있다.
- 메모리 관리는 게임 개발에서 매우 중요한 요소이므로, 메모리 구조에 대한 이해는 필수적이다.

## 3. 핵심 개념 (What)
- **스택(Stack):** 함수 호출과 관련된 지역 변수, 매개변수, 반환 주소 등이 저장되는 영역. LIFO(Last-In-First-Out) 구조를 가진다.
- **힙(Heap):** 동적으로 할당되는 메모리가 저장되는 영역. `new` 연산자를 통해 할당된 메모리는 힙에 저장된다.
- **데이터 영역:** 전역 변수, 정적 변수 등이 저장되는 영역. 프로그램 시작 시 할당되어 종료 시 해제된다.
- **코드 영역:** 실행할 프로그램의 코드가 저장되는 영역.

## 4. 동작 과정 (How)
1.  함수가 호출되면 스택에 새로운 프레임이 생성된다.
2.  프레임에는 지역 변수, 매개변수, 반환 주소 등이 저장된다.
3.  함수가 종료되면 스택에서 해당 프레임이 제거된다.
4.  `new` 연산자를 통해 힙에 메모리가 할당된다.
5.  `delete` 연산자를 통해 힙에 할당된 메모리가 해제된다.
6.  전역 변수와 정적 변수는 프로그램 시작 시 데이터 영역에 할당된다.
7.  실행할 프로그램의 코드는 코드 영역에 저장된다.

## 5. 장단점 / 트레이드오프
- 스택:
  - 장점: 빠른 접근 속도, 자동 메모리 관리
  - 단점: 크기 제한, 동적 할당 불가능
- 힙:
  - 장점: 동적 할당 가능, 크기 제한 없음
  - 단점: 느린 접근 속도, 수동 메모리 관리 필요
- 데이터 영역:
  - 장점: 프로그램 전체에서 접근 가능
  - 단점: 메모리 낭비 가능성, 초기화 순서 중요
- 코드 영역:
  - 장점: 실행 코드 저장
  - 단점: 수정 불가능

## 6. 자주 나오는 질문 / 오해
- Q: 스택과 힙의 차이점은 무엇인가요?
- A: 스택은 함수 호출과 관련된 데이터를 저장하는 영역으로, LIFO 구조를 가지며 빠른 접근 속도를 제공합니다. 힙은 동적으로 할당되는 메모리를 저장하는 영역으로, 크기 제한이 없지만 느린 접근 속도를 가집니다.

# [CS] 직렬화(Serialization)와 파싱(Parsing)

## 1. 한 줄 요약
직렬화는 메모리에 있는 객체나 데이터를 파일, 네트워크 등으로 전송하기 위해 특정 형식으로 변환하는 과정이며, 파싱은 그 데이터를 다시 객체로 복원하는 과정이다.

## 2. 왜 필요한가? (Why)
- 게임 상태 저장 및 로드
- 네트워크를 통한 데이터 전송
- 에디터와 런타임 간의 데이터 교환
- 설정 파일 관리

## 3. 핵심 개념 (What)
- **직렬화(Serialization):** 객체의 상태를 바이트 스트림으로 변환하는 과정.
- **파싱(Parsing):** 바이트 스트림을 다시 객체로 복원하는 과정.
- **포맷(Format):** 데이터를 저장하는 방식 (JSON, XML, Binary 등).

## 4. 동작 과정 (How)
1.  객체의 데이터를 특정 포맷에 맞춰 바이트 스트림으로 변환한다.
2.  변환된 바이트 스트림을 파일에 저장하거나 네트워크를 통해 전송한다.
3.  수신 측에서는 바이트 스트림을 다시 객체로 복원한다.

## 5. 장단점 / 트레이드오프
- 장점:
  - 데이터 저장 및 전송 용이
  - 플랫폼 간 호환성
- 단점:
  - 성능 오버헤드
  - 보안 문제 (데이터 위변조)
  - 포맷에 따른 복잡성 증가

## 6. 자주 나오는 질문 / 오해
- Q: 직렬화와 파싱은 왜 필요한가요?
- A: 직렬화는 객체의 상태를 저장하거나 네트워크를 통해 전송하기 위해 필요하며, 파싱은 그 데이터를 다시 객체로 복원하기 위해 필요합니다.

## 7. 프로젝트에서 어디에 쓰일 수 있는가
- 게임 저장 및 로드 시스템

### 3. 객체 풀링(Object Pooling)

- **개선된 코드:**
  ```cpp
  #include <iostream>
  #include <vector>

  class ObjectPool {
  public:
      ObjectPool(int size) {
          objects.resize(size);
          for (int i = 0; i < size; ++i) {
              available.push_back(&objects[i]);
          }
      }

      GameObject* GetObject() {
          if (available.empty()) {
              return nullptr; // 풀에 객체가 없으면 nullptr 반환
          }
          GameObject* obj = available.back();
          available.pop_back();
          return obj;
      }

      void ReturnObject(GameObject* obj) {
          available.push_back(obj);
      }

  private:
      std::vector<GameObject> objects;
      std::vector<GameObject*> available;
  };

  int main() {
      ObjectPool pool(10);
      GameObject* obj = pool.GetObject();
      if (obj) {
          // 객체 사용
          pool.ReturnObject(obj);
      }
      return 0;
  }
  ```
- **성능 최적화:**
  - 객체 풀링은 객체 생성 및 삭제 비용을 줄여 성능을 향상시킬 수 있습니다.
  - 자주 사용되는 객체를 미리 생성해두고 재사용하는 방식으로 메모리 할당 및 해제 빈도를 줄입니다.

**답변:** C++에서 메모리 누수를 방지하는 방법은 여러 가지가 있습니다.

1.  **RAII(Resource Acquisition Is Initialization) 원칙 준수:** 객체 생성 시 자원을 할당하고, 객체 소멸 시 자원을 해제하는 방식으로 자원 관리를 자동화합니다.

3.  **`new`와 `delete` 쌍으로 사용:** `new`로 할당된 메모리는 반드시 `delete`로 해제해야 합니다. 배열을 할당할 때는 `new[]`를 사용하고, 해제할 때는 `delete[]`를 사용해야 합니다.
4.  **객체 풀링 사용:** 자주 사용되는 객체를 미리 생성해두고 재사용하는 방식으로 메모리 할당 및 해제 빈도를 줄입니다.
