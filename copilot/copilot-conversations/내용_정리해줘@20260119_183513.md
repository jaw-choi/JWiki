### OT 및 장비 셋팅

- 기업 자소서에 AI 사용 관련 보고서가 많아지는 추세

### 그래픽 공부 방향

- DirectX 11로 시작
- Vulkan
- 운영체제, 하드웨어, CPU(주), GPU, 엔진(미들웨어)

### 강사 소개

- 기술 스택: C#, C++, HLSL, Node.js, Java, DB
- 선발 기준: 컨텐츠 vs 시스템 중 더 재미있는 분야

### 주요 내용

- 파일 입출력, DLL 관련 작업 多
- 자료구조 중요 (선형, 비선형)
  - 선형 자료구조: 동적 배열 (중요)
  - 비선형 자료구조: HashTable
  - 자료구조 선택 기준: 속도 우선
- 정렬 알고리즘
  - 버블, 선택, 삽입 (개수가 적을 때 사용, 삽입 정렬이 그나마 나음)
  - 퀵, 병합, 힙
  - 인트로소트: 퀵, 삽입, 힙 결합 (자료 개수에 따라 정렬 방식 변경)
- A* 알고리즘, 쿼드트리 시각화 프로젝트
- 탐색 알고리즘: BFS, DFS, RedBlackTree
- 보간: Lerp(선형 보간) 공식 암기, 베지어 곡선, 스플라인

### 언리얼 엔진

- `EXAMPLEPROJECT_API`: DLL 외부 or 내부 관련
- `GENERATED_BODY()`: RTTI 관련
- 언리얼은 소멸자를 직접 만들면 안 됨 (내부적으로 처리)
- 유니티와 달리 언리얼도 MAIN 함수 존재
- 동적/정적 라이브러리 (DLL)
  - 전략 1: 엔진을 DLL로, 게임에서 엔진 DLL 로드 후 EXE 생성
  - 전략 2: 자체 기능도 DLL로 추출, 엔진이 최종 조립
  - 컴파일러 옵션, IL2CPP

### 코딩 스탠다드

- 에픽게임즈 코딩 스탠다드 준수
  - [에픽게임즈 C++ 코딩 스탠다드](https://dev.epicgames.com/documentation/ko-kr/unreal-engine/epic-cplusplus-coding-standard-for-unreal-engine#%ED%81%B4%EB%9E%98%EC%8A%A4%EC%B2%B4%EA%B3%84)

### 기타

- 언리얼은 64비트만 제공 (포인터 8바이트)
- 포인터 크기 추정 금지
- 문자 관련: `const char*` (1byte), `wchar_t*` (2byte), `\n` (LF), `\r\n` (CRLF)

- 컴파일 과정: 전처리, 컴파일, 어셈블러, OBJ 파일

**ai**: 컴파일 과정은 다음과 같습니다:

1.  **전처리 (Preprocessing)**:
    -   `#include`와 같은 전처리 지시문을 처리합니다.
    -   헤더 파일을 포함하고, 매크로를 확장하며, 조건부 컴파일을 수행합니다.
    -   주석을 제거합니다.
    -   결과물은 수정된 소스 코드입니다.

2.  **컴파일 (Compilation)**:
    -   전처리된 소스 코드를 어셈블리어로 변환합니다.
    -   각 소스 파일은 독립적으로 컴파일됩니다.
    -   컴파일러는 문법 및 의미론적 오류를 검사합니다.
    -   결과물은 어셈블리어 코드입니다.

3.  **어셈블 (Assembly)**:
    -   어셈블리어 코드를 기계어(object code)로 변환합니다.
    -   각 어셈블리 파일은 해당하는 목적 파일(.obj 또는 .o)로 변환됩니다.
    -   결과물은 목적 파일입니다.

4.  **링크 (Linking)**:
    -   여러 개의 목적 파일과 라이브러리 파일을 결합하여 하나의 실행 파일 또는 라이브러리 파일을 생성합니다.
    -   외부 참조(external references)를 해결합니다. 예를 들어, 다른 파일에서 정의된 함수나 변수를 연결합니다.
    -   정적 라이브러리(.lib 또는 .a)는 링크 시에 실행 파일에 포함됩니다.
    -   동적 라이브러리(.dll 또는 .so)는 실행 시에 로드됩니다.
    -   결과물은 실행 파일(.exe) 또는 라이브러리 파일(.dll, .so, .lib, .a)입니다.

# [CS - 동적 배열]

## 1. 한 줄 요약
동적 배열은 실행 시간에 크기를 변경할 수 있는 배열로, 메모리 관리의 유연성을 제공한다.

## 2. 왜 필요한가? (Why)
- 기존 배열의 고정 크기 제약 극복
- 런타임에 데이터 크기 변화에 대응
- 메모리 효율성 향상 (필요한 만큼만 할당)

## 3. 핵심 개념 (What)
- 연속된 메모리 공간에 데이터 저장
- 크기 자동 조절 ( reallocation )
- 요소 추가/삭제 시 메모리 재할당 발생 가능

## 4. 동작 과정 (How)
1.  초기 크기로 배열 생성
2.  요소 추가 시, 배열이 가득 차면 더 큰 메모리 공간 할당 후 데이터 복사
3.  기존 메모리 공간 해제

## 5. 장단점 / 트레이드오프
- 장점: 유연한 크기 조절, 메모리 효율성
- 단점: 잦은 reallocation 시 성능 저하, 메모리 복사 오버헤드

## 6. 자주 나오는 질문 / 오해
- Q: reallocation 은 언제 발생하는가?
- A: 배열의 capacity 를 초과하는 요소가 추가될 때 발생

## 7. 프로젝트에서 어디에 쓰일 수 있는가
- 게임 오브젝트 관리
- 파티클 시스템
- 사용자 입력 처리

# [CS - HashTable]

## 1. 한 줄 요약
HashTable 은 키-값 쌍을 저장하고, 키를 사용하여 빠르게 값을 검색할 수 있는 자료구조이다.

## 2. 왜 필요한가? (Why)
- 빠른 데이터 검색 (평균 O(1) 시간 복잡도)
- 대용량 데이터 처리 효율성
- 데이터베이스 인덱싱, 캐싱 등에 활용

## 3. 핵심 개념 (What)
- 키(Key)와 값(Value)의 쌍으로 데이터 저장
- 해시 함수(Hash Function)를 사용하여 키를 해시값으로 변환
- 해시값을 인덱스로 사용하여 배열에 데이터 저장

## 4. 동작 과정 (How)
1.  키를 해시 함수에 입력하여 해시값 생성
2.  해시값을 배열의 인덱스로 사용
3.  해당 인덱스에 키-값 쌍 저장 (충돌 발생 시 Collision Resolution 전략 사용)

## 5. 장단점 / 트레이드오프
- 장점: 빠른 검색 속도, 효율적인 데이터 관리
- 단점: 해시 충돌 가능성, 추가적인 공간 필요

## 6. 자주 나오는 질문 / 오해
- Q: 해시 충돌은 어떻게 해결하는가?
- A: Separate Chaining, Open Addressing 등 다양한 방법 존재

## 7. 프로젝트에서 어디에 쓰일 수 있는가
- 게임 오브젝트의 빠른 검색
- 설정 데이터 관리
- 캐싱 시스템 구현

## 1. 한 줄 요약
정렬 알고리즘은 데이터를 특정 순서대로 재배열하는 알고리즘으로, 효율적인 데이터 검색 및 관리에 필수적이다.

## 2. 왜 필요한가? (Why)
- 데이터 검색 속도 향상
- 데이터 분석 및 시각화 용이
- 효율적인 데이터 관리

- 각 알고리즘은 시간 복잡도와 공간 복잡도 측면에서 트레이드오프 존재

## 4. 동작 과정 (How)

# [Unreal Engine - RTTI]

## 1. 한 줄 요약
RTTI (Runtime Type Information)는 런타임에 객체의 타입을 식별하고 정보를 얻을 수 있는 메커니즘이다.

## 2. 왜 필요한가? (Why)
- 런타임에 객체 타입 확인
- 다형성 구현
- 안전한 타입 캐스팅

## 3. 핵심 개념 (What)
- `dynamic_cast`, `typeid` 연산자 사용
- 클래스 계층 구조 정보 제공
- 런타임 타입 검사

## 4. 동작 과정 (How)
1.  `dynamic_cast`: 런타임에 타입 변환 시도, 실패 시 `nullptr` 반환
2.  `typeid`: 객체의 `type_info` 객체 반환

## 5. 장단점 / 트레이드오프
- 장점: 런타임 타입 안정성 확보, 다형성 활용
- 단점: 성능 오버헤드 발생 가능성, 코드 복잡성 증가

## 6. 자주 나오는 질문 / 오해
- Q: RTTI 를 사용하지 않고 다형성을 구현할 수 있는가?
- A: 템플릿 메타 프로그래밍 등 다른 방법 존재

## 7. 프로젝트에서 어디에 쓰일 수 있는가
- 게임 오브젝트 타입에 따른 동작 분기
- 에디터 기능 확장
- 시리얼라이제이션
