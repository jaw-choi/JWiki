## 1. [CS] const 위치에 따른 의미

### 1. 한 줄 요약

C++에서 `const`의 위치에 따라 포인터, 레퍼런스, 멤버 함수의 상수성을 지정하여 객체의 불변성을 강화하고, 코드의 안정성을 높일 수 있습니다.

### 2. 왜 필요한가? (Why)

-   **코드 안정성**: `const`를 통해 의도치 않은 값 변경을 방지하여 프로그램의 안정성을 높입니다.
-   **가독성**: 변수나 함수가 변경 가능한지 여부를 명확히 하여 코드의 가독성을 향상시킵니다.
-   **컴파일러 최적화**: `const` 정보를 활용하여 컴파일러가 더 효율적인 코드를 생성할 수 있습니다.

### 3. 핵심 개념 (What)

-   **`const T& x`**: 참조 대상인 `T` 객체의 상태를 변경할 수 없습니다.
-   **`T& const x`**: 참조는 재바인딩이 불가능하므로 `const`를 붙여도 의미가 없습니다.
-   **`const T* p`**: 포인터 `p`가 가리키는 대상 `T`의 값을 변경할 수 없지만, `p`는 다른 주소를 가리킬 수 있습니다.
-   **`T* const p`**: 포인터 `p` 자체(주소값)를 변경할 수 없지만, `p`가 가리키는 대상 `T`의 값은 변경할 수 있습니다.
-   **`const T* const p`**: 포인터 `p`와 `p`가 가리키는 대상 `T` 모두 변경할 수 없습니다.
-   **`T::Func() const`**: 멤버 함수 내에서 `this` 포인터가 가리키는 객체의 상태를 변경할 수 없습니다 (논리적 `const`).

### 4. 동작 과정 (How)

-   컴파일러는 `const`로 선언된 변수나 함수가 해당 규칙을 위반하는지 검사합니다.
-   위반 시 컴파일 에러를 발생시켜 잠재적인 버그를 사전에 방지합니다.
-   `const` 멤버 함수 내에서는 멤버 변수의 값을 변경할 수 없습니다 (mutable 키워드 예외).

### 5. 장단점 / 트레이드오프

-   **장점**:
    -   코드 안정성 및 가독성 향상
    -   컴파일러 최적화 가능성 증가
-   **단점**:
    -   `const`를 남용하면 코드 수정이 번거로워질 수 있습니다.
    -   `const`를 사용하는 데 대한 학습 비용이 발생할 수 있습니다.

### 6. 자주 나오는 질문 / 오해

-   **Q**: 논리적 `const`란 무엇인가요?
-   **A**: 객체의 외부 상태는 변하지 않지만, 내부적인 상태(예: 캐시)는 변경할 수 있는 경우를 의미합니다. `mutable` 키워드를 사용하여 논리적 `const`를 구현할 수 있습니다.

### 7. 프로젝트에서 어디에 쓰일 수 있는가

-   **API 설계**: 함수 인자를 `const` 참조로 전달하여 불필요한 복사를 방지하고, 원본 데이터를 보호합니다.
-   **클래스 설계**: 멤버 함수를 `const`로 선언하여 객체의 상태를 변경하지 않는 함수임을 명시합니다.
-   **멀티스레드 환경**: `const` 객체는 여러 스레드에서 동시에 접근해도 안전하므로, 동기화 비용을 줄일 수 있습니다.

## 2. [CS] 널 포인터 멤버 함수 호출

### 1. 한 줄 요약

C++에서 널 포인터로 멤버 함수를 호출하는 것은 정의되지 않은 동작(Undefined Behavior)이지만, 함수 자체는 호출될 수 있으며, 멤버 변수에 접근할 때 런타임 오류가 발생합니다.

### 2. 왜 필요한가? (Why)

-   **오류 방지**: 널 포인터 역참조로 인한 예기치 않은 동작을 이해하고 방지합니다.
-   **디버깅**: 널 포인터 관련 문제를 효과적으로 디버깅합니다.
-   **안전한 코딩**: 널 포인터에 대한 방어적인 코딩 습관을 기릅니다.

### 3. 핵심 개념 (What)

-   **Undefined Behavior**: C++ 표준에서 정의되지 않은 동작으로, 컴파일러나 환경에 따라 다르게 동작할 수 있습니다.
-   **`this` 포인터**: 멤버 함수는 암묵적으로 `this` 포인터를 전달받아 객체 자신을 가리킵니다.
-   **널 포인터 역참조**: 널 포인터를 통해 메모리에 접근하려는 시도입니다.

### 4. 동작 과정 (How)

1.  널 포인터로 멤버 함수를 호출하면, 함수 자체는 호출될 수 있습니다.
2.  멤버 함수 내에서 `this` 포인터를 통해 멤버 변수에 접근하려는 순간 런타임 오류(세그멘테이션 오류)가 발생합니다.
3.  C++은 C의 방식을 활용하므로, 클래스 내부 함수도 전역 함수처럼 취급될 수 있습니다.

### 5. 장단점 / 트레이드오프

-   **장점**:
    -   널 포인터 관련 오류를 사전에 방지할 수 있습니다.
-   **단점**:
    -   널 포인터 오류는 디버깅이 어려울 수 있습니다.
    -   방어적인 코딩이 필요합니다.

### 6. 자주 나오는 질문 / 오해

-   **Q**: 왜 널 포인터로 멤버 함수 호출이 겉보기에는 되는 경우가 있나요?
-   **A**: 멤버 함수가 멤버 변수에 접근하지 않는 경우, `this` 포인터를 사용하지 않으므로 런타임 오류가 발생하지 않을 수 있습니다.

### 7. 프로젝트에서 어디에 쓰일 수 있는가

-   **객체 유효성 검사**: 멤버 함수 호출 전에 객체가 유효한지 확인합니다.
-   **방어적 프로그래밍**: 널 포인터에 대한 예외 처리를 추가합니다.
-   **디버깅 도구**: 널 포인터 역참조를 감지하는 디버깅 도구를 활용합니다.

## 3. [CS] 포인터 배열 삭제

### 1. 한 줄 요약

C++에서 포인터 배열을 삭제할 때는 배열의 각 요소를 개별적으로 삭제해야 하는지, 배열 전체를 `delete[]`로 삭제해야 하는지 주의해야 합니다.

### 2. 왜 필요한가? (Why)

-   **메모리 누수 방지**: 동적으로 할당된 메모리를 제대로 해제하지 않으면 메모리 누수가 발생합니다.
-   **이중 해제 방지**: 이미 해제된 메모리를 다시 해제하면 프로그램이 비정상적으로 종료될 수 있습니다.
-   **안전한 코드**: 메모리 관리를 철저히 하여 안정적인 코드를 작성합니다.

### 3. 핵심 개념 (What)

-   **스택 vs 힙**: 스택에 할당된 메모리는 자동으로 해제되지만, 힙에 할당된 메모리는 프로그래머가 직접 해제해야 합니다.
-   **`new` vs `new[]`**: `new`는 단일 객체를 할당하고, `new[]`는 객체 배열을 할당합니다.
-   **`delete` vs `delete[]`**: `delete`는 단일 객체를 해제하고, `delete[]`는 객체 배열을 해제합니다.

### 4. 동작 과정 (How)

1.  `Entity* entities[count]`는 스택에 할당된 포인터 배열이므로, `delete[] entities`는 잘못된 연산입니다.
2.  각 포인터가 가리키는 객체를 `delete entity`로 개별적으로 해제해야 합니다.
3.  range-for 루프에서 포인터 값을 `nullptr`로 변경하려면, 참조(`Entity*&`)를 사용해야 합니다.

### 5. 장단점 / 트레이드오프

-   **장점**:
    -   메모리 누수 및 이중 해제를 방지할 수 있습니다.
-   **단점**:
    -   메모리 관리 코드가 복잡해질 수 있습니다.
    -   실수하기 쉽습니다.

### 6. 자주 나오는 질문 / 오해

-   **Q**: `delete[] entities`가 왜 잘못되었나요?
-   **A**: `entities` 배열 자체가 `new[]`로 할당되지 않았기 때문입니다. 스택에 할당된 배열은 자동으로 해제됩니다.

### 7. 프로젝트에서 어디에 쓰일 수 있는가

-   **동적 배열 관리**: 동적으로 할당된 배열을 안전하게 해제합니다.
-   **리소스 관리**: 객체의 생명 주기를 철저히 관리합니다.
-   **스마트 포인터**: 메모리 관리를 자동화하기 위해 스마트 포인터를 사용합니다.

## 4. [CS] Friend 함수

### 1. 한 줄 요약

`friend`는 특정 외부 함수나 클래스에게만 `private`/`protected` 멤버에 대한 접근 권한을 예외적으로 허용하는 키워드입니다.

### 2. 왜 필요한가? (Why)

-   **캡슐화 유지**: 클래스의 내부 구현을 숨기면서, 필요한 경우에만 외부 접근을 허용합니다.
-   **유연성**: 클래스 간의 결합도를 낮추면서, 특정 함수나 클래스에게만 특별한 권한을 부여합니다.
-   **코드 재사용성**: 외부 함수나 클래스가 특정 클래스의 멤버에 접근할 수 있도록 허용하여 코드 재사용성을 높입니다.

### 3. 핵심 개념 (What)

-   **캡슐화**: 클래스의 멤버 변수와 함수를 묶어 외부로부터 보호하는 개념입니다.
-   **접근 제어**: `private`, `protected`, `public` 키워드를 사용하여 멤버의 접근 권한을 제어합니다.
-   **Friendship**: 특정 함수나 클래스에게 `private`/`protected` 멤버에 대한 접근 권한을 부여하는 관계입니다.

### 4. 동작 과정 (How)

1.  클래스 내부에 `friend` 키워드를 사용하여 외부 함수나 클래스를 선언합니다.
2.  `friend`로 선언된 함수나 클래스는 해당 클래스의 `private`/`protected` 멤버에 접근할 수 있습니다.
3.  `friend` 함수는 클래스의 멤버 함수가 아니므로, `this` 포인터를 사용할 수 없습니다.

### 5. 장단점 / 트레이드오프

-   **장점**:
    -   캡슐화를 유지하면서 필요한 경우에만 외부 접근을 허용합니다.
    -   클래스 간의 결합도를 낮출 수 있습니다.
    -   코드 재사용성을 높일 수 있습니다.
-   **단점**:
    -   캡슐화를 약화시킬 수 있습니다.
    -   남용하면 코드의 유지보수성이 떨어질 수 있습니다.

### 6. 자주 나오는 질문 / 오해

-   **Q**: `friend` 함수는 클래스의 멤버 함수인가요?
-   **A**: 아닙니다. `friend` 함수는 클래스 내부에 선언되지만, 클래스의 멤버 함수가 아니라 외부 함수입니다.

### 7. 프로젝트에서 어디에 쓰일 수 있는가

-   **연산자 오버로딩**: 클래스 외부에서 연산자를 오버로딩하여 클래스 멤버에 접근할 수 있도록 합니다.
-   **테스트**: 테스트 함수가 클래스의 `private` 멤버에 접근하여 내부 상태를 검증할 수 있도록 합니다.
-   **상호 의존적인 클래스**: 두 클래스가 서로의 `private` 멤버에 접근해야 하는 경우에 사용합니다.

## 5. [CS] 전방 선언

### 1. 한 줄 요약

전방 선언은 컴파일러에게 타입의 존재를 알리지만, 타입의 크기나 멤버에 대한 정보는 제공하지 않는 불완전한 타입 선언입니다.

### 2. 왜 필요한가? (Why)

-   **컴파일 시간 단축**: 헤더 파일의 불필요한 포함을 줄여 컴파일 시간을 단축합니다.
-   **상호 참조 문제 해결**: 두 클래스가 서로를 참조하는 경우, 전방 선언을 사용하여 순환 의존성을 해결합니다.
-   **결합도 감소**: 클래스 간의 결합도를 낮추어 코드의 유연성을 높입니다.

### 3. 핵심 개념 (What)

-   **불완전 타입**: 타입의 크기나 멤버에 대한 정보가 없는 타입입니다.
-   **순환 의존성**: 두 개 이상의 타입이 서로를 참조하는 의존성입니다.
-   **헤더 파일 포함**: 타입의 정의를 포함하는 헤더 파일을 포함하는 것입니다.

### 4. 동작 과정 (How)

1.  클래스 정의 전에 `class MyClass;`와 같이 전방 선언을 합니다.
2.  전방 선언된 타입은 포인터나 참조 타입으로만 사용할 수 있습니다.
3.  타입의 크기나 멤버에 접근해야 하는 경우에는 헤더 파일을 포함해야 합니다.

### 5. 장단점 / 트레이드오프

-   **장점**:
    -   컴파일 시간을 단축할 수 있습니다.
    -   순환 의존성 문제를 해결할 수 있습니다.
    -   클래스 간의 결합도를 낮출 수 있습니다.
-   **단점**:
    -   불완전 타입이므로 사용할 수 있는 연산이 제한됩니다.
    -   헤더 파일을 포함해야 하는 경우가 있습니다.

### 6. 자주 나오는 질문 / 오해

-   **Q**: 전방 선언된 타입으로 객체를 생성할 수 있나요?
-   **A**: 아니요. 전방 선언된 타입은 불완전 타입이므로 객체를 생성할 수 없습니다. 포인터나 참조 타입으로만 사용할 수 있습니다.

### 7. 프로젝트에서 어디에 쓰일 수 있는가

-   **헤더 파일**: 클래스 정의를 포함하지 않고, 전방 선언만으로 충분한 경우에 사용합니다.
-   **상호 참조 클래스**: 두 클래스가 서로를 참조하는 경우에 사용합니다.
-   **컴파일 시간 최적화**: 헤더 파일 포함을 줄여 컴파일 시간을 최적화합니다.

## 코드 개선

### 1. 얕은 복사 vs 깊은 복사

```c++
class Vector {
public:
    int x;
    int y;
};

class MyClass {
public:
    Vector* position;

    // 얕은 복사 (문제 발생)
    MyClass(const MyClass& other) : position(other.position) {}

    // 깊은 복사 (올바른 방법)
    MyClass(const MyClass& other) {
        position = new Vector();
        position->x = other.position->x;
        position->y = other.position->y;
    }

    ~MyClass() {
        delete position; // 깊은 복사를 사용하면 이중 해제 문제 해결
    }
};
```

**개선 사항**:

-   깊은 복사를 통해 메모리 이중 해제 문제를 해결했습니다.
-   복사 생성자에서 멤버 초기화 목록을 사용하여 코드를 간결하게 만들었습니다.

### 2. Range-based for loop

```c++
// 잘못된 코드
/*for (Entity* entity : entities) {
    delete entity;
    entity = nullptr;
}*/

// 올바른 코드
for (Entity*& entity : entities) {
    delete entity;
    entity = nullptr;
}
```

**개선 사항**:

-   참조를 사용하여 배열의 원소를 직접 수정하도록 변경했습니다.
-   이제 `entity = nullptr;`가 배열의 원소를 실제로 `nullptr`로 설정합니다.

## 1. [CS] 포인터와 메모리 관리

### 1. 한 줄 요약

C++에서 포인터는 메모리 주소를 저장하는 변수이며, 메모리 관리는 동적 할당된 메모리의 생명주기를 관리하여 메모리 누수 및 이중 해제를 방지하는 중요한 과정입니다.

### 2. 왜 필요한가? (Why)

-   **유연한 메모리 사용**: 런타임에 필요한 만큼 메모리를 할당하고 해제하여 효율적인 메모리 사용을 가능하게 합니다.
-   **동적 자료 구조**: 연결 리스트, 트리 등 크기가 변할 수 있는 자료 구조를 구현하는 데 필수적입니다.
-   **객체 공유**: 포인터를 통해 객체를 공유하고, 객체의 복사본 없이도 여러 곳에서 동일한 객체를 참조할 수 있습니다.
-   **메모리 누수 방지**: 동적 할당된 메모리를 해제하지 않으면 메모리 누수가 발생하여 시스템 성능 저하를 초래할 수 있습니다.
-   **이중 해제 방지**: 이미 해제된 메모리를 다시 해제하면 프로그램이 비정상적으로 종료될 수 있습니다.

### 3. 핵심 개념 (What)

-   **포인터**: 메모리 주소를 값으로 가지는 변수입니다. `*` 연산자를 사용하여 포인터가 가리키는 메모리 위치의 값에 접근할 수 있습니다.
-   **동적 메모리 할당**: `new` 연산자를 사용하여 힙(heap) 영역에 메모리를 할당하는 것입니다.
-   **동적 메모리 해제**: `delete` 연산자를 사용하여 힙 영역에 할당된 메모리를 해제하는 것입니다. 배열의 경우 `delete[]`를 사용합니다.
-   **스택 vs 힙**: 스택은 함수 호출과 관련된 지역 변수 등을 저장하는 메모리 영역이고, 힙은 동적으로 할당된 메모리를 저장하는 영역입니다. 스택 메모리는 자동으로 관리되지만, 힙 메모리는 프로그래머가 직접 관리해야 합니다.
-   **얕은 복사 vs 깊은 복사**: 얕은 복사는 포인터만 복사하여 동일한 메모리 주소를 가리키게 하는 것이고, 깊은 복사는 메모리를 새로 할당하여 값을 복사하는 것입니다. 깊은 복사를 사용해야 이중 해제 문제를 방지할 수 있습니다.
-   **스마트 포인터**: `std::unique_ptr`, `std::shared_ptr` 등 메모리 관리를 자동화하는 클래스입니다.

### 4. 동작 과정 (How)

1.  포인터 변수를 선언하고, `new` 연산자를 사용하여 메모리를 할당합니다.
2.  포인터를 사용하여 할당된 메모리에 접근하고, 값을 읽거나 씁니다.
3.  더 이상 필요하지 않은 메모리는 `delete` 연산자를 사용하여 해제합니다.
4.  스마트 포인터를 사용하는 경우, 객체가 더 이상 참조되지 않으면 자동으로 메모리가 해제됩니다.

### 5. 장단점 / 트레이드오프

-   **장점**:
    -   유연한 메모리 사용이 가능합니다.
    -   동적 자료 구조를 구현할 수 있습니다.
    -   객체 공유가 가능합니다.
-   **단점**:
    -   메모리 누수 및 이중 해제 위험이 있습니다.
    -   포인터 연산은 오류를 발생시키기 쉽습니다.
    -   스마트 포인터 사용 시 약간의 성능 오버헤드가 발생할 수 있습니다.

### 6. 자주 나오는 질문 / 오해

-   **Q**: 얕은 복사와 깊은 복사의 차이점은 무엇인가요?
-   **A**: 얕은 복사는 포인터만 복사하여 동일한 메모리 주소를 가리키게 하는 것이고, 깊은 복사는 메모리를 새로 할당하여 값을 복사하는 것입니다. 깊은 복사를 사용해야 이중 해제 문제를 방지할 수 있습니다.
-   **Q**: 스마트 포인터는 어떻게 메모리 관리를 자동화하나요?
-   **A**: 스마트 포인터는 객체가 더 이상 참조되지 않으면 자동으로 메모리를 해제합니다. `std::unique_ptr`는 단일 소유권을 가지며, `std::shared_ptr`는 여러 소유권을 가질 수 있습니다.

### 7. 프로젝트에서 어디에 쓰일 수 있는가

-   **게임 엔진**: 게임 오브젝트, 컴포넌트 등 동적으로 생성되고 소멸되는 객체 관리에 사용됩니다.
-   **그래픽스 엔진**: 텍스처, 메시 등 대용량 데이터를 관리하는 데 사용됩니다.
-   **네트워크 프로그래밍**: 네트워크 연결, 패킷 데이터 등을 관리하는 데 사용됩니다.
-   **운영체제**: 프로세스, 스레드 등 시스템 자원을 관리하는 데 사용됩니다.

## 2. [CS] Friend 함수와 전방 선언

### 1. 한 줄 요약

`friend` 함수는 특정 클래스의 `private` 및 `protected` 멤버에 접근할 수 있는 외부 함수이며, 전방 선언은 컴파일러에게 타입의 존재를 알리지만 타입의 크기나 멤버에 대한 정보는 제공하지 않는 불완전한 타입 선언입니다.

### 2. 왜 필요한가? (Why)

-   **캡슐화 유지**: `friend` 함수를 통해 클래스의 내부 구현을 숨기면서, 필요한 경우에만 외부 접근을 허용합니다.
-   **유연성**: `friend` 함수를 사용하여 클래스 간의 결합도를 낮추면서, 특정 함수에게만 특별한 권한을 부여합니다.
-   **코드 재사용성**: `friend` 함수를 통해 외부 함수가 특정 클래스의 멤버에 접근할 수 있도록 허용하여 코드 재사용성을 높입니다.
-   **컴파일 시간 단축**: 전방 선언을 통해 헤더 파일의 불필요한 포함을 줄여 컴파일 시간을 단축합니다.
-   **상호 참조 문제 해결**: 전방 선언을 사용하여 두 클래스가 서로를 참조하는 경우의 순환 의존성을 해결합니다.
-   **결합도 감소**: 전방 선언을 통해 클래스 간의 결합도를 낮추어 코드의 유연성을 높입니다.

### 3. 핵심 개념 (What)

-   **캡슐화**: 클래스의 멤버 변수와 함수를 묶어 외부로부터 보호하는 개념입니다.
-   **접근 제어**: `private`, `protected`, `public` 키워드를 사용하여 멤버의 접근 권한을 제어합니다.
-   **Friendship**: 특정 함수에게 `private`/`protected` 멤버에 대한 접근 권한을 부여하는 관계입니다.
-   **불완전 타입**: 타입의 크기나 멤버에 대한 정보가 없는 타입입니다.
-   **순환 의존성**: 두 개 이상의 타입이 서로를 참조하는 의존성입니다.
-   **헤더 파일 포함**: 타입의 정의를 포함하는 헤더 파일을 포함하는 것입니다.

### 4. 동작 과정 (How)

1.  클래스 내부에 `friend` 키워드를 사용하여 외부 함수를 선언합니다.
2.  `friend`로 선언된 함수는 해당 클래스의 `private`/`protected` 멤버에 접근할 수 있습니다.
3.  클래스 정의 전에 `class MyClass;`와 같이 전방 선언을 합니다.
4.  전방 선언된 타입은 포인터나 참조 타입으로만 사용할 수 있습니다.
5.  타입의 크기나 멤버에 접근해야 하는 경우에는 헤더 파일을 포함해야 합니다.

### 5. 장단점 / 트레이드오프

-   **장점**:
    -   캡슐화를 유지하면서 필요한 경우에만 외부 접근을 허용합니다.
    -   클래스 간의 결합도를 낮출 수 있습니다.
    -   코드 재사용성을 높일 수 있습니다.
    -   컴파일 시간을 단축할 수 있습니다.
    -   순환 의존성 문제를 해결할 수 있습니다.
-   **단점**:
    -   캡슐화를 약화시킬 수 있습니다.
    -   남용하면 코드의 유지보수성이 떨어질 수 있습니다.
    -   불완전 타입이므로 사용할 수 있는 연산이 제한됩니다.
    -   헤더 파일을 포함해야 하는 경우가 있습니다.

### 6. 자주 나오는 질문 / 오해

-   **Q**: `friend` 함수는 클래스의 멤버 함수인가요?
-   **A**: 아닙니다. `friend` 함수는 클래스 내부에 선언되지만, 클래스의 멤버 함수가 아니라 외부 함수입니다.
-   **Q**: 전방 선언된 타입으로 객체를 생성할 수 있나요?
-   **A**: 아니요. 전방 선언된 타입은 불완전 타입이므로 객체를 생성할 수 없습니다. 포인터나 참조 타입으로만 사용할 수 있습니다.

### 7. 프로젝트에서 어디에 쓰일 수 있는가

-   **연산자 오버로딩**: 클래스 외부에서 연산자를 오버로딩하여 클래스 멤버에 접근할 수 있도록 합니다.
-   **테스트**: 테스트 함수가 클래스의 `private` 멤버에 접근하여 내부 상태를 검증할 수 있도록 합니다.
-   **상호 의존적인 클래스**: 두 클래스가 서로의 `private` 멤버에 접근해야 하는 경우에 사용합니다.
-   **헤더 파일**: 클래스 정의를 포함하지 않고, 전방 선언만으로 충분한 경우에 사용합니다.
-   **상호 참조 클래스**: 두 클래스가 서로를 참조하는 경우에 사용합니다.
-   **컴파일 시간 최적화**: 헤더 파일 포함을 줄여 컴파일 시간을 최적화합니다.
