1. 해시테이블 설계 의도    

- 버킷 1차 배열(크기 19, 소수)을 두고, 각 버킷은 vector(동적 배열)로 엔트리 목록을 관리하는 구조

- 키를 string으로 고른 이유: 문자열을 문자 배열로 보고 직접 해시를 만들기 쉬워, 해시 원리 학습에 가장 적합함
    
- STL unordered_map도 동일하게 키 타입에 해시가 정의돼 있어야만 쓸 수 있다는 제약이 존재함
    

2. 해시 함수와 버킷 인덱싱
    

- 문자열 각 문자를 기반으로 곱하고 더하는 방식으로 큰 정수 해시를 생성
    
- 해시 값이 매우 커지고 int에서 오버플로가 발생할 수 있음(디버깅에서 실제로 음수로 넘어감)
    
- 최종 버킷 인덱스는 hash % bucketCount 로 0~18 범위로 가둠
    

3. Add 동작(중복 키 금지)
    

- 버킷 인덱스를 구한 뒤 해당 버킷(vector)을 참조로 받아야 실제 버킷에 추가됨(복사로 받으면 변경 반영 안 됨)
    
- 버킷 내부를 순차 탐색으로 돌며 같은 키가 있으면 실패(false) 반환
    
- 없으면 emplace_back 등으로 엔트리 추가 후 성공(true) 반환
    
- 상용 구현(C# Dictionary, STL unordered_map)도 기본적으로 같은 키 중복을 허용하지 않는 형태가 일반적임
    

4. Delete/Find/Empty/Print 개념
    

- Delete도 동일한 방식으로 버킷을 찾고 버킷 내부를 순차 탐색해 키가 나오면 제거 후 true, 못 찾으면 false
    
- Empty는 전체 버킷을 순회하며 각 vector의 size 합을 구해 0이면 비어있다고 판단
    
- Print는 전체 버킷을 순회하며 각 엔트리의 key/value를 출력
    
- 출력 순서가 입력 순서와 무관한 이유: 해시로 버킷이 결정되므로 저장 위치가 입력 순서와 직접 연동되지 않음

- 핵심 목적은 검색 속도 향상

- 전제: 런타임에 삽입이 매우 빈번하면 해시 계산 비용 때문에 장점이 약해질 수 있음
    
- 추가 최적화 아이디어: 한 번 계산한 해시 값을 캐싱해 다음 검색부터는 문자열→해시 변환을 생략(언리얼은 이런 방식이 내부적으로 활용되는 경우가 있음)

    - 후위: 자식들 먼저, 마지막에 부모

1. 다중 트리

- 부모 노드와 자식 노드 연결
    
    - parent -> AddChild(child)
        
    - child의 parent 포인터 설정
        
    - parent의 children 벡터에 child 주소 저장
        
    - 디버거로 실제 주소값/사이즈 확인 완료
        
- RemoveChild 동작 검증
    
    - parent의 children 벡터에서 해당 child 포인터를 find → erase
        
    - 벡터에서 제거는 정상
        
    - 외부에서 들고 있던 child 포인터는 여전히 이전 주소를 가리킴 (dangling pointer 가능)
        
    - 이건 정상적인 관찰이고, 포인터 소유권/삭제 책임을 어떻게 둘지 설계 이슈임
        
- 재귀 삭제(RemoveRecursive) 구현 방향
    
    - 먼저 찾기 (FindRecursive)
        
    - 찾은 노드의 자손들을 먼저 재귀적으로 제거
        
    - 부모 children 목록에서 본인 제거
        
    - 마지막에 delete
        
    - 이 순서가 맞습니다 (후위 삭제 개념)
        
- 전위 순회(Preorder Traversal) 구현
    
    - 부모 방문 → 자식 순회
        
    - depth 인자로 들여쓰기 출력
        
    - 콘솔에서 계층 구조 확인 가능
        
- 소멸자에서 전체 트리 파괴
    
    - 루트부터 시작해서 자손 먼저 제거 후 자기 제거
        
    - 최종적으로 루트까지 delete
        
    - 메모리 누수 체크
        


4. 객체지향
    

설명하신 메시지 / 공개 메소드 / 정보은닉 비유(은행 직원)는 면접에서도 통하는 설명입니다.  
특히 아래 흐름이 좋습니다.

- 외부는 요청만 한다 (public method 호출)
    
- 내부 구현은 숨긴다 (private)
    
- 필요한 것만 공개한다 (인터페이스)
    

면접용으로 더 짧게 압축하면 이렇게 말하면 좋습니다.

- 객체지향은 객체 간 협력을 중심으로 설계하며, 협력은 공개된 인터페이스(메시지)를 통해 이뤄집니다.
    
- 내부 상태와 구현은 숨기고, 외부에는 필요한 기능만 노출해 결합도를 낮춥니다.
    
- 그래서 변경이 내부에 머물고, 사용자는 인터페이스만 보고 사용할 수 있습니다.
