## 1. 일반적인 웹 서비스 vs 게임 네트워크 서비스

- **일반적인 웹/스트리밍 서비스 (Request-Response 중심)**
    
    - 클라이언트가 요청하면 서버가 응답하는 구조가 일반적임 (예: 로그인, 페이지 이동).
        
    - 스트리밍의 경우, 한 번 요청하면 데이터를 지속적으로 내려받지만 본질적으로 클라이언트의 요청에 응당하는 답을 주는 흐름임.
        
- **게임 서비스 (Continuous Data Flow)**
    
    - 클라이언트의 요청 여부와 상관없이, 서버가 자체 로직에 따라 연산한 변경된 데이터를 클라이언트에게 지속적으로 전송(무지성 송신)함.
        
    - 서버는 렌더링을 하지 않고 오직 데이터(상태) 연산만 돌리며, 클라이언트는 그 데이터를 받아 **렌더링**에 집중함.

## 2. 시대별 MMORPG 서버-클라이언트 역할 변화

- **과거 (강한 서버 중심 구조)**
    
    - 한국은 실시간 동시접속자(동접) 수십~100만 명을 버티는 강력한 서버 기술력을 보유함.
        
    - 해킹 방지 및 데이터 무결성을 위해 **이동, 타격 판정, UI 타이밍 등 핵심 코어 로직을 100% 서버에서 처리**함.
        
    - 클라이언트는 단순히 요청만 보내고 서버가 준 값을 렌더링만 수행하여, 클라 개발자가 엔진의 핵심 코어를 만질 기회가 적었음.
        
- **현재 (클라이언트 연산 비중 확대)**
    
    - 여전히 서버가 메인이지만, 클라이언트 엔진(Unity, Unreal)의 기능이 고도화되면서 클라 쪽으로 로직이 많이 넘어옴.
        
    - 서버가 직접 물리 규칙을 계산해서 이동 속도와 위치를 매번 주는 것이 아니라, **클라에서 먼저 로직(이동 느낌, 타격감 등)을 구현한 뒤 서버와 '동기화'하는 방식**을 취함.
        

## 3. 네트워크 패킷(Packet) 변환과 언리얼 엔진의 역할

- **전통적인 네트워크 프로그래밍 (수동 변환)**
    
    - 서버는 클라이언트 엔진 내부의 데이터 타입(예: 언리얼의 `FVector`)을 알지 못함.
        
    - 따라서 클라와 서버가 모두 이해할 수 있는 공통 구조체 포맷인 '패킷(Packet)'으로 변환(직렬화)하여 주고받아야 함.
        
    - `클라 데이터 타입` → `패킷 변환` → `송신` → `수신` → `패킷 역직렬화` → `서버/클라 타입으로 적용`하는 번거로운 과정을 거침.
        
- **언리얼 엔진의 역할 (RPC 및 복제 자동화)**
    
    - 언리얼 엔진은 이 번거로운 패킷 변환, 커넥션 관리, 번치(Bunch) 처리 등을 내부 엔진 레이어에서 자동으로 수행해 줌.
        
    - 개발자 입장에서는 내부가 가려진 **블랙박스**처럼 느껴질 수 있지만, 핵심 네트워크 코드는 모두 엔진 내부에 구현되어 있음.
        

## 4. 언리얼 엔진 네트워크 실무 및 RPC 검증 (실습 핵심)

- **서버/클라이언트 환경 판별 (`HasAuthority`)**
    
    - 하나의 코드가 서버와 클라이언트 양쪽 모두에 배포될 수 있으므로, 실행 시점에 현재 호스트의 권한을 파악해야 함.
        
    - **오소리티가 있는 경우 (`HasAuthority` == true):** 서버(Server) 또는 독립형 게임(Standalone) 환경임.
        
    - **권한이 없는 경우:** 클라이언트 환경으로, 주체는 프록시(`SimulatedProxy` 또는 `AutonomousProxy`)로 설정됨.
        
- **네트워크 랙(Lag) 시뮬레이션 및 예외 처리 (10강 목표)**
    
    - 실제 네트워크 환경의 지연(Lag)을 의도적으로 발생시키는 엔진 내장 옵션을 활성화하여 테스트 진행.
        
    - **경고 메시지 분석:** `타임스탬프 만료(Timestamp Expired)` → 지연이 너무 심해 데이터의 유효 시간이 지나 폐기됨을 의미. 변경 문구를 새롭게 생성하고 클라 검증 로직을 고도화해야 함.
        
- **랙 극복을 위한 예측(Prediction) 기법**
    
    - **이상적인 구조:** 클라는 요청만 하고, 서버가 처리한 결과를 통보받아 렌더링만 하는 구조 (안전하지만 랙 발생 시 체감이 최악임).
        
    - **보완 방식 (예측 및 클라 선행 실행):** 클라에서 공격이나 이동 등의 명령을 내리면, 서버의 허락(응답)을 기다리지 않고 클라에서 일부 로직을 즉시 선행 실행(Prediction)하여 반응성을 높이고, 추후 서버 데이터와 동기화 및 보정을 진행함.
