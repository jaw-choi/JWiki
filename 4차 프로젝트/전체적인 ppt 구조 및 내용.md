1. 주요 시스템  
플레이어 전투 시스템  
 - CurrentComboState와 ComboGraph 데이터 에셋으로 “상태 노드 → 다음 상태 전이 → 해당 상태의 몽타주 실행” 구조  
 왜?  
  - JumpToSection 중심 방식보다 상태 단위 확장성을 우선한 설계  
  - Attack1 -> Attack2 -> Attack3처럼 단순 일자 콤보만 있으면 JumpToSection도 충분하지만, 이 프로젝트는 검방, 대검, 활마다 입력 분기, 차징, 가드, 패링, 대시, 조준 상태가 섞여 있습니다. 그래서          CurrentComboState를 기준으로 ComboGraph에서 다음 상태를 찾고, 그 상태에 연결된 몽타주를 재생하는 구조를 쓴 것입니다.  
  -콤보 UI와 연결하기 좋습니다.현재 state의 NextTransitions를 보면 다음에 가능한 입력을 UI에 바로 표시할 수 있습니다.  
  - 상태별 로직을 분리하기 좋습니다. 각 state에 들어갈 때 스태미나 감소, 공격속도 적용, 데미지 배율, 무적, 방어력 증가 같은 처리를 명확하게 넣을 수 있습니다.  
  
  
  
퀘스트 시스템  
  - 퀘스트는 데이터 테이블로 내용을 관리하고, 실제 진행 상태는 Player가 EQuestState로 들고 있습니다. 몬스터 처치 이벤트를 받아 진행도를 갱신하는 방식으로 설계했습니다. NPC, UI, 몬스터가 직접 강하게 연결되지 않도록 이벤트 기반 구조를 사용했습니다.  
  
  
  
인벤토리 및 아이템 드랍  
 - 인벤토리는 컴포넌트로 분리했고, 실제 아이템 상세 정보는 데이터 테이블에서 가져오도록 했습니다. 아이템 정보 자체는 FWOMItemData 데이터 테이블에서 가져오고, 플레이어는 FOwnedItemInfo 형태로 ItemID와 개수만 보관합니다. 드랍 아이템은 월드 액터로 존재하다가 플레이어가 상호작용하면 인벤토리에 들어가는 방식입니다.  
  
  
  
무기 강화 시스템  
 - 강화 시스템은 현재 무기 레벨을 기준으로 데이터 테이블에서 필요 재료를 찾고, 인벤토리 검사 후 재료를 차감하는 방식입니다. 강화 조건은 FWOMWeaponUpgradeData에 들어 있습니다. UpgradeLevel과 StepMaterials를 통해 현재 레벨에서 어떤 재료가 필요한지 관리합니다. 강화 조건을 데이터화해서 밸런싱과 수정이 쉽도록 설계했습니다.  
  
  
  
UI / HUD 시스템  
  
  - HUD는 여러 하위 UI를 관리하는 중심 위젯으로 만들었고, 체력/스태미나는 이벤트 기반으로 갱신합니다. 로그나 콤보 UI처럼 여러 시스템에서 접근해야 하는 기능은 GameSingleton을 통해 HUD에 전달했습니다.  
  
몬스터 AI 시스템  
  
  - 몬스터 AI는 Behavior Tree와 Blackboard로 구성했고, 실제 공격 실행은 인터페이스를 통해 몬스터 클래스에 위임했습니다. 그래서 공통 AI Task를 재사용하면서도 몬스터별 공격 방식은 다르게 구현할 수 있었습니다.전체 설계 요약 이 프로젝트의 공통 설계 방향은 꽤 명확합니다.데이터는 DataTable상태 진행은 Enum / Blackboard시스템 연결은 Delegate / InterfaceUI 갱신은 Controller / HUD / Singleton 경유반복 기능은 Component로 분리  
  
  - 발표에서 한 문장으로 정리하면:  
MonsterWorld는 퀘스트, 아이템, 강화 같은 변경이 잦은 정보는 데이터 테이블로 분리하고, 전투와 AI처럼 실행 흐름이 중요한 부분은 상태 기반 구조와 이벤트 기반 구조로 설계했습니다. 덕분에 기능 확장과 밸런싱 수정이 비교적 쉬운 구조를 목표로 했습니다.  
  
  - 몬스터별 AIController가 따로 있고, 실제 몬스터 액터와 AI Task 사이에는 WOMEnemyAIInterface가 끼어 있다는 점입니다.  
BT Task는 “공격해라”라고 인터페이스 함수 AttackByAI()를 호출하고, 실제 어떤 몽타주를 재생할지, 어떤 패턴을 쓸지는 몬스터 클래스가 담당합니다.
