함수를 호출하면 **포인터 값이 그대로 복사되어 매개변수 `ptr`로 전달**된다.  
이때 `delete ptr`을 호출하면 **`ptr`이 가리키던 힙 메모리는 정상적으로 해제**된다.  
그러나 `ptr`은 **복사본이므로**, 함수 내부에서 `ptr = nullptr`로 바꾸더라도  
**함수 호출 이후 원래의 포인터(`pointer`) 값은 변경되지 않는다.**

그 결과,

- 힙 메모리는 해제되었고
    
- 원래의 포인터는 여전히 해제된 주소를 가지고 있어
    

**`pointer`는 댕글링 포인터(dangling pointer)가 된다.**

이 문제를 해결하기 위해  
**이중 포인터(`void**`)를 매개변수로 받는 함수**를 만들고 `&pointer`를 전달하면,  
비록 매개변수 자체는 값 복사이지만 그 값은 **원래 포인터(`pointer`)의 주소**를 가리킨다.

따라서

- `delete *ptr`로 힙 메모리를 해제하고
    
- `*ptr = nullptr`로 원래 포인터를 직접 nullptr로 만들 수 있어
    

**포인터 정리까지 정상적으로 수행된다.**

### 2️⃣ 레퍼런스(`void*&`) 전달인 경우

매개변수를 `void*& ptr`로 받으면,  
이는 **포인터 값의 복사본이 아니라 원래 포인터에 대한 참조(alias)** 가 된다.

따라서

- `delete ptr`은 힙 메모리를 해제하고
    
- `ptr = nullptr`는 곧바로 원래 포인터(`pointer`)를 nullptr로 만든다.
    

이 경우에는  
**이중 포인터를 사용할 때와 동일한 효과를 얻되, 문법적으로 더 간결하게**  
포인터와 메모리를 함께 정리할 수 있다.

**ai**: ## [[CS - #pragma once]]

## 1. 한 줄 요약

`#pragma once`는 헤더 파일이 한 컴파일 단위 내에서 한 번만 포함되도록 하는 전처리기 지시문이다.

## 2. 왜 필요한가? (Why)

- 헤더 파일의 중복 포함을 방지하여 컴파일 시간 단축 및 오류 방지
- include guard (`#ifndef ... #define ... #endif`) 보다 간결하고 효율적

## 3. 핵심 개념 (What)

- 컴파일러에게 헤더 파일이 한 번만 포함되도록 지시
- include guard와 동일한 목적을 달성하지만, 컴파일러 수준에서 처리

## 4. 동작 과정 (How)

1.  컴파일러가 헤더 파일을 처음 포함할 때, 해당 파일을 "포함됨"으로 표시
2.  같은 파일이 다시 포함되려고 하면, 컴파일러는 이를 무시

## 5. 장단점 / 트레이드오프

- 장점:
  -   include guard보다 간결하고 빠름
  -   코드 가독성 향상
- 단점:
  -   표준이 아니므로 일부 컴파일러에서 지원하지 않을 수 있음 (대부분 지원)
  -   파일 시스템에 의존적이므로, 심볼릭 링크 등에 취약할 수 있음 ❓추가 확인 필요

## 6. 자주 나오는 질문 / 오해

- Q: `#pragma once`가 include guard보다 항상 좋은가?
- A: 대부분의 경우 더 나은 선택이지만, 이식성이 중요한 경우 include guard를 사용하는 것이 안전

## 7. 프로젝트에서 어디에 쓰일 수 있는가

- 모든 C++ 프로젝트에서 헤더 파일 중복 포함 방지를 위해 사용 가능

## [[CS - DLL (Dynamic Link Library)]]

## 1. 한 줄 요약

DLL은 동적으로 링크되는 라이브러리로, 프로그램 실행 중에 로드되어 코드와 데이터를 공유한다.

## 2. 왜 필요한가? (Why)

- 코드 재사용성 증대
- 프로그램 크기 감소
- 모듈화된 개발 가능
- 업데이트 및 유지보수 용이

## 3. 핵심 개념 (What)

- 동적 링크: 프로그램 실행 시점에 라이브러리 연결
- 코드 및 데이터 공유
- API (Application Programming Interface) 제공
- `dllexport`: DLL에서 외부로 함수/클래스를 내보낼 때 사용
- `dllimport`: DLL에서 내보낸 함수/클래스를 사용할 때 사용

## 4. 동작 과정 (How)

1.  프로그램 실행 시, 필요한 DLL 로드
2.  DLL 내의 함수 호출
3.  DLL 과 프로그램 간의 데이터 교환

## 5. 장단점 / 트레이드오프

- 장점:
  -   코드 재사용성, 모듈화, 프로그램 크기 감소
  -   업데이트 용이성
- 단점:
  -   DLL 관리 복잡성, 의존성 문제 발생 가능성 (DLL Hell)
  -   보안 취약점 발생 가능성

## 6. 자주 나오는 질문 / 오해

- Q: DLL Hell 이란 무엇인가?
- A: DLL 버전 충돌로 인해 발생하는 문제

## 7. 프로젝트에서 어디에 쓰일 수 있는가

- 게임 엔진 플러그인 개발
- 외부 라이브러리 통합
- 모듈화된 기능 제공

## [[그래픽스 - 색상 표현]]

## 1. 한 줄 요약

색상은 CPU와 GPU를 통해 픽셀 단위로 표현되며, RGB 값을 사용하여 다양한 색상을 나타낸다.

## 2. 왜 필요한가? (Why)

- 화면에 다양한 색상을 표시하여 시각적인 풍부함을 제공
- 게임 및 그래픽 애플리케이션에서 필수적인 요소

## 3. 핵심 개념 (What)

- 픽셀: 화면을 구성하는 가장 작은 단위, RGB 값을 가짐
- RGB: Red, Green, Blue의 약자로, 각 색상 채널의 강도를 나타냄 (0~255 또는 0.0~1.0)
- CPU: 색상 계산 및 처리
- GPU: 화면에 픽셀을 렌더링

## 4. 동작 과정 (How)

1.  CPU에서 색상 계산 및 픽셀 데이터 생성
2.  GPU에서 픽셀 데이터를 받아 화면에 렌더링
3.  각 픽셀은 RGB 값에 따라 해당 색상으로 표시

## 5. 장단점 / 트레이드오프

- 다양한 색상 표현 가능
- CPU 및 GPU 성능에 따라 렌더링 속도 차이 발생

## 6. 자주 나오는 질문 / 오해

- Q: 픽셀은 항상 정사각형인가?
- A: 대부분의 경우 정사각형이지만, 디스플레이에 따라 다를 수 있음

## 7. 프로젝트에서 어디에 쓰일 수 있는가

- 게임 내 캐릭터 및 배경 색상 표현
- UI 디자인
- 특수 효과

## [[CS - 포인터 형변환의 위험성]]

## 1. 한 줄 요약

포인터 형변환은 메모리 주소를 다루는 방식을 변경하므로, 잘못 사용하면 예기치 않은 동작이나 오류를 초래할 수 있다.

## 2. 왜 필요한가? (Why)

- 때로는 특정 자료형의 데이터를 다른 자료형으로 해석해야 할 필요가 있음
- 하지만 잘못된 형변환은 메모리 손상, 데이터 손실, 프로그램 충돌 등을 유발할 수 있음

## 3. 핵심 개념 (What)

- 포인터: 메모리 주소를 저장하는 변수
- 자료형: 데이터의 종류와 크기를 정의
- 형변환: 변수의 자료형을 다른 자료형으로 변경
- 메모리 정렬 (Alignment): CPU가 데이터를 효율적으로 읽고 쓰기 위해 메모리 주소를 특정 바이트 수의 배수로 정렬하는 것

## 4. 동작 과정 (How)

1.  포인터 형변환을 통해 메모리 주소를 다른 자료형으로 해석
2.  잘못된 형변환은 메모리 접근 오류, 데이터 손상 등을 초래

## 5. 장단점 / 트레이드오프

- 장점:
  -   유연한 메모리 관리 가능
  -   저수준 프로그래밍에서 필수적
- 단점:
  -   오류 발생 가능성이 높음
  -   코드 가독성 저하

## 6. 자주 나오는 질문 / 오해

- Q: 모든 포인터 형변환은 위험한가?
- A: 안전한 형변환도 있지만, 주의해서 사용해야 함

## 7. 프로젝트에서 어디에 쓰일 수 있는가

- 저수준 시스템 프로그래밍
- 하드웨어 제어
- 특정 자료형으로 데이터를 해석해야 하는 경우

## [[CS - 매크로 함수와 인라인 함수]]

## 1. 한 줄 요약

매크로 함수는 전처리기에 의해 코드가 치환되는 방식이고, 인라인 함수는 컴파일러에게 함수 호출 오버헤드를 줄이도록 요청하는 방식이다.

## 2. 왜 필요한가? (Why)

- 성능 향상: 함수 호출 오버헤드를 줄여 실행 속도 개선
- 코드 재사용성: 매크로 또는 인라인 함수를 통해 코드 중복 방지

## 3. 핵심 개념 (What)

- 매크로 함수:
  -   전처리기에 의해 코드가 치환됨
  -   콜 스택을 사용하지 않음
  -   타입 검사를 하지 않음
- 인라인 함수:
  -   컴파일러에게 함수 호출 오버헤드를 줄이도록 요청
  -   실제로 인라인될지는 컴파일러가 결정
  -   타입 검사를 함
- `#define FORCEINLINE __forceinline`: 컴파일러에게 반드시 인라인하도록 지시 (컴파일러에 따라 다름)

## 4. 동작 과정 (How)

- 매크로 함수: 전처리기가 코드를 치환
- 인라인 함수: 컴파일러가 함수 호출 부분을 함수 코드로 대체 (가능한 경우)

## 5. 장단점 / 트레이드오프

- 매크로 함수:
  -   장점:
    -   함수 호출 오버헤드 없음
    -   유연한 코드 생성 가능
  -   단점:
    -   타입 검사 없음
    -   디버깅 어려움
    -   예상치 못한 동작 가능성
- 인라인 함수:
  -   장점:
    -   타입 검사
    -   디버깅 용이
    -   성능 향상
  -   단점:
    -   컴파일러가 인라인을 거부할 수 있음
    -   코드 크기 증가 가능성

## 6. 자주 나오는 질문 / 오해

- Q: 매크로 함수와 인라인 함수 중 어떤 것을 사용하는 것이 좋은가?
- A: 타입 안전성과 디버깅 용이성을 고려하면 인라인 함수가 더 나은 선택이지만, 특수한 경우에는 매크로 함수가 필요할 수 있음

- 자주 호출되는 작은 함수

## [[CS - typedef와 using]]

## 1. 한 줄 요약

`typedef`와 `using`은 새로운 자료형 이름을 정의하는 데 사용되며, 코드 가독성을 높이고 유지보수를 용이하게 한다.

## 2. 왜 필요한가? (Why)

- 코드 가독성 향상
- 복잡한 자료형을 간단하게 표현
- 유지보수 용이성 증대

## 3. 핵심 개념 (What)

- `typedef`: C 스타일의 자료형 정의
- `using`: C++11부터 도입된 자료형 정의 방식 (type alias)

## 4. 동작 과정 (How)

- `typedef 기존자료형 새로운자료형이름;`
- `using 새로운자료형이름 = 기존자료형;`

## 5. 장단점 / 트레이드오프

- `typedef`:
  -   장점: 널리 사용되는 방식
  -   단점: 템플릿에 사용하기 불편함
- `using`:
  -   장점: 템플릿에 사용하기 용이, 가독성 향상
  -   단점: C++11 이상에서만 사용 가능

## 6. 자주 나오는 질문 / 오해

- Q: `typedef`와 `using`의 차이점은 무엇인가?
- A: 기능적으로는 거의 동일하지만, `using`은 템플릿에 더 유연하게 사용 가능

## 7. 프로젝트에서 어디에 쓰일 수 있는가

- 복잡한 자료형을 간단하게 표현
- 코드 가독성 향상
- 템플릿 코드 작성

## [[CS - NULL 포인터]]

## 1. 한 줄 요약

NULL 포인터는 유효한 메모리 주소를 가리키지 않는 포인터로, 초기화되지 않은 포인터 또는 더 이상 사용하지 않는 포인터를 명시적으로 설정하는 데 사용된다.

## 2. 왜 필요한가? (Why)

- 포인터의 유효성 검사
- 댕글링 포인터 방지
- 프로그램 안정성 향상

## 3. 핵심 개념 (What)

- NULL: 0으로 정의된 상수 (C++) 또는 매크로 (C)
- 댕글링 포인터: 유효하지 않은 메모리 주소를 가리키는 포인터
- 초기화: 변수를 사용하기 전에 값을 할당하는 과정

## 4. 동작 과정 (How)

1.  포인터를 NULL로 초기화
2.  포인터를 사용하기 전에 NULL 여부 검사
3.  더 이상 사용하지 않는 포인터를 NULL로 설정

## 5. 장단점 / 트레이드오프

- 장점:
  -   포인터의 유효성 검사 용이
  -   댕글링 포인터로 인한 오류 방지
- 단점:
  -   NULL 포인터 역참조 시 프로그램 충돌 발생

## 6. 자주 나오는 질문 / 오해

- Q: NULL 포인터는 항상 0번지인가?
- A: 운영체제에 따라 다를 수 있지만, 일반적으로 0번지를 사용

## 7. 프로젝트에서 어디에 쓰일 수 있는가

- 메모리 할당 실패 처리
- 함수 인자로 전달된 포인터 유효성 검사
- 객체 소멸 후 포인터 초기화

## 5. 장단점 / 트레이드오프

- 댕글링 포인터: 유효하지 않은 메모리 주소를 가리키는 포인터
- 이중 포인터: 포인터를 가리키는 포인터

## 4. 동작 과정 (How)

1.  포인터로 메모리 할당
2.  이중 포인터 또는 참조를 사용하여 메모리 해제 및 포인터 초기화

## 5. 장단점 / 트레이드오프

- 장점:

## 개선된 코드 제공

```cpp
#define LOG(x) std::cout << x << std::endl

// 이중 포인터를 사용한 메모리 해제 함수
void DeletePointer(void** ptr)
{
    if (ptr != nullptr && *ptr != nullptr)
    {
        delete *ptr;
        *ptr = nullptr;
    }
}

// 참조를 사용한 메모리 해제 함수
void DeletePointer(void*& ptr)
{
    if (ptr != nullptr)
    {
        delete ptr;
        ptr = nullptr;
    }
}

int main()
{
    // 이중 포인터 사용 예시
    int* pointer1 = new int;
    int** ptrToPtr = &pointer1;
    DeletePointer(ptrToPtr);

    // 참조 사용 예시
    int* pointer2 = new int;
    DeletePointer(pointer2);
}
```

## 성능 최적화 포인트 설명 (Memory, CPU)

### Memory

- **댕글링 포인터 방지**: 메모리 해제 후 포인터를 NULL로 설정하여 댕글링 포인터로 인한 오류를 방지한다.
- **이중 포인터 또는 참조 사용**: 함수 내에서 포인터 값을 변경하여 원본 포인터를 NULL로 설정할 수 있도록 한다.

### CPU

- **인라인 함수**: `DeletePointer` 함수를 인라인 함수로 선언하여 함수 호출 오버헤드를 줄일 수 있다.

## 이 코드에서 배운점

- 포인터 메모리 해제 시 이중 포인터 또는 참조를 사용하여 원본 포인터를 NULL로 설정해야 댕글링 포인터를 방지할 수 있다.
- 메모리 누수를 방지하기 위해 할당된 메모리는 반드시 해제해야 한다.

## 면접에서 나올 법한 질문 1가지와 답변

### 질문

댕글링 포인터란 무엇이며, 어떻게 방지할 수 있나요?

### 답변

댕글링 포인터는 이미 해제된 메모리 영역을 가리키는 포인터입니다. 이는 메모리 손상, 예기치 않은 동작, 심지어 프로그램 충돌을 일으킬 수 있습니다. 댕글링 포인터를 방지하는 방법은 다음과 같습니다.

1.  메모리 해제 후 포인터를 NULL로 설정합니다.
2.  포인터의 유효 범위를 명확하게 관리합니다.
3.  스마트 포인터를 사용하여 메모리 관리를 자동화합니다.
