- 원시 오브젝트 포인터(Raw Object Pointer)는 64비트 기반 포인터 시스템

### 메모리 릭 검사 (CRT 라이브러리)

**기본 설정:**

1. `#include <crtdbg.h>` 헤더 추가
2. 메인 함수 시작 부분에 `_CrtSetDbgFlag(_CRTDBG_ALLOC_MEM_DF | _CRTDBG_LEAK_CHECK_DF);` 추가
3. 프로그램 종료 시 출력창에서 메모리 릭 정보 확인 (오류 목록이 아닌 출력창 확인 필요)

**메모리 릭 위치 찾기 (방법 1):**

- 출력창에서 메모리 블록 번호 확인 (예: `{155}`)
- `_CrtSetBreakAlloc(155);` 추가하여 해당 할당 지점에서 중단점 설정
- 디버깅 시 Call Stack에서 main 함수를 찾아 해당 코드 라인 확인

**메모리 릭 위치 찾기 (방법 2 - 권장):**

1. 다음 매크로 정의 추가:

```cpp
#ifdef _DEBUG
#define DBG_NEW new ( _NORMAL_BLOCK , __FILE__ , __LINE__ )
#define new DBG_NEW
#endif
```

1. 기존 `new` 연산자 사용 시 자동으로 파일명과 라인 번호 포함
2. 프로그램 종료 시 출력창에 정확한 파일명과 라인 번호 표시 (예: `main.cpp(31)`)

**중요 사항:**

- 스택 변수는 자동으로 해제되므로 릭이 발생하지 않음
- 힙에 할당된 메모리만 릭 검사 대상
- MS 컴파일러 기준 int는 4바이트 (C++ 표준은 최소 4바이트)

정리하면, 이 강의 내용은 C++에서 “값을 함수에 넘길 때 어떻게 원본을 바꾸는가”, “포인터/레퍼런스를 어떻게 안전하게 쓰는가”, 그리고 “배열과 디버그/릴리즈 모드에서 메모리가 왜 다르게 보이는가”를 한 번에 묶어서 설명하고 있습니다.

1. 함수에 값 전달 vs 원본 변경
    

- 값으로 전달(Call by value)
    
    - 함수에 들어갈 때 복사본이 생깁니다.
        
    - 함수 안에서 값을 바꿔도 원본 변수에는 영향이 없습니다.
        
- 원본을 바꾸고 싶을 때
    
    - 포인터로 주소를 전달하거나
        
    - 레퍼런스(참조)로 전달해야 합니다.
        
    - 이 방식이 있어야 “함수 안에서 변경한 결과가 원래 변수에 반영”됩니다.
        

2. swap(두 값 바꾸기) 예시와 실수 포인트
    

- 일반적인 swap 방식
    
    - 임시 변수(temp)에 A를 저장
        
    - A에 B를 대입
        
    - B에 temp를 대입
        
- 포인터로 swap을 만들면 생길 수 있는 실수
    
    - 잘못된 주소를 넘기거나
        
    - null/댕글링 포인터를 만들거나
        
    - 같은 주소를 두 인자로 넘겨버리는 등
        
    - “주소”라는 위험 요소 때문에 실수 여지가 늘어납니다.
        
- 그래서 레퍼런스 기반 swap이 문법도 깔끔하고(별표 *가 사라짐), 실수도 줄이기 좋습니다.
    

3. 레퍼런스의 장점과 주의점
    

- 장점
    
    - 포인터처럼 원본 변경이 가능하면서 문법이 간결합니다.
        
    - 함수 파라미터에서 특히 많이 쓰입니다. (특히 알고리즘/자료구조 구현에서)
        
- 주의점(매우 중요)
    
    - 지역 변수(함수 안에서 만든 임시 변수)를 레퍼런스로 반환하면 안 됩니다.
        
    - 이유: 함수가 끝나면 그 지역 변수는 사라지는데, 그걸 참조하는 레퍼런스를 밖으로 주면 바로 위험한 참조(댕글링)가 됩니다.
        
    - 반면, “원래 들어온 인자의 참조/주소를 그대로 다시 반환”하는 것은 의도에 따라 가능할 수 있습니다. 핵심은 참조 대상이 함수 종료 후에도 살아있느냐입니다.
        

4. Value Category(값 분류) 핵심 요지
    

- lvalue
    
    - “이름이 있고”, “메모리 위치(주소)가 있고”, “대체로 수정 가능”한 값
        
    - 예: 변수 x, y
        
- rvalue
    
    - 임시 값(계산 결과 등), 곧 사라지는 값
        
    - 예: x + 5 같은 표현식 결과
        
- 레퍼런스 종류
    
    - lvalue reference: 우리가 보통 말하는 일반 레퍼런스 (T&)
        
    - rvalue reference: 이동 시맨틱에 쓰이는 레퍼런스 (T&&)
        
- 강의 결론 톤은 이겁니다
    
    - rvalue reference까지 알면 좋지만,
        
    - lvalue reference를 제대로 쓰는 것만으로도 성능/안전성에 큰 도움이 된다.
        

5. 배열은 왜 “최우선으로 고려”하라고 하나
    

- 배열은 같은 타입 데이터를 연속 메모리에 저장
    
- 장점이 매우 큼
    
    - 접근이 빠름(인덱스 접근)
        
    - 캐시 효율이 좋음
        
    - 구조가 단순하고 오버헤드가 적음
        
- 단점/제약
    
    - 연속 메모리가 필요
        
    - 크기 고정(일반 배열)
        
- 그래서 현실에서는 “크기 자동 증가”하는 동적 배열(예: vector)이 왕이라는 이야기로 연결됩니다.
    

6. 디버그 모드 vs 릴리즈 모드에서 메모리가 달라 보이는 이유
    

- 디버그 모드
    
    - 디버깅을 돕기 위해 메모리 주변에 여유 공간(가드)을 두거나
        
    - 초기값을 특정 패턴으로 채우는 등
        
    - 실수(잘못된 접근)를 더 빨리 드러내게 만드는 장치들이 많습니다.
        
- 릴리즈 모드
    
    - 최적화 중심
        
    - 메모리를 더 촘촘히 쓰고, 방어 장치가 줄어듭니다.
        
    - 그래서 “디버그에선 안 터지는데 릴리즈에서 터지는” 메모리 버그가 생길 수 있고, 이게 제일 잡기 어렵다고 강조합니다.

1. 포인터 vs 레퍼런스, 값 변경의 의도
    

- 함수에 값을 전달하면 기본은 복사(call by value)라서 함수 안에서 바꿔도 원본에 영향이 없습니다.
    
- 원본을 바꾸려면 포인터(주소) 또는 레퍼런스(참조)로 받아야 합니다.
    
- 대표 예시가 swap(두 값 교환)이고, 알고리즘/자료구조 구현에서 아주 자주 나옵니다.
    
- 포인터는 강력하지만 실수(널, 댕글링, 범위 밖 접근)를 유발하기 쉬워서, 가능하면 레퍼런스로 더 안전하고 깔끔하게 쓰는 편이 많습니다.
    
- 단, 지역 변수의 주소/레퍼런스를 반환하는 건 위험합니다. 지역 변수는 함수가 끝나면 사라져서 반환된 주소가 무의미해집니다.
    

2. value category 요약 (C++ 값 분류)
    

- lvalue: 메모리 위치를 가지는 것(이름이 있고, 보통 대입/수정 가능)
    
- rvalue: 임시 값(계산 결과처럼 잠깐 쓰이고 사라지는 값)
    
- lvalue reference(&): lvalue를 참조하는 일반적인 레퍼런스
    
- rvalue reference(&&): 임시 값(rvalue)을 잡아 이동 시맨틱/퍼펙트 포워딩에 활용(성능 최적화와 자원 소유권 이동에 연결)
    

3. 배열과 포인터의 관계, 디버그/릴리즈 차이
    

- 원시 배열 이름은 첫 원소의 주소처럼 동작합니다(배열은 포인터처럼 취급 가능).
    
- 그래서 int arr[10]; 과 int* p = arr; 같은 형태가 가능합니다.
    
- p[1] 처럼 포인터도 배열 인덱싱 문법을 쓸 수 있고, *(p+1) 같은 포인터 산술과 동일한 의미입니다.
    
- 배열/포인터에서 가장 흔한 실수는 범위 밖 인덱스 접근과 널 포인터 접근입니다.
    
- 디버그 빌드는 메모리 가드/패딩 등으로 실수가 덜 터지는 것처럼 보일 수 있고, 릴리즈 빌드는 최적화 때문에 동일 실수가 더 랜덤하게 터져 디버깅이 어려워질 수 있습니다.
    

4. 루프에서 ++i vs i++ (전위/후위 증가)
    

- 개념적으로는 후위(i++)가 임시 값을 만들 수 있어 전위(++i)가 더 유리하다는 얘기가 있었습니다.
    
- 하지만 현대 컴파일러는 대부분 최적화로 차이를 없애는 경우가 많습니다.
    
- 다만 사용자 정의 이터레이터(특히 복잡한 타입)에서는 전위 증가가 유리한 경우가 여전히 있어 습관적으로 ++i를 권장하기도 합니다.
    

5. 반복 작업 자동화 관점 (프로젝트 생성/빌드)
    

- 비주얼 스튜디오에서 매번 프로젝트 만들고 출력/중간 폴더 바꾸는 반복 작업은 자동화 대상입니다.

- 핵심은 사람이 버튼으로 하는 일을 결국 설정 파일/스크립트로 재현하는 것입니다.

char는 사실 숫자이다



1. ASCII와 대소문자 변환 원리
    

- ASCII는 0~127까지 총 128개 코드로 문자/기호를 숫자에 매핑한 표입니다.
    
- 대문자 A는 65, 소문자 a는 97이라서 차이는 32입니다.
    
- 규칙: 대문자 + 32 = 소문자, 소문자 - 32 = 대문자
    
- 구현 관점 핵심은 “범위 체크”입니다. (A~Z일 때만 +32, a~z일 때만 -32)
    

2. char의 본질
    

- char는 “문자 타입”이라기보다 “1바이트 정수 저장 공간”입니다.
    
- 컴퓨터는 문자를 직접 아는 게 아니라 숫자를 저장하고, 해석(표)을 붙여서 사람이 문자로 보는 구조입니다.
    
- 그래서 char에 10 같은 숫자를 넣어도 되고, 산술 연산도 됩니다.
    

3. 문자열의 본질과 C 문자열 종료 규칙
    

- 문자열은 “문자(char)의 연속(배열)”입니다.
    
- C 스타일 문자열은 끝을 알기 위해 마지막에 널 종료 문자 \0(숫자 0)을 둡니다.
    
- \0이 없으면 출력/처리 시 메모리를 계속 읽다가 우연히 0을 만날 때까지 진행해 “이상한 문자”가 뒤에 붙는 현상이 생깁니다.
    

4. 문자열 리터럴과 const char*
    

- C/C++에서 "Hello" 같은 문자열 리터럴은 보통 const char*로 취급됩니다.
    
- char*로 받으려 하면(즉 수정 가능 포인터로 받으려 하면) 컴파일러가 막는 경우가 많습니다.
    
- 의미: 리터럴로 잡힌 문자열 메모리는 수정 대상이 아니라는 약속(불변)에 가깝습니다.
    

5. 문자열 불변성과 성능 포인트
    

- 문자열을 “중간만 바꿔치기”하는 게 쉬운 구조가 아니라, 보통은 새 문자열을 만들어 교체하는 방식이 됩니다.
    
- 그래서 잦은 결합/수정은 비용이 커질 수 있고, 언어/라이브러리들이 이를 보완하는 여러 방식(버퍼, 빌더 등)을 제공합니다.
    

6. 인코딩(cp949 vs UTF-8)과 한글 깨짐
    

- 같은 “텍스트 파일”이라도 저장 인코딩이 달라지면 한글이 깨질 수 있습니다.
    
- Visual Studio가 기본으로 cp949인 경우가 있고, 엔진(언리얼/유니티)나 협업 환경은 UTF-8을 더 선호하는 흐름이 많습니다.
    
- 실무 포인트: 프로젝트 차원에서 “소스 파일 인코딩 표준”을 정해두면 충돌이 크게 줄어듭니다.
    

7. 좌표계(오른손/왼손) 요지
    

- 오른손 좌표계/왼손 좌표계 차이는 주로 Z축(깊이 방향) 부호/방향 정의가 뒤집히는 문제로 나타납니다.
    
- OpenGL 계열은 흔히 오른손, DirectX 계열은 흔히 왼손이라는 구분이 자주 언급됩니다.
    
- 유니티/언리얼은 실사용에서 왼손 좌표계로 설명되는 경우가 많고, 좌표 변환 자체는 보통 Z 부호 반전 같은 방식으로 정리됩니다.
    
- 실무 포인트: “어느 축이 앞/위/오른쪽인지”를 엔진 기준으로 먼저 고정하고, 외부 데이터(모델, 수학식, 라이브러리) 연결 시 변환 규칙을 문서화하는 게 중요합니다.
    

8. if 조건식의 진짜 판정 규칙(0/비0)
    

- C/C++에서 조건식은 “0이면 false, 0이 아니면 true”입니다.
    
- 포인터를 if(ptr)로 쓰는 건 “ptr이 null(0)인가 아닌가”를 보는 패턴입니다.
    
- 스타일은 팀 규칙에 따라 if(ptr) / if(ptr != nullptr) 둘 다 쓰이지만, 본질은 동일합니다.

## 12. [C++] 값 전달 방식 (Call by Value, Pointer, Reference)

### 1. 한 줄 요약
함수에 값을 전달할 때 값 복사(Call by Value), 포인터, 레퍼런스를 사용하여 원본을 변경하는 방법을 이해하고 안전하게 사용한다.

### 2. 왜 필요한가? (Why)
- 함수에서 원본 변수 변경 필요
- 포인터/레퍼런스의 안전한 사용

### 3. 핵심 개념 (What)
- Call by Value: 함수에 값 전달 시 복사본 생성
- 포인터: 주소를 전달하여 원본 변경
- 레퍼런스: 참조를 전달하여 원본 변경

### 4. 동작 과정 (How)
1.  Call by Value: 함수 내부에서 값 변경 시 원본 변수에 영향 없음
2.  포인터: 함수 내부에서 포인터를 통해 원본 변수 변경 가능
3.  레퍼런스: 함수 내부에서 레퍼런스를 통해 원본 변수 변경 가능

### 5. 장단점 / 트레이드오프
- 장점:
  - 포인터: 유연한 메모리 접근
  - 레퍼런스: 간결한 문법
- 단점:
  - 포인터: 널 포인터, 댕글링 포인터 위험
  - 레퍼런스: 지역 변수 반환 시 댕글링 레퍼런스 위험

### 6. 자주 나오는 질문 / 오해
- Q: 지역 변수를 레퍼런스로 반환하면 왜 안 되는가?
- A: 함수 종료 후 지역 변수가 사라지므로 댕글링 레퍼런스가 된다.
