## 핵심 요지

현재 문제는:

- 위젯이 HP 같은 정보를 업데이트해야 함
- 그런데 실제 정보는 캐릭터가 가지고 있음
- 위젯이 캐릭터를 직접 알게 하면 **커플링이 커짐**
- 이걸 줄이려고 중간에 **인터페이스 계층**을 하나 둠

즉,

**위젯 → 액터 직접 캐스팅 → 캐릭터 직접 접근**  
이 방식 대신

**위젯 → 소유 액터 → 인터페이스 호출 → 필요한 정보만 전달**  
이 구조로 바꾸는 거예요.

---

## 왜 이렇게 하는가

### 1. 직접 캐릭터를 넘기면 커플링이 심해짐

- 위젯이 캐릭터 타입을 직접 알아야 함
- 그러면 결국 위젯과 캐릭터가 강하게 묶임
- 애초에 커플링 줄이려고 구조 나눈 의미가 약해짐

### 2. 인터페이스를 두면 필요한 기능만 연결 가능

- 위젯은 “이 액터가 어떤 캐릭터인지”까지 몰라도 됨
- 그냥 “이 인터페이스를 구현했는가?”만 확인하면 됨
- 필요한 정보 전달 함수만 호출하면 됨

---

## 전체 구조 흐름

지금 만들려는 구조는 대략 이거예요.

### 기존에 문제 있던 방식

- 스탯 컴포넌트가 델리게이트 발행
- 위젯의 HP 업데이트 함수를 등록하고 싶음
- 그런데 위젯이 캐릭터 전체 정보를 알아야 하면 다시 커플링 발생

### 바꾸는 방식

1. **캐릭터가 인터페이스를 구현**
2. **위젯은 자신을 소유한 액터를 받음**
3. 그 액터를 캐릭터로 직접 캐스팅하지 않고
4. **인터페이스로 접근**
5. 인터페이스 함수로 필요한 정보만 전달받음
6. 델리게이트에 위젯 함수 등록

---

## 설계적으로 말하고 싶은 포인트

이 수업 내용에서 중요한 메시지는 단순히 “인터페이스 써라”가 아니라 이거예요.

### 1. 복잡한 설계는 무조건 정답이 아님

- 커플링을 줄이는 구조는 확장성 면에서 이점이 있음
- 하지만 지금 프로젝트 규모나 본인 실력에서
- **이 복잡도를 감당 가능한가**를 계속 판단해야 함

### 2. 감당 가능하면 유지

- 앞으로 비슷한 구조가 반복돼도
- “이 정도 목적도는 내가 관리 가능하다” 싶으면
- 이런 식으로 인터페이스, 델리게이트, 계층 분리를 유지하면 됨

### 3. 감당이 안 되면 단순화도 가능

- 커플링이 조금 생기더라도
- 직접 호출해서 동작하게 만드는 게 더 나을 수도 있음
- 특히 소규모 프로젝트나 빠른 구현이 중요할 때는 현실적인 선택임

즉,  
**좋은 설계 = 무조건 복잡한 설계**가 아니라  
**내가 유지 가능한 수준의 설계**가 중요하다는 뜻이에요.

---

## 실제 구현 순서 요약

### 1. 인터페이스 생성

- Common 탭에서 Interface 생성
- 이름 예시: `ABCharacterWidgetInterface`

### 2. 인터페이스에 함수 선언

예:

- `SetupCharacterWidget`

즉, 캐릭터가 위젯에 필요한 정보를 세팅해주는 함수 선언

### 3. 캐릭터 베이스 클래스에 인터페이스 상속

- `ABCharacterBase`가 해당 인터페이스를 구현하도록 설정
- 헤더에 인터페이스 include
- 클래스 선언부에 인터페이스 상속 추가

### 4. 함수 구현 자동 생성

- Visual Studio에서
- 인터페이스의 pure virtual 함수 구현 추가
- cpp / header에 구현 코드 생성

### 5. 위젯은 액터만 알고 인터페이스로 접근

- 위젯이 소유 액터를 받음
- 캐릭터로 직접 캐스팅하지 않음
- 인터페이스로 변환해서 필요한 함수 호출

---

## 한 줄 정리

**위젯이 캐릭터를 직접 알지 않게 하고, 중간에 인터페이스를 둬서 필요한 정보만 연결함으로써 커플링을 줄이려는 설계**예요.  
다만 이런 구조는 복잡도가 올라가므로, 프로젝트마다 **내가 감당 가능한 수준인지 판단하면서 쓰는 게 중요함**이 핵심이에요.

- 목적은 **확장성과 결합도 완화**
