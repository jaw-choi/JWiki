1. 람다: 로직을 “그 자리에서” 정의·전달하는 문법, 캡처로 외부 맥락(상태)을 함께 가져오는 클로저 성격
    
2. 스마트 포인터(특히 unique_ptr): 힙 메모리 소유권을 안전하게 관리하고, 복사/이동 규칙으로 실수(누수/댕글링)를 구조적으로 막는 도구
    
3. 람다 정리
     

- 목적: 함수 포인터처럼 “로직을 인자로 넘기는” 일을 훨씬 짧게, 호출 지점에서 바로 작성해서 편하게 만든 문법
    
- 기본 형태(4요소)
    
    - 캡처: [] 외부 변수를 람다 안에서 쓰기 위해 가져오는 부분
        
        - 값 캡처: [x] x를 복사해서 람다 내부에 저장
            
        - 참조 캡처: [&x] x를 참조로 연결(외부 x에 영향)
            
        - 디폴트 캡처
            
            - [&] : 외부에서 쓰는 것들을 전부 참조로[&변수]
                
            - [=] : 외부에서 쓰는 것들을 전부 값으로[변수]
                
            - 혼합도 가능: [&, a, b] 또는 [=, &a, &b] 처럼 일부만 반대로 지정
                
            - 디폴트와 동일 방식의 중복 지정은 오류(예: [&]에서 다시 &x 지정 등)
                
    - 파라미터: (int a, int b) 같은 함수 인자
        
    - 본문: { ... } 실제 로직
        
    - 반환형: -> T
        
        - 보통은 컴파일러가 추론 가능하면 생략
            
        - 분기마다 반환 타입이 다르거나 추론이 애매하면 명시
            
- 람다의 중요한 사실
    
    - 람다는 “함수”가 아니라 “객체”입니다(컴파일러가 익명 타입의 functor 클래스로 변환)
        
    - 그래서 타입 이름을 직접 적기 어렵고, 보통 auto로 저장함
        
    - STL 알고리즘(sort, for_each, remove_if 등)에 조건/비교 로직을 넘길 때 특히 많이 씀
        
- 캡처를 왜 조심해야 하나
    
    - 값 캡처는 내부에서 수정해도 외부 원본에는 영향 없음
        
    - 외부 값을 누적/변경해야 하면 보통 참조 캡처가 필요(예: totalMoney 누적)
        

2. 스마트 포인터 전체 맥락
    

- 배경: C++은 기본 언어 차원 GC가 없어서 힙 메모리는 new/delete 실수로 누수, 댕글링 포인터 문제가 자주 발생
    
- 스마트 포인터는 “원시 포인터를 감싸는 객체”로서, 소멸 시점에 자동 해제를 수행(RAII)하고 실수를 구조적으로 줄임
    
- 종류 3개
    
    - unique_ptr: 단독 소유(소유자 1명)
        
    - shared_ptr: 공유 소유(참조 카운팅)
        
    - weak_ptr: 약한 참조(shared_ptr과 함께 사용, 카운트 증가 없음, 유효성 확인/순환 참조 완화)
        

3. unique_ptr 핵심 규칙
    

- 소유권이 1명만 가능하므로 복사 금지
    
    - unique_ptr 복사 시도는 컴파일 오류가 나야 정상(두 주인이 생기기 때문)
        
- 이동(move)만 가능
    
    - std::move를 통해 소유권을 “이전”하면 원래 unique_ptr은 비게 됨(보통 nullptr 상태)
        
    - 상속 비유로 설명한 것처럼, 기존 소유자가 포기하고 새 소유자가 받는 구조
        
- 생성은 make_unique 권장(C++14부터 표준화)
    
    - 예전처럼 new를 직접 넣기보다 make_unique로 생성 + 예외 안정성 + 코드 간결
        
- 가장 안전한 기본값
    
    - 가능하면 힙 자원의 소유는 unique_ptr로 시작하는 것이 안전(불편하지만 실수 방지 효과가 큼)
        

4. 복사 막는 기법(클래스 차원) 정리
    

- 의도: 객체 자체가 복사되면 안 되는 타입(리소스 소유, 고유 핸들 등)을 컴파일 타임에 막기
    
- 방법 2가지
    
    - 옛 방식: 복사 생성자/대입 연산자를 private에 두고 정의 안 함(또는 더미 정의)
        
    - 현대 방식: = delete로 명시적으로 삭제
        
        - 컴파일 에러 메시지가 더 명확하고 의도가 코드에 그대로 드러남
            
- 중요한 태도
    
    - 누가 복사를 막아놨으면 이유가 있음
        
    - 임의로 public으로 풀기보다, 왜 막았는지 의도를 확인하고 설계를 맞추는 것이 정석
        

5. 마지막 질문으로 이어지는 포인트: unique_ptr을 “다른 곳에 넘겨야” 하는 경우
    

- 이 대목의 핵심만 요약하면 이렇습니다.
    
    - 소유권을 넘길 거면 unique_ptr 자체를 이동(move)해서 넘긴다(소유권 이전)
        
    - 소유권은 유지하고 “잠깐 접근만” 시키려면 raw pointer 또는 reference를 얻어서 넘긴다(비소유 관찰)
        
    - 여러 곳이 오래 함께 소유해야 하면 shared_ptr 설계를 고려한다(공유 소유)
        
    - 순환 참조나 “살아있는지 확인만” 같은 요구가 있으면 weak_ptr을 섞는다(유효성/순환 완화)
