1. unique_ptr 소유권 이전(move)에서 주의할 점
    

- unique_ptr은 복사 불가, 이동(move)만 가능입니다.
    
- move로 소유권을 넘긴 뒤 원래 변수는 더 이상 “주인”이 아닙니다.
    
- 현실적으로는 move 이후 원래 unique_ptr이 nullptr로 비워지는 것이 보통이지만, 핵심 규칙은 하나입니다.
    
    - move 이후 원래 소유자(unique_ptr)는 사용하지 않는다.
        
- move 후 원래 포인터를 계속 쓰면 “주인 잃은 포인터/무효 상태”를 건드리는 꼴이 되고, 실수로 접근하면 버그 가능성이 커집니다.
    

2. unique_ptr을 함수에 넘겨야 할 때의 3가지 정석(중요도 순)  
    (1) 가장 권장: 원시 객체 레퍼런스(T&)로 넘기기
    

- 소유권을 넘기는 게 아니라 “사용만” 하고 싶다면 이게 가장 안전합니다.
    
- 예: void Use(Player& p); // 소유권 변화 없음, nullptr 걱정 없음
    

(2) 그다음: raw pointer(T*)로 넘기기

- 포인터가 필요한 API(없을 수도 있음/nullable)라면 T*가 실용적입니다.
    
- 단, 소유권은 절대 넘기지 않고 “관찰/사용만” 한다는 규칙이 같이 따라야 합니다.
    
- 호출자는 ptr.get() 같은 식으로 넘기고, 받은 쪽은 delete 하면 안 됩니다.
    

(3) 경우에 따라: unique_ptr 자체를 참조로 받기(unique_ptr<T>& 또는 const unique_ptr<T>&)

- 함수 내부에서 ptr 자체를 다루거나(예: reset, move 등) 정책적으로 unique_ptr을 직접 만져야 할 때 쓰는 방식입니다.
    
- 다만 이 방식은 “소유권 모델을 함수가 건드릴 수 있게 열어주는” 형태라, 인터페이스 설계가 더 신중해야 합니다.
    

보너스: 소유권 이전이 목적이라면 아예 값으로 받기

- void Take(std::unique_ptr<Player> p); // 호출자가 std::move로 넘김
    
- 이건 “이 함수가 소유권을 가져간다”를 타입으로 못 박는 방식이라 오히려 명확합니다.
    

3. unique_ptr을 “억지로” 우회하는 위험한 패턴(하지 말아야 할 것)
    

- const Player&처럼 “원래 복사 금지인 객체를 const 참조로 받았으니 괜찮다” 식의 우회가 잠깐은 되지만, 의도는 달라집니다.
    
    - 이건 소유권 문제를 해결한 게 아니라 “복사 없이 접근만” 가능하게 만든 것뿐입니다.
        
- 더 위험한 건 get()로 원시 포인터를 꺼내놓고 외부에서 delete 해버리는 패턴입니다.
    
    - 스마트 포인터가 여전히 그 메모리를 소유하고 있다고 믿는 상태에서, 누군가 delete를 해버리면 이후 접근은 바로 대참사(댕글링/이중 해제)입니다.
        
    - “가능하긴 하지만 하면 안 되는” 대표 사례입니다.
        

4. shared_ptr / weak_ptr 핵심 정리
    

- shared_ptr: 여러 소유자가 같은 힙 객체를 “공동 소유”합니다.
    
    - 복사될 때 참조 카운트(use_count)가 증가
        
    - 소멸될 때 감소
        
    - 0이 되면 delete 수행
        
- 장점: 복사가 쉬워서 API 설계가 편해지고, 소유권 공유가 자연스럽습니다.
    
- 단점(핵심): 순환 참조(cycle)가 생기면 use_count가 0이 안 되어 메모리가 해제되지 않습니다.
    

5. 순환 참조와 weak_ptr의 역할(면접 단골)
    

- 문제: A가 shared_ptr로 B를 들고, B도 shared_ptr로 A를 들면
    
    - 서로가 서로의 카운트를 잡고 있어서 둘 다 0이 안 됨 → 누수
        
- 해결: 한쪽(보통 “역참조/부모를 가리키는 쪽”)을 weak_ptr로 바꿉니다.
    
    - weak_ptr은 참조 카운트에 참여하지 않아서 cycle을 끊습니다.
        
- 사용법 핵심: weak_ptr은 바로 쓰지 않고 lock()으로 shared_ptr을 “잠깐” 얻어서 유효성 체크 후 사용합니다.
    
    - lock() 결과가 nullptr이면 이미 소멸된 객체라는 뜻입니다.
        

6. 실무에서의 감각적 규칙(지금 말한 흐름을 한 문장으로)
    

- 소유권은 가능하면 unique_ptr로 단일화하고,
    
- 여러 곳이 진짜로 소유해야만 하는 경우에만 shared_ptr을 쓰며,
    
- shared_ptr 관계가 그래프/양방향이 되면 weak_ptr로 cycle을 끊는다,
    
- 함수 인자는 소유권을 바꾸지 않으면 T& 또는 T*로 “사용만” 하게 설계한다.
    

7. 면접에서 거의 나오는 질문 포인트
    

- unique_ptr
    
    - 복사 안 되는 이유
        
    - move 의미(소유권 이전)
        
    - 함수 인자로 어떻게 넘길지(소유권 이전 vs 사용만)
        
- shared_ptr / weak_ptr
    
    - shared_ptr의 대표 문제: 순환 참조로 인한 누수
        
    - 해결: weak_ptr + lock()으로 유효성 확인 후 사용
