QuadTree Rect Debug 설명
**1) QuadTree 디버깅 방법 (실제 확인 루틴)**

- **시각화 켜기**: showQuadTreeDebug = true, showQuadTreeDebugRects = true
- **깊이 제한으로 단계 확인**
    - quadDebugOnlyDepth = 0 → 루트(전체 화면)만 보임
    - quadDebugOnlyDepth = 1 → 4분할만 보임
    - quadDebugOnlyDepth = 2 → 그 아래 분할까지 보임
- **Split 기준 확인**
    - 적/탄환 많아지는 순간에 분할이 더 생기는지 확인
    - 객체 수가 적은데 계속 깊게 쪼개지면 capacity/조건 오류 의심
- **좌표 이상 유무**
    - 사각형이 화면 밖으로 삐져나오면 bounds 계산 문제 의심
- **충돌 후보군 비교** (정확성 체크)
    - AABB 전체 탐색 결과가 쿼드트리 후보군에 **모두 포함**되는지 확인
    - 누락이 있으면 Query, GetIndex, ContainsRect 로직 점검

**2) 화면에 그려진 사각형이 의미하는 것**

- **각 사각형 = QuadTree 노드의 영역(bounds)**
- **depth 0**: 화면 전체 (루트 노드)
- **depth 1**: 화면을 4개로 나눈 첫 분할
- **depth 2, 3…**: 더 세분화된 영역
- **색상(현재 구현)**: depth에 따라 색 바뀜
    - White → Red → Green → Blue 순으로 반복
    - 깊이별 분할 구조를 한눈에 보기 위한 구분용

즉, “화면을 어떻게 쪼개서 관리하는지”를 직관적으로 보여주는 지도라고 생각하면 돼.

**3) 발표할 때 설명 추천 흐름 (짧고 설득력 있게)**

1. **문제 제기**
    - “AABB 전수 비교는 O(N²)라 적이 많아지면 성능이 급격히 떨어진다.”
2. **해결 전략**
    - “QuadTree로 공간을 분할해 충돌 후보군만 검사한다.”
3. **시각화 설명**
    - “화면에 그려진 사각형이 각 QuadTree 노드의 bounds이며, 깊이가 깊을수록 더 작은 공간 단위로 나뉜다.”
4. **동작 확인 방법**
    - “특정 depth만 출력해 단계적으로 분할이 발생하는 시점을 확인했고, 적이 많아질수록 더 깊게 분할되는 것을 확인했다.”
5. **효과**
    - “충돌 검사 대상 수가 줄어들어 프레임 안정성이 개선된다.”

**발표용 한 줄 요약**  
“분할 구조를 화면에 직접 그려서 QuadTree가 언제, 어떻게 쪼개지는지를 시각적으로 검증했고, 이를 통해 후보군 충돌 검사만 수행하는 구조임을 증명했다.”
