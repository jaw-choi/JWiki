# 2026-09-21 Linux 실습 정리

## 오늘의 핵심 흐름

오늘 내용은 명령어를 개별적으로 외우는 수업이라기보다, **Linux 서버에서 반복 작업을 자동화하고 → 실행 중인 프로세스와 자원을 관찰하고 → 로그를 남기고 → 그 기록을 바탕으로 장애를 판단하는 구조**를 이해하는 것이 핵심이었다.

전체 흐름을 한 줄로 정리하면 다음과 같다.

```text
반복 작업 정의
→ cron / Shell Script로 자동 실행
→ ps / top / htop으로 실제 실행 상태 확인
→ 로그로 결과를 남김
→ HTML이나 보고서로 사람이 보기 좋게 표현
→ 정해진 규칙은 자동화
→ 원인이 불명확한 문제는 AI Agent가 조사·판단
```

즉, **자동화와 AI Agent는 같은 것이 아니다.**
자동화는 이미 정해진 조건과 행동을 반복하는 데 적합하고, AI Agent는 “무엇이 문제인지 아직 모르는 상황”에서 어떤 정보를 더 확인해야 하는지 판단하는 데 의미가 있다.

## 1. cron은 일을 판단하는 기능이 아니라, 일을 시작시키는 스케줄러다

`crontab`의 역할은 특정 시간에 명령이나 스크립트를 실행하는 것이다.

```bash
crontab -e
crontab -l
```

cron 표현식은 다음 순서로 읽는다.

```text
분  시  일  월  요일  실행할 명령
```

예를 들어 5분마다 스크립트를 실행한다면 다음과 같다.

```cron
*/5 * * * * /home/ubuntu/script.sh
```

중요한 점은 **cron 자체에 복잡한 판단 로직을 넣는 것이 아니라는 것**이다.

```text
cron
→ "5분마다 실행해"

Shell Script
→ "CPU가 80% 이상인가?"
→ "디스크 공간이 충분한가?"
→ "ping이 성공했는가?"
→ 조건에 따라 실제 행동 결정
```

따라서 업무에서는 `cron + Shell Script`가 한 세트로 많이 사용된다.

### 예시

패키지를 매일 새벽 2시에 업데이트해야 한다고 해도 바로 업데이트하는 것이 아니라,

```text
새벽 2시
↓
디스크 여유 공간 확인
↓
충분함 → 업데이트
부족함 → 실행하지 않고 로그 기록
```

처럼 **실행 전 조건을 확인하는 것이 더 안전한 자동화**다.

## 2. Shell Script의 핵심은 명령어보다 '조건과 반복'이다

Shell Script를 사용하는 이유는 Linux 명령어 여러 개를 묶는 것뿐만 아니라 **상황에 따라 행동을 다르게 만들기 위해서**다.

### 조건 분기

```text
디스크 사용량 80% 이상 → 위험
60% 이상 → 주의
그 외 → 정상
```

이 구조는 `if / elif / else`로 표현할 수 있다.

중요한 것은 문법 자체보다 다음처럼 생각하는 것이다.

```text
현재 상태를 측정한다
→ 기준과 비교한다
→ 조건에 맞는 행동을 선택한다
→ 결과를 기록한다
```

### 반복

`for`, `while`은 같은 작업을 반복할 때 사용한다.

예를 들어 여러 서버의 연결 상태를 점검한다면:

```text
8.8.8.8
1.1.1.1
127.0.0.1
```

각 주소에 `ping`을 수행하고 성공/실패 결과를 하나의 로그에 남길 수 있다.

여기에 cron을 연결하면 사람이 직접 확인하지 않아도 5분마다 네트워크 상태를 점검할 수 있다.

## 3. 실행시켰다면 반드시 '프로세스'를 이해해야 한다

Linux에서는 사용자가 아무것도 하지 않는 것처럼 보여도 많은 프로세스가 계속 실행되고 있다.

따라서 스크립트나 서비스를 자동 실행하기 시작하면 다음 질문에 답할 수 있어야 한다.

```text
지금 어떤 프로세스가 실행 중인가?
누가 실행했는가?
PID는 무엇인가?
부모 프로세스는 무엇인가?
CPU와 메모리를 얼마나 쓰는가?
종료해도 되는 프로세스인가?
```

### `ps`

`ps`는 **현재 시점의 프로세스 상태를 한 번 찍어서 보여주는 명령어**라고 이해하면 쉽다.

```bash
ps
ps -ef
```

결과를 파일로 저장할 수도 있다.

```bash
ps -ef > ps.txt
```

이 방식은 나중에 CSV, HTML, DB로 변환해서 자원 보고서나 대시보드를 만드는 데 활용할 수 있다.

### `pgrep`

특정 이름의 프로세스를 찾을 때 일반 `grep`보다 `pgrep`이 편리하다.

```bash
pgrep -f worker.sh
```

`grep` 자체도 하나의 프로세스이기 때문에 `ps | grep` 방식에서는 grep 자신이 결과에 포함되는 경우가 있다.

## 4. 포그라운드와 백그라운드의 차이

스크립트를 그냥 실행하면 보통 포그라운드에서 동작한다.

```bash
./worker.sh
```

프로그램이 계속 실행되고 있으면 해당 터미널에서 다른 명령을 입력하기 어렵다.

반면 뒤에 `&`를 붙이면 백그라운드로 실행된다.

```bash
./worker.sh &
```

그러면 프로세스는 계속 동작하지만 사용자는 같은 터미널에서 다른 작업을 할 수 있다.

### 작업 번호와 PID는 다르다

```text
Job Number
→ 현재 Shell이 관리하는 백그라운드 작업 번호

PID
→ Linux 전체에서 프로세스를 구분하는 실제 Process ID
```

`jobs`는 현재 Shell의 작업을 보고, `ps`는 시스템의 프로세스를 본다.

프로세스를 종료할 때는 PID를 정확히 확인한 뒤 `kill`을 사용해야 한다.

```bash
kill PID
```

여기서 가장 중요한 원칙은 다음과 같다.

> **프로세스 이름만 보고 무턱대고 종료하지 않는다.**

시스템 프로세스, DB, 부모 프로세스 등을 잘못 종료하면 서비스 전체에 영향을 줄 수 있다.

## 5. `top`과 `htop`은 서버가 '왜 느린지' 숫자로 확인하는 도구다

사용자가 “서버가 느리다”고 말해도 그것만으로는 원인을 알 수 없다.

느리다는 현상을 다음과 같은 숫자로 바꿔서 봐야 한다.

```text
CPU 사용량
Memory 사용량
Load Average
Swap
프로세스별 자원 사용량
```

### `ps`와 `top`의 차이

```text
ps
→ 한 시점의 상태 확인

 top
→ 상태가 계속 갱신되는 실시간 모니터링
```

`top`의 위쪽은 시스템 전체 요약이고, 아래쪽은 프로세스별 사용량이다.

특히 다음 항목을 먼저 본다.

```text
Load Average
→ 처리하지 못하고 기다리는 작업이 얼마나 있는가

CPU
→ CPU가 얼마나 바쁜가

Memory
→ 실제 사용할 수 있는 메모리가 얼마나 남았는가
```

### `htop`

`htop`은 `top`을 사람이 보기 쉽게 만든 도구라고 이해하면 된다.

- CPU/Memory 기준 정렬
- 사용자별 필터
- Process Tree 확인
- PID와 상태 확인
- 마우스/기능키 사용

등이 편리하다.

하지만 `htop`에서 프로세스를 쉽게 종료할 수 있다고 해서 **잘 모르는 프로세스를 바로 kill하면 안 된다.**

## 6. 프로세스 상태와 Zombie Process

프로세스 상태에서 자주 보게 되는 값 중 `S`는 sleeping 상태다.

Linux 프로세스는 계속 CPU를 사용하는 것이 아니라 대부분 필요한 순간까지 대기하므로 `S` 상태가 많은 것은 자연스럽다.

반면 `Z`는 Zombie Process를 뜻한다.

```text
자식 프로세스 실행 종료
↓
부모 프로세스가 종료 상태를 제대로 수거하지 않음
↓
프로세스 테이블에 흔적이 남음
```

따라서 Zombie가 보인다고 자식만 무작정 제거하기보다 **PPID를 통해 부모-자식 관계를 같이 확인해야 한다.**

## 7. `.bashrc`, `.vimrc`, `htoprc`의 공통점

오늘 여러 번 등장한 `rc` 파일은 프로그램 실행 시 참고하는 **사용자 설정 파일**이라고 이해하면 된다.

예:

```text
.bashrc
→ Bash Shell 설정

.vimrc
→ Vim 설정

htoprc
→ htop 정렬 방식 등 사용자 설정
```

예를 들어 터미널에서 alias를 한 번 입력하면 현재 세션에서만 적용될 수 있지만, `.bashrc`에 저장하면 다음 로그인 이후에도 유지된다.

이 부분의 핵심은:

> **현재 터미널에서 변경된 것과 영구적으로 저장된 설정을 구분해야 한다.**

설정 파일은 시스템 동작에 영향을 줄 수 있으므로 내용을 이해하지 못한 상태에서 무작정 수정하지 않는 것도 중요하다.

## 8. 권한 문제는 '파일이 존재한다'와 '실행할 수 있다'를 구분해야 한다

Shell Script를 만들었다고 바로 실행할 수 있는 것은 아니다.

예를 들어:

```text
rw-rw-r--
```

이라면 읽고 쓰는 것은 가능하지만 실행 권한 `x`가 없다.

```bash
chmod +x worker.sh
```

처럼 실행 권한을 추가해야 한다.

숫자 권한은 다음 값의 합으로 이해한다.

```text
r = 4
w = 2
x = 1
```

예를 들어 `644`는:

```text
사용자: 읽기 + 쓰기
그룹:   읽기
기타:   읽기
```

이다.

권한 오류가 발생하면 프로그램 문제부터 의심하기보다 **실행 권한, 소유자, 그룹, 파일 접근 권한**을 먼저 확인할 필요가 있다.

## 9. 로그는 '출력 저장'이 아니라 장애를 다시 설명할 수 있게 만드는 기록이다

자동화에서 가장 중요한 것은 실행 자체보다 **무엇을 했고 결과가 어땠는지 남기는 것**이다.

예를 들어 `worker.sh`가 5초마다 실행된다면:

```text
2026-09-21 10:00:00 worker 동작 중 PID=1234
2026-09-21 10:00:05 worker 동작 중 PID=1234
2026-09-21 10:00:10 worker 동작 중 PID=1234
```

처럼 시간이 포함된 기록이 있어야 한다.

프로세스를 정리할 때도 단순히 `kill`하고 끝내는 것이 아니라:

```text
언제
어떤 PID를
왜 종료했고
종료 후 상태가 어떻게 바뀌었는가
```

를 기록해야 한다.

그래서 보고서 이름에도 날짜를 붙이는 습관이 중요하다.

```text
2026-09-21-process-cleanup-report.md
```

## 10. Linux 주니어가 로그를 볼 때의 기본 사고 순서

로그 관리에서 중요한 것은 파일 이름을 많이 외우는 것이 아니라 **문제가 발생했을 때 조사 범위를 좁히는 순서**다.

```text
1. 어떤 증상인가?
2. 언제부터 발생했는가?
3. 관련 서비스가 살아 있는가?
4. 그 시간대에 어떤 로그가 남았는가?
5. CPU / Memory / Disk 등 자원 문제인가?
6. Network 문제인가?
7. Application 자체 오류인가?
8. 여러 로그의 시간 관계가 이어지는가?
```

### 실무에서 먼저 알아야 할 로그 영역

| 영역 | 대표적으로 확인할 내용 | 중요도 | Agent에 사용할 Description |
|---|---|---:|---|
| SSH / 인증 | SSH 접속, 로그인 실패, 사용자 접속 기록, 인증 문제 | ★★★★★ | SSH 로그인 성공·실패, 사용자 접속 기록, public key/password/PAM 등 인증 문제를 조사할 때 사용한다. |
| Service | 서비스 시작 실패, 갑작스러운 종료, 재시작 반복, exit code | ★★★★★ | systemd 서비스가 시작되지 않거나 종료·재시작되는 원인을 조사할 때 사용한다. |
| System / Journal | 최근 시스템 오류, 특정 시간대 이벤트 | ★★★★★ | 장애 원인이 명확하지 않을 때 최근 Linux 시스템 이벤트 전체를 1차 탐색할 때 사용한다. |
| Process | 실행 여부, CPU/Memory 과다 사용, Zombie | ★★★★★ | 특정 프로세스의 실행 상태와 비정상적인 자원 사용, 프로세스 상태를 확인할 때 사용한다. |
| CPU / Memory | CPU 부하, Load Average, OOM, Swap | ★★★★★ | 서버 지연이나 프로세스 종료가 CPU·Memory 부족과 관련 있는지 조사할 때 사용한다. |
| Disk / Filesystem | 용량 부족, inode, I/O Error, read-only | ★★★★★ | 디스크 공간과 filesystem 문제 때문에 서비스가 실패하는지 조사할 때 사용한다. |
| Network | ping, Port, timeout, connection refused | ★★★★★ | 서버 간 통신, 포트, HTTP 응답 및 네트워크 연결 실패 원인을 조사할 때 사용한다. |
| Cron | 예약 작업 실행/실패, PATH, 권한 문제 | ★★★★☆ | cron 작업이 예정된 시간에 실행되었는지와 실패 원인을 조사할 때 사용한다. |
| Kernel | OOM, segfault, device/I/O 문제 | ★★★★☆ | 애플리케이션보다 낮은 커널 수준의 시스템 오류를 조사할 때 사용한다. |
| Application | Exception, ERROR, timeout, 반복 오류 | ★★★★★ | 애플리케이션 내부 로그의 예외와 반복 패턴을 분석하여 코드 또는 외부 연동 문제를 조사할 때 사용한다. |
| Web Server | access/error log, 4xx/5xx, upstream | ★★★★☆ | Nginx 등의 HTTP 요청과 서버 오류, upstream 연결 문제를 조사할 때 사용한다. |
| 로그 파일 관리 | 로그 크기, logrotate, 오래된 로그 | ★★★★☆ | 로그 파일 증가로 인한 디스크 문제와 rotation/retention 설정을 확인할 때 사용한다. |

## 11. 로그를 HTML로 보여주는 이유: 수집과 표현을 분리하기 위해서

오늘 수업에서는 `ps`나 시스템 자원 결과를 일정 시간마다 로그에 저장하고, 그 값을 HTML 보고서에 반영하는 흐름도 다뤘다.

구조를 분리해서 보면 쉽다.

```text
Linux
↓
CPU / Memory / Process 값 수집
↓
로그 또는 CSV / DB 저장
↓
HTML에 전달
↓
Dashboard / 보고서 출력
```

여기서 중요한 것은 **Linux에서 값을 수집하는 일과 화면을 만드는 일을 한 번에 해결하려고 하지 않는 것**이다.

각 단계를 분리하면 한 부분이 실패해도 어디서 문제가 발생했는지 확인하기 쉽다.

```text
수집 실패인가?
저장 실패인가?
HTML 전달 실패인가?
화면 렌더링 문제인가?
GPT API 문제인가?
```

이런 구조가 유지보수에 훨씬 유리하다.

---

## 12. 데이터를 처음부터 일정한 형식으로 남겨야 하는 이유

오늘 강조된 중요한 관점 중 하나는 **나중에 검색하고 AI가 활용할 것을 생각해서 처음부터 데이터를 구조화하는 것**이다.

예를 들어 Linux 실습 기록을 단순 텍스트로 계속 쌓기보다:

```text
대분류: Linux
중분류: Process
소분류: Monitoring
명령어: ps -ef
목적: 전체 프로세스 확인
결과: ...
시간: ...
```

처럼 일정한 형식으로 저장하면 나중에 검색하기 쉬워진다.

같은 명령어도 실행 시점과 시스템 상태에 따라 결과가 달라지므로 **명령어뿐 아니라 실행 시간과 결과까지 함께 저장하는 것**이 중요하다.

이 자료들이 쌓이면 나중에는 단순 키워드 검색을 넘어:

```text
"예전에 프로세스가 너무 많이 떠서 서버가 느렸던 경우"
```

처럼 의미가 비슷한 과거 사례를 찾는 AI 검색에도 활용할 수 있다.

---

# 13. 자동화와 AI Agent의 경계

오늘 대화에서 가장 중요한 정리는 이 부분이다.

단순히 `CPU > 90%`일 때 프로세스를 재시작하는 것은 AI Agent가 아니라 **조건 기반 자동화**다.

```text
CPU > 90%
→ restart
```

이 정도는 Shell Script의 `if`로 충분하다.

AI가 필요한 문제는 다음과 같다.

```text
"웹 서버가 갑자기 느리다. 원인을 찾아라."
```

이 경우 처음부터 무엇이 문제인지 알 수 없다.

```text
CPU 문제인가?
Memory 문제인가?
Disk인가?
Network인가?
Application인가?
정상적인 배치 작업인가?
```

따라서 AI Agent가 맡아야 할 핵심은 **명령 실행 자체가 아니라 조사 방향을 결정하는 일**이다.

### 역할 분리

| 작업 | 적합한 방식 |
|---|---|
| CPU 값 수집 | 일반 코드 |
| `ps`, `free`, `df` 실행 | Linux Tool |
| cron 실행 | 자동화 |
| 임계치 검사 | 일반 조건문 |
| 어떤 로그를 먼저 볼지 결정 | AI Agent |
| 로그 문맥 해석 | AI Agent |
| 장애 가설 생성 | AI Agent |
| 추가 조사가 필요한지 판단 | AI Agent |
| 실제 위험한 명령 실행 허용 여부 | 규칙 기반 Policy |
| 조치 후 정상화 확인 | 코드 + Agent |

즉 **모든 것을 AI로 만드는 것이 좋은 설계가 아니라, 정형화할 수 없는 판단에만 AI를 넣는 것이 좋은 설계**다.

---

# 14. LangGraph를 쓰는 이유

오늘 설계한 Agent가 단순히:

```text
A → B → C → D
```

처럼 한 번 지나가는 구조라면 일반 Python 코드로도 충분하다.

LangGraph가 의미를 갖는 이유는 조사 결과에 따라 **다시 이전 단계로 돌아가거나, 다른 Agent를 선택하고, 여러 Agent를 병렬로 호출해야 하기 때문**이다.

핵심 흐름은 다음과 같다.

```text
사용자 증상
↓
Triage Agent
↓
Supervisor Agent
↓
필요한 조사 Agent 선택
├─ Resource
├─ Process
├─ Network
└─ Log
↓
Hypothesis Agent
↓
"원인이 무엇일까?"
↓
Evidence Judge
├─ 근거 부족 → 추가 조사
└─ 근거 충분 → Critic
                    ↓
               반론 검증
                    ↓
              Diagnosis
                    ↓
              Action Plan
                    ↓
                 Policy
                    ↓
                 Execute
                    ↓
                 Verify
              ├─ 성공 → 기록
              └─ 실패 → 재진단
```

이 구조의 핵심은 **순환**이다.

> 원인을 한 번에 맞히는 AI가 아니라, 부족한 정보를 스스로 찾아가면서 가설을 검증하는 AI를 만드는 것이다.

## 15. Linux 로그 Agent의 핵심은 Description이다

Agent가 여러 Tool 중 무엇을 사용할지 선택하게 하려면 각 Tool의 이름보다 **Description이 명확해야 한다.**

예를 들어 SSH Agent를 단순히 `ssh_agent`라고만 정의하는 것보다:

```text
SSH 로그인 성공/실패, 사용자 접속 기록,
public key, password, PAM 등 인증 문제를 조사할 때 사용한다.
```

라고 설명하는 편이 LLM이 적절한 Tool을 선택하기 쉽다.

예를 들어 사용자가:

```text
"어제부터 어떤 사용자가 SSH 로그인을 계속 실패하고 있어"
```

라고 하면 Agent는 Description을 보고 SSH/인증 도구를 선택한다.

반대로:

```text
"서버 용량이 부족한 것 같다"
```

라고 하면 Disk Agent를 선택해야 한다.

즉 Agent 설계에서는 **함수를 많이 만드는 것보다 서로 겹치지 않는 역할과 Description을 잘 정의하는 것이 먼저**다.

# 16. 현재 프로젝트와 연결

현재 진행 중인 `linux-ps-monitor`는 좋은 기반이다.

현재 구조는 대략:

```text
cron
↓
collect_ps.sh
↓
프로세스/자원 로그 축적
↓
Dashboard
```

여기에 바로 AI를 붙이기보다 다음 단계로 확장하는 것이 자연스럽다.

```text
1. Linux 상태 수집
2. 로그 저장
3. 이상 현상 발견
4. Supervisor가 조사할 로그 영역 선택
5. 각 Tool이 실제 Linux 정보를 수집
6. AI가 여러 결과를 연결해 가설 생성
7. 근거 부족 시 추가 조사
8. 최종 진단과 권고사항 생성
```

즉 현재 시스템은 **관찰 계층**, 이후 LangGraph Agent는 **판단 계층**으로 나누면 된다.

# 17. 오늘 내용을 실무 관점에서 다시 정리하면

오늘 배운 것들은 사실 하나의 운영 흐름으로 연결된다.

### 1단계 — 실행

```text
Shell Script
cron
foreground / background
```

반복 업무를 실행한다.

### 2단계 — 관찰

```text
ps
top
htop
PID / PPID
```

무엇이 실제로 실행되고 자원을 사용하는지 본다.

### 3단계 — 기록

```text
log
CSV
시간 정보
작업 결과
```

나중에 원인을 추적할 수 있도록 남긴다.

### 4단계 — 표현

```text
HTML
Dashboard
보고서
```

사람이 판단하기 쉽게 바꾼다.

### 5단계 — 자동화

```text
if
while
cron
```

이미 규칙이 명확한 작업을 자동 처리한다.

### 6단계 — Agent

```text
로그를 어디서 볼지 결정
가설 생성
추가 조사
로그 간 상관관계 분석
최종 원인 판단
```

규칙만으로 정하기 어려운 부분에 AI를 사용한다.

# 18. 오늘의 핵심 문장

> **cron은 시간을 결정하고, Shell Script는 조건을 결정하며, 프로세스 도구는 실제 실행 상태를 보여주고, 로그는 그 결과를 증명한다. AI Agent는 이 정보들 사이에서 무엇을 더 조사해야 하고 어떤 원인이 가능한지를 판단한다.**

그리고 Linux 운영에서 가장 중요한 습관은:

> **실행하기 전에 상태를 확인하고, 실행한 뒤에는 결과를 검증하고, 중요한 작업은 반드시 로그를 남기는 것**이다.

이 흐름이 잡히면 `ps`, `top`, `cron`, 로그, Agent가 각각 따로 떨어진 주제가 아니라 하나의 Linux 운영 과정으로 연결된다.
