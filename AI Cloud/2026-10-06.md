**[정확성 보충]** 녹취에서는 MCP를 “모델과 모델끼리 연결하는 통신 규약”처럼 표현한 부분이 있지만, 학습할 때는 **AI 애플리케이션이 외부 데이터·도구·서비스와 표준화된 방식으로 연결되도록 하는 프로토콜**이라고 이해하는 편이 정확합니다. 수업의 핵심은 “외부 기능을 AI가 호출 가능한 도구로 만든다”는 점입니다.

함수 이름, 매개변수, 타입, 기본값, 설명(docstring)을 프로그램이 읽을 수 있다면, 사람이 도구 설명서를 일일이 다시 작성하지 않아도 **함수 자체에서 도구 명세(schema)를 자동 생성**할 수 있습니다. 오늘 뒤쪽에서 `inspect`, decorator, registry를 배운 이유가 바로 여기에 연결됩니다.

→ 왜 배우나·현업 활용: 함수의 입력·출력과 설명이 API·AI 도구의 계약이 되는 원리를 이해하여, 실제로 FastAPI 엔드포인트나 MCP Tool을 연결할 때 어떤 함수가 어떤 값을 받고 돌려주는지 빠르게 파악하기 위해 배웁니다.

## 2. MCP와 Agent를 수업에서 어떻게 구분했는가

**[수업 내용]** MCP는 여러 외부 프로그램의 기능을 AI가 사용할 수 있도록 **Tool 형태로 연결하는 규약**으로 설명했습니다. 예를 들어 `add`라는 도구의 설명이 “두 숫자를 더한다”라면 사용자의 요청이 덧셈과 관련되었을 때 해당 도구를 선택하는 식입니다. 반대로 `hello` 도구의 설명이 인사와 관련되었다면 인사 요청에 대응할 수 있습니다.

여기서 중요한 것은 함수 이름만이 아니라 **description, 즉 함수가 무엇을 하는지 적은 설명**입니다. 뒤에서 배우는 `__doc__`와 docstring이 중요한 이유도 도구가 어떤 기능인지 모델이나 프레임워크가 알아낼 수 있기 때문입니다.

수업에서는 Agent를 MCP보다 한 단계 더 “판단”하는 구조로 설명했습니다. 즉 MCP가 도구를 제공하고 연결하는 역할에 가깝다면, Agent는 여러 도구 중 무엇을 쓸지 판단하고 실행 결과를 보고 다음 행동까지 결정하는 흐름으로 이해할 수 있습니다.

→ 왜 배우나·현업 활용: 도구를 “연결하는 계층”과 도구를 “선택하고 연속 실행하는 계층”을 구분하여, 실제 AI Agent 장애 시 도구 등록 문제인지 Agent의 판단 문제인지 원인을 분리하기 위해 배웁니다.

## 3. 동기와 비동기: 왜 MCP/API에서 자주 등장하는가

**동기(Synchronous)**는 앞 작업이 끝나야 다음 작업으로 넘어가는 방식입니다. 예를 들어 DB 조회가 끝날 때까지 프로그램이 다음 네트워크 요청을 시작하지 않는 구조입니다.

**비동기(Asynchronous)**는 네트워크나 DB 응답처럼 기다리는 시간이 생겼을 때 다른 작업을 수행할 수 있는 방식입니다. MCP나 API에서는 DB 조회, 외부 API 호출, 파일 접근처럼 **I/O 대기 시간이 긴 작업이 동시에 많이 발생**할 수 있기 때문에 비동기 구조가 자주 사용됩니다.

중요한 점은 비동기가 “여러 CPU 연산을 무조건 동시에 실행한다”는 뜻이 아니라, 주로 **기다리는 시간 동안 다른 일을 진행해 전체 처리 효율을 높이는 방식**이라는 것입니다.

→ 왜 배우나·현업 활용: 외부 API·DB·AI 모델 호출의 대기 시간을 이해하여, 실제로 API 응답이 느릴 때 코드 계산이 느린 것인지 I/O를 순차 대기하는 구조 때문인지 판단하기 위해 배웁니다.

# 4. Python 함수 기초: 입력 → 처리 → 반환

## 4.1 `def`, 매개변수(parameter), 인자(argument)

녹취에서는 “define”이라고 반복해서 표현되었지만 Python의 실제 문법은 **`def`**입니다.

```python
def add(a, b):
    return a + b
```

여기서 `a`, `b`는 함수를 정의할 때 적는 **매개변수(parameter)**이고, `add(3, 5)`에서 `3`, `5`는 실제 호출 시 넘기는 **인자(argument)**입니다.

```python
result = add(3, 5)
```

위 코드에서는 `3`, `5`가 함수 내부 `a`, `b`로 전달되고, 계산 결과가 `return`을 통해 함수 밖으로 나옵니다.

→ 왜 배우나·현업 활용: 함수가 어떤 입력을 요구하는지 정확히 구분하여, 실제 패키지 함수나 API 도구 호출 시 “어떤 인자를 어느 위치에 넣어야 하는가”를 문서만 보고 판단하기 위해 배웁니다.

## 4.2 위치 인자, 키워드 인자, 기본값

매개변수에는 기본값을 줄 수 있습니다.

```python
def repeat_text(value="*", repeat=10):
    return value * repeat
```

```python
repeat_text()                 # 기본값 사용
repeat_text("-")              # 첫 번째 매개변수 value만 변경
repeat_text("-", 5)           # 위치 순서대로 전달
repeat_text(repeat=3, value="@")  # 이름을 지정하므로 순서 변경 가능
```

위치 인자는 순서가 중요하지만, 키워드 인자는 매개변수 이름을 직접 적기 때문에 순서를 바꿀 수 있습니다. 특히 타입이 서로 다른 인자를 위치만 믿고 전달하면 의도하지 않은 TypeError가 발생할 수 있으므로 외부 API나 복잡한 함수에서는 키워드 인자가 가독성을 높여줍니다.

→ 왜 배우나·현업 활용: 인자 순서 오류를 줄이고 함수 호출 의도를 명확히 하여, 실제 AI SDK나 클라우드 SDK처럼 매개변수가 많은 함수를 안전하게 호출하기 위해 배웁니다.

## 4.3 `print`와 `return`은 다르다

`print()`는 화면에 내용을 보여주는 동작이고, `return`은 **함수 결과를 호출한 곳에 전달하는 동작**입니다.

```python
def bad_add(a, b):
    print(a + b)

x = bad_add(3, 5)
```

화면에는 `8`이 출력되더라도 `x`에는 계산 결과가 저장되는 것이 아니라 반환값이 없으므로 `None`이 들어갑니다.

```python
def add(a, b):
    return a + b

x = add(3, 5)
print(x)
```

API나 MCP Tool은 화면 출력보다 **다른 프로그램이 사용할 수 있는 값의 반환**이 중요하므로 `return` 설계가 핵심입니다.

→ 왜 배우나·현업 활용: 로그 출력과 실제 반환 데이터를 구분하여, API 함수가 콘솔에는 정상처럼 보이는데 클라이언트에는 값이 전달되지 않는 문제를 예방하기 위해 배웁니다.

## 4.4 지역 변수와 함수의 수명

함수 안에서 만든 변수는 일반적으로 해당 함수의 지역 범위(local scope)에 속합니다. 함수 외부에서 직접 접근하려고 하면 사용할 수 없는 경우가 많습니다.

```python
def calc():
    total = 10
    return total
```

따라서 함수 내부에서 계산한 값을 외부에서 계속 사용해야 한다면 `return`으로 전달하거나 객체의 속성으로 저장하는 식의 설계가 필요합니다.

→ 왜 배우나·현업 활용: 변수의 생존 범위를 이해하여, 실제 함수 분리 후 “왜 이 변수는 다른 파일이나 다른 함수에서 보이지 않는가” 같은 Scope 오류를 해결하기 위해 배웁니다.

# 5. 입력 개수가 정해지지 않을 때: `*args`, `**kwargs`

## 5.1 `*args`: 여러 위치 인자를 Tuple로 받기

```python
def sum_values(*args):
    total = 0
    for value in args:
        total += value
    return total
```

`sum_values(1, 2, 3, 4)`처럼 인자의 개수가 달라져도 받을 수 있습니다. `args`라는 이름 자체가 필수는 아니지만 관례적으로 사용하며, 전달된 값은 **tuple**로 묶입니다.

→ 왜 배우나·현업 활용: 입력 개수가 고정되지 않은 함수 구조를 이해하여, 실제 decorator나 wrapper가 원래 함수의 다양한 인자를 그대로 전달하도록 만들기 위해 배웁니다.

## 5.2 `**kwargs`: 여러 키워드 인자를 Dictionary로 받기

```python
def create_profile(**kwargs):
    return kwargs

profile = create_profile(name="Kim", age=30)
```

결과는 개념적으로 다음과 같은 dictionary입니다.

```python
{"name": "Kim", "age": 30}
```

AI 관련 SDK나 설정 함수는 옵션 종류가 많기 때문에 `**kwargs` 패턴을 자주 사용합니다.

→ 왜 배우나·현업 활용: 이름이 붙은 여러 옵션을 동적으로 전달하는 방법을 이해하여, 실제 AI SDK·클라우드 SDK에서 선택적 설정값을 유연하게 넘기기 위해 배웁니다.

# 6. 자주 사용한 Python 자료형 정리

| 자료형 | 특징 | 대표 사용 상황 |
|---|---|---|
| `int` | 정수 | 개수, 순위, 포트 번호 |
| `float` | 실수 | 비율, 측정값 |
| `str` | 문자열 | 이름, 경로, JSON의 문자열 값 |
| `bool` | `True`/`False` | 상태 플래그 |
| `list` | 순서 있음, 수정 가능 | 여러 행 데이터 |
| `tuple` | 순서 있음, 수정 불가 | 변경하지 않을 묶음, `*args` |
| `dict` | key-value 구조 | API 응답, JSON과 유사한 데이터 구조 |
| `set` | 중복 제거, 인덱스 없음 | 고유 지역명 추출 |
| `range` | 연속 숫자 범위 표현 | 반복문 |

**[정확성 보충]** 녹취에서는 `array`도 Python 기본 자료형처럼 함께 언급되었지만, Python에서 일반적으로 기본 내장 컨테이너로 먼저 배우는 것은 `list`, `tuple`, `dict`, `set`입니다. 배열은 `array` 모듈이나 NumPy의 `ndarray`처럼 별도 구현을 사용하는 경우가 많습니다.

`set`은 중복 제거에는 편리하지만 순번으로 `data[0]`처럼 접근하는 일반적인 인덱싱 구조가 아닙니다. 필요한 경우 `list(set(data))`처럼 변환할 수 있지만, set은 순서를 보존하기 위한 자료형으로 사용해서는 안 됩니다.

→ 왜 배우나·현업 활용: 함수 입력과 API 응답의 실제 자료형을 읽을 수 있게 하여, 데이터가 list인지 dict인지 착각해서 발생하는 인덱싱·키 접근 오류를 줄이기 위해 배웁니다.

# 7. Dictionary, JSON, CSV, YAML이 연결되는 이유

## 7.1 Dictionary는 Python 내부의 key-value 구조

```python
user = {
    "name": "Kim",
    "age": 30
}
```

Python 프로그램 내부에서는 `dict`를 사용하고, 외부 프로그램과 데이터를 주고받을 때는 이와 유사한 구조를 **JSON**으로 직렬화하는 경우가 많습니다.

→ 왜 배우나·현업 활용: Python 내부 자료와 외부 API 데이터 형식의 연결 관계를 이해하여, API 응답 JSON에서 필요한 key를 정확히 찾아 사용하기 위해 배웁니다.

## 7.2 JSON을 API와 MCP에서 많이 쓰는 이유

JSON은 JavaScript Object Notation의 약자입니다. 특정 프로그래밍 언어의 객체 자체를 그대로 보내는 것이 아니라, 문자열·숫자·배열·객체(key-value) 등 여러 언어가 공통으로 해석하기 쉬운 형태로 데이터를 표현할 수 있습니다.

수업에서는 JSON이 프로그램 사이 데이터 교환에 유리하다는 점을 강조했습니다. 특히 Python, JavaScript, Java 등 서로 다른 언어로 작성된 시스템끼리 통신할 때 공통 교환 형식으로 사용하기 좋습니다.

**[정확성 보충]** CSV도 첫 행을 header로 사용해 컬럼명을 가질 수 있습니다. JSON의 더 큰 강점은 CSV보다 **중첩 구조, key-value 관계, 배열과 객체의 조합을 자연스럽게 표현할 수 있다는 점**입니다. 반대로 집계·표 계산처럼 행과 열이 중요한 데이터는 CSV나 관계형 DB가 더 단순하고 효율적인 경우도 있습니다.

→ 왜 배우나·현업 활용: 시스템마다 내부 데이터 구조가 달라도 공통 교환 형식으로 맞추는 방법을 이해하여, 실제 백엔드·프론트엔드·AI 서비스 사이의 데이터 계약을 설계하기 위해 배웁니다.

## 7.3 YAML과 Dictionary

YAML도 key-value를 표현할 수 있으며 JSON보다 사람이 읽기 쉬운 설정 파일 용도로 자주 사용됩니다. Docker Compose나 Kubernetes 설정에서 YAML을 자주 보는 이유도 사람이 설정 구조를 작성하고 수정하기 편하기 때문입니다.

→ 왜 배우나·현업 활용: 같은 key-value 사고방식을 JSON·YAML에 연결하여, API 응답과 Docker/Cloud 설정 파일을 서로 완전히 다른 개념으로 보지 않고 구조적으로 읽기 위해 배웁니다.

# 8. JSON 직렬화와 “보낼 수 없는 객체”

Python의 모든 객체를 그대로 JSON으로 변환할 수 있는 것은 아닙니다. 예를 들어 `datetime`이나 `Decimal` 같은 객체는 그대로 `json.dumps()`에 넣으면 직렬화 오류가 날 수 있습니다.

```python
from datetime import datetime

now = datetime.now()
text = now.isoformat()
```

`isoformat()`을 사용하면 날짜·시간 객체를 표준화된 문자열 형태로 바꾸어 다른 시스템으로 전달하기 쉬워집니다. 수업에서는 단순 `str(now)`도 문자열이 되지만, 날짜와 시간 사이에 `T`가 들어가는 ISO 계열 표현이 시스템 간 교환에 더 적합하다는 점을 설명했습니다.

**[확인 필요]** 녹취의 “isFormat”은 문맥상 `isoformat()`을 의미하는 것으로 보입니다.

→ 왜 배우나·현업 활용: Python 내부 객체와 네트워크 전송 가능한 데이터 형식의 차이를 이해하여, 실제 API 응답에서 `Object of type datetime is not JSON serializable` 같은 오류를 처리하기 위해 배웁니다.

# 9. Type Hint: 타입을 “강제”하는 것이 아니라 함수 계약을 설명한다

```python
def add(a: int, b: int) -> int:
    return a + b
```

`a: int`, `b: int`는 어떤 타입을 기대하는지 알려주고, `-> int`는 반환 타입이 무엇인지 설명합니다. 하지만 Python의 type hint 자체가 C++처럼 실행 시 타입을 강제로 막아주는 것은 아닙니다.

값이 없을 수도 있다면 최신 Python에서는 다음과 같이 표현할 수 있습니다.

```python
def find_user(name: str | None = None) -> dict | None:
    ...
```

**[정확성 보충]** 녹취에서 “난”이라고 들리는 부분은 문맥상 `None`인 경우가 많습니다. `None`은 “값이 없음”을 뜻하고, 데이터 분석에서 사용하는 `NaN`은 “숫자 데이터의 결측값” 개념이므로 서로 다릅니다.

→ 왜 배우나·현업 활용: 함수 코드를 모두 읽지 않고도 필요한 입력과 반환 형식을 파악하여, 실제 다른 개발자가 만든 라이브러리나 API 함수를 빠르게 연결하기 위해 배웁니다.

## 9.1 Type Hint와 Validation은 다르다

Type hint는 설명입니다. 실제 값이 조건에 맞는지 검사하려면 별도의 **validation(검증)**이 필요합니다. 수업 후반부에서 FastAPI와 검증용 class를 연결한 이유가 이것입니다.

예를 들어 Pydantic 계열의 모델은 type hint를 읽어 입력값을 검사하거나 가능한 경우 변환할 수 있습니다.

```python
from pydantic import BaseModel

class User(BaseModel):
    name: str
    age: int
```

이런 모델은 입력 데이터가 설계한 필드와 맞는지 확인하는 역할을 합니다.

**[확인 필요]** 녹취의 “Synthetic” 또는 비슷하게 인식된 검증 명칭은 정확한 원자료 확인이 필요합니다. 수업 흐름상 핵심은 **BaseModel과 같은 검증 도구가 type hint를 실제 입력 검증에 활용한다**는 점입니다.

→ 왜 배우나·현업 활용: “문서상 int라고 적혀 있음”과 “실제로 int인지 검증됨”을 구분하여, 실제 FastAPI 요청 데이터가 잘못 들어왔을 때 어디에서 검증할지 설계하기 위해 배웁니다.

# 10. 실습 핵심 1: `loader.py`는 읽기만 담당하게 분리한다

## 10.1 왜 로더를 따로 만드는가

수업에서는 **CSV 읽기와 매출 집계를 한 함수 안에 섞지 말라**는 점을 강조했습니다. 데이터 소스가 CSV에서 DB로 바뀌더라도 계산 로직까지 전부 다시 수정하지 않으려면 읽기 책임을 분리해야 합니다.

```text
project/
├─ tools/
│  ├─ loader.py
│  └─ sales_tools.py

```

`loader.py`는 데이터를 읽어 공통 형태로 변환하고, `sales_tools.py`는 그 데이터를 이용해 집계하는 역할을 맡습니다.

→ 왜 배우나·현업 활용: 데이터 소스 변경이 계산 코드 전체로 번지지 않게 하여, 실제 CSV에서 DB·API로 이전할 때 수정 범위를 loader 계층으로 제한하기 위해 배웁니다.

## 10.2 `__file__`과 `pathlib`를 이용한 경로 처리

실행 위치가 달라져도 파일을 안정적으로 찾으려면 “현재 터미널 위치”보다 **실행 중인 `.py` 파일 위치를 기준으로 경로를 계산**하는 방법이 유용합니다.

```python
from pathlib import Path

BASE_DIR = Path(__file__).resolve().parent
```

`parent`를 한 번 쓰면 현재 파일이 있는 폴더의 상위, 여러 번 쓰면 더 위의 폴더로 올라갑니다. 수업에서는 `loader.py`의 위치를 기준으로 `sales.csv`를 찾는 흐름을 실습했습니다.

**[주의]** Jupyter Notebook(`.ipynb`) 환경에서는 일반 `.py` 파일과 달리 `__file__`이 기본적으로 존재하지 않을 수 있습니다. 녹취에서 `.py`와 Notebook의 경로 처리 방식이 다르다고 한 이유입니다.

→ 왜 배우나·현업 활용: 실행 디렉터리가 바뀌어도 파일 경로가 깨지지 않게 하여, 실제 cron·Docker·서버 실행 환경에서 상대경로 오류를 줄이기 위해 배웁니다.

## 10.3 CSV를 읽고 공통 데이터로 변환하기

개념적으로는 다음 형태입니다.

```python
[
    {"region": "...", "quantity": ..., "price": ..., "amount": ...},
    {"region": "...", "quantity": ..., "price": ..., "amount": ...},

```

CSV에서 읽은 값은 문자열인 경우가 많으므로 실제 계산 전에 `int()` 또는 `float()` 변환이 필요한지도 확인해야 합니다.

→ 왜 배우나·현업 활용: 파일 원본 형식을 계산하기 좋은 공통 구조로 정규화하여, 실제 분석·API 코드가 입력 파일 형식에 직접 의존하지 않게 만들기 위해 배웁니다.

# 12. 실습 핵심 3: `defaultdict`로 지역별 매출 집계

지역별 누적값을 계산할 때 일반 dict를 사용하면 키가 처음 등장할 때 초기값을 직접 만들어야 합니다.

```python
sales = {}
if region not in sales:
    sales[region] = 0
sales[region] += amount
```

`collections.defaultdict(int)`를 사용하면 없는 키를 처음 만났을 때 `int()`의 기본값인 `0`이 자동으로 만들어집니다.

```python
from collections import defaultdict

by_region = defaultdict(int)

for row in rows:
    by_region[row["region"]] += row["amount"]
```

따라서 새로운 지역이 추가되어도 `서울`, `부산`, `제주`를 미리 코드에 하드코딩할 필요가 없습니다.

→ 왜 배우나·현업 활용: 데이터에 새로운 key가 들어와도 집계 코드를 수정하지 않게 하여, 실제 로그·매출·지역 통계처럼 값 종류가 동적으로 늘어나는 데이터를 처리하기 위해 배웁니다.

# 14. 함수 정보를 코드가 스스로 읽게 하기: Introspection

오늘 수업의 중요한 전환점입니다. 함수는 실행만 할 수 있는 것이 아니라, Python에서 함수 객체가 가진 정보를 읽어낼 수 있습니다.

```python
print(func.__name__)
print(func.__doc__)
print(func.__annotations__)
```

- `__name__`: 함수 이름
- `__doc__`: 함수 바로 아래 docstring
- `__annotations__`: type hint 정보

또 `inspect.signature()`를 사용하면 매개변수, 기본값, annotation 등을 프로그램이 분석할 수 있습니다.

```python
import inspect

sig = inspect.signature(func)
print(sig)
print(sig.parameters)
```

이 기능을 사용하면 사람이 별도로 문서를 작성하지 않아도 함수의 기본 정보를 읽어 **API/MCP Tool schema의 재료**로 사용할 수 있습니다.

→ 왜 배우나·현업 활용: 함수의 이름·설명·매개변수를 자동 추출하여, 실제 수십 개 도구의 문서를 수작업으로 유지하지 않고 자동 명세 생성 시스템을 만들기 위해 배웁니다.

```python
def add(a: int, b: int) -> int:
```

# 16. Function Object: `hello`와 `hello()`는 다르다

```python
def hello():
    return "hi"
```

- `hello` → 함수 **자체 객체**
- `hello()` → 함수를 **실행한 결과값**

```python
registry[hello.__name__] = hello
```

→ 왜 배우나·현업 활용: 함수 실행 결과와 함수 객체 자체를 구분하여, 실제 plugin registry·event handler·AI tool registry처럼 “나중에 실행할 함수”를 저장하는 구조를 이해하기 위해 배웁니다.

# 17. Decorator와 Wrapper: 함수를 감싸서 등록 기능을 추가한다

Decorator는 기존 함수 코드를 직접 수정하지 않고, 함수를 다른 함수로 감싸 부가 기능을 붙이는 패턴입니다.

```python
def my_decorator(func):
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)
    return wrapper
```

그리고 `@` 문법으로 사용할 수 있습니다.

```python
@my_decorator
def hello():
    return "hi"
```

FastAPI의 `@app.get(...)`이나 MCP 계열의 `@...tool(...)` 형태를 이해할 때 이 원리가 필요합니다. 데코레이터가 함수를 전달받아 라우터나 registry에 등록하고, 필요하면 원래 함수를 다시 실행하는 구조입니다.

→ 왜 배우나·현업 활용: `@app.get`, `@tool` 같은 문법이 마법처럼 동작하는 것이 아니라 함수를 전달·등록하는 구조임을 이해하여, 실제 decorator 내부 오류나 등록 누락을 추적하기 위해 배웁니다.

# 18. Closure와 `nonlocal`: 함수가 바깥 함수의 상태를 기억하는 방법

Closure는 내부 함수가 자신이 만들어질 때의 바깥 함수 변수를 기억하고 사용할 수 있는 구조입니다.

```python
def make_counter():
    count = 0

    def counter():
        nonlocal count
        count += 1
        return count

    return counter
```

`nonlocal`은 전역변수(global)가 아니라 **바로 바깥쪽 함수 scope의 변수**를 수정하겠다는 뜻입니다.

```python
c = make_counter()
c()  # 1
c()  # 2
```

수업에서는 이런 구조가 decorator나 여러 프레임워크 내부 동작을 이해하는 데 연결된다고 설명했습니다.

→ 왜 배우나·현업 활용: 함수가 호출 사이에 상태를 유지하는 구조를 이해하여, 실제 decorator·callback·등록 함수가 왜 이전 상태를 기억하는지 디버깅하기 위해 배웁니다.

# 19. Registry: 함수 목록과 실행 정보를 한 곳에 등록하기

Registry는 사용 가능한 함수를 dictionary 같은 자료구조에 모아두는 방식입니다.

개념 예시:

```python
REGISTRY = {}

def tool(func):
    REGISTRY[func.__name__] = {
        "function": func,
        "description": func.__doc__,
    }
    return func
```

```python
@tool
def add(a: int, b: int) -> int:
    """두 숫자를 더합니다."""
    return a + b
```

이제 `REGISTRY`에는 `add` 함수 자체와 설명을 보관할 수 있습니다. 여기에 `inspect.signature()`로 매개변수 정보를 더하면 Tool schema를 만들 수 있습니다.

→ 왜 배우나·현업 활용: 여러 도구를 한 곳에서 검색·조회·호출할 수 있게 하여, 실제 MCP 서버나 plugin 시스템에서 등록된 Tool 목록을 제공하고 이름으로 실행하기 위해 배웁니다.

## 19.1 `list_tools`와 `call_tool`의 역할

수업 후반에서는 registry를 이용해 크게 두 기능을 설명했습니다.

1. **list_tools**: 현재 어떤 도구가 등록되어 있는지 외부에 알려준다.
2. **call_tool**: 도구 이름과 argument를 받아 실제 함수를 호출한다.

개념적으로 다음 흐름입니다.

```text
사용자/AI 요청
    ↓
사용 가능한 tool 목록 조회
    ↓
description + schema 확인
    ↓
적절한 tool 이름 선택
    ↓
arguments 구성
    ↓
call_tool(name, arguments)
    ↓
실제 Python 함수 실행
    ↓
JSON 형태 결과 반환
```

이 구조가 오늘 수업에서 만든 “작은 Tool 시스템”이며, 이후 MCP를 볼 때 내부 동작을 이해하기 위한 축소 모델입니다.

→ 왜 배우나·현업 활용: AI가 실제 Python 함수를 직접 아는 것이 아니라 등록된 도구 목록과 명세를 통해 호출한다는 원리를 이해하여, Tool not found·argument mismatch 장애를 추적하기 위해 배웁니다.

# 20. Python 모듈 import와 module cache

Python은 일반적으로 한 번 import한 모듈을 `sys.modules`에 보관하고 같은 프로세스에서 다시 import할 때 이미 로드된 모듈 객체를 재사용합니다.

수업에서는 이 동작이 Tool 자동 등록과 연결될 수 있다고 설명했습니다. 만약 모듈 import 시점에 decorator가 함수를 registry에 등록한다면, 같은 모듈을 반복 로드할 때 중복 등록 문제가 생길 수 있으므로 **import가 어떻게 캐시되는지** 이해할 필요가 있습니다.

```python
import sys
print(sys.modules.keys())
```

위 명령은 현재 프로세스에 로드된 모듈을 이해할 때 참고할 수 있습니다. 실제 출력은 실행 환경마다 달라지므로 특정 결과를 외우는 것이 아니라 “이미 import된 모듈이 메모리에 유지된다”는 개념이 중요합니다.

→ 왜 배우나·현업 활용: import 시 자동 등록되는 plugin/tool 구조를 이해하여, 실제 개발 서버에서 코드 수정이 반영되지 않거나 도구가 중복 등록되는 현상의 원인을 추적하기 위해 배웁니다.

# 21. Auto Loader: 폴더의 Tool 모듈을 자동으로 불러오기

도구가 몇 개 없을 때는 직접 import할 수 있지만, 파일이 많아지면 모든 함수를 수동으로 registry에 등록하는 것은 비효율적입니다. 수업에서는 Tools 폴더 내부의 `.py` 모듈을 순회하면서 자동 import하고, import 시 decorator가 자동 등록하도록 하는 구조를 설명했습니다.

개념 흐름은 다음과 같습니다.

```text
Tools 폴더 탐색
    ↓
모듈 이름 발견
    ↓
각 모듈 import
    ↓
모듈 안의 @tool decorator 실행
    ↓
REGISTRY에 함수 자동 등록
```

이것이 규모가 커졌을 때 plugin 방식으로 확장하는 기본 아이디어입니다.

→ 왜 배우나·현업 활용: Tool 파일이 늘어나도 중앙 파일을 매번 수정하지 않게 하여, 실제 플러그인·AI Tool 시스템에서 새 기능 추가 시 자동 탐색·등록되도록 설계하기 위해 배웁니다.

# 22. Class 기초: 왜 갑자기 객체지향을 배웠는가

수업 후반에 class가 나온 이유는 Python 라이브러리 내부에 함수만 있는 것이 아니라 **class와 상속 구조가 매우 많이 사용되기 때문**입니다. 특히 검증 라이브러리의 `BaseModel`처럼 이미 만들어진 class를 상속해 사용하는 구조를 읽으려면 최소한의 객체지향 문법이 필요합니다.

Class를 초보자 관점에서는 “관련 있는 데이터와 함수를 하나의 단위로 묶는 설계”라고 이해할 수 있습니다.

```python
class Calculator:
    def add(self, a, b):
        return a + b

calc = Calculator()
print(calc.add(3, 4))
```

`calc`는 `Calculator` 클래스로 만든 **instance(인스턴스)**입니다.

→ 왜 배우나·현업 활용: 외부 라이브러리가 class 형태로 제공될 때 구조를 읽을 수 있게 하여, 실제 SDK 객체에서 `.method()`를 호출하거나 상속받은 기능의 출처를 파악하기 위해 배웁니다.

## 22.1 `__init__`, `self`, attribute

`__init__`은 인스턴스가 만들어질 때 초기 상태를 설정하는 메서드입니다.

```python
class User:
    def __init__(self, name, age=10):
        self.name = name
        self.age = age
```

`self.name`, `self.age`는 해당 객체가 가지고 있는 attribute(속성)입니다.

→ 왜 배우나·현업 활용: 객체 내부 상태가 어디에 저장되는지 이해하여, 실제 클래스 기반 SDK에서 설정값이 생성 시점에 저장되는지 메서드 호출 시 전달되는지 구분하기 위해 배웁니다.

## 22.2 상속과 `super()`

공통 기능을 부모 class에 두고 여러 자식 class에서 재사용할 수 있습니다.

```python
class Organization:
    def __init__(self, name):
        self.name = name

class Course(Organization):
    def __init__(self, name, course_name):
        super().__init__(name)
        self.course_name = course_name
```

`super()`는 부모 class 쪽 기능을 사용하겠다는 의미로 이해하면 됩니다.

→ 왜 배우나·현업 활용: 공통 코드를 중복 작성하지 않고 재사용하는 구조를 이해하여, 실제 프레임워크의 부모 class가 제공하는 초기화·검증 로직을 자식 class에서 활용하기 위해 배웁니다.

## 22.3 Overriding

부모 class와 자식 class가 같은 이름의 메서드를 가질 때 자식 class의 구현으로 동작을 바꾸는 것을 overriding이라고 합니다.

**[정확성 보충]** 녹취에서 “Python은 Overriding이 안 된다”처럼 들리는 부분은 문맥상 확인이 필요합니다. Python은 메서드 overriding을 지원합니다. 반면 C++/Java와 같은 방식의 **정적 타입 기반 함수 overloading**은 Python에서 같은 방식으로 사용하지 않습니다.

→ 왜 배우나·현업 활용: 상속받은 메서드가 실제로 어느 class 구현을 실행하는지 이해하여, 라이브러리 동작이 부모 문서와 다를 때 자식 class의 override 여부를 확인하기 위해 배웁니다.

# 24. 코드 모듈화와 문서화가 오늘 수업의 숨은 핵심

오늘 수업 전체를 관통하는 설계 원리는 “**한 함수·한 파일은 가능한 한 하나의 책임을 갖게 하고, 다른 팀원이 사용할 수 있도록 입력·출력 계약을 명확히 한다**”입니다.

예를 들면 다음처럼 나눌 수 있습니다.

```text
loader.py        → 데이터를 읽고 공통 구조로 변환
sales_tools.py   → 매출 집계·상세 조회
schema.py        → 함수 메타정보를 도구 명세로 변환
registry.py      → 함수 등록·목록 조회·호출
main.py          → 전체 기능 연결
```

이렇게 나누면 CSV가 DB로 바뀌어도 `loader.py` 중심으로 수정하고, 집계 방식이 바뀌면 `sales_tools.py`를 수정할 수 있습니다. 또한 함수 type hint와 docstring이 잘 작성되어 있으면 다른 개발자·운영자·AI 시스템이 코드를 전부 읽지 않고도 사용 방법을 파악할 수 있습니다.

→ 왜 배우나·현업 활용: 코드 변경 영향 범위를 줄이고 협업자가 함수 계약을 빠르게 이해하게 하여, 실제 백엔드·클라우드·AI 팀이 서로 다른 모듈을 병렬 개발할 때 통합 비용을 줄이기 위해 배웁니다.

Linux/macOS 또는 `python3` 명령을 사용하는 환경:

## 3단계 — 모듈 연결 검증

`from tools.loader import load_rows`처럼 다른 파일에서 함수를 불러오고, `sales_tools.py`가 loader를 정상적으로 사용할 수 있는지 확인합니다.

## 4단계 — 함수 메타정보 확인

```python
import inspect

print(load_rows.__name__)
print(load_rows.__doc__)
print(load_rows.__annotations__)
print(inspect.signature(load_rows))
```

함수 이름, 설명, 매개변수, 반환 타입을 코드가 읽을 수 있는지 확인합니다.

## 5단계 — Registry에 함수 등록

Decorator 또는 직접 등록 방식으로 함수 객체를 registry에 넣고, `list_tools()`에서 목록이 보이는지 확인합니다.

## 6단계 — `call_tool()`로 문자열 이름 실행

도구 이름과 argument dictionary를 전달해 실제 함수가 실행되는지 확인합니다. 여기까지 되면 MCP의 “도구 목록 제공 → 도구 선택 → argument 전달 → 실행 → 결과 반환” 구조를 축소판으로 재현한 것입니다.

→ 왜 배우나·현업 활용: 복잡한 시스템을 한 번에 실행하지 않고 입력→계산→모듈→명세→등록→호출 순서로 검증하여, 실제 장애 발생 시 문제가 생긴 계층을 빠르게 좁히기 위해 배웁니다.

# 26. 오늘 녹취에서 특히 헷갈릴 수 있는 표현 정리

| 녹취 표현 | 학습할 때 정리 |
|---|---|
| define 함수 | 실제 Python 문법은 `def` |
| 난 / Nan처럼 들림 | 문맥상 대부분 `None`으로 보임. `NaN`과 구분 필요 |
| string | Python 실제 타입 이름은 `str` |

→ 왜 배우나·현업 활용: 음성 인식 오류를 그대로 기술 용어로 외우지 않게 하여, 실제 공식 문서 검색이나 오류 해결 시 잘못된 키워드 때문에 시간을 낭비하지 않기 위해 정리합니다.

> API와 MCP를 제대로 이해하려면 “함수를 만드는 문법”보다 **함수의 입력·출력·타입·설명·등록 정보를 명확한 계약으로 만드는 방법**을 이해해야 합니다.

### 복습 과제 B — `*args`, `**kwargs`

# 예상 면접 질문과 답변

## Q1. `print`와 `return`의 차이를 설명해 주세요.

`print`는 사람이 확인할 수 있도록 콘솔에 값을 출력하는 동작이고, `return`은 함수 호출자에게 결과값을 전달하는 동작입니다. API나 다른 모듈에서 결과를 다시 사용하려면 `print`만 해서는 부족하고 반환값을 설계해야 합니다. 디버깅 로그와 실제 비즈니스 결과를 구분하는 것이 중요합니다.

## Q2. Python의 Type Hint가 있으면 잘못된 타입 입력을 자동으로 막을 수 있나요?

기본 Type Hint 자체는 타입에 대한 설명이며 실행 시 강제 검증을 보장하지 않습니다. 실제 요청 데이터를 검사하려면 Pydantic 같은 validation 도구나 별도 검사 로직이 필요합니다. FastAPI가 type hint를 적극 활용하지만 검증은 추가 시스템이 수행한다고 이해하고 있습니다.

## Q3. API 응답에서 JSON을 많이 사용하는 이유는 무엇인가요?

JSON은 key-value와 배열 구조를 표현할 수 있고 여러 프로그래밍 언어에서 쉽게 직렬화·역직렬화할 수 있어 시스템 간 데이터 교환에 적합합니다. 다만 Python의 모든 객체를 그대로 보낼 수 있는 것은 아니기 때문에 `datetime` 같은 객체는 문자열 등 JSON이 처리할 수 있는 형식으로 변환해야 합니다.

## Q4. CSV 로딩과 매출 집계를 한 함수에 넣지 않고 분리하는 이유는 무엇인가요?

두 책임을 분리하면 데이터 소스가 CSV에서 DB나 API로 바뀌더라도 로딩 부분만 교체하고 집계 로직은 재사용할 수 있습니다. 이렇게 변경 영향 범위를 줄이면 테스트와 장애 원인 파악도 쉬워집니다. 실무에서는 이런 책임 분리가 유지보수성과 협업성을 높입니다.

## Q5. MCP나 Tool 시스템에서 decorator와 registry가 왜 필요한가요?

도구가 많아지면 어떤 함수가 사용 가능한지 중앙에서 조회하고 이름으로 실행할 구조가 필요합니다. Decorator를 사용하면 함수 정의 시점에 함수 객체, 이름, 설명, signature 등을 registry에 자동 등록할 수 있습니다. 이후 AI나 외부 프로그램은 도구 목록과 schema를 보고 적절한 함수를 선택해 argument와 함께 호출할 수 있습니다.
