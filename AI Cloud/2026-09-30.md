## 1. 왜 가상화에서 컨테이너, Docker로 이어지는가?

### 1-1. 출발점은 “남는 자원을 활용하면서 실행 환경을 나누자”이다

서버에 처리 능력이 남아 있는데 프로그램 하나만 실행하면 자원을 충분히 활용하지 못할 수 있다. 그렇다고 여러 프로그램을 같은 환경에 무작정 설치하면 서비스별 실행 환경을 나누어 관리하기 어렵다. 수업은 이 문제에서 가상화와 컨테이너의 필요성을 설명했다. **결국 이 개념을 배우는 이유는 프로그램의 기능뿐 아니라, 여러 프로그램을 어떤 환경에 나누어 실행할지도 설계하기 위해서다.**

```
물리 서버의 자원을 더 활용하고 싶다
    ↓
가상화: 한 대를 여러 서버처럼 사용한다
    ↓
VM마다 운영체제를 실행하는 부담을 생각한다
    ↓
컨테이너: 운영체제 전체 대신 프로세스 실행 환경을 격리한다
    ↓
Docker: 이러한 환경을 만들고 실행·전달하는 작업을 다루기 쉽게 한다
```

자료 후반의 구분에 따르면 **VM은 각각 운영체제를 실행하는 방식**, **컨테이너는 프로세스 실행 환경을 격리하는 방식**이다. 둘을 단순히 같은 것으로 외우지 않는 것이 중요하다. **실무 연결: 지금 관리하는 대상이 VM인지 컨테이너인지 알아야 실행 위치와 관리 범위를 혼동하지 않는다.**

### 1-2. Docker의 가치는 “실행 자체”보다 “환경을 반복해서 준비하는 방법”에 있다

Nginx는 Docker 없이 Linux에 직접 설치해 실행할 수도 있다. 수업에서 설명한 Docker의 의의는 Linux의 namespaces, cgroups 같은 기술을 개발자가 이용하기 쉬운 명령·이미지·생태계로 묶었다는 것이다. 질문을 “웹 서버가 켜졌는가?”에서 “이 실행 환경을 다른 곳에서도 어떻게 다시 준비할 것인가?”로 바꾸어 이해하면 된다. **실무 연결: 내 컴퓨터에서만 되는 상태를 넘어서, 다른 개발 환경이나 서버에서도 구성을 다시 사용할 방법을 마련한다.**[^background]

## 2. Dockerfile·이미지·컨테이너·Docker Hub는 무엇이 다른가?

|개념|내가 구분해야 할 역할|확인할 질문|
|---|---|---|
|**Dockerfile**|실행 환경을 만드는 절차를 적은 파일|무엇을 기반으로 무엇을 설치하고 복사할까?|
|**이미지**|필요한 환경과 파일을 묶어 놓은 컨테이너 생성용 결과물|어떤 환경을 전달하고 다시 사용할까?|
|**컨테이너**|이미지를 이용해 생성하고 실행하는 대상|지금 무엇을 실행·중지·삭제하고 있나?|
|**Docker Hub**|이미지를 찾아 내려받고 배포하는 레지스트리 서비스|필요한 이미지를 어디에서 가져올까?|

```
직접 만드는 흐름
Dockerfile 작성 → 이미지 빌드 → 컨테이너 생성·실행

기존 이미지를 쓰는 흐름
Docker Hub에서 선택 → pull로 내려받기 → 로컬 이미지 확인 → run
```

핵심은 **만드는 절차, 만들어진 결과물, 실제 실행 대상, 결과물을 유통하는 곳**을 나누는 것이다. Dockerfile을 고르는 일과 컨테이너를 중지하는 일은 서로 다른 단계의 작업이다. **실무 연결: 작업 대상을 정확히 구분해야 잘못된 대상을 지우거나, 필요한 환경 구성을 빠뜨리는 일을 줄일 수 있다.**

자료는 이미지가 여러 레이어로 구성된다고 설명하며 Ubuntu·Python·웹 프로그램을 차례로 쌓는 비유를 사용했다. 다만 모든 이미지가 반드시 그 조합으로 만들어진다는 뜻은 아니다. 기억할 것은 필요한 환경과 프로그램 구성이 이미지에 담기며, 그 구성 방법을 파일에 남기는 관점이 Infrastructure as Code와 연결된다는 점이다. **실무 연결: 완성된 실행 상태뿐 아니라 환경을 만드는 방법도 관리 대상으로 본다.**[^objects]

## 3. Docker Hub에서 찾았다고 바로 쓰면 되는 것은 아니다

기존 이미지는 환경을 처음부터 준비하는 수고를 줄여 준다. 수업에서는 Nginx, Python, 데이터베이스, MediaPipe, TensorFlow·PyTorch 관련 이미지를 찾아보았다. 하지만 MediaPipe 예시처럼 오래전에 갱신된 이미지는 필요한 환경과 맞는지 따져야 하며, 공식 Python 이미지를 기반으로 필요한 패키지를 직접 설치하는 선택도 제시됐다. **실무 연결: 이미지 선택은 검색 결과를 고르는 일이 아니라 프로젝트의 실행 환경을 결정하는 일이다.**

> **판단 기준:** “누군가 만들어 놓았는가?”와 “내 프로젝트에 적합한가?”는 별개의 질문이다.

복습할 때는 이미지의 업데이트 시점과 필요한 버전·환경의 적합성을 확인하는 이유를 설명해 보자. 이번 자료만으로 특정 이미지의 현재 상태나 최신 버전을 판단할 수는 없다. **실무 연결: 준비된 도구를 재사용하되, 내 작업에 맞는지 확인하는 책임까지 넘기지는 않는다.**[^hub]

## 4. Windows와 Multipass VM에서는 “어디에서 실행 중인가?”부터 확인한다

```
Windows PC
├─ Docker Desktop 환경
│  └─ 이미지 준비 / 컨테이너 실행 / 웹 화면 확인
│
└─ Multipass
   └─ Ubuntu VM
      └─ VM 안의 Docker로 이미지와 컨테이너 사용
```

두 환경에서 작업하는 목적은 Windows에서 성공한 것으로 끝내지 않고, Linux VM에서도 애플리케이션을 다루는 흐름을 경험하는 것이다. 이때 Windows 쪽 Docker를 조작하는지, VM 안의 Docker를 조작하는지 구분해야 한다. **실무 연결: 실행 위치를 알아야 상태를 확인할 대상과 브라우저의 접속 주소를 올바르게 선택할 수 있다.**

자료의 Windows 실습에서는 `[http://localhost:8080](http://localhost:8080/)`으로 웹 화면을 확인했고, VM에서 실행할 때는 VM의 실제 주소와 공개한 포트를 확인하도록 안내했다. 녹취에서 옮겨진 IP 숫자는 일관되지 않으므로 그대로 재사용하지 않는다. Docker Desktop을 사용하는 실습에서는 해당 프로그램이 실행되어 있어야 한다는 안내도 있었다. **실무 연결: 예제의 주소를 복사하기보다 실제 실행 환경을 확인하는 습관을 들인다.**[^environment]

## 5. Nginx 실습은 포트 연결과 실행 확인을 배우는 과정이다

### 5-1. 자료에 나온 기본 명령

```
docker pull nginx
docker images
docker run -d --name test -p 8080:80 nginx
docker ps
```

|명령·옵션|의미|
|---|---|
|`docker pull nginx`|Nginx 이미지를 내려받는다.|
|`docker images`|로컬 이미지를 확인한다.|
|`docker run ... nginx`|이미지로 새 컨테이너를 생성하고 실행한다.|
|`-d`|백그라운드로 실행한다.|
|`--name test`|컨테이너에 `test`라는 이름을 붙인다.|
|`-p 8080:80`|호스트 8080 포트와 컨테이너 80 포트를 연결한다.|
|`docker ps`|실행 중인 컨테이너의 상태를 확인한다.|

`test`는 자료의 예시 이름이다. 이후 중지·삭제 명령을 사용할 때는 실제 작업 대상의 이름을 확인해야 한다. **실무 연결: 예제 명령을 외우는 것보다, 명령이 어떤 대상에 어떤 변화를 만드는지 확인하는 것이 우선이다.**

### 5-2. `8080:80`은 요청이 들어오고 전달되는 두 위치다

```
브라우저 요청
    ↓
Docker 호스트의 8080 포트
    ↓
컨테이너의 80 포트
    ↓
Nginx 응답
```

앞의 `8080`은 호스트 쪽, 뒤의 `80`은 컨테이너 쪽이다. 단순히 “웹은 8080”이라고 외우지 말고, 바깥에서 들어온 요청을 안쪽 어느 포트로 전달하는 설정인지 이해해야 한다. **실무 연결: 접속이 안 될 때 주소·공개 포트·컨테이너 내부 포트를 구분해 살펴볼 수 있다.**

### 5-3. 실행 상태와 사용자 응답을 함께 확인한다

자료에서는 `docker ps`로 컨테이너 상태를 확인하고, 브라우저에서 Nginx 기본 페이지가 나타나는지도 확인했다. 두 확인은 질문이 다르다. 하나는 “대상이 실행 중인가?”, 다른 하나는 “사용자가 실제 응답을 받는가?”이다. **실무 연결: 실행 명령을 입력한 사실을 성공으로 기록하지 않고, 상태와 서비스 결과를 근거로 확인한다.**[^nginx]

## 6. 중지·재실행·삭제·새로 생성은 서로 다른 작업이다

|목적|자료의 명령|핵심 구분|
|---|---|---|
|잠시 중지|`docker stop test`|컨테이너 삭제가 아니다.|
|중지한 대상 다시 실행|`docker start test`|기존 컨테이너를 다시 실행한다.|
|중지한 대상 삭제|`docker rm test`|컨테이너를 제거한다.|
|실행 중인 대상 강제 삭제|`docker rm -f test`|실행 중이어도 강제로 제거한다.|
|이미지로 새 대상 생성|`docker run ... nginx`|기존 대상을 되살리는 것이 아니라 새로 만든다.|

```
잠시 멈춘 뒤 다시 사용: stop → start

지운 뒤 새로 생성: stop → rm → 남아 있는 이미지로 run
```

컨테이너를 삭제해도 이미지가 남을 수 있으며, 남은 이미지로 새 컨테이너를 만들 수 있다. 따라서 이미지가 있다는 사실과 이전 컨테이너가 남아 있다는 사실을 혼동하면 안 된다. **실무 연결: 잠깐 서비스를 멈추려는 상황에서 삭제 명령을 사용하는 실수를 피한다.**

`docker rm -f`는 단순 조회나 재시작 명령이 아니다. 자료에서도 강제로 대상을 제거하는 명령이므로 이름부터 확인하도록 주의를 줬다. 이미지 삭제와 컨테이너 삭제가 자동으로 함께 이루어진다는 식의 설명은 자료에 혼용되어 있어, 이번 정리에서는 그런 규칙으로 외우지 않는다. **실무 연결: 삭제처럼 되돌리기 어려울 수 있는 작업은 대상과 영향을 확인한 뒤 수행한다.**[^lifecycle]

## 7. Nginx 화면을 바꾸는 실습에서 알아야 할 연결

```
컨테이너 내부 파일 확인
    → index.html 내용 확인
    → HTML 수정
    → cat으로 저장 내용 확인
    → 브라우저 새로고침으로 결과 확인
```

자료에서는 `echo`와 리다이렉션으로 내용을 쓰고, `cat`으로 확인했다. `>`는 덮어쓰기, `>>`는 추가하기로 설명했다. 이 실습의 의미는 화면에 문구 하나를 띄우는 데 있지 않고, **컨테이너 내부의 파일이 웹 서버의 응답 결과와 연결되어 있다는 것**을 확인하는 데 있다. **실무 연결: 수정한 파일과 사용자가 보는 결과 사이의 연결을 따라가며 변경을 검증한다.**

그다음 학습 방향은 준비한 애플리케이션과 환경을 이미지로 만들어 다른 곳에서도 사용하는 것이다. 다만 컨테이너 안에서 직접 바꾼 내용을 최종 이미지에 반영하는 전체 명령은 자료에 없다. 화면을 바꾼 실습과 재사용 가능한 이미지를 완성한 작업을 같은 성과로 기록하면 안 된다. **실무 연결: 현재 화면이 바뀌었다는 확인과 배포 가능한 결과물을 만들었다는 확인을 구분한다.**[^html]

## 8. AI에게 명령 실행을 맡겨도 작업 대상을 이해해야 한다

수업에서는 Codex에 이미지 목록 확인, Nginx 실행, 컨테이너 삭제, 프로젝트에 필요한 이미지 추천 등을 요청하는 시연을 다뤘다. 웹·Python·DB를 구성하는 예에서는 필요한 이미지를 먼저 추천받고, 허가한 뒤 내려받아 실행하는 흐름을 제시했다. **실무 연결: AI를 사용할 때도 추천·검토·실행을 구분하면 무엇이 바뀌는지 확인하기 쉽다.**

정리자의 복습 기준으로는 다음 세 가지를 설명할 수 있으면 좋다. **어느 환경에서 실행하는지, 대상이 이미지인지 컨테이너인지, 작업이 조회인지 생성·삭제인지**이다. 자료 속 Codex 시연을 모든 대화형 AI가 동일한 실행 권한을 가진다는 뜻으로 해석하지 않는다. **실무 연결: 자연어 요청을 실제 작업 대상과 명령의 영향으로 연결해 검토하는 능력을 기른다.**[^ai]

## 9. Part 2: CSV 분석보다 중요한 것은 웹과 API의 연결이다

### 9-1. 데이터는 어디에서 처리되고 어디에서 보이는가?

```
sales.csv
    ↓
Python API가 파일을 읽는다
    ↓
각 행의 판매 금액을 계산하고 합계를 구성한다
    ↓
요약 데이터를 응답한다
    ↓
웹이 응답을 받아 HTML에 표시한다
```

자료에 나온 CSV 항목은 날짜·지역·상품명·판매 개수·단가다. 행별 판매 금액은 `수량 × 단가`로 계산한다. Python이 계산하고 웹은 응답받은 값을 화면에 넣는 역할 분담이다. API는 5000번 포트를 사용하는 예로 설명됐으며, HTTP 상태 코드 200은 정상 응답을 확인하는 맥락에서 언급됐다. **실무 연결: 데이터 처리와 화면 표시를 나누고, 두 프로그램 사이에서 어떤 정보가 오가는지 설명할 수 있다.**

### 9-2. 왜 pandas를 사용하지 않았는가?

자료는 pandas를 쓰면 편리하지만 설치할 패키지가 하나 더 생긴다는 점을 언급했다. 이 예제는 별도 패키지를 줄이고 파일 읽기·계산 과정을 직접 보는 방향으로 구성됐다. 성능 측정 결과는 없으므로 “pandas를 쓰지 않으면 항상 더 빠르다”는 결론은 낼 수 없다. **실무 연결: 도구 선택 이유를 편의성·환경 구성·학습 목적과 연결하고, 측정하지 않은 성능을 성과로 주장하지 않는다.**

### 9-3. 이번 실습의 중심 목표

```
내 프로그램
    → 실행 환경을 담은 이미지
    → 컨테이너로 실행
    → 다른 서비스와 통신
```

판매 분석 기능을 크게 만드는 것이 우선은 아니다. 자료에서도 HTML이나 분석 코드가 어렵다면 더 단순한 예제로 진행해도 된다고 안내했다. 정확한 API 경로와 전체 응답 구조는 제공되지 않았으므로 여기서 새로 만들어 넣지 않는다. **실무 연결: 현재 배우려는 문제가 서비스 실행·연결이라면 기능 범위를 줄여서라도 그 흐름을 직접 확인한다.**[^api]

## 10. Docker Compose는 왜 필요한가?

### 10-1. 서비스가 늘어나면 명령뿐 아니라 관계를 관리해야 한다

컨테이너 하나는 명령으로 실행할 수 있다. 하지만 웹·API·DB로 나뉘면 빌드할 폴더, 공개 포트, 연결 대상, 환경 변수, 데이터 저장 방식을 함께 관리해야 한다. Compose는 이런 구성을 하나의 YAML 파일에 구조화해 사용하는 방법으로 소개됐다. **실무 연결: 실행할 때마다 기억에 의존하지 않고, 파일을 기준으로 구성을 확인하고 수정한다.**

|구분|중심 질문|
|---|---|
|**Dockerfile**|이 서비스의 이미지를 어떻게 만들 것인가?|
|**Compose 파일**|여러 서비스를 어떤 설정과 관계로 실행할 것인가?|

자료에서 Compose를 “서비스 구조를 설계하는 파일”이라는 관점으로 설명한 이유가 여기에 있다. 서비스별 설정이 모이면 무엇을 외부에 공개하고, 무엇을 내부에서 연결하며, 어디에 데이터를 남길지가 드러난다. **실무 연결: Compose를 단순한 실행 명령 묶음이 아니라 서비스 구성의 설명서로 읽는다.**[^compose]

## 11. 이커머스 예시에서는 네 가지 설계 질문을 확인한다

```
사용자
    ↓
프론트엔드 / 웹
    ↓
백엔드 / Python
    ↓
데이터베이스
```

자료의 프로젝트 범위는 Windows·Docker·Multipass VM이며, Kubernetes는 구현 대상에서 제외했다. 위 역할을 서비스별 컨테이너로 나누고 Compose로 연결하는 방향이다. 컨테이너의 개수를 늘리는 것이 아니라 연결·공개·저장·확인을 설명하는 것이 핵심이다. **실무 연결: 사용한 기술 이름보다 그 기술로 구성한 서비스의 동작 관계를 보여 준다.**

|설계 질문|자료에서 제시한 방향|배우는 이유·실무 연결|
|---|---|---|
|**어떻게 연결할까?**|서비스 이름을 연결에 활용하고, DB 주소를 무조건 `localhost`로 적지 않는다.|연결 주소가 실제 대상 서비스를 가리키도록 설정한다.|
|**무엇을 외부에 공개할까?**|프론트엔드는 외부 접속을 제공하고, 이 예제의 DB는 백엔드가 내부에서 연결한다.|외부에서 접근할 서비스와 내부에서 사용할 서비스를 구분한다.|
|**데이터는 어디에 남길까?**|DB 데이터를 보존하기 위해 볼륨과 저장 연결을 고려한다.|컨테이너 관리와 데이터 보존을 함께 설계한다.|
|**문제는 어떻게 찾을까?**|상태 확인과 문제 발생 위치·원인 추적을 별도 실습으로 다룬다.|실행 이후에도 문제를 설명하고 대응할 근거를 남긴다.|

DB를 외부에 직접 공개하지 않는다는 설명은 **이 예제의 설계 방향**이다. 모든 환경에 동일하게 적용되는 절대 규칙이라고 확장하지 않는다. 실제 볼륨 방식과 경로 역시 전체 설정이 없어 확정할 수 없다. **실무 연결: 예제의 선택을 외우는 데서 멈추지 않고, 그 선택의 목적과 적용 범위를 함께 기록한다.**

### 자료에서 다룬 Compose 설정

|설정|이번 수업에서 이해할 범위|
|---|---|
|`build`|해당 서비스 이미지를 만들 폴더를 지정한다.|
|`ports`|호스트에서 컨테이너로 연결할 포트를 설정한다.|
|`environment`|DB 연결 정보 등 환경 설정을 전달한다.|
|`depends_on`|서비스 사이의 의존 관계를 표현한다.|
|`volumes`|데이터 보존을 위한 저장 연결을 구성한다.|
|서비스 이름|서비스를 구분하고 서비스 간 연결에 사용한다.|

특히 `depends_on`은 자료에서 의존 관계로 설명됐을 뿐, 대상 서비스가 실제 요청을 처리할 준비까지 보장하는지에 대한 세부 설명은 없었다. 이를 준비 완료나 자동 복구의 보장으로 확대하지 않는다. **실무 연결: 설정 이름만 보고 효과를 추측하지 말고, 필요한 동작을 확인 대상으로 남긴다.**[^design]

## 12. YAML과 도움말: 구조를 이해하고 확인할 수 있어야 한다

YAML의 기본은 `키: 값`, 스페이스 들여쓰기, 목록의 `-`, 주석의 `#`이다. 들여쓰기는 꾸미기가 아니라 설정의 소속과 구조를 나타낸다. **실무 연결: 키를 알고 있어도 잘못된 위치에 적으면 의도한 구성이 되지 않을 수 있으므로 구조를 함께 읽는다.**

```
# Compose 설정의 작성 오류를 확인하는 출발점
docker compose config

# 사용 가능한 명령과 도움말을 확인하는 출발점
docker compose --help
```

자료의 과제는 도움말에 나오는 명령과 각 명령의 옵션을 찾아 자신이 다시 볼 수 있는 자료로 정리하는 것이었다. 여기서 CLI 명령·옵션과 YAML의 서비스 설정 키는 구분해야 한다. **실무 연결: 모든 옵션을 외우기보다 필요한 기능을 찾아보고, 실행 명령과 설정 파일을 각각 올바르게 다룬다.**[^yaml]

## 13. 상태 확인과 장애 대응은 작은 예제로 검증한다

### 13-1. “켜졌다” 이후에 알아야 할 것

```
서비스 상태 확인
    ↓
문제가 발생한 위치와 원인 추적
    ↓
대응
    ↓
그 대응이 실제로 작동했는지 확인
```

자료는 처음부터 큰 운영 체계를 만들기보다 Nginx와 Python 두 컨테이너 정도로 범위를 줄여도 좋다고 설명했다. 핵심은 Python이나 Compose를 사용했다는 사실이 아니라, 어떤 설정으로 어떤 문제를 다뤘는지 설명할 수 있는가이다. **실무 연결: 작은 구성에서라도 증상·원인·조치·확인 결과를 연결해 기록한다.**

### 13-2. 정리자의 복습 실습 제안 — 아직 수행한 결과가 아니다

|순서|앞으로 해 볼 일|남길 근거|
|---|---|---|
|정상 상태 확인|서비스 구성과 접속 흐름을 설명하고 실제 응답을 확인한다.|실행 위치, 서비스 상태, 화면 또는 응답|
|상태 변화 관찰|실습용 대상을 중지했을 때 달라지는 점을 관찰한다.|어떤 서비스가 멈췄는지, 사용자에게 어떤 증상이 나타났는지|
|조치 후 재확인|사용한 실행 방식에 맞게 되돌린 뒤 상태와 응답을 다시 확인한다.|수행한 조치와 전후 비교|
|설명 정리|관찰된 사실과 원인에 대한 추측을 구분한다.|“확인한 것”과 “추가 확인할 것”|

위 표는 수업의 상태 확인·원인 추적 방향을 복습 과제로 옮긴 것이다. 자료에는 구체적인 장애 주입 절차, 복구 시간, 자동 복구 성공 결과가 없다. **실무 연결: 계획한 실험을 이미 성공한 성과처럼 쓰지 않고, 직접 확인한 결과만 증거로 남긴다.**

Kubernetes는 여러 컨테이너를 운영하는 오케스트레이션 기술이라는 수준에서 소개됐으며 이번 구현 대상은 아니다. 자료는 Compose로 가능한 일과 그 한계를 먼저 이해하라고 강조했다. **실무 연결: 도구의 개수를 늘리기보다 현재 도구로 해결할 수 있는 문제와 남는 문제를 설명한다.**[^operations]

## 14. 포트폴리오는 “사용 기술”보다 “문제·선택·검증”으로 쓴다

“Docker와 Compose로 프론트엔드·백엔드·DB를 실행했다”만으로는 선택 이유가 드러나지 않는다. 자료는 직접 설치하거나 개별 명령으로 실행할 때의 어려움, 이미지·Compose를 선택한 이유, 연결·공개·보존의 구성, 실행과 상태를 확인한 근거를 기록하도록 강조했다. **실무 연결: 결과물을 보는 사람이 무엇을 만들었는지뿐 아니라 왜 그렇게 만들었는지 이해할 수 있게 한다.**

### STAR 작성 틀 — 실제 경험으로 채울 것

|구분|작성할 내용|
|---|---|
|**S · 상황**|환경 준비나 서비스별 실행 설정에서 실제로 어떤 어려움을 겪었는가?|
|**T · 과제**|어떤 구성을 반복해서 사용하고, 어떤 문제를 확인할 수 있게 만들려 했는가?|
|**A · 행동**|Dockerfile·Compose로 무엇을 정리했고 연결·공개 포트·저장을 어떻게 구성했는가?|
|**R · 결과**|다른 환경에서의 실행, 응답, 상태 변화 등을 무엇으로 확인했는가? 미검증 사항은 무엇인가?|

작성 예시는 다음처럼 **빈칸을 실제 결과로 채우는 방식**으로 사용한다.

> `[실제로 겪은 환경·설정 문제]`를 해결하기 위해 Dockerfile과 Compose로 실행 환경과 서비스 구성을 정리했다.  
> `[서비스 연결·외부 공개·데이터 저장에 대한 선택]`을 했고, `[직접 확인한 환경과 테스트]`로 동작을 확인했다.  
> 확인 결과는 `[실제 관찰 결과]`이며, 아직 검증하지 못한 범위는 `[남은 한계]`이다.

성과를 크게 보이게 만드는 것보다 확인 범위를 정확히 쓰는 것이 중요하다. 측정하지 않은 배포 시간 단축이나 자동 복구 성공을 덧붙이지 않는다. **실무 연결: 면접에서 후속 질문을 받아도 근거를 들어 설명할 수 있는 경험을 남긴다.**[^portfolio]

## 15. 이번 자료만으로 확정하지 않을 내용

|항목|이번 정리의 판단|
|---|---|
|컨테이너와 VM의 혼용|자료 후반의 구분으로 이해하되, 앞부분에 혼용된 표현이 있음을 남긴다.|
|포트·IP 분리와 보안|구체적인 접근 통제 설정이 없으므로 분리만으로 안전이 보장된다고 결론 내리지 않는다.|
|이미지 삭제와 컨테이너 삭제|표현이 서로 달라 자동으로 함께 삭제된다는 규칙으로 정리하지 않는다.|
|VM IP·전체 API 경로·응답 구조|불일치하거나 전체 정보가 없으므로 임의로 완성하지 않는다.|
|`depends_on`과 준비 완료|의존 관계 설명을 준비 완료나 복구의 보장으로 확대하지 않는다.|
|볼륨 방식·저장 경로|데이터 보존의 필요성은 배우되 실제 설정은 별도로 확인한다.|
|이미지의 최신 상태·성능·복구 결과|현재 조회나 측정 결과가 없으므로 검증된 사실로 적지 않는다.|

이 구분은 외부 자료를 조사해 정정한 목록이 아니다. **자료가 설명한 것과 설명하지 않은 것을 나누어 둔 확인 목록**이다. **실무 연결: 불확실한 설정과 미검증 결과를 명시하면 다음 조사·실습에서 무엇을 확인해야 할지 분명해진다.**[^limits]

## 16. 오늘 정리한 내용 요약

|오늘 남길 핵심|한 문장 결론|
|---|---|
|Docker의 목적|프로그램 실행뿐 아니라 실행 환경의 준비·재사용을 다룬다.|
|네 가지 개념|Dockerfile은 절차, 이미지는 결과물, 컨테이너는 실행 대상, Docker Hub는 레지스트리다.|
|포트와 실행 위치|어느 환경에서 실행하고 요청을 어느 포트로 전달하는지 구분한다.|
|웹·API 분리|Python이 데이터를 처리하고 웹이 응답을 받아 표시한다.|
|Compose의 목적|여러 서비스의 설정과 연결 관계를 파일로 관리한다.|
|운영과 검증|실행 상태, 실제 응답, 문제 원인, 조치 결과를 구분해 확인한다.|

**최종 결론:** 오늘 배운 것은 “컨테이너를 몇 개 켜는 법”이 아니라, **왜 서비스를 나누고, 어떻게 연결하며, 어디에 데이터를 남기고, 무엇으로 동작을 확인할지 설명하는 방법**이다. 이는 서비스 구성을 다시 만들고 문제를 추적하기 위한 기초가 된다.[^conclusion]

## 19. 자료 기반 면접 예상 질문과 답변

> 실제 기출이 아니라, 이번 자료의 개념을 말로 설명하는 연습용 문답이다. 프로젝트 경험 질문에는 실제 수행한 내용만 답한다.

### Q1. Nginx를 직접 설치할 수도 있는데 Docker를 사용하는 이유는 무엇인가요?

**답변:** Nginx를 실행하는 것 자체에는 Docker가 필수는 아닙니다. Docker를 사용하는 목적은 필요한 실행 환경을 이미지로 준비하고, 그 환경으로 컨테이너를 생성해 다른 환경에서도 구성을 다시 사용하기 쉽게 만드는 데 있습니다. 단순 실행 여부보다 실행 환경의 준비와 재사용에 초점을 맞췄습니다.

### Q2. Dockerfile·이미지·컨테이너의 차이를 설명해 주세요.

**답변:** Dockerfile은 실행 환경을 만드는 절차를 적은 파일이고, 이미지는 필요한 환경과 파일을 담아 컨테이너 생성에 사용하는 결과물입니다. 컨테이너는 그 이미지로 생성하고 실행하는 대상입니다. 따라서 만드는 절차와 결과물, 실행 대상을 구분해서 이해하고 있습니다.

### Q3. `docker run -p 8080:80 nginx`에서 두 포트는 각각 무엇인가요?

**답변:** 앞의 8080은 Docker 호스트 쪽 포트이고 뒤의 80은 컨테이너 쪽 포트입니다. 호스트 8080 포트로 들어온 요청을 컨테이너 80 포트에 전달하는 설정입니다. 접속을 확인할 때도 호스트가 Windows 쪽인지 VM인지와 실제 접속 주소를 함께 살펴봐야 합니다.

### Q4. `docker start`와 `docker run`은 어떻게 다른가요?

**답변:** `start`는 이미 존재하며 중지된 컨테이너를 다시 실행하는 명령이고, `run`은 이미지로 새 컨테이너를 생성하고 실행하는 명령입니다. 삭제한 컨테이너를 `run`으로 되살리는 것이 아니라 새 대상을 만드는 것이므로 구분해서 사용합니다.

### Q5. Docker Compose를 도입하려는 이유는 무엇인가요?

**답변:** 웹·API·DB처럼 서비스가 늘어나면 실행할 이미지뿐 아니라 포트, 연결 대상, 환경 변수, 데이터 저장 설정도 함께 관리해야 합니다. Compose 파일에 이 구성을 정리하면 파일을 기준으로 서비스를 어떻게 실행하고 연결하는지 확인하고 수정할 수 있습니다.

### Q6. DB 연결과 데이터 저장에서는 무엇을 확인해야 하나요?

**답변:** 먼저 연결 주소가 실제 대상 DB 서비스를 가리키는지 확인해야 합니다. 수업에서는 서비스 이름을 연결에 활용하고 DB 주소를 무조건 `localhost`로 적지 않도록 설명했습니다. 또 데이터 보존을 위해 볼륨과 저장 연결을 검토해야 합니다. 다만 해당 예제의 정확한 저장 방식과 경로는 전체 설정을 확인해야 합니다.

### Q7. 서비스가 정상 동작한다고 어떻게 확인하겠습니까?

**답변:** 실행 명령을 입력한 사실만으로 판단하지 않고 컨테이너 상태와 실제 서비스 응답을 함께 확인하겠습니다. 수업의 Nginx 예제에서는 `docker ps`와 브라우저 기본 페이지를 함께 확인했습니다. 웹과 API가 연결된 경우에는 응답과 화면 반영 흐름도 확인 대상으로 삼겠습니다.

### Q8. `depends_on`을 썼다는 이유만으로 서비스가 준비됐다고 설명할 수 있나요?

**답변:** 이번 자료는 `depends_on`을 서비스 사이의 의존 관계로 설명했습니다. 실제 요청을 처리할 준비까지 어떤 조건에서 보장되는지는 다루지 않았으므로, 준비 완료를 확인했다고 단정하지 않겠습니다. 해당 동작은 추가 문서 확인과 실습으로 검증할 항목입니다.

### Q9. AI가 명령을 만들어 주면 개발자는 무엇을 검토해야 하나요?

**답변:** 작업 환경이 어디인지, 대상이 이미지인지 컨테이너인지, 조회·생성·삭제 중 어떤 작업인지 확인해야 합니다. 특히 삭제처럼 상태를 바꾸는 작업은 대상과 영향을 먼저 검토하겠습니다. AI에게 요청했다는 사실과 실제 작업 결과를 확인했다는 사실을 구분하겠습니다.

### Q10. 이 프로젝트의 성과를 어떻게 설명하겠습니까?

**답변 틀:** `[실제로 겪은 문제]` 때문에 실행 환경과 서비스 구성을 정리했습니다. `[실제로 적용한 설정과 선택 이유]`를 바탕으로 구성했고, `[직접 수행한 확인 절차]`에서 `[관찰한 결과]`를 확인했습니다. 아직 검증하지 못한 범위는 `[남은 항목]`입니다.
