# 2026-09-30 Docker · 컨테이너 · Docker Compose 수업 정리

> **오늘의 핵심:** 애플리케이션을 단순히 실행하는 데서 끝내지 않고, 실행 환경을 이미지로 만들고 서비스의 연결 관계를 Compose로 정리하여 다른 환경에서도 구성하고 운영할 수 있게 한다.

이 문서는 첨부된 수업 녹취를 바탕으로 정리했습니다. 수업에서 언급한 교안 Part 1~3의 원문과 전체 실습 코드는 첨부되어 있지 않으므로, 정확한 버전·전체 설정·실행 결과가 확인되지 않는 부분은 확정하지 않았습니다. 구두로 설명한 기본 명령은 읽기 쉬운 터미널 표기로 옮겼으며, 녹취에서 표현이 혼용된 대목은 마지막에 따로 모았습니다.

## 1. 왜 가상화와 컨테이너를 배우는가?

### 출발점: 컴퓨터의 자원을 충분히 활용하지 못한다

수업은 컴퓨터가 많은 일을 처리할 능력이 있어도, 입출력 등을 기다리는 동안 일부 자원이 사용되지 않는다는 설명에서 시작했습니다. 여기서 등장한 말이 **아이들 타임(idle time)**과 **유휴 자원**입니다.

서버 한 대에 애플리케이션 하나만 실행하면 남는 자원이 생길 수 있습니다. 그렇다고 여러 프로그램을 한 환경에 무작정 넣으면 실행 환경과 서비스 구성을 나누어 관리하기가 어려워집니다.

이 문제를 해결하는 흐름으로 다음 세 가지를 연결했습니다.

```text
물리 서버의 자원을 더 활용하고 싶다
    ↓
한 대의 서버를 여러 서버처럼 사용하는 가상화
    ↓
VM마다 운영체제를 실행하는 데 따른 부담
    ↓
운영체제 전체를 복제하지 않고
프로세스 실행 환경을 격리하는 컨테이너
    ↓
컨테이너를 쉽게 만들고 실행·배포하게 해 주는 Docker
```

수업 후반의 정리에서는 **VM은 각각 운영체제를 실행하는 방식**, **컨테이너는 프로세스 실행 환경을 격리하는 방식**으로 구분했습니다. 다만 앞부분에는 컨테이너를 VM처럼 표현한 대목도 있으므로, 두 용어의 혼용은 주의해야 합니다.

### Docker의 의의: 기존 기술을 사용하기 쉽게 만든다

수업에서는 Linux에 이미 namespaces, cgroups 같은 기술이 있었으며, Docker가 이를 개발자가 쉽게 사용할 수 있는 제품과 생태계로 묶었다고 설명했습니다.

핵심은 “Docker가 있어야만 웹 서버를 실행할 수 있다”가 아닙니다. Linux에 직접 Nginx를 설치하고 실행할 수도 있지만, 실행 환경을 준비하고 분리하는 여러 작업을 Docker의 명령과 이미지로 다루기 쉽게 만든다는 것입니다.

따라서 오늘의 질문은 다음과 같습니다.

> **“Nginx를 실행했는가?”보다 “어떤 환경을 준비했고, 그 환경을 다른 곳에서도 어떻게 다시 사용할 것인가?”가 중요하다.**[^concept]

## 2. Dockerfile · 이미지 · 컨테이너 · Docker Hub의 관계

이 네 가지를 섞지 않고 이해하는 것이 기본입니다.

| 구분 | 수업에서 설명한 역할 | 이해할 때의 질문 |
|---|---|---|
| Dockerfile | 실행 환경을 만들기 위한 절차를 적은 파일 | 어떤 기반 환경에 무엇을 설치하고 복사할 것인가? |
| 이미지(Image) | 필요한 환경과 파일을 묶어 컨테이너 생성에 사용하는 결과물 | 무엇을 전달하고 다시 사용할 것인가? |
| 컨테이너(Container) | 이미지를 이용해 생성하고 실행하는 대상 | 지금 실제로 실행하거나 중지하는 대상은 무엇인가? |
| Docker Hub | 이미지를 찾아 내려받고 배포하는 레지스트리 서비스 | 필요한 이미지를 어디서 가져올 것인가? |

### 직접 만드는 흐름과 이미 만들어진 것을 쓰는 흐름

```text
[직접 구성하는 경우]

Dockerfile 작성
    → 이미지 빌드
    → 이미지로 컨테이너 생성·실행


[기존 이미지를 사용하는 경우]

Docker Hub에서 이미지 선택
    → pull로 내려받기
    → 로컬 이미지 확인
    → run으로 컨테이너 생성·실행
```

Dockerfile에는 기반 이미지, 필요한 파일 복사, 라이브러리 설치, 프로그램 실행과 관련된 구성을 적습니다. 수업에서 “내 컴퓨터에서는 되는데 다른 컴퓨터에서는 안 된다”는 문제와 연결한 이유도 여기에 있습니다. 실행 환경을 만드는 방법을 파일에 남겨야 다른 사람이나 다른 환경에서도 같은 구성을 만들기 쉬워집니다.

수업은 이 관점을 **환경 구성을 코드로 관리하는 흐름, 즉 Infrastructure as Code와의 연결**로 설명했습니다.

### 이미지의 레이어

이미지는 여러 겹의 레이어로 구성된다고 설명했습니다. 강의에서는 Ubuntu, Python, 웹 프로그램 등을 차례로 쌓는 모습에 비유했습니다.

여기서 기억할 핵심은 **필요한 실행 환경과 프로그램 구성이 이미지에 담긴다**는 점입니다. 강의의 비유를 모든 이미지의 실제 구성으로 단정할 필요는 없습니다.[^concept]

## 3. Docker Hub를 활용하는 이유와 이미지 선택 시 확인할 점

Nginx, Python, 데이터베이스, AI 관련 패키지처럼 이미 준비된 이미지가 있다면 매번 직접 처음부터 만들 필요는 없습니다.

수업에서는 Python 이미지, MediaPipe 관련 이미지, TensorFlow·PyTorch 관련 이미지를 찾아보는 예를 들었습니다. 이는 특정 이미지 목록을 외우려는 활동이 아니라 **필요한 실행 환경을 기존 이미지에서 출발해 준비하는 방법**을 익히는 활동이었습니다.

### MediaPipe 예시에서 배운 점

수업 중 검색한 MediaPipe 이미지에는 오래전에 업데이트된 사례가 있었습니다. 강의에서는 그 이미지가 현재 작업 환경과 맞지 않을 수 있다는 이유로, 공식 Python 이미지를 기반으로 필요한 패키지를 직접 설치하는 방안도 함께 소개했습니다.

따라서 이미지를 찾았다고 바로 선택하기보다, **업데이트 시점과 필요한 버전·환경이 맞는지 확인한다**는 판단 과정을 기억해야 합니다.

> “이미 누군가 만들어 놓았다”와 “내 프로젝트에 적합하다”는 같은 판단이 아니다.

이 문서에는 당시 언급한 이미지의 현재 상태나 최신 버전을 추가하지 않았습니다. 실제 선택할 이미지와 버전은 별도로 확인해야 합니다.[^concept]

## 4. 실습 환경: Windows와 Multipass Ubuntu VM

이번 수업에서는 먼저 Windows의 Docker Desktop에서 Docker 사용에 익숙해진 뒤, Multipass의 Ubuntu VM에서도 작업하는 흐름을 다뤘습니다.

```text
Windows PC
│
├─ Docker Desktop 환경
│   └─ 이미지 준비 / 컨테이너 실행 / 웹 화면 확인
│
└─ Multipass
    └─ Ubuntu VM
        └─ Docker로 이미지와 컨테이너 사용
```

### 왜 두 환경에서 작업하는가?

Windows에서 실행하는 데서 끝내지 않고, Linux VM에서도 같은 애플리케이션을 다루는 경험을 하기 위해서입니다. 수업은 Windows에서 이미지를 만들고 VM으로 전달하여 사용하는 흐름을 설명했습니다.

여기서 중요한 것은 **지금 어느 환경의 Docker를 조작하고 있는지**입니다. Windows 쪽 컨테이너와 VM 안의 컨테이너를 구분하고, 브라우저에서 접속할 주소도 실행 위치에 맞추어 확인해야 합니다.

수업에서는 Docker Desktop을 사용하는 동안 해당 프로그램이 백그라운드에서 실행되어 있어야 한다고 안내했습니다.

녹취의 VM IP는 숫자가 일관되게 기록되어 있지 않습니다. 따라서 녹취에 나온 숫자를 그대로 복사하기보다 실제 실습 중인 VM 주소를 확인해야 합니다.[^concept][^custom]

## 5. 첫 실습: Nginx를 컨테이너로 실행하기

### 기본 명령의 의미

수업에서 설명한 실행 예시는 다음과 같이 정리할 수 있습니다.

```bash
docker pull nginx
docker images
docker run -d --name test -p 8080:80 nginx
docker ps
```

`test`는 수업 중 사용한 예시 이름입니다. 이미 만든 컨테이너를 조작할 때는 실제 이름으로 바꾸어 사용해야 합니다.

| 명령 또는 옵션 | 의미 |
|---|---|
| `docker pull nginx` | Nginx 이미지를 내려받는다. |
| `docker images` | 로컬에 있는 이미지를 확인한다. |
| `docker run ... nginx` | Nginx 이미지로 새 컨테이너를 생성하고 실행한다. |
| `-d` | 터미널에 붙여 두지 않고 백그라운드로 실행한다. |
| `--name test` | 컨테이너 이름을 `test`로 지정한다. |
| `-p 8080:80` | 호스트의 8080 포트를 컨테이너의 80 포트에 연결한다. |
| `docker ps` | 실행 중인 컨테이너의 상태를 확인한다. |

### 포트 연결은 “어디로 들어와서 어디로 전달되는가”로 이해한다

```text
브라우저의 요청
    ↓
Docker 호스트의 8080 포트
    ↓
컨테이너의 80 포트
    ↓
Nginx가 응답
```

`8080:80`에서 앞의 숫자는 호스트 쪽, 뒤의 숫자는 컨테이너 쪽입니다. 포트 번호만 외우지 말고 두 위치를 구분해야 합니다.

Windows 쪽 실습에서 사용하는 브라우저 주소 예시는 다음과 같습니다.

```text
http://localhost:8080
```

VM 안에서 실행한 서비스는 VM의 실제 주소와 공개한 포트에 맞추어 접속 대상을 확인해야 합니다.

### 무엇으로 실행을 확인했는가?

수업에서는 `docker ps`의 상태와 브라우저에 나타나는 Nginx 기본 페이지를 확인했습니다. 즉, **컨테이너가 실행 중인지 확인하는 것**과 **사용자가 실제 웹 응답을 받는지 확인하는 것**을 함께 진행한 것입니다.[^run]

## 6. 컨테이너의 생성 · 중지 · 재시작 · 삭제를 구분하기

가장 중요한 구분은 **중지와 삭제는 다르다**는 점입니다.

| 하고 싶은 작업 | 수업에서 다룬 명령 | 구분할 점 |
|---|---|---|
| 기존 컨테이너 중지 | `docker stop test` | 컨테이너를 지우는 작업이 아니다. |
| 중지한 컨테이너 다시 실행 | `docker start test` | 기존 컨테이너를 다시 실행한다. |
| 중지한 컨테이너 삭제 | `docker rm test` | 해당 컨테이너를 제거한다. |
| 실행 중인 컨테이너 강제 삭제 | `docker rm -f test` | 실행 중이어도 강제로 제거한다. |
| 이미지로 새 컨테이너 생성 | `docker run ... nginx` | 삭제한 컨테이너를 되살리는 것이 아니라 새로 만든다. |

수업에서 확인한 내용은 **컨테이너를 삭제해도 이미지가 남을 수 있고, 남아 있는 이미지로 새 컨테이너를 만들 수 있다**는 점입니다.

따라서 다음 흐름을 구분해야 합니다.

```text
[잠시 멈췄다가 다시 쓰기]

stop → start


[컨테이너를 지운 뒤 새로 만들기]

stop → rm → 남아 있는 이미지로 run
```

강제 삭제 명령은 일반 삭제와 같은 뜻으로 사용하면 안 됩니다. 실습 중인 대상을 실제로 제거하는 명령이므로 컨테이너 이름을 먼저 확인해야 합니다.

수업에서는 이미지까지 정리할 때 **사용 중인 컨테이너를 중지하고 삭제한 뒤 이미지를 삭제하는 순서**를 안내했습니다. 다만 이미지 삭제와 컨테이너 삭제의 관계에 관해서는 녹취에 서로 다른 표현이 있어, 마지막의 확인 필요 항목에 따로 남겼습니다.[^run]

## 7. Nginx 기본 화면을 내 HTML로 바꾸기

기본 페이지가 뜨는 것을 확인한 다음에는 Nginx가 제공하는 `index.html`을 확인하고 수정했습니다.

### 실습의 흐름

```text
컨테이너 내부 파일 확인
    → index.html 내용 확인
    → HTML 내용 변경
    → cat으로 저장된 내용 확인
    → 브라우저를 새로고침하여 결과 확인
```

수업에서는 `echo`와 리다이렉션을 이용해 내용을 쓰거나 추가하는 방법, `cat`으로 파일 내용을 확인하는 방법을 다뤘습니다. `>`는 내용을 덮어쓰는 용도, `>>`는 내용을 추가하는 용도로 설명했습니다.

또한 Docker Desktop의 파일 보기 기능이나 컨테이너 내부 작업을 통해 파일을 확인했습니다.

### 이 실습을 하는 이유

단순히 “Hello”를 화면에 띄우는 것이 목적은 아닙니다. 컨테이너 안에도 웹 서버가 사용할 파일이 있고, 그 파일을 바꾸면 서비스 결과가 달라진다는 연결을 확인하는 실습입니다.

이후에는 홈페이지와 상세 페이지를 만들거나 JavaScript를 추가하는 식으로 확장할 수 있다고 설명했습니다. 수업의 다음 흐름은 **이렇게 준비한 애플리케이션과 환경을 다시 이미지로 만들어 다른 곳에서 사용할 수 있게 하는 것**이었습니다.

다만 컨테이너 안에서 직접 바꾼 내용을 최종 이미지에 반영하는 전체 명령은 이 녹취에 제시되어 있지 않습니다. 해당 절차는 실습 교안과 대조해야 합니다.[^custom]

## 8. AI 활용: 명령 실행을 대신시키되 작업 대상을 이해하기

강의에서는 Codex를 켜고 자연어로 Docker 관련 작업을 요청하는 모습을 시연했습니다.

대표적으로 이미지 목록 확인, 특정 컨테이너 삭제, Nginx 실행, 프로젝트에 필요한 이미지 추천, 컨테이너 실행, 현재 Docker 상태 설명 등을 요청했습니다.

### 프로젝트 준비 요청의 예

수업에서 다룬 요청의 취지는 다음과 같습니다.

> 웹·데이터베이스·Python으로 Open API를 연결하는 프로젝트에 필요한 이미지를 먼저 추천하고, 허가한 뒤 내려받아 컨테이너까지 실행한다.

이 예시에서는 Nginx, Python, PostgreSQL을 조합했습니다. 웹 화면 제공, API 처리, 데이터 저장을 각각 담당하게 하려는 구성입니다.

중요한 점은 AI가 사용하는 명령의 대상이 **이미지인지, 컨테이너인지, 특정 프로젝트인지**를 사용자가 구분하는 것입니다. 자연어로 요청한다고 해서 그 구분이 없어지는 것은 아닙니다.

또한 녹취의 “프롬프트로 실행할 수 있다”는 말은 강의에서 사용한 Codex 실행 환경에서의 시연 설명입니다. 모든 대화 환경에서 동일한 실행 권한을 갖는다는 뜻으로 확대해서 읽지 않습니다.[^run][^custom]

## 9. Part 2: 웹과 Python API를 나누어 연결하기

### 실습에서 다룬 데이터 흐름

Part 2 설명에서는 `sales.csv`를 읽는 Python API와, 그 결과를 화면에 표시하는 웹 구성을 다뤘습니다.

```text
sales.csv
    ↓
Python API가 파일을 읽음
    ↓
행별 판매 금액 계산 및 합계 구성
    ↓
요약 데이터를 응답
    ↓
웹에서 응답을 받아 HTML에 반영
```

녹취에서 설명한 CSV 항목은 날짜, 지역, 상품명, 판매 개수, 단가입니다. 각 행에 대해 다음 계산을 수행합니다.

```text
판매 금액 = 수량 × 단가
```

Python은 행 단위로 자료를 읽고, 계산한 판매 금액을 추가하고, 전체 합계 등을 구성합니다. 웹은 응답받은 값들을 해당 HTML 요소에 넣어 화면에 보여줍니다.

수업에서는 API가 **5000번 포트**에서 실행되는 예를 설명했고, HTTP 상태 코드 **200**을 통신이 정상적으로 이루어진 응답을 확인하는 맥락에서 다뤘습니다.

### 왜 pandas 없이 CSV를 읽었는가?

수업에서는 pandas를 사용하면 쉽게 처리할 수 있지만, 실습 환경에 설치할 패키지가 하나 더 생긴다는 점을 언급했습니다.

이 예제에서는 별도 패키지 설치를 줄이고 파일을 읽고 계산하는 과정을 직접 볼 수 있도록 구성했습니다. 녹취에는 pandas 사용 여부에 따른 실제 성능 측정 결과가 없으므로, 어느 방식이 항상 더 빠르다고 결론 내릴 수는 없습니다.

### 이 실습의 진짜 목표

판매 데이터 분석 자체보다 중요한 것은 **각 프로그램을 이미지로 만들고, 컨테이너로 실행하고, 서로 연결하는 과정**입니다.

강의에서도 HTML이나 코드가 어렵다면 더 단순한 예제로 진행해도 된다고 안내했습니다. 기능을 크게 만드는 것보다 다음 연결을 이해하는 것이 우선입니다.

> **내 프로그램 → 실행 환경을 포함한 이미지 → 컨테이너 실행 → 다른 서비스와 통신**

정확한 API 경로, 응답 JSON의 전체 구조, 모든 집계 항목은 녹취만으로 확정할 수 없습니다.[^part2]

## 10. 왜 Docker Compose가 필요한가?

컨테이너 하나를 실행할 때는 명령을 직접 입력해도 됩니다. 하지만 웹, API, 데이터베이스처럼 서비스가 늘어나면 실행할 때마다 확인할 내용이 많아집니다.

어떤 폴더를 빌드할지, 어떤 포트를 열지, 어느 서비스에 연결할지, 어떤 환경 변수를 전달할지, 데이터를 어디에 보존할지를 함께 관리해야 합니다.

수업에서는 이 구성을 **하나의 YAML 파일에 구조화해 두고 사용하는 방법**으로 Docker Compose를 소개했습니다.

```text
개별 명령을 반복해서 입력
    ↓
여러 서비스의 실행 설정이 흩어짐
    ↓
Compose 파일에 서비스별 구성을 정리
    ↓
파일을 기준으로 구성 확인·실행·수정
```

### Dockerfile과 Compose는 담당하는 범위가 다르다

| 구분 | 주로 정리하는 내용 |
|---|---|
| Dockerfile | 개별 서비스의 실행 환경과 이미지를 어떻게 만들 것인가? |
| Compose 파일 | 여러 서비스를 어떤 설정과 관계로 실행할 것인가? |

강의 후반의 핵심 표현은 다음과 같습니다.

> **Docker Compose는 단순한 명령어 모음이 아니라 서비스 구조를 설계하는 파일이다.**

서비스 이름, 연결 관계, 외부 공개 범위, 데이터 보존 방식을 어떻게 정했는지가 곧 설계 내용이기 때문입니다.[^project][^compose]

## 11. 이커머스 예시로 이해하는 Compose 설계

수업에서는 **Windows, Docker, Multipass VM을 사용하되 Kubernetes는 제외한 이커머스 프로젝트**를 예로 들었습니다.

### 기본 서비스 구성

```text
사용자
    ↓
프론트엔드 / 웹
    ↓
백엔드 / Python
    ↓
데이터베이스
```

이 구조를 서비스별 컨테이너로 나누고 Compose로 연결하는 방향입니다. Windows에서 준비한 구성을 Linux VM에서도 다루는 배포 흐름까지 포함했습니다.

### 핵심은 컨테이너 개수가 아니라 연결 방식이다

**첫째, 서비스가 분리되어도 서로 통신할 수 있어야 합니다.**

수업은 Compose의 서비스 이름이 서비스 간 연결에 사용될 수 있다고 설명했습니다. 특히 백엔드에서 DB 주소를 무조건 `localhost`로 적는 것이 아니라, 대상 DB 서비스에 맞추어 설정해야 한다고 강조했습니다.

**둘째, 데이터베이스는 이 예제에서 외부에 직접 공개하지 않습니다.**

프론트엔드에는 외부 접속을 위한 포트를 설정하지만, DB는 백엔드가 내부에서 연결하도록 설명했습니다. 백엔드가 사용할 DB 이름, 계정, 비밀번호 등은 환경 설정으로 전달하는 구조였습니다.

이는 수업에서 제시한 프로젝트 설계 방향입니다. 녹취에 나온 “DB는 절대 오픈되면 안 된다”는 표현을 모든 환경에 그대로 적용하는 보편 규칙으로 확장하지는 않습니다.

**셋째, 컨테이너에 문제가 생겨도 데이터는 보존되어야 합니다.**

수업에서는 DB 데이터를 보존하기 위해 볼륨과 호스트 쪽 저장을 고려해야 한다고 설명했습니다. 다만 실제 예제가 어떤 마운트 방식과 경로를 사용했는지는 전체 설정이 없어 확정할 수 없습니다.

**넷째, 서비스 상태와 문제 발생 위치를 확인할 수 있어야 합니다.**

서비스를 실행하는 것과, 문제가 생겼을 때 어디에서 발생했는지 설명하는 것은 별개입니다. 강의에서는 Compose를 활용한 상태 확인과 원인 추적을 별도의 작은 실습 주제로 삼아도 좋다고 안내했습니다.

### 수업에서 다룬 주요 설정

| 설정 | 수업의 맥락에서 이해할 내용 |
|---|---|
| `build` | 해당 서비스의 이미지를 만들 폴더를 지정한다. |
| `ports` | 호스트에서 컨테이너로 연결할 포트를 설정한다. |
| `environment` | DB 연결 정보 등 서비스에 전달할 환경 설정을 둔다. |
| `depends_on` | 서비스 사이의 의존 관계를 표현한다. |
| `volumes` | 데이터 보존을 위한 저장 연결을 구성한다. |
| 서비스 이름 | 서비스 구분과 서비스 간 연결에 사용한다. |

`depends_on`을 설정했을 때 서비스가 실제 요청을 처리할 준비까지 보장되는지 등의 세부 동작은 녹취에서 설명하지 않았습니다. 단순한 의존 관계 설명을 그 이상의 보장으로 해석하지 않도록 주의합니다.[^project][^compose]

## 12. YAML 규칙과 도움말을 확인하는 방법

### YAML은 들여쓰기도 구조다

수업에서는 다음 기본 규칙을 강조했습니다.

| 규칙 | 기억할 점 |
|---|---|
| 키와 값 | `키: 값` 형태로 작성한다. |
| 들여쓰기 | 스페이스를 사용하고 같은 단계는 같은 깊이로 맞춘다. |
| 목록 | 하이픈 `-`으로 항목을 구분한다. |
| 주석 | `#` 뒤에 설명을 적는다. |

단순히 보기 좋게 정렬하는 문제가 아닙니다. 들여쓰기가 달라지면 설정의 소속과 구조가 달라질 수 있으므로, 작성한 파일을 확인하는 과정이 필요합니다.

수업에서는 YAML 작성 오류를 확인하는 명령으로 다음을 제시했습니다.

```bash
docker compose config
```

탭이나 목록 표시 등을 잘못 사용했을 때 오류 메시지를 확인해 보라는 실습도 제안했습니다.

### 모든 옵션을 외우기보다 확인할 수 있어야 한다

Compose 도움말의 출발점으로 다음 명령을 다뤘습니다.

```bash
docker compose --help
```

수업의 과제는 도움말에 나오는 명령과 각 명령의 옵션을 확인하고, 자신이 다시 찾아볼 수 있는 자료로 정리하는 것이었습니다. 공식 문서의 레퍼런스를 확인하는 습관도 강조했습니다.

여기서 구분할 점은 **CLI의 명령·옵션을 확인하는 일**과 **Compose YAML에 서비스 설정을 작성하는 일**입니다. 녹취에는 명령을 “키값”이라고 부르는 대목이 있지만, 이 문서에서는 두 대상을 한 목록으로 합치지 않았습니다.[^project][^compose]

## 13. 상태 확인과 장애 대응: 범위를 작게 잡고 직접 검증하기

### 수업에서 권장한 접근

처음부터 복잡한 운영 체계를 모두 만들려고 하지 말고, 다음 범위부터 이해하라고 안내했습니다.

```text
서비스가 어떤 상태인지 확인
    ↓
문제가 발생한 위치와 원인 추적
    ↓
구성한 대응이 실제로 작동하는지 테스트
```

이것만 별도 주제로 삼아도 프로젝트가 될 수 있다는 설명이었습니다.

강의 후반에는 Nginx와 Python 정도의 **컨테이너 두 개로 단순한 샘플을 구성**하고, 필요한 패키지를 `requirements.txt`로 설치하며, Compose에서 직접 설정을 작성해 보는 방향을 제시했습니다.

중요한 것은 Python을 썼는지 여부가 아니라, **Compose의 어떤 설정으로 어떤 문제를 다루는지 설명할 수 있는가**입니다.

### Compose와 Kubernetes를 연결한 이유

Kubernetes는 여러 컨테이너를 운영하는 오케스트레이션 기술이라는 개념 수준에서 소개했습니다. 이번 프로젝트의 구현 대상에서는 제외했습니다.

수업은 Compose에도 한계가 있으며, 그 한계를 이해해야 나중에 Kubernetes를 사용하는 이유가 보인다고 설명했습니다. 따라서 지금 단계에서는 “Kubernetes까지 사용했다”는 기술 목록을 늘리는 것보다, 현재 구성으로 할 수 있는 운영과 한계를 이해하는 데 초점을 둡니다.

녹취에는 구체적인 장애 주입 절차, 복구 시간, 자동 복구 성공 결과가 제시되지 않았습니다. 따라서 이번 내용을 실제 장애 대응 검증까지 완료한 것으로 기록해서는 안 됩니다.[^project][^compose]

## 16. 녹취에서 표현이 혼용되거나 확인이 필요한 부분

아래 항목은 외부 자료로 검증한 정정 목록이 아니라, **이번 녹취만으로 단정하기 어려운 부분**입니다.

| 항목 | 녹취에 나타난 내용 | 이 문서에서의 처리 |
|---|---|---|
| 컨테이너와 VM | 앞부분은 Nginx 컨테이너를 별도의 VM처럼 표현하지만, 후반에는 운영체제 전체를 복제하지 않는 프로세스 환경 격리로 설명한다. | 두 표현의 혼용을 명시하고, 개념 흐름은 후반의 구분에 따라 정리했다. |
| 네트워크 분리와 보안 | 포트나 IP를 나누면 다른 서비스가 공격에서 제외될 수 있다는 설명이 있다. | 구체적인 접근 통제 설정이 제시되지 않아, 포트·IP 분리만으로 안전이 보장된다고 결론 내리지 않았다. |
| 이미지 삭제와 컨테이너 삭제 | “이미지를 삭제하면 컨테이너도 같이 삭제된다”는 표현과, 컨테이너를 먼저 중지·삭제한 뒤 이미지를 삭제하라는 안내가 함께 있다. | 자동으로 함께 삭제된다고 정리하지 않고, 수업에서 안내한 정리 순서만 기록했다. |
| VM IP 및 일부 포트 | 음성 인식으로 보이는 숫자 불일치가 있다. | 해당 숫자를 실습용 실제 주소로 재사용하지 않았다. |
| API 경로와 응답 구조 | `summary`, API 응답 처리, HTML 반영을 설명하지만 전체 코드는 없다. | 처리 흐름만 정리하고 완성된 엔드포인트나 응답 구조를 만들지 않았다. |
| 의존성과 준비 상태 | `depends_on`으로 의존 관계를 설명한다. | 준비 완료나 자동 복구의 구체적인 보장까지 확대하지 않았다. |
| CLI 명령과 YAML 키 | 도움말의 명령을 “키값”이라고 표현하는 대목이 있다. | 명령·옵션 확인과 YAML 서비스 설정을 구분했다. |
| 데이터 저장 방식 | 볼륨, 로컬 보존을 언급하지만 전체 마운트 설정은 없다. | 저장 경로나 구체적인 마운트 방식을 확정하지 않았다. |

---

## 마지막으로 기억할 핵심

**Docker는 실행 환경을 이미지로 만들어 사용하고 전달하는 흐름, Compose는 여러 서비스의 실행 설정과 연결 관계를 파일로 관리하는 흐름으로 이해하면 됩니다.**

오늘의 학습 성과는 명령을 몇 개 실행했는지가 아니라, **왜 서비스를 나누었고, 어떻게 연결했으며, 데이터와 상태를 어떻게 확인할 것인지 설명할 수 있게 되는 것**입니다.
