## 1. 오늘 수업의 전체 흐름

오늘 수업은 단순히 Docker 명령어를 더 배우는 시간이 아니라, **개발한 프로그램을 컨테이너 단위로 나누고, 이미지로 만들어 다른 환경으로 옮기고, 여러 컨테이너를 운영할 때 왜 Kubernetes 계열 도구가 필요한지**까지 연결하는 수업이었습니다.

전체 흐름은 다음과 같이 볼 수 있습니다.

```text
Windows 개발 환경
    ↓ SSH 또는 Multipass
Ubuntu Linux
    ↓
Docker Engine
    ↓
Python report 컨테이너 + Nginx web 컨테이너
    ↓
Docker Compose로 역할 연결
    ↓
Docker 이미지를 TAR로 저장/이동
    ↓
Kubernetes 계열 환경(K3/K3s로 추정)에서 Pod와 Service로 실행
```

즉, **코드를 실행하는 것 → 컨테이너로 묶는 것 → 컨테이너를 역할별로 분리하는 것 → 다른 환경으로 옮기는 것 → 여러 컨테이너를 운영하는 것**으로 단계가 확장되었습니다.

→ 왜 배우나·현업 활용: 애플리케이션을 개인 PC에서만 실행하는 수준을 넘어, 개발·테스트·운영 서버에 같은 형태로 배포하고 장애가 발생했을 때 어느 구성 요소가 문제인지 분리하여 대응하기 위해 배웁니다.

# 2. Windows와 Linux에서 Docker를 사용하는 방식의 차이

## 문제·배경

개발자는 Windows PC를 사용하더라도 실제 서버 운영 환경은 Linux인 경우가 많습니다. 그래서 Windows에서 코드를 작성하면서 Ubuntu 같은 Linux 환경에 접속하고, 그 안에서 Docker를 실행하는 흐름을 익혀야 합니다.

수업에서는 Windows에서 Linux로 접근할 때 **SSH**를 사용하는 방법을 중심으로 설명했고, SSH 연결이 잘 되지 않을 경우 Multipass VM 내부에서 직접 작업하는 방법도 언급했습니다.

→ 왜 배우나·현업 활용: Windows 개발 PC와 Linux 서버가 분리된 환경에서 원격 서버에 접속해 로그를 확인하고 컨테이너를 실행하거나 배포하기 위해 배웁니다.

## SSH와 Multipass의 역할

SSH(Secure Shell)는 네트워크를 통해 다른 컴퓨터의 터미널에 접속하는 방식입니다. Windows의 VS Code에서 Ubuntu에 SSH로 접속하면, 화면은 Windows에서 보면서 실제 파일과 명령은 Linux에서 실행하는 형태로 작업할 수 있습니다.

SSH 접속이 어려울 경우에는 `multipass shell <VM이름>`처럼 VM 안으로 직접 들어가 작업할 수 있고, Windows와 Ubuntu가 같은 파일을 사용해야 한다면 폴더를 **마운트(mount)**하여 공유하는 방식도 사용할 수 있습니다.

> **확인 필요:** 녹취에서 Multipass의 파일 공유 관련 명령 이름 일부가 정확하게 인식되지 않았습니다. 실제 명령은 수업 자료를 다시 확인하는 것이 좋습니다.

→ 왜 배우나·현업 활용: 원격 Linux 서버 접속이 끊기거나 개발 도구 연동이 되지 않을 때도 VM 직접 접속이나 공유 폴더 같은 대체 경로로 작업을 계속하기 위해 배웁니다.

# 3. Linux에서 Docker를 사용하는 기본 흐름

수업에서 강조한 Linux Docker 사용 순서는 다음과 같습니다.

```text
Docker Engine 설치
    ↓
Docker 서비스 시작
    ↓
설치 상태 확인
    ↓
필요한 이미지 다운로드
    ↓
컨테이너 실행
```

Windows에서는 Docker Desktop을 실행해 Docker 환경을 사용하는 경우가 많지만, Linux에서는 Docker Engine과 Docker 서비스를 직접 설치·실행하는 구조를 이해해야 합니다.

또한 Docker 사용 권한 설정이 필요할 수 있다는 점도 언급되었지만, 오늘 수업에서는 권한 부분을 깊게 다루지는 않았습니다.

→ 왜 배우나·현업 활용: 서버에 GUI가 없는 Linux 환경에서도 Docker 데몬 상태를 확인하고 이미지와 컨테이너를 직접 운영하기 위해 배웁니다.

### 이해 보충: 확인에 자주 사용하는 명령 형태

아래는 수업의 의도를 이해하기 위한 일반적인 예시입니다. **정확한 설치 명령은 배포판과 수업 자료를 기준으로 확인해야 합니다.**

```bash
docker --version
docker images
docker ps
```

- **실행 위치:** Ubuntu/Linux 터미널
- **목적:** Docker 설치 여부, 보유 이미지, 실행 중 컨테이너 확인
- **예상 결과:** 버전 정보 또는 이미지·컨테이너 목록
- **해석:** 명령 자체가 실행되지 않으면 Docker 설치/환경 문제를, 목록이 비어 있으면 아직 이미지나 실행 중 컨테이너가 없음을 의미합니다.

→ 왜 배우나·현업 활용: 배포 실패가 애플리케이션 문제인지 Docker 자체가 실행되지 않는 문제인지 가장 먼저 구분하기 위해 배웁니다.

# 4. 데이터베이스 컨테이너를 사용할 때의 기본 원칙

오늘 데이터베이스를 깊게 실습한 것은 아니지만, 앞으로 Docker 기반 프로젝트에서 DB 컨테이너를 사용할 때 주의해야 할 사항을 미리 다뤘습니다.

핵심은 다음 세 가지입니다.

1. **데이터는 컨테이너 내부에만 두지 말고 별도 저장 공간을 사용해야 합니다.**
2. **비밀번호 같은 민감 정보가 그대로 노출되지 않도록 관리해야 합니다.**
3. **MySQL, MariaDB, PostgreSQL 같은 DBMS의 버전을 명확하게 지정하는 것이 좋습니다.**

DBMS(Database Management System)는 데이터를 저장·조회·수정할 수 있도록 관리하는 소프트웨어이고, RDBMS(Relational DBMS)는 데이터를 행과 열 형태의 관계형 구조로 관리하는 DBMS입니다.

→ 왜 배우나·현업 활용: DB 컨테이너를 다시 만들거나 삭제했을 때 데이터가 함께 사라지는 사고를 방지하고, 개발·운영 서버 간 DB 버전 차이로 발생하는 호환성 문제를 줄이기 위해 배웁니다.

# 5. 프로젝트 구조를 먼저 이해해야 하는 이유

수업에서는 폴더 구조를 트리 형태로 확인하는 것이 중요하다고 설명했습니다. 프로젝트에 `data`, `out`, `report`, `web` 같은 폴더가 있다면 각 폴더의 역할을 먼저 알아야 Dockerfile이나 Compose 파일을 읽을 수 있습니다.

예를 들어 오늘 구조는 개념적으로 다음과 같이 볼 수 있습니다.

```text
project/
├─ data/        # 입력 데이터(CSV)
├─ out/         # 생성된 report.html
├─ report/      # CSV를 읽어 리포트를 만드는 Python 프로그램
└─ web/         # 생성된 결과를 사용자에게 제공하는 웹 영역
```

폴더 구조를 모르고 명령어부터 실행하면 파일 경로 오류가 발생했을 때 원인을 찾기 어렵습니다.

→ 왜 배우나·현업 활용: 처음 보는 프로젝트를 인수받았을 때 어떤 폴더가 입력·출력·애플리케이션·설정 역할을 담당하는지 빠르게 파악하여 잘못된 경로 수정이나 배포 실수를 줄이기 위해 배웁니다.

# 6. CSV → Python report.py → HTML 리포트 생성

## 문제·배경

오늘 Python 실습에서는 CSV 데이터를 읽어 계산하고, 그 결과를 HTML 파일로 만드는 `report.py`를 구성했습니다. 목표는 단순한 Python 연습이 아니라 **데이터 처리 프로그램을 Docker 컨테이너로 실행할 수 있는 구조를 만드는 것**입니다.

→ 왜 배우나·현업 활용: 배치 분석, 통계 리포트, 로그 집계처럼 입력 데이터를 처리해 결과 파일을 생성하는 작업을 자동화된 컨테이너 작업으로 만들기 위해 배웁니다.

## pandas의 역할

`pandas`는 CSV 같은 표 형태의 데이터를 DataFrame으로 읽고 계산하기 위한 Python 라이브러리입니다. 수업에서는 `sales.csv`를 읽은 뒤 총매출과 지역별·제품별 집계 등을 만들고, 결과를 HTML로 조립하는 흐름을 다뤘습니다.

실습 중에는 결과를 바로 HTML로 만들기 전에 `print()` 등을 이용해 **CSV가 정상적으로 읽혔는지와 집계 결과가 올바르게 나오는지 먼저 확인하는 과정**이 강조되었습니다.

→ 왜 배우나·현업 활용: 최종 화면이 잘못되었을 때 원인이 데이터 입력인지 계산 로직인지 HTML 출력인지 단계별로 분리해 확인하기 위해 배웁니다.

## requirements.txt가 필요한 이유

내 PC에 pandas가 설치되어 있다고 해서 Docker 컨테이너에도 자동으로 pandas가 존재하는 것은 아닙니다. 그래서 애플리케이션에 필요한 Python 패키지를 `requirements.txt`에 기록하고, Docker 이미지 생성 과정에서 다시 설치해야 합니다.

수업에서는 pandas 버전을 명확하게 기록하는 것을 권장했습니다. 녹취에는 `2.1.4` 예시가 등장하지만, 실제 실습 환경에서 사용한 최종 버전은 다시 확인하는 것이 좋습니다.

```text
pandas==<사용 버전>
```

→ 왜 배우나·현업 활용: 개발자마다 설치된 라이브러리 버전이 달라 생기는 “내 PC에서는 되는데 서버에서는 안 되는” 문제를 줄이고 재현 가능한 실행 환경을 만들기 위해 배웁니다.

# 7. Dockerfile: 프로그램과 실행 환경을 이미지로 묶기

`report.py`만 전달하면 상대방의 컴퓨터에 Python과 pandas가 별도로 준비되어 있어야 합니다. Dockerfile은 이 문제를 해결하기 위해 **기본 Python 환경, 필요한 라이브러리, 소스 코드, 실행 명령**을 하나의 이미지 제작 절차로 정의합니다.

오늘 수업의 흐름은 대략 다음과 같습니다.

```text
Python 기반 이미지 선택
    ↓
컨테이너 내부 작업 폴더 지정
    ↓
requirements.txt 복사
    ↓
필요한 패키지 설치
    ↓
report.py 등 코드 복사
    ↓
컨테이너 실행 시 Python 프로그램 실행
```

정확한 Python 이미지 버전은 녹취가 불명확하므로 **확인 필요**입니다.

→ 왜 배우나·현업 활용: 애플리케이션 실행에 필요한 OS 환경과 라이브러리까지 함께 정의하여 개발 PC와 테스트/운영 서버에서 동일한 방식으로 실행하기 위해 배웁니다.

# 8. 멀티 컨테이너: 왜 Python과 Nginx를 나누는가

오늘 수업에서 중요한 개념 중 하나는 **한 컨테이너에 모든 기능을 넣지 않고 역할별로 분리하는 것**입니다.

예를 들어 오늘 구조에서는 다음처럼 역할을 나눌 수 있습니다.

```text
report 컨테이너
- CSV 읽기
- pandas 계산
- report.html 생성
- 작업 완료 후 종료

web 컨테이너
- Nginx 실행
- report.html 제공
- 사용자가 접속할 수 있도록 계속 실행
```

Python과 Nginx를 분리하면 Python 코드만 변경했을 때 report 쪽만 다시 빌드할 수 있고, 한쪽에서 장애가 발생해도 다른 역할까지 한꺼번에 영향을 받는 범위를 줄일 수 있습니다. 반대로 컨테이너가 여러 개가 되면 서로 데이터를 공유하고 통신하는 구성이 필요해지는 복잡성이 생깁니다.

→ 왜 배우나·현업 활용: API, 배치, 웹 서버, DB 같은 구성 요소를 독립적으로 배포·재시작하고 장애 영향을 줄이기 위해 역할별 컨테이너 설계를 배웁니다.

# 9. “종료된 컨테이너”가 항상 장애는 아니다

오늘 수업에서 꼭 이해해야 할 부분입니다. `report` 작업은 CSV를 읽고 HTML을 만들면 할 일이 끝납니다. 따라서 정상적으로 실행된 뒤 컨테이너가 종료될 수 있습니다.

반대로 Nginx 웹 서버는 사용자의 요청을 계속 받아야 하므로 프로세스가 계속 살아 있어야 합니다.

즉, 운영에서는 단순히 **컨테이너가 종료되었는가**만 보면 안 되고, 그 프로세스가 원래 한 번 실행되고 끝나는 배치 작업인지, 계속 실행되어야 하는 서비스인지 구분해야 합니다. 정상 종료라면 종료 코드 `0`을 확인하는 방식도 중요합니다.

→ 왜 배우나·현업 활용: 배치 컨테이너가 정상 완료된 것을 장애로 잘못 판단하거나, 반대로 계속 살아 있어야 할 웹 서비스가 종료된 상태를 놓치는 운영 실수를 방지하기 위해 배웁니다.

# 10. Volume으로 report와 web 연결하기

`report` 컨테이너에서 생성한 `report.html`을 Nginx가 보여주려면 두 컨테이너가 결과 파일을 공유해야 합니다. 오늘 수업에서는 호스트의 `out` 폴더를 두 컨테이너에서 함께 사용하는 방식으로 연결하는 구조를 다뤘습니다.

개념적으로는 다음과 같습니다.

```text
sales.csv
   ↓
report 컨테이너
   ↓
호스트 ./out/report.html
   ↓
web 컨테이너(Nginx)
   ↓
브라우저
```

이때 Volume은 컨테이너가 사용하는 파일을 컨테이너 생명주기와 분리하고, 여러 컨테이너가 같은 데이터를 공유하도록 도와줍니다.

→ 왜 배우나·현업 활용: 컨테이너가 재생성되어도 결과 파일이나 데이터가 유지되게 하고, 배치 프로그램의 출력물을 웹 서버나 다른 서비스가 이어서 사용할 수 있도록 만들기 위해 배웁니다.

# 11. Docker Compose의 역할

여러 컨테이너를 각각 긴 `docker run` 명령으로 실행하면 포트, 볼륨, 이미지, 실행 순서를 관리하기 어렵습니다. Docker Compose는 이러한 여러 서비스의 구성을 YAML 파일에 선언해 함께 관리할 수 있게 해 줍니다.

오늘 수업에서는 Compose YAML을 읽고 **“이 서비스는 무엇을 빌드하는가, 어떤 이미지를 사용하는가, 어떤 폴더를 공유하는가, 계속 실행되는가 또는 한 번 실행되고 끝나는가”**를 설명할 수 있어야 한다고 강조했습니다.

또한 실제 프로젝트에서는 처음 기획했던 구조와 최종 Compose 구성이 달라질 수 있으므로, 이미 만들어진 YAML을 읽고 설명 문서로 변환하는 능력도 중요하다고 했습니다.

→ 왜 배우나·현업 활용: 운영 중인 프로젝트를 인수받았을 때 Compose 파일만 보고 서비스 구성, 포트, 볼륨, 의존 관계를 파악하고 장애 원인을 추적하기 위해 배웁니다.

# 12. 작업을 한 번에 만들지 않고 단계별로 검증하기

수업에서 반복해서 나온 실무적인 습관은 **한꺼번에 모든 것을 만든 뒤 실행하지 말고, 작은 단계마다 정상 동작을 확인하는 것**입니다.

예를 들어 다음 순서가 좋습니다.

```text
1. CSV 파일이 있는지 확인
2. Python에서 CSV가 읽히는지 확인
3. pandas 계산 결과를 print로 확인
4. report.html이 만들어지는지 확인
5. Docker 이미지 빌드
6. report 컨테이너만 실행해 결과 확인
7. Nginx 컨테이너 연결
8. Compose 전체 실행
9. 브라우저에서 최종 확인
```

이렇게 하면 최종 화면이 나오지 않을 때 어느 단계부터 실패했는지 범위를 빠르게 좁힐 수 있습니다.

→ 왜 배우나·현업 활용: 배포 과정에서 문제가 발생했을 때 전체 시스템을 무작정 다시 만드는 대신 입력·코드·이미지·컨테이너·네트워크 중 어느 단계가 원인인지 빠르게 찾기 위해 배웁니다.

# 13. `.dockerignore`: 이미지에 넣지 않아야 할 파일 제외

Docker 이미지를 만들 때 현재 폴더의 모든 파일을 무조건 복사하면 가상환경, Git 정보, `.env`, 캐시 파일 등 불필요하거나 민감한 파일까지 이미지에 포함될 수 있습니다.

수업에서는 Python 패키지 폴더나 개발 환경에서만 필요한 파일을 이미지에서 제외하는 것이 좋다고 설명했습니다. 일반적으로 이런 역할을 `.dockerignore` 파일이 담당합니다.

예를 들어 **이해 보충용**으로 다음과 같은 항목을 생각할 수 있습니다.

```text
.venv/
.git/
.env
__pycache__/
*.pyc
```

→ 왜 배우나·현업 활용: Docker 이미지 용량을 줄이고 빌드 속도를 높이며, API 키가 들어 있는 `.env` 같은 민감 파일이 이미지에 포함되어 유출되는 사고를 방지하기 위해 배웁니다.

# 14. Docker 이미지를 TAR 파일로 저장하고 공유하기

Docker 이미지는 Docker Hub 같은 레지스트리에 올리지 않아도 파일로 저장해 다른 컴퓨터로 전달할 수 있습니다. 수업에서는 `docker save`로 이미지를 TAR 형식으로 저장하고, 다른 환경에서 `docker load`로 불러오는 흐름을 다뤘습니다.

TAR는 여러 파일을 하나로 묶는 아카이브 형식입니다. 기본 TAR 자체는 반드시 압축을 의미하지는 않으며, `tar.gz`는 TAR로 묶은 뒤 gzip 압축까지 적용한 형태입니다.

### 이해 보충: 명령 형태

```bash
docker save -o product-app.tar product-app:v1
```

- **실행 위치:** Docker 이미지가 존재하는 PC의 터미널
- **목적:** `product-app:v1` 이미지를 `product-app.tar` 파일로 저장
- **주요 옵션:** `-o`는 출력 파일 지정
- **예상 결과:** 현재 폴더에 TAR 파일 생성
- **해석:** 파일이 생성되면 레지스트리 없이도 해당 파일을 다른 PC로 전달할 수 있습니다.

```bash
docker load -i product-app.tar
```

- **실행 위치:** 이미지를 사용할 다른 PC의 Docker 환경
- **목적:** TAR 파일 안의 Docker 이미지를 로컬 Docker 이미지 저장소로 가져오기
- **주요 옵션:** `-i`는 입력 파일 지정
- **예상 결과:** 이미지가 로드되었다는 메시지
- **다음 확인:** `docker images`로 이미지 이름과 태그 확인

→ 왜 배우나·현업 활용: 인터넷이 제한된 서버나 사내망 환경에서 Docker Hub를 사용하지 않고도 검증된 이미지를 전달해 같은 애플리케이션을 실행하기 위해 배웁니다.

# 15. 컨테이너 안의 파일을 꺼내는 방법

수업에서는 이미지를 단순히 실행하는 것뿐 아니라 **컨테이너 내부 파일을 호스트로 복사하여 확인하거나 수정할 수 있다**는 점도 다뤘습니다.

일반적인 흐름은 다음과 같습니다.

```text
이미지로 컨테이너 생성
    ↓
컨테이너 내부 파일을 호스트로 복사
    ↓
필요하면 컨테이너 삭제
```

### 이해 보충: 일반적인 명령 형태

```bash
docker create --name extractor <이미지이름>
docker cp extractor:/app ./my_files
docker rm extractor
```

- **`docker create` 실행 위치:** Docker가 설치된 호스트
- **목적:** 이미지를 실행하지 않고 컨테이너 파일 시스템만 준비
- **`docker cp` 목적:** 컨테이너 `/app` 파일을 호스트 `./my_files`로 복사
- **`docker rm` 목적:** 파일 추출 후 임시 컨테이너 삭제
- **예상 결과:** `my_files` 폴더에 컨테이너 내부 파일이 복사됨

> 주의: 이렇게 꺼낸 소스가 있다고 해서 동일하게 실행된다는 보장은 없습니다. Python 버전과 `requirements.txt`에 정의된 라이브러리 환경도 함께 맞아야 합니다.

→ 왜 배우나·현업 활용: 전달받은 Docker 이미지의 파일 구조를 조사하거나, 특정 설정·정적 파일을 확인해야 할 때 컨테이너를 실제 서비스로 실행하지 않고 필요한 파일만 추출하기 위해 배웁니다.

# 16. Docker만으로 부족해지는 지점: Kubernetes가 필요한 이유

Docker는 개별 컨테이너를 만들고 실행하는 데 매우 유용하지만, 컨테이너 수가 많아지고 장애가 발생했을 때 자동 복구, 여러 인스턴스 관리, 서비스 노출 등을 직접 처리하려면 관리가 복잡해집니다.

수업에서는 이 지점에서 **컨테이너 오케스트레이션(Container Orchestration)** 개념을 연결했습니다. 오케스트레이션은 여러 컨테이너의 생성·배치·네트워크·복구·확장 등을 체계적으로 관리하는 것을 의미합니다.

→ 왜 배우나·현업 활용: 여러 서버와 수십~수백 개 컨테이너를 사람이 일일이 재시작하고 포트를 관리하지 않고 선언된 상태에 맞게 자동으로 운영하기 위해 배웁니다.

# 17. K3/K3s와 Kubernetes의 기본 용어

녹취에서는 `K3`라고 표현되었는데, 일반적으로 경량 Kubernetes 배포판인 **K3s를 의미한 것으로 보입니다. 확인 필요**입니다.

오늘은 Kubernetes의 모든 기능을 배우는 것이 아니라 아주 기본적인 개념을 실습했습니다.

### Pod

Pod는 Kubernetes에서 컨테이너를 실행하는 기본 단위입니다. 수업에서는 Nginx 이미지를 이용해 `hello`라는 Pod를 만들고, Pod 목록과 상태를 확인하는 흐름을 다뤘습니다.

→ 왜 배우나·현업 활용: Kubernetes에서는 Docker 컨테이너 자체보다 Pod 단위로 애플리케이션 상태를 확인하고 배포하므로, 문제 발생 시 어떤 Pod가 정상인지 먼저 확인하기 위해 배웁니다.

### Service

Pod는 내부 IP를 받을 수 있지만, 외부 사용자가 그 Pod에 안정적으로 접근하려면 Service 같은 별도의 네트워크 객체가 필요합니다. 수업에서는 포트 포워딩과 NodePort 방식을 사용해 외부에서 Nginx 또는 Product API에 접근하는 흐름을 설명했습니다.

→ 왜 배우나·현업 활용: Pod가 재생성되거나 IP가 바뀌더라도 사용자가 일정한 서비스 주소와 포트를 통해 애플리케이션에 접근할 수 있도록 하기 위해 배웁니다.

### Pod와 Service는 별개

오늘 수업에서 중요한 포인트는 **Pod를 삭제했다고 해서 Service가 자동으로 함께 삭제되는 것은 아니라는 점**입니다. 둘은 별도의 Kubernetes 리소스이므로 불필요한 Service나 포트 노출은 별도로 정리해야 합니다.

→ 왜 배우나·현업 활용: 테스트 Pod를 삭제했는데도 포트가 계속 열려 있거나 오래된 Service가 남아 트래픽이 잘못 연결되는 문제를 방지하기 위해 배웁니다.

# 18. Kubernetes에서 상태를 확인하는 기본 흐름

수업에서는 다음과 같은 확인 흐름을 반복했습니다.

```text
Pod 생성
    ↓
Pod 목록 확인
    ↓
상세 정보 확인(describe)
    ↓
로그 확인
    ↓
필요하면 Pod 내부 셸 접속
    ↓
포트 포워딩 또는 Service 생성
    ↓
웹 브라우저에서 접속 확인
```

### 이해 보충: 일반적인 명령 예시

```bash
kubectl get pods
kubectl describe pod hello
kubectl logs hello
kubectl exec -it hello -- /bin/sh
```

- **실행 위치:** Kubernetes/K3s가 구성된 Ubuntu 터미널
- **`get pods`:** Pod 이름, 상태, 재시작 횟수 등 확인
- **`describe`:** 이미지, 이벤트, 상태, 컨테이너 정보 등 상세 확인
- **`logs`:** 애플리케이션이 출력한 로그 확인
- **`exec`:** 실행 중인 Pod 내부 셸에 들어가 파일이나 프로세스 상태 확인

> 정확한 명령 옵션은 수업 자료와 실제 K3/K3s 환경을 기준으로 확인해야 합니다.

→ 왜 배우나·현업 활용: 웹 서비스가 접속되지 않을 때 Pod가 죽었는지, 이미지 실행이 실패했는지, 애플리케이션 로그에 오류가 있는지 단계적으로 진단하기 위해 배웁니다.

# 19. Port Forward와 NodePort의 차이

오늘 수업에서는 Pod에 접근하기 위한 방법으로 포트 포워딩과 NodePort가 언급되었습니다.

| 구분 | Port Forward | NodePort |
|---|---|---|
| 목적 | 임시 테스트용 접근 | 노드의 특정 포트로 서비스 노출 |
| 접근 범위 | 보통 실행한 개발 환경 중심 | 노드 주소 + 지정된 포트로 접근 |
| 사용 상황 | 빠른 동작 확인, 디버깅 | 외부에서 Service 접근 테스트 |
| 특징 | 명령을 종료하면 연결도 끝날 수 있음 | Service 리소스로 관리됨 |

수업에서는 `hello` Pod의 80번 포트를 바깥의 8080 포트로 연결하는 포트 포워딩 예와, Product API의 8000번 포트를 NodePort를 통해 외부에 노출하는 흐름을 설명했습니다.

> 녹취에는 `30074` 같은 예시 포트가 등장하지만, NodePort는 환경에 따라 실제 할당 값이 달라질 수 있으므로 고정값으로 외우면 안 됩니다.

→ 왜 배우나·현업 활용: 개발 중에는 포트 포워딩으로 빠르게 확인하고, 서비스 단위 외부 접근 테스트가 필요할 때는 NodePort 같은 방식을 구분해서 사용하기 위해 배웁니다.

# 20. 오늘 수업에서 배운 가장 중요한 문제 해결 방식

오늘 수업 전체에서 반복된 메시지는 **“작업을 작게 쪼개고, 각 단계가 정상인지 확인한 뒤 다음 단계로 넘어간다”**는 것입니다.

SSH 설정에 너무 오랜 시간이 걸리면 오늘 학습 목표 자체를 놓칠 수 있으므로 Multipass 내부에서 직접 작업하는 다른 경로를 선택하는 것도 실무적인 판단입니다. 도구를 완벽하게 세팅하는 것보다 **현재 해결해야 할 핵심 문제를 잃지 않는 것**이 중요하다는 의미입니다.

→ 왜 배우나·현업 활용: 특정 개발 도구 설정 문제에 과도하게 시간을 쓰지 않고 우회 경로를 사용해 서비스 장애 대응이나 배포 같은 핵심 업무를 먼저 완료하기 위해 배웁니다.

# 21. 오늘 한 것 요약

1. **Windows ↔ Ubuntu 작업 방식**  
   SSH로 Linux에 접속하고, 문제가 있으면 Multipass 내부 작업이나 폴더 공유 같은 대체 방식을 사용할 수 있음을 확인했습니다.

2. **Python 리포트 프로그램을 Docker 이미지로 만드는 흐름**  
   CSV → pandas → `report.py` → `report.html` → `requirements.txt` → Dockerfile 순서로 실행 환경을 구성했습니다.

3. **멀티 컨테이너와 Docker Compose**  
   한 번 실행되고 종료되는 report 작업과 계속 실행되어야 하는 Nginx 웹 서비스를 역할별로 분리하고, Volume으로 결과 파일을 공유하는 구조를 학습했습니다.

4. **Docker 이미지 이동**  
   이미지를 TAR 파일로 저장한 뒤 다른 환경에서 다시 불러오거나, 컨테이너 내부 파일을 호스트로 꺼내는 방법의 목적을 배웠습니다.

5. **Kubernetes/K3 계열 기초**  
   Pod, Service, 로그, 내부 셸 접속, 포트 포워딩, NodePort의 기본 역할을 살펴보고 Docker보다 더 큰 규모의 컨테이너 운영이 왜 필요한지 연결했습니다.

### 오늘 수업을 관통하는 결론

**애플리케이션을 작은 역할 단위로 분리하고, 각 단계를 검증하면서 컨테이너화한 뒤, 규모가 커지면 Kubernetes 같은 오케스트레이션 도구로 운영 범위를 확장하는 것이 오늘 수업의 핵심입니다.**

3. 복사된 폴더 구조 확인
4. 임시 컨테이너 삭제

**확인할 것:** `docker create`와 `docker run`의 차이를 설명해 보세요.

### 실습 3 — 장애 위치 찾기 연습

아래 상황을 가정해 순서를 말해 보세요.

> “브라우저에서 report.html이 보이지 않는다.”

확인 순서 예시:

```text
CSV 존재 여부
→ report.py 단독 실행
→ report.html 생성 여부
→ out 볼륨 연결 여부
→ Nginx 실행 여부
→ 포트 매핑 여부
→ 브라우저 접근
```

# 25. 예상 면접 질문과 답변

## Q1. 왜 여러 기능을 하나의 Docker 컨테이너에 넣지 않고 분리했나요?

**답변:**  
기능을 분리하면 한 서비스의 수정이나 장애가 다른 서비스에 미치는 영향을 줄일 수 있습니다. 예를 들어 Python 리포트 코드만 수정했다면 Nginx까지 다시 빌드하지 않고 report 컨테이너만 변경할 수 있어서 배포와 장애 대응 범위를 줄일 수 있습니다.

---

## Q2. 컨테이너가 종료되어 있으면 무조건 장애인가요?

**답변:**  
아닙니다. 컨테이너 안의 프로세스 목적에 따라 다릅니다. CSV를 읽고 HTML을 만든 뒤 끝나는 배치 작업은 정상적으로 종료될 수 있지만, Nginx 같은 웹 서버는 계속 요청을 받아야 하므로 종료되면 문제일 가능성이 높습니다.

---

## Q3. Docker Volume을 사용하는 이유는 무엇인가요?

**답변:**  
컨테이너의 파일 시스템은 컨테이너가 삭제되면 함께 사라질 수 있기 때문에 중요한 데이터나 결과 파일을 외부에 유지하려면 Volume이 필요합니다. 또한 오늘 실습처럼 report 컨테이너가 만든 HTML을 Nginx 컨테이너가 사용하도록 같은 폴더를 공유할 때도 사용할 수 있습니다.

---

## Q4. Docker와 Kubernetes의 차이를 설명해 주세요.

**답변:**  
Docker는 애플리케이션을 이미지로 만들고 컨테이너로 실행하는 데 초점이 있습니다. Kubernetes는 컨테이너가 많아졌을 때 Pod 배치, 서비스 연결, 재시작, 확장 같은 운영을 자동화하기 위한 오케스트레이션 도구입니다.

---

## Q5. 웹 서비스에 접속되지 않는다면 어떤 순서로 확인하시겠습니까?

**답변:**  
먼저 컨테이너나 Pod가 실행 중인지 확인하고, 애플리케이션 로그에 오류가 있는지 확인하겠습니다. 그다음 서비스 포트와 Volume 또는 네트워크 연결을 확인하고, 마지막으로 외부에서 접근하는 주소와 포트가 올바른지 단계적으로 확인하겠습니다.

# 26. 최종 정리

오늘은 개별 Docker 명령을 외우는 것보다 **“하나의 애플리케이션을 어떤 단위로 분리할 것인가”**, **“각 단위의 실행 결과를 어떻게 검증할 것인가”**, **“그 컨테이너를 다른 환경으로 어떻게 옮길 것인가”**, **“컨테이너가 많아졌을 때 어떻게 운영할 것인가”**를 연결해서 이해하는 것이 중요했습니다.

특히 다음 문장을 말로 설명할 수 있으면 오늘 수업의 핵심을 잘 잡은 것입니다.

> **Docker는 애플리케이션을 독립적인 실행 단위로 만들고, Compose는 여러 컨테이너의 관계를 정의하며, Kubernetes는 많은 컨테이너를 지속적으로 운영하고 관리하기 위한 단계로 이어진다.**
