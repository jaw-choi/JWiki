오늘 수업에서는 프론트엔드, 백엔드, 데이터 엔지니어, 클라우드 엔지니어처럼 여러 직군이 나왔습니다.

예를 들어 백엔드 개발자가 프로그램을 하나 만들어 전달했다고 해도 코드만 받으면 끝나는 것이 아닙니다.

그래서 앞으로 새로운 프로그램을 보게 되면 코드부터 보는 것이 아니라 먼저

```text
이 프로그램을 실행하려면
무엇이 필요한가?
```

를 생각해야겠다고 이해했습니다.

# 2. 다른 개발자와 협업할 때 무엇을 확인해야 하는지도 이해했다

수업에서는 단순히 직군의 역할만 본 것이 아니라 **클라우드 엔지니어가 다른 개발자로부터 어떤 정보를 받아야 하는지**도 확인했습니다.

### 프론트엔드 프로그램을 받았다면

단순히 React 프로젝트를 받는 것으로 끝나는 것이 아닙니다.

```text
어떤 프레임워크인가?
        ↓
Node.js 버전은?
        ↓
어떻게 설치하고 빌드하는가?
        ↓
빌드 결과는 어디에 생성되는가?
        ↓
어떤 API 서버와 연결되는가?
        ↓
환경변수는 무엇인가?
        ↓
정적 웹인가? SSR인가?
        ↓
어떻게 배포할 것인가?
```

를 확인해야 합니다.

### 백엔드 프로그램을 받았다면

특히 중요한 것은 다음과 같습니다.

```text
실행환경
+ 실행방법
+ Port
+ Network
+ DB
+ 환경변수
+ 보안
+ Monitoring
```

예를 들어 백엔드가 `8080` 포트에서 실행된다면 Load Balancer나 방화벽에서도 이 구조를 고려해야 합니다.

### 데이터 시스템을 운영한다면

데이터에서는 프로그램이 실행되는 것만큼

```text
데이터가 어디서 오는가?
얼마나 많은가?
실시간인가? 주기적으로 처리하는가?
어디에 저장하는가?
실패하면 다시 실행할 수 있는가?
중복 데이터가 발생하지 않는가?
백업은 되어 있는가?
```

같은 문제가 중요합니다.

특히 가장 기억할 질문은

> **처리 과정이 실패했을 때 데이터가 사라지거나 중복되지 않는가?**

입니다.

즉 클라우드에서는 단순히 "서버가 켜져 있는가"만 보는 것이 아니라 **프로그램과 데이터가 안정적으로 계속 동작할 수 있는지**까지 봐야 합니다.

# 4. 웹페이지를 만드는 것과 서버에 띄우는 것은 다르다는 것을 이해했다

수업에서 `index.html` 파일과 다음 명령을 사용했습니다.

```bash
python -m http.server 8000
```

처음에는 HTML 파일이 있는데 왜 서버를 또 실행해야 하는지 헷갈렸습니다.

이번 수업을 통해 다음과 같이 이해했습니다.

```text
index.html 작성
→ 웹페이지를 만드는 것

python -m http.server 8000 실행
→ 만든 웹페이지를 HTTP로 제공하는 것
```

즉,

**웹페이지 제작과 웹페이지 서비스는 다른 작업입니다.**

그리고 `8000`은 서버의 종류를 나타내는 번호가 아니라 **Port 번호**입니다.

```text
localhost
= 내 컴퓨터

localhost:8000
= 내 컴퓨터의 8000번 포트에서 실행 중인 프로그램
```

서버가 실행되고 브라우저가 접속하면

```text
Browser
   ↓
GET /
   ↓
Python HTTP Server :8000
   ↓
index.html
   ↓
Browser에 표시
```

됩니다.

여기서 사용한 `python -m http.server`는 실습용 간이 서버이고 실제 운영 서버와는 구분해야 합니다.

# 5. Python이 웹을 사용하는 방법도 두 가지로 구분할 수 있었다

Python에서 웹과 관련된 코드를 봤는데, 처음에는 모두 비슷해 보였습니다.

하지만 역할이 다릅니다.

### 브라우저를 여는 경우

```python
import webbrowser

webbrowser.open("https://www.google.com")
```

이 코드는 **사용자의 브라우저를 실행하는 것**입니다.

### Python 프로그램이 직접 요청하는 경우

```python
import requests

response = requests.get("https://example.com")
print(response.status_code)
print(response.text)
```

이 경우에는 Python 프로그램 자체가 서버에 HTTP 요청을 보냅니다.

그래서

```text
Python
 ↓
HTTP Request
 ↓
Web Server
 ↓
HTML / JSON Response
```

의 구조가 됩니다.

앞으로 API를 사용할 때는 브라우저가 아니라 대부분 이러한 **HTTP 요청 방식**을 사용한다고 생각하면 될 것 같습니다.

# 6. 정적 웹과 동적 웹의 차이를 이해했다

정적 웹은

```text
HTML 파일
→ Web Server
→ 사용자
```

처럼 이미 만들어진 파일을 그대로 전달합니다.

반면 동적 웹은

```text
사용자 요청
→ Backend
→ Database
→ 데이터 처리
→ 결과 생성
→ 사용자
```

의 과정을 거칩니다.

예를 들어 상품 소개 HTML을 그대로 보여주면 정적 웹에 가깝습니다.

하지만

```text
GET /products/100
```

이라는 요청이 들어왔을 때 DB에서 100번 상품을 찾아 결과를 만들어 준다면 동적 웹입니다.

이것을 이해하고 나니 Flask, Django, FastAPI 같은 서버 프로그램을 왜 사용하는지도 조금 명확해졌습니다.

**사용자의 요청에 따라 Python 프로그램을 실행해야 하기 때문입니다.**

# 7. 데이터도 단순히 CSV와 JSON으로만 나누는 것이 아니었다

클라우드에서는 데이터를 크게 세 가지 형태로 생각할 수 있었습니다.

```text
정형 데이터
→ SQL / CSV

반정형 데이터
→ JSON / XML / Log

비정형 데이터
→ 이미지 / 영상 / 음성 / 문서
```

여기서 중요한 것은 분류 이름을 외우는 것이 아니라 **데이터의 특성이 달라지면 저장 방법과 처리 방법도 달라진다**는 것입니다.

예를 들어

```text
회원 / 주문 데이터
→ RDS

상품 이미지
→ S3

로그
→ CloudWatch / S3

실시간 데이터
→ Kinesis

대량 분석 데이터
→ S3 + Glue + Athena / Redshift
```

처럼 사용할 수 있습니다.

그래서 앞으로 AWS 서비스를 볼 때도

```text
AWS 서비스 이름을 외운다
```

보다

```text
어떤 데이터를 처리하려는가?
        ↓
그 데이터의 특성은 무엇인가?
        ↓
어디에 저장해야 하는가?
        ↓
어떤 AWS 서비스를 사용하면 되는가?
```

순서로 보는 것이 이해하기 좋을 것 같습니다.

# 8. 데이터 종류에 따라 컴퓨터 자원 사용도 달라진다는 것을 이해했다

어제 수업의 중요한 내용 중 하나는

> **Data 종류에 따라 CPU, Memory, Storage, Network 사용량이 달라진다.**

는 것이었습니다.

처음에는 CSV, JSON, Array, API를 단순히 데이터 형식의 차이로 생각했습니다.

하지만 시스템을 운영하는 입장에서는 각각 어떤 자원을 사용하는지도 봐야 합니다.

```text
CSV
→ 파일 읽기
→ Disk와 CPU

JSON
→ 파일 읽기 + 구조 분석
→ CPU / Memory

Array
→ 데이터를 Memory에 올리고 계산
→ Memory

API
→ 다른 서버와 통신
→ Network + CPU

이미지 / 영상
→ 큰 파일
→ Storage + Network

Log
→ 계속 생성
→ Storage + I/O
```

따라서 앞으로 데이터를 볼 때는

```text
어떤 데이터인가?
        ↓
어디에 있는가?
        ↓
어떻게 읽는가?
        ↓
CPU / Memory / Disk / Network 중
무엇을 많이 사용하는가?
```

까지 생각해야겠다고 이해했습니다.

```text
최대 Python Memory

파일 크기
```

를 측정했습니다.

결과는

```text
logs/resource_log.csv
```

에 기록했습니다.

여기에서 이해한 것은

> **성능은 느낌으로 판단하는 것이 아니라 실제로 여러 번 측정하고 비교해야 한다.**

는 것입니다.

단순히 CSV만 보는 것이 아니라 Streamlit으로 데이터 조회 화면도 만들어 봤습니다.

구조는

```text
data.csv
   ↓
Python
   ↓
Streamlit
   ↓
localhost:8501
   ↓
```

였습니다.

화면에서는 장비 데이터를 표로 보고, 상태별로 필터링하고, 몇 건을 조회했는지 확인했습니다.

즉 Streamlit 자체를 배우는 것도 있지만 이번 실습에서는 **데이터 처리 결과와 성능 차이를 눈으로 확인하기 위한 도구**라는 의미가 더 컸다고 이해했습니다.

# 11. Cache를 왜 사용하는지 실제 숫자로 이해했다

Cache가 없다면

```text
요청
→ 파일 다시 읽기
→ 계산
→ 결과
```

를 반복합니다.

Cache를 사용하면

```text
첫 요청
→ 파일 읽기
→ 계산
→ Cache 저장

다음 요청
→ 저장된 결과 사용
```

이 가능합니다.

실제 실습에서는

```text
Cache 미사용 평균 : 8.40 ms
Cache 사용 평균   : 2.36 ms
```

였습니다.

그래서 Cache는

**반복해서 수행하는 파일 읽기나 계산을 줄이기 위해 이전 결과를 재사용하는 방법**

이라고 이해했습니다.

하지만 데이터가 변경되었는데 Cache가 남아 있다면 오래된 데이터를 보여줄 수도 있습니다.

따라서 앞으로 Cache를 볼 때는

```text
언제 저장하는가?
언제 다시 사용하는가?
언제 삭제하는가?
언제 새로 갱신하는가?
```

까지 생각해야 합니다.

# 12. SQL을 배우는 이유도 연결됐다

CSV와 JSON은 파일 형태로 데이터를 저장할 수 있습니다.

하지만 데이터가 많아지고 특정 조건의 데이터만 가져와야 한다면 파일을 계속 직접 읽는 것은 불편해집니다.

그래서 Database와 SQL을 사용합니다.

예를 들어

```sql
SELECT *
FROM orders
WHERE user_id = 100;
```

이라고 하면 전체 주문 중 특정 사용자의 주문만 가져올 수 있습니다.

즉 SQL은 새로운 문법을 외우는 것보다

**많은 데이터 중에서 원하는 데이터를 찾아오기 위한 방법**

이라고 이해했습니다.

우선 확실히 알아야 할 것은

```text
Table
Row
Column
Primary Key
SELECT
WHERE
ORDER BY
JOIN
```

정도라고 생각했습니다.

# 13. Codex는 직접 코딩을 대신하는 것보다 일을 맡기는 방식이 중요했다

수업에서는 Python 기초나 CSV, JSON처럼 내가 이해해야 할 부분은 직접 작성하고 규모가 커지는 작업은 Codex에 작업지시서를 주는 방식도 사용했습니다.

구조는 다음과 같습니다.

```text
사람
 ↓
목표 정의
 ↓
조건 정의
 ↓
TASK.md 작성
 ↓
Codex
 ↓
파일 확인
 ↓
코드 / SQL 작성
 ↓
실행
 ↓
오류 수정
 ↓
테스트
 ↓
결과 보고
```

예를 들어 단순히

```text
SQLite 만들어줘
```

라고 요청하는 것이 아니라

```text
목표
→ SQLite DB 생성

테이블
→ products

필드
→ id / name / price / stock

작업
→ DB 생성
→ CSV 입력
→ 전체 조회
→ 가격순 조회
→ 결과 검증
```

처럼 작업 조건을 명확하게 주는 것입니다.

이것을 통해 AI를 사용할 때도 결국 중요한 것은

> **사람이 목표와 조건을 얼마나 명확하게 정의하는가**

라는 것을 이해했습니다.

# 20. 수업 내용을 설명할 수 있는지도 확인해야 한다

이번 내용을 제대로 이해했다면 단순히 코드를 실행하는 것뿐 아니라 다음 질문에 **내 말로 간단히 설명할 수 있어야 합니다.**

### 1. `python -m http.server 8000`은 무엇인가?

Python의 기본 `http.server` 모듈을 이용해 현재 폴더의 파일을 **8000번 포트로 제공하는 간단한 웹 서버**를 실행하는 명령입니다.  
실습용으로 적합하며 실제 운영 서버용으로 사용하는 것은 적절하지 않습니다.

---

### 2. localhost와 Port는 무엇인가?

`localhost`는 **현재 내가 사용하고 있는 컴퓨터 자신**을 의미합니다.  
Port는 한 컴퓨터 안에서 여러 프로그램을 구분하기 위한 번호이며, `localhost:8000`은 내 컴퓨터의 8000번 포트에 접속한다는 뜻입니다.

---

### 3. 정적 웹과 동적 웹의 차이는 무엇인가?

정적 웹은 미리 만들어진 HTML 같은 파일을 그대로 사용자에게 전달합니다.  
동적 웹은 사용자의 요청에 따라 Backend나 DB를 실행하여 새로운 결과를 만들어 전달합니다.

```text
정적
HTML → 사용자

동적
사용자 → Backend → DB → 결과 → 사용자
```

---

### 4. CSV와 JSON의 차이는 무엇인가?

CSV는 행과 열 중심의 **단순한 표 데이터**를 저장하기 좋습니다.  
JSON은 객체와 배열을 사용해 중첩된 구조를 표현할 수 있어 **API에서 데이터를 주고받을 때 많이 사용**합니다.

---

### 5. Streamlit을 사용한 이유는 무엇인가?

Python으로 처리한 데이터를 복잡한 웹 개발 없이 **빠르게 웹 화면으로 확인하기 위해 사용**했습니다.  
이번 실습에서는 CSV 데이터 조회, 필터링, 실행시간과 Cache 결과 확인에 사용했습니다.

---

### 6. Cache란 무엇이며 왜 사용했나요?

Cache는 한 번 처리한 결과를 저장해두었다가 같은 작업이 다시 필요할 때 **기존 결과를 재사용하는 방법**입니다.  
반복적인 파일 읽기나 계산을 줄여 처리 시간을 단축할 수 있습니다.

---

### 7. Cache 적용 전후 성능 차이는 어땠나요?

실습에서는 Cache 미사용 시 평균 **8.40ms**, Streamlit Cache 사용 시 평균 **2.36ms**가 측정되었습니다.  
따라서 반복해서 데이터를 읽을 때 Cache를 사용한 경우 처리 시간이 감소했습니다.

---

### 8. 왜 성능 측정을 여러 번 했나요?

한 번의 실행 결과는 컴퓨터 상태나 다른 프로그램의 영향으로 달라질 수 있습니다.  
그래서 여러 번 측정한 뒤 평균을 확인하면 한 번의 결과보다 **더 신뢰할 수 있는 성능 비교**를 할 수 있습니다.

---

### 9. 이 프로그램을 AWS에 올리려면 무엇부터 확인해야 하나요?

먼저 프로그램의 **실행환경, 실행방법, Port, 환경변수, DB, CPU와 Memory 요구량** 등을 확인해야 합니다.  
그 후 프로그램의 특성에 맞는 EC2, ECS, S3, RDS 등의 서비스를 선택합니다.

---

### 10. 서버 장애 발생 시 어떤 순서로 확인하시겠습니까?

먼저 서비스가 실제로 실행 중인지 확인하고, 그다음 **CPU·Memory·Network와 로그**를 확인합니다.  
이후 DB나 외부 API 등 연결된 서비스까지 확인하면서 장애 범위를 좁혀갑니다.

```text
서비스 상태
   ↓
CPU / Memory
   ↓
Network / Port
   ↓
Log
   ↓
DB / 외부 서비스
```

---

### 11. 프론트 개발자에게 무엇을 받아야 하나요?

사용 프레임워크와 Node.js 버전, 설치·빌드 방법, 빌드 결과물 위치, API 주소와 환경변수 등을 확인해야 합니다.  
또한 정적 웹인지 SSR인지와 배포 방법도 확인해야 합니다.

---

### 12. 백엔드 개발자에게 무엇을 받아야 하나요?

사용 언어와 Runtime 버전, 실행 명령, Port, 환경변수, DB와 외부 서비스 정보를 받아야 합니다.  
운영을 위해 로그 위치, Health Check, Docker 사용 여부, CPU와 RAM 요구량도 확인해야 합니다.

---

### 13. 데이터 엔지니어에게 무엇을 확인해야 하나요?

데이터가 어디에서 오는지, 데이터 양은 어느 정도인지, Batch인지 Streaming인지, 어디에 저장되는지를 확인해야 합니다.  
또한 실패했을 때 재처리가 가능한지와 **데이터가 사라지거나 중복되지 않는지**도 중요합니다.

---

### 14. AI 프로그램 배포 시 CPU/GPU를 어떻게 판단하나요?

먼저 프로그램이 일반적인 데이터 처리 중심인지, AI 모델의 학습·추론처럼 많은 병렬 연산이 필요한지를 확인해야 합니다.  
일반적인 Python/API 작업은 CPU부터 검토하고, 큰 AI 모델의 학습이나 고성능 추론이 필요하다면 GPU 사용을 검토합니다.

---

## 실습을 한 문장으로 설명한다면
