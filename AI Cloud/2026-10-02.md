# Part 1. Kubernetes 모니터링과 운영

## 2. 왜 Kubernetes에서 모니터링이 필요한가

Kubernetes에서는 하나의 프로그램만 실행하는 것이 아니라 여러 Pod, Deployment, Service 같은 리소스가 동시에 동작합니다. 따라서 운영자는 단순히 “프로그램이 켜져 있는가”만 보는 것이 아니라 CPU·메모리 사용량, 컨테이너 상태, 요청량, 오류 발생 여부 등을 계속 확인해야 합니다.

수업에서는 Kubernetes 안의 모니터링 관련 모듈들이 실행 중인지 확인하고, 최종적으로 Grafana 대시보드 형태로 상태를 확인하는 흐름을 살펴보았습니다.

Grafana는 수집된 데이터를 사람이 보기 쉬운 그래프와 대시보드로 표현하는 도구입니다. Grafana 자체가 모든 데이터를 직접 수집한다기보다, 일반적으로 다른 모니터링 시스템이 수집한 데이터를 시각화하는 역할을 맡습니다.

**[추가 설명]** Kubernetes에서는 흔히 Prometheus가 메트릭을 수집하고 Grafana가 이를 시각화하는 조합을 많이 사용합니다. 다만 오늘 녹취에서는 Grafana 중심으로 설명되었으며 Prometheus 실습 여부는 명확하지 않습니다.

→ **왜 배우나·현업 활용:** 여러 컨테이너와 서비스 중 어느 부분에서 장애나 자원 부족이 발생했는지 빠르게 확인하여, 실제 Kubernetes 운영 환경에서 원인 분석과 장애 대응을 하기 위해 배웁니다.

## 3. Grafana를 단순한 그래프 도구가 아니라 운영 도구로 보기

수업에서 중요한 포인트는 Grafana 화면 자체를 외우는 것이 아니라, **“운영 중인 시스템의 상태를 한눈에 판단할 수 있는가”**입니다.

예를 들어 다음과 같은 질문에 답할 수 있어야 합니다.

- 특정 서버나 Pod의 CPU 사용량이 갑자기 증가했는가?
- 메모리 사용량이 지속적으로 증가하는가?
- 특정 시간대에 오류가 집중되는가?
- 서비스가 정상적으로 실행 중인가?
- 배포 이후 성능이 이전보다 나빠졌는가?

대규모 프로덕션 환경에서는 사람이 서버 하나씩 접속해서 확인하기 어렵기 때문에 대시보드와 알림 시스템이 중요합니다.

→ **왜 배우나·현업 활용:** 여러 서버와 컨테이너의 상태를 직접 접속하지 않고 통합해서 확인하여, 운영 엔지니어가 장애 징후를 조기에 발견하고 대응하기 위해 배웁니다.

## 4. 서비스 테스트를 AI 에이전트로 자동화하는 아이디어

수업에서는 HTML로 제공된 작업 지시를 코딩 에이전트가 읽고 필요한 테스트를 수행할 수 있는지 고민해 보라는 내용이 있었습니다.

즉 다음 흐름을 사람이 모두 수행하지 않고 자동화하는 방향입니다.

```text
서비스 목록 확인
    ↓
각 서비스 상태 검사
    ↓
문제 여부 판별
    ↓
로그·메트릭 확인
    ↓
이상 항목 정리
    ↓
리포트 생성
```

이 방식은 단순 챗봇이 질문에 답하는 것보다 한 단계 더 나아간 형태입니다. 에이전트가 실제 시스템 상태를 확인하고, 명령을 실행하고, 결과를 해석하여 보고서를 만드는 구조입니다.

다만 운영 환경에서는 에이전트에 무제한 권한을 주면 위험합니다. 조회 전용 권한, 실행 가능한 명령 제한, 변경 작업 승인 절차 등을 함께 설계해야 합니다.

→ **왜 배우나·현업 활용:** 반복적인 상태 점검과 리포트 작성 작업을 자동화하여, SRE·DevOps 환경에서 사람이 장애 판단과 의사결정에 집중할 수 있도록 하기 위해 배웁니다.

## 5. Helm의 역할

녹취에서 음성 인식상 “필름”으로 기록된 부분은 문맥상 **Helm**을 의미하는 것으로 보입니다. **[확인 필요]**

Helm은 Kubernetes에서 여러 리소스를 하나의 패키지처럼 관리할 수 있게 도와주는 도구입니다. Kubernetes 서비스를 직접 설치하려면 Deployment, Service, ConfigMap 등 여러 YAML 파일을 관리해야 할 수 있는데, Helm은 이러한 구성을 Chart라는 단위로 묶어 설치·업데이트할 수 있게 합니다.

개념적으로는 다음과 같습니다.

```text
여러 Kubernetes YAML
        ↓
   Helm Chart로 묶음
        ↓
한 번의 설치/업데이트 작업
```

수업에서는 Grafana 같은 서비스를 Kubernetes 환경에 설치하고 운영할 때 Helm을 활용하는 흐름을 살펴보는 것이 목적이었습니다.

→ **왜 배우나·현업 활용:** 여러 Kubernetes 리소스를 반복해서 수동 배포하지 않고 패키지화하여, 실제 개발·운영 환경에서 동일한 애플리케이션을 일관되게 설치하고 업그레이드하기 위해 배웁니다.

# Part 2. 데이터베이스가 필요한 이유

## 7. 실시간 데이터와 집계 데이터의 요구사항이 다르다

수업에서는 모든 데이터를 같은 방식으로 처리하면 데이터베이스 부하가 커질 수 있다는 점을 설명했습니다.

예를 들어 쇼핑몰을 생각하면 다음 두 요청은 성격이 다릅니다.

### 실시간성이 중요한 요청

- 현재 상품 재고가 몇 개인가?
- 주문이 정상적으로 등록되었는가?
- 사용자의 장바구니에는 무엇이 들어 있는가?

### 즉시 갱신될 필요가 상대적으로 낮은 요청

- 서울 지역의 하루 총매출은 얼마인가?
- 지난달 카테고리별 판매량은 얼마인가?
- 월별 매출 추이는 어떠한가?

두 종류의 작업을 모두 운영 DB에 무겁게 수행하면 실시간 요청의 응답 속도까지 느려질 수 있습니다. 따라서 규모가 커지면 운영용 데이터와 분석·집계용 데이터를 분리하거나 별도의 저장소와 파이프라인을 구성하기도 합니다.

**[추가 설명]** 실제 현업에서는 OLTP(온라인 트랜잭션 처리)와 OLAP(온라인 분석 처리)의 요구사항이 다르다고 설명합니다. 오늘 수업은 이 차이를 개념적으로 이해하는 단계였습니다.

→ **왜 배우나·현업 활용:** 실시간 주문 처리와 대규모 통계 분석이 서로 성능을 방해하지 않도록 데이터 처리 목적을 구분하여, 서비스 성능과 분석 성능을 함께 확보하기 위해 배웁니다.

# Part 3. SQL 기본 조회 문법

## 8. SELECT 문을 구성하는 주요 요소

수업에서는 SQL 조회에서 자주 사용하는 요소를 다음과 같이 다뤘습니다.

| 요소 | 역할 | 예시 상황 |
|---|---|---|
| `SELECT` | 어떤 열을 볼지 지정 | 이름과 가격만 조회 |
| `FROM` | 어떤 테이블에서 가져올지 지정 | 메뉴 테이블 조회 |
| `WHERE` | 행에 조건 지정 | 가격이 5,000원 이상 |
| `GROUP BY` | 같은 기준으로 묶음 | 지역별 매출 집계 |
| `HAVING` | 그룹화 결과에 조건 지정 | 매출 합계가 일정 금액 이상인 지역 |
| `ORDER BY` | 결과 정렬 | 가격이 높은 순 |
| `ASC` | 오름차순 | 작은 값 → 큰 값 |
| `DESC` | 내림차순 | 큰 값 → 작은 값 |
| `LIMIT` | 일부 행만 조회 | 상위 10개 확인 |

### 예시

```sql
SELECT menu_name, unit_price
FROM menu
ORDER BY unit_price DESC
LIMIT 10;
```

- **실행 위치:** MySQL에 접속한 뒤 `mysql>` 프롬프트
- **목적:** 가격이 높은 메뉴부터 최대 10개 확인
- **주요 옵션:** `DESC`는 내림차순, `LIMIT 10`은 최대 10행
- **예상 결과:** 조건에 맞는 메뉴 이름과 가격이 최대 10행 출력
- **해석:** 첫 행에 가까울수록 가격이 높은 데이터

대규모 테이블에서 무조건 전체 행을 출력하면 결과가 매우 많아질 수 있으므로 확인 단계에서는 `LIMIT`을 적극적으로 사용하는 것이 좋습니다.

→ **왜 배우나·현업 활용:** 필요한 데이터만 조건·정렬·집계하여 가져오고, 실제 운영 DB에서 불필요한 전체 조회를 줄이기 위해 배웁니다.

# Part 4. 기본키, 외래키와 데이터 무결성

## 9. 기본키(Primary Key)와 개체 무결성

기본키는 테이블의 각 행을 유일하게 식별하기 위한 값입니다.

기본키는 일반적으로 다음 조건을 지켜야 합니다.

1. 중복될 수 없습니다.
2. `NULL`일 수 없습니다.

예를 들어 고객 이름을 기본키로 사용하면 동명이인이 있을 수 있기 때문에 적절하지 않습니다. 대신 회원번호, 주문번호, 계좌번호처럼 각 레코드를 유일하게 구분할 수 있는 값이 필요합니다.

이를 **개체 무결성(Entity Integrity)**과 연결해서 이해할 수 있습니다.

→ **왜 배우나·현업 활용:** 한 행을 정확히 식별하여, 특정 주문 수정이나 사용자 조회 시 다른 사람의 데이터를 잘못 변경하는 문제를 막기 위해 배웁니다.

## 10. 외래키(Foreign Key)와 참조 무결성

외래키는 다른 테이블의 기본키 또는 고유한 값을 참조하는 열입니다.

수업의 예시는 다음 구조였습니다.

```text
Manager
- manager_id (PK)
- name
- position

Category
- category_id (PK)
- category_name
- manager_id (FK → Manager.manager_id)
```

조건은 다음과 같습니다.

- 한 명의 매니저가 여러 카테고리를 담당할 수 있음
- 하나의 카테고리는 한 명의 매니저가 담당

따라서 관계는 다음과 같습니다.

```text
Manager 1 ───── N Category
```

`Category.manager_id`에 존재하지 않는 매니저 번호를 넣으면 외래키 제약조건 때문에 입력이 거부될 수 있습니다.

→ **왜 배우나·현업 활용:** 주문·회원·상품처럼 서로 연결된 테이블에서 존재하지 않는 데이터를 참조하지 못하게 하여, 데이터 관계가 깨지는 문제를 방지하기 위해 배웁니다.

## 11. ON UPDATE / ON DELETE 규칙

외래키를 만들 때 부모 데이터가 변경되거나 삭제될 경우 자식 데이터를 어떻게 처리할지 규칙을 정할 수 있습니다.

대표적인 방식은 다음과 같습니다.

| 규칙 | 의미 |
|---|---|
| `CASCADE` | 부모 변경/삭제를 자식에도 반영 |
| `RESTRICT` / `NO ACTION` | 자식이 참조 중이면 부모 변경/삭제 제한 |
| `SET NULL` | 부모가 삭제되면 자식 외래키를 `NULL`로 변경 |

수업에서는 카테고리가 특정 매니저를 참조 중이라면 해당 매니저를 쉽게 삭제하지 못하도록 하는 상황을 예로 들었습니다.

또한 퇴사자처럼 더 이상 활동하지 않는 데이터를 무조건 삭제하기보다 상태값이나 이관 정책으로 보존하는 경우가 있다는 운영 관점도 설명했습니다.

→ **왜 배우나·현업 활용:** 부모 데이터를 삭제했을 때 주문이나 카테고리 같은 관련 데이터가 고아 데이터로 남지 않도록, 서비스 정책에 맞는 삭제·변경 규칙을 설계하기 위해 배웁니다.

---

# Part 5. 정규화와 이상 현상

## 12. 왜 테이블을 나누는가 — 이상 현상

하나의 테이블에 서로 다른 종류의 정보를 반복해서 저장하면 데이터가 중복되고 수정 과정에서 문제가 발생할 수 있습니다.

대표적인 이상 현상은 다음과 같습니다.

- **삽입 이상:** 필요한 일부 정보만 추가하려는데 다른 불필요한 정보까지 있어야 입력 가능
- **수정 이상:** 같은 정보가 여러 행에 있어 일부만 수정되고 일부는 예전 값으로 남음
- **삭제 이상:** 한 데이터를 지우면서 보존해야 할 다른 정보까지 함께 사라짐

이를 줄이기 위해 데이터의 역할을 나누어 여러 테이블로 설계하고 관계를 연결합니다.

→ **왜 배우나·현업 활용:** 같은 정보를 여러 곳에서 따로 수정하다 데이터가 서로 달라지는 문제를 줄여, 회원·상품·담당자 정보가 일관되게 유지되도록 하기 위해 배웁니다.

---

## 13. 녹취의 정규화 설명에서 주의할 점

수업 녹취에서는 대략 다음처럼 설명되었습니다.

- 1:N 관계에서 외래키를 넣는 것을 2정규화와 연결
- N:M 관계에서 중간 테이블을 만드는 것을 3정규화와 연결

이 설명은 관계형 설계를 이해하기 위한 직관적인 설명으로 볼 수 있지만, **표준 데이터베이스 이론의 2NF·3NF 정의와 정확히 같지는 않습니다.**

### [추가 설명] 표준 정의

#### 제1정규형(1NF)

한 컬럼에 여러 값을 한꺼번에 넣지 않고 값이 원자적이어야 합니다.

#### 제2정규형(2NF)

1NF를 만족하면서, 복합 기본키를 사용할 경우 일반 속성이 기본키의 일부에만 종속되지 않고 **기본키 전체에 완전 함수 종속**되어야 합니다.

#### 제3정규형(3NF)

2NF를 만족하면서, 기본키가 아닌 일반 속성이 다른 일반 속성을 통해 간접적으로 결정되는 **이행적 종속**을 제거합니다.

### 관계 모델링과 정규화는 연결되어 있지만 같은 말은 아니다

- 1:N 관계 → 보통 N쪽 테이블에 외래키 배치
- N:M 관계 → 중간 연결 테이블 생성

이것은 매우 중요한 관계 설계 방법이지만, 그 자체를 곧바로 “2정규화 = 1:N”, “3정규화 = N:M”이라고 외우면 시험이나 면접에서 틀릴 수 있습니다.

→ **왜 배우나·현업 활용:** 테이블을 단순히 나누는 것이 아니라 데이터 중복과 종속 관계를 기준으로 올바르게 설계하여, 스키마 변경과 데이터 수정 과정의 오류를 줄이기 위해 배웁니다.

---

# Part 6. JOIN — 여러 테이블을 다시 연결해서 보기

## 14. JOIN이 필요한 이유

정규화하여 데이터를 여러 테이블로 나누면 중복은 줄어들지만, 실제 화면에서는 다시 여러 테이블의 정보가 함께 필요합니다.

예를 들어 다음 정보가 각각 나뉘어 있다고 가정합니다.

```text
Menu → 메뉴 이름, 가격, category_id
Category → 카테고리 이름, manager_id
Manager → 담당자 이름, 연락처
```

사용자가 “아메리카노의 카테고리와 담당자 이름을 알려줘”라고 요청하면 세 테이블을 연결해야 합니다.

이때 사용하는 것이 JOIN입니다.

→ **왜 배우나·현업 활용:** 정규화되어 나뉜 주문·상품·회원 데이터를 필요한 순간 다시 연결하여, API 응답이나 관리자 화면에 필요한 정보를 만들기 위해 배웁니다.

---

## 15. 조건 없이 두 테이블을 조회하면 왜 데이터가 폭증하는가

수업에서는 다음과 같이 두 테이블을 조건 없이 함께 조회했을 때 행이 매우 많이 나오는 모습을 확인했습니다.

개념적으로는 다음과 같습니다.

```sql
SELECT A.*, B.*
FROM manager A, category B;
```

조건이 없다면 Manager의 각 행과 Category의 각 행이 모두 조합됩니다.

예를 들어:

```text
Manager 4명 × Category 3개 = 12개 조합
```

이와 같은 결과를 Cartesian Product(카티션 곱)라고 합니다.

필요한 데이터만 연결하려면 다음처럼 관계 조건을 줘야 합니다.

```sql
SELECT A.*, B.*
FROM manager A, category B
WHERE A.manager_id = B.manager_id;
```

하지만 테이블 연결 목적이라면 명시적인 `JOIN ... ON ...` 구문이 더 읽기 쉽습니다.

→ **왜 배우나·현업 활용:** JOIN 조건을 빠뜨려 데이터 건수가 폭발하거나 서버 부하가 발생하는 실수를 막고, 정확한 관계 데이터만 조회하기 위해 배웁니다.

---

## 16. INNER JOIN과 LEFT JOIN

### INNER JOIN

양쪽 테이블에서 JOIN 조건이 일치하는 행만 보여줍니다.

```sql
SELECT A.name, B.category_name
FROM manager A
INNER JOIN category B
    ON A.manager_id = B.manager_id;
```

담당 카테고리가 없는 매니저는 결과에서 제외될 수 있습니다.

### LEFT JOIN

왼쪽 테이블의 모든 행을 유지하고, 오른쪽에 일치하는 데이터가 없으면 해당 열에 `NULL`이 나옵니다.

```sql
SELECT A.manager_id, A.name, B.category_name
FROM manager A
LEFT JOIN category B
    ON A.manager_id = B.manager_id;
```

이 쿼리는 “현재 카테고리를 담당하지 않는 매니저가 누구인가?” 같은 질문에 사용할 수 있습니다.

### 중요한 해석

`LEFT JOIN`에서 **FROM 뒤에 먼저 적힌 테이블이 왼쪽 기준**입니다.

```text
FROM manager A
LEFT JOIN category B
```

이면 `manager`가 기준입니다.

→ **왜 배우나·현업 활용:** “연결된 데이터만 볼 것인지” 또는 “연결되지 않은 데이터까지 포함할 것인지”를 구분하여, 미할당 사용자·담당자가 없는 업무 같은 예외 상황까지 조회하기 위해 배웁니다.

---

# Part 7. VIEW — 자주 쓰는 복잡한 조회를 재사용하기

## 17. VIEW가 필요한 이유

테이블이 세 개, 네 개 이상 연결되면 매번 긴 JOIN 문장을 작성하는 것이 번거롭습니다.

이때 자주 사용하는 조회문에 이름을 붙여 **VIEW**로 만들 수 있습니다.

개념적으로는 다음과 같습니다.

```sql
CREATE VIEW cafe_view AS
SELECT ...
FROM menu
JOIN category ...
JOIN manager ...;
```

그 이후에는 일반 테이블처럼 다음과 같이 조회할 수 있습니다.

```sql
SELECT * FROM cafe_view;
```

### VIEW의 특징

- 실제 원본 데이터를 복사해서 별도 테이블에 저장하는 일반 VIEW와는 다름
- 조회 SQL의 논리적인 결과를 테이블처럼 사용할 수 있음
- 복잡한 JOIN을 반복해서 작성하지 않아도 됨
- 사용자에게 원본 테이블 전체 권한을 주지 않고 필요한 데이터만 보여주는 데 활용 가능

**[추가 설명]** 일반 VIEW는 보통 실제 조회 결과를 물리적으로 저장하지 않고 정의를 저장합니다. DBMS에 따라 Materialized View라는 별도 개념은 결과를 물리적으로 저장할 수 있습니다.

→ **왜 배우나·현업 활용:** 복잡한 JOIN 결과를 재사용하고 원본 테이블 노출을 줄여, 분석가나 애플리케이션에 필요한 데이터만 간단하고 안전하게 제공하기 위해 배웁니다.

---

## 18. VIEW와 임시 테이블의 차이

| 구분 | VIEW | 임시 테이블 |
|---|---|---|
| 성격 | 저장된 조회 정의 | 실제 임시 데이터 저장 |
| 세션 종료 후 | 정의가 남을 수 있음 | 일반적으로 사라짐 |
| 데이터 | 원본 테이블을 조회 | 별도 데이터를 가짐 |
| 주 용도 | 반복 조회·권한 분리 | 중간 계산 결과 저장 |

수업에서는 VIEW와 임시 테이블의 차이가 시험에서도 자주 나올 수 있는 개념이라고 설명했습니다.

→ **왜 배우나·현업 활용:** 반복적으로 사용하는 조회 결과와 일시적으로 필요한 중간 데이터를 구분하여, 목적에 맞는 저장·조회 방식을 선택하기 위해 배웁니다.

---

# Part 8. 서브쿼리

## 19. 쿼리의 결과를 다시 조건으로 사용하기

서브쿼리(Subquery)는 하나의 SQL 쿼리 안에 다른 SQL 쿼리가 들어가는 구조입니다.

예를 들어 전체 메뉴의 평균 가격보다 비싼 메뉴를 찾고 싶다고 가정합니다.

먼저 평균 가격을 구합니다.

```sql
SELECT AVG(unit_price)
FROM menu;
```

그리고 그 결과보다 가격이 높은 메뉴를 찾습니다.

```sql
SELECT menu_name, unit_price
FROM menu
WHERE unit_price > (
    SELECT AVG(unit_price)
    FROM menu
);
```

안쪽 쿼리가 먼저 평균 가격을 계산하고, 바깥 쿼리가 그 값을 조건으로 사용합니다.

→ **왜 배우나·현업 활용:** “평균보다 높은 상품”, “최대값과 같은 주문”, “특정 집합에 포함되는 사용자”처럼 한 번의 단순 조건으로 표현하기 어려운 조회를 만들기 위해 배웁니다.

---

## 20. 서브쿼리는 항상 느린가?

수업에서는 서브쿼리가 복잡해질수록 속도가 느려질 수 있고 쿼리 튜닝이 필요하다는 점을 강조했습니다.

다만 **“서브쿼리는 항상 JOIN보다 느리다”라고 외우면 안 됩니다.**

**[추가 설명]** 현대 DBMS의 옵티마이저는 서브쿼리를 내부적으로 JOIN과 비슷한 형태로 변환하기도 합니다. 실제 성능은 데이터량, 인덱스, 쿼리 구조, 실행 계획에 따라 달라집니다.

따라서 중요한 것은 문법 모양만 보고 판단하는 것이 아니라 실제 실행 계획과 처리량을 확인하는 것입니다.

→ **왜 배우나·현업 활용:** 대용량 데이터에서 특정 SQL이 왜 느린지 실행 계획과 인덱스를 기준으로 분석하여, API 응답 지연이나 배치 처리 지연을 개선하기 위해 배웁니다.

---

# Part 9. 쿼리 튜닝과 인덱스

## 21. 쿼리 튜닝이란

같은 결과를 반환하는 SQL이라도 작성 방법과 인덱스에 따라 처리 시간이 크게 달라질 수 있습니다.

쿼리 튜닝에서는 주로 다음을 확인합니다.

- 불필요하게 전체 테이블을 읽고 있는가?
- JOIN 순서와 조건이 적절한가?
- 필요한 인덱스가 존재하는가?
- 너무 많은 열을 조회하고 있지 않은가?
- `LIMIT`을 사용할 수 있는가?
- 반복적으로 동일한 계산을 하고 있지 않은가?

대량 데이터에서는 작은 차이가 전체 서비스 응답 시간에 큰 영향을 줄 수 있습니다.

→ **왜 배우나·현업 활용:** 데이터가 수백만 건 이상으로 증가했을 때 SQL 한 문장 때문에 API가 느려지는 원인을 찾아, DB 부하와 사용자 응답 시간을 줄이기 위해 배웁니다.

---

## 22. 인덱스의 역할

인덱스는 책 뒤의 색인과 비슷한 역할을 합니다. 원하는 데이터를 찾기 위해 전체 페이지를 처음부터 읽는 대신, 색인을 통해 위치를 빠르게 찾아갑니다.

예를 들어 지역 기준 조회가 매우 빈번하다면 적절한 인덱스가 조회 성능을 높일 수 있습니다.

하지만 인덱스에도 비용이 있습니다.

- 저장 공간을 추가로 사용함
- INSERT/UPDATE/DELETE 시 인덱스도 갱신해야 함
- 인덱스가 너무 많으면 오히려 쓰기 성능과 관리 비용이 증가함

**[추가 설명]** 녹취에서는 조회할 때 인덱스를 만들었다가 다시 해제하는 흐름처럼 들리는 부분이 있지만, 실제 운영에서는 쿼리마다 인덱스를 생성·삭제하는 방식이 일반적이지 않습니다. 쿼리 패턴과 데이터 분포를 분석해 지속적으로 사용할 인덱스를 설계하는 편이 일반적입니다.

→ **왜 배우나·현업 활용:** 자주 검색하는 조건의 데이터를 빠르게 찾도록 하면서도 쓰기 비용을 고려하여, 실제 서비스의 조회 성능을 최적화하기 위해 배웁니다.

---

# Part 10. COMMIT과 ROLLBACK

## 23. 여러 DB 작업을 하나의 단위로 생각하기

사용자가 상품을 구매한다고 하면 내부적으로는 여러 DB 작업이 연속으로 일어날 수 있습니다.

```text
상품 확인
 → 장바구니 확인
 → 주문 생성
 → 재고 변경
 → 결제 처리
 → 주문 상태 변경
```

이 과정 중 일부만 성공하고 일부가 실패하면 데이터가 이상한 상태가 될 수 있습니다.

그래서 여러 작업을 하나의 트랜잭션으로 묶어 처리합니다.

### COMMIT

현재 트랜잭션의 변경을 확정합니다.

### ROLLBACK

아직 COMMIT되지 않은 변경을 이전 상태로 되돌립니다.

**중요:** 이미 `COMMIT`으로 확정된 일반 트랜잭션을 단순 `ROLLBACK`으로 다시 되돌리는 것은 아닙니다. 따라서 “어디까지 하나의 트랜잭션으로 묶을 것인가”를 설계하는 것이 중요합니다.

→ **왜 배우나·현업 활용:** 주문·결제처럼 여러 DB 변경이 함께 성공하거나 함께 실패해야 하는 상황에서, 일부 데이터만 변경된 불일치 상태를 방지하기 위해 배웁니다.

# Part 11. 오늘 직접 겪은 MySQL 권한 문제

## 24. `appuser`가 데이터베이스를 삭제하지 못한 이유

오늘 다음 명령을 실행했을 때 오류가 발생했습니다.

```sql
DROP DATABASE IF EXISTS cafe_sales;
```

오류:

```text
ERROR 1044 (42000): Access denied for user 'appuser'@'localhost' to database 'cafe_sales'
```

이 오류의 핵심은 SQL 문법이 아니라 **권한**입니다.

`appuser`에게 `cafe_sales` 데이터베이스를 삭제할 권한이 없기 때문에 MySQL이 명령을 거부한 것입니다.

### 권한 확인

```sql
SHOW GRANTS FOR CURRENT_USER;
```

- **실행 위치:** MySQL 프롬프트
- **목적:** 현재 사용자에게 부여된 권한 확인
- **예상 결과:** `SELECT`, `INSERT`, 특정 DB 접근 권한 등이 `GRANT` 형태로 출력
- **해석:** `DROP` 권한이 없다면 DB 삭제는 불가능

→ **왜 배우나·현업 활용:** 애플리케이션 계정에 불필요한 삭제 권한을 주지 않아, 실수나 침해 사고가 발생해도 데이터베이스 전체가 삭제되는 위험을 줄이기 위해 배웁니다.

---

## 25. `DESC cafe_sales;`가 적절하지 않았던 이유

`DESC` 또는 `DESCRIBE`는 데이터베이스 자체가 아니라 **테이블의 컬럼 구조를 확인하는 명령**입니다.

```sql
DESC manager;
```

같이 사용합니다.

데이터베이스 목록을 확인하려면:

```sql
SHOW DATABASES;
```

특정 DB의 테이블 목록을 확인하려면:

```sql
SHOW TABLES FROM cafe_sales;
```

→ **왜 배우나·현업 활용:** 데이터베이스·테이블·컬럼의 계층을 구분하여, 장애 점검이나 스키마 확인 시 올바른 관리 명령을 사용하기 위해 배웁니다.

## 26. `mysql -u root -p`는 실패하고 `sudo mysql`은 성공한 이유

오늘 Ubuntu에서 다음 명령은 실패했습니다.

```bash
mysql -u root -p
```

오류:

```text
ERROR 1698 (28000): Access denied for user 'root'@'localhost'
```

반면 다음 명령은 정상 접속되었습니다.

```bash
sudo mysql
```

### 원인

Ubuntu의 MySQL/MariaDB 설치에서는 `root@localhost` 계정이 비밀번호 인증이 아니라 `auth_socket` 또는 `unix_socket` 기반 인증을 사용하는 경우가 있습니다.

즉:

```text
mysql -u root -p
        ↓
MySQL 비밀번호 인증 시도
        ↓
현재 root 인증 방식과 맞지 않음
        ↓
접속 실패
```

반면:

```text
sudo mysql
    ↓
Linux 관리자(root) 권한으로 실행
    ↓
Socket 인증 조건 만족
    ↓
접속 성공
```

따라서 알고 있던 `1234`가 반드시 MySQL `root` 계정의 로그인 비밀번호라는 뜻은 아닙니다.

### 인증 플러그인 확인

MySQL에 들어간 뒤 다음을 실행할 수 있습니다.

```sql
SELECT user, host, plugin
FROM mysql.user
WHERE user = 'root';
```

결과에 `auth_socket` 또는 `unix_socket`이 표시되면 현재 상황을 설명할 수 있습니다.

### 비밀번호 입력 중 화면에 아무것도 안 보인 이유

Linux 터미널에서 비밀번호를 입력할 때는 보안을 위해 `*`조차 표시하지 않는 것이 정상입니다. 키 입력이 안 되는 것이 아니라 화면에만 표시되지 않는 것입니다.

→ **왜 배우나·현업 활용:** Linux 계정 인증과 DB 계정 인증이 서로 다를 수 있다는 점을 이해하여, 서버에서 “비밀번호가 맞는데 왜 root 로그인이 안 되지?” 같은 인증 장애를 정확히 진단하기 위해 배웁니다.

# Part 12. 오늘 실습을 다시 할 때의 권장 순서

## 27. 데이터베이스 실습 흐름

다음 순서로 복습하면 각각의 개념이 자연스럽게 연결됩니다.

### 1단계 — 현재 사용자와 권한 확인

```sql
SELECT USER(), CURRENT_USER();
SHOW GRANTS FOR CURRENT_USER;
```

**왜 먼저 하나:** 이후 CREATE/DROP/ALTER 등이 실패했을 때 문법 문제인지 권한 문제인지 구분하기 위해서입니다.

### 2단계 — 테이블 구조 확인

```sql
SHOW TABLES;
DESC manager;
DESC category;
DESC menu;
```

**무엇을 확인하나:** 기본키와 외래키가 어느 컬럼인지 확인합니다.

### 3단계 — 각각의 테이블을 단독 조회

```sql
SELECT * FROM manager;
SELECT * FROM category;
SELECT * FROM menu LIMIT 10;
```

**왜 필요한가:** JOIN 전에 원본 데이터가 어떻게 생겼는지 알아야 JOIN 결과가 정상인지 판단할 수 있습니다.

### 4단계 — 두 테이블 JOIN

```sql
SELECT A.name, B.category_name
FROM manager A
INNER JOIN category B
    ON A.manager_id = B.manager_id;
```

**확인할 것:** 조건이 맞는 행만 연결되는지 확인합니다.

### 5단계 — LEFT JOIN으로 미할당 데이터 확인

```sql
SELECT A.manager_id, A.name, B.category_name
FROM manager A
LEFT JOIN category B
    ON A.manager_id = B.manager_id;
```

**확인할 것:** 담당 카테고리가 없는 매니저가 `NULL`로 나타나는지 확인합니다.

### 6단계 — 세 테이블 JOIN

Menu → Category → Manager 순서로 한 테이블씩 연결합니다.

**왜 한 번에 하지 않나:** JOIN이 틀렸을 때 어느 연결에서 문제가 생겼는지 찾기 쉽기 때문입니다.

### 7단계 — VIEW 생성

자주 사용하는 세 테이블 JOIN 결과를 VIEW로 만들어 반복 사용합니다.

### 8단계 — 서브쿼리

평균 가격을 구한 뒤 평균보다 높은 메뉴를 조회하는 방식으로 내부 쿼리와 외부 쿼리의 실행 관계를 확인합니다.

### 9단계 — `EXPLAIN` 학습으로 연결

오늘은 쿼리 튜닝 개념까지 다뤘으므로 다음 실습에서는 `EXPLAIN`을 이용해 SQL 실행 계획을 확인하는 단계로 넘어가면 좋습니다.

→ **왜 배우나·현업 활용:** 복잡한 SQL을 한 번에 작성하기보다 단계별 결과를 검증하여, 실제 장애 상황에서 어느 테이블 연결이나 조건이 잘못되었는지 빠르게 찾기 위해 배웁니다.

# 예상 면접 질문과 답변

## Q1. INNER JOIN과 LEFT JOIN의 차이를 설명해 주세요.

**답변:** INNER JOIN은 두 테이블에서 JOIN 조건이 일치하는 행만 결과에 포함합니다. LEFT JOIN은 왼쪽 테이블의 데이터는 모두 유지하고 오른쪽에 일치하는 값이 없으면 `NULL`로 표시합니다. 그래서 담당 업무가 없는 사용자처럼 “연결되지 않은 데이터까지 찾고 싶을 때” LEFT JOIN을 사용할 수 있습니다.

---

## Q2. 기본키와 외래키가 각각 필요한 이유는 무엇인가요?

**답변:** 기본키는 하나의 테이블에서 각 행을 유일하게 식별하기 위해 사용합니다. 외래키는 다른 테이블의 데이터를 참조하여 두 테이블의 관계가 유효한 상태로 유지되도록 합니다. 예를 들어 존재하지 않는 매니저 ID가 카테고리에 들어가는 것을 외래키로 막을 수 있습니다.

---

## Q3. 인덱스를 만들면 왜 조회가 빨라지고, 단점은 무엇인가요?

**답변:** 인덱스는 전체 테이블을 처음부터 읽지 않고 검색 대상의 위치를 빠르게 찾을 수 있게 해 줍니다. 대신 별도의 저장 공간이 필요하고 INSERT, UPDATE, DELETE가 발생할 때 인덱스도 갱신해야 하므로 쓰기 비용이 증가합니다. 따라서 자주 조회하는 조건을 기준으로 선택적으로 설계해야 합니다.

---

## Q4. Kubernetes 운영 중 Grafana를 사용하는 이유는 무엇인가요?

**답변:** Kubernetes에는 여러 Pod와 컨테이너가 동시에 실행되기 때문에 각 리소스를 개별적으로 확인하는 것은 비효율적입니다. Grafana 같은 도구를 사용하면 CPU, 메모리, 요청량 등의 상태를 대시보드에서 한 번에 확인할 수 있어 장애 징후를 빠르게 찾는 데 도움이 됩니다.

---

## Q5. Ubuntu에서 `mysql -u root -p`가 실패했지만 `sudo mysql`은 성공했습니다. 어떤 원인을 생각할 수 있나요?

**답변:** MySQL root 계정이 비밀번호 인증이 아니라 `auth_socket` 또는 `unix_socket` 인증을 사용하고 있을 가능성을 확인할 수 있습니다. 이 경우 MySQL 비밀번호보다 Linux에서 관리자 권한으로 실행했는지가 중요하므로 `sudo mysql`로 접속될 수 있습니다. 실제 설정은 `mysql.user`의 `plugin` 값을 확인해서 검증할 수 있습니다.

# 마지막 정리

오늘은 Kubernetes 모니터링과 데이터베이스를 각각 따로 배운 것처럼 보이지만 실제 운영에서는 두 영역이 연결됩니다. 애플리케이션이 DB에 요청을 보내고, DB 쿼리가 느려지면 API 응답이 느려지며, 그 결과를 Kubernetes와 Grafana의 메트릭에서 관찰할 수 있습니다.

따라서 앞으로는 다음과 같은 흐름으로 연결해서 이해하는 것이 좋습니다.

```text
사용자 요청
   ↓
애플리케이션 / API
   ↓
SQL 실행
   ↓
MySQL
   ↓
응답 시간·CPU·메모리 변화
   ↓
Prometheus / 모니터링 수집
   ↓
Grafana 대시보드
   ↓
장애 분석 및 쿼리/인프라 개선
```

이 연결을 이해하면 단순히 SQL 문법이나 Grafana 사용법을 외우는 수준을 넘어, **“서비스가 느려졌을 때 어디부터 확인해야 하는가”**라는 운영 관점으로 발전할 수 있습니다.
