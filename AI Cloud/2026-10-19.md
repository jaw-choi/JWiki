# 2026-10-19 | 개인 AI 비서(Jarvis) 프로젝트 개발 기록

> **기록 기준:** 제공된 당일 작업 요약을 재구성했습니다. 코드나 Git 로그를 직접 열어 검증한 기록은 아니므로, 성공 여부는 사용자 제공 내용에 근거합니다.  
> **프로젝트:** 노트북 사용자를 위한 개인 AI 비서  
> **담당:** AI 에이전트 및 음성 인식  
> **작업 환경:** Windows, `C:\AI비서_연습`(개인 연습), `C:\Jarvis-server`(팀 백엔드)

## 1. 오늘의 핵심 성과

1. **기획 구체화:** 노트북 사용자 대상 AI 비서의 목적·기능, 담당 포지션과 **5일/40시간** 실행 계획을 작성했습니다.
2. **에이전트 코어 구성:** 규칙 우선·LLM 보완의 하이브리드 명령 처리 구조와 **19개 도구의 정의 및 목업**, 평가 문장 **69개**를 정리했습니다.
3. **음성 입력 파이프라인 구성:** **Vosk 호출어 감지 → 마이크 녹음 → Google STT V1**로 이어지는 기능을 구현하고 호출어 모드 실행을 확인했다고 기록했습니다.
4. **Windows 실동작 테스트 기반 마련:** 로컬 전용 실제 도구와 WAV 통합 테스트로 앱 실행·URL 열기·검색·폴더 열기·음소거를 연습 환경에서 시험했습니다.
5. **팀 협업 경계 수립:** 담당 폴더만 수정하고 문서는 로컬에만 유지하며, FE/BE·클라우드/PC 간 역할을 구분했습니다.

**하루를 관통하는 결론:** 기획 단계의 AI 비서 아이디어를 *명령 해석 → 도구 선택 → 음성 입력 → PC 동작*을 시험할 수 있는 모듈 구조로 구체화했지만, 실제 팀 통합·정확도 검증·TTS·배포는 아직 남아 있습니다.

## 2. 무엇을 만들었고, 왜 이렇게 설계했는가

### A. 기획 및 범위 정리

- 프로젝트 주제를 **노트북 사용자를 위한 개인 AI 비서**로 확정하고, 기능의 목적을 구체화했습니다.
- 노션용 기능 요약, Claude Docs의 **5일/40시간 단위 계획**, 포트폴리오용 성과 문장 및 도구 8개 설명을 작성했습니다.
- 전체 기능 **86개**를 *포함 39개 / 조건부 24개 / 제외 23개*로 분류하고 `기능_구현가능성_검토.xlsx`에 영역별·담당별 통계와 MVP 수정안을 담았습니다.
- MVP(최소 기능 제품) 수정 제안: 호출어 인식 실패 시 단축키 제공, 일정 관리 우선순위를 P0로 상향, TTS 담당 조정.

프로젝트에서는 기능 수를 늘리는 것보다 **제한된 기간에 실제로 검증 가능한 사용 흐름을 정하는 것**이 중요합니다.  
→ **왜 배우나·현업 활용:** 우선순위와 역할을 명확히 하여, 실제 스프린트에서 구현 범위 초과와 담당 중복을 줄이기 위해 배웁니다.

### B. 연습 레포에서 구조 검증

- `C:\AI비서_연습`에 명령 처리 에이전트, 도구 호출, `/assistant/text` 엔드포인트, 규칙 라우터, 평가 문장 세트를 만들었습니다.
- 첫 평가 결과는 **58/69개 성공(약 84.1%)**이었고, 실패 유형을 우선순위별로 나눠 수정했습니다. **수정 후 점수는 제공되지 않았으므로 확인 필요**입니다.
- 시리 스타일의 전체 화면 물결 오버레이를 추가하고, 침묵 시 정지·Ctrl+Space 중복 호출·브라우저 캐시·반복 확인 질문 문제를 고쳤다고 기록했습니다.

이 공간은 팀 코드에 영향을 주지 않고 화면과 명령 흐름의 실패를 재현·실험하는 용도였습니다.  
→ **왜 배우나·현업 활용:** 실험 환경에서 문제를 분리하여, 협업 저장소의 안정성을 해치지 않고 UI·명령 처리 회귀 문제를 줄이기 위해 배웁니다.

### C. 팀 에이전트 코어 구현 (15:27~)

`C:\Jarvis-server\modules\agent\`에 다음 요소를 만들었습니다.

| 구성 요소 | 역할 |
|---|---|
| `service.py` | `handle_command` 진입점에서 명령 처리 흐름 연결 |
| `router.py` | LLM 없이 특정 명령을 분류하는 규칙 라우터 |
| `tools.py` | 도구 **19개**의 명세 및 목업 동작 |
| `config.py` | 에이전트 설정 관리 |
| 평가 데이터 및 채점 스크립트 | 명령 분류·처리의 정확도 검증 |

**하이브리드 라우팅 동작:** 사용자의 명령을 먼저 규칙으로 판별하고, 규칙으로 처리하기 어려울 때만 LLM(대규모 언어 모델)로 넘깁니다. 반복적이고 예측 가능한 명령의 토큰 사용 및 응답 지연을 줄이려는 설계입니다. 단, 규칙 누락과 잘못된 매칭은 평가 데이터로 검증해야 합니다.

**도구 분리:** `register_tool`로 실제 실행 함수를 나중에 연결할 수 있도록 만들고, OpenAI 의존성은 필요 시에만 로드했습니다. 아직 연결되지 않은 목업 응답에는 반드시 **`[시뮬레이션]`**을 붙여 실제 수행과 구별했습니다.

**확인 질문 정책:** 무조건적인 “네/아니오” 재확인을 제거하고, 대상을 특정할 수 없을 때만 다시 묻도록 했습니다. 앱 종료는 정상적인 종료 요청으로 처리하고 일정 충돌은 안내합니다. 다만 **파괴적 작업·외부 전송·권한 변경처럼 영향이 큰 도구에는 별도의 실행 정책 및 사용자 승인 기준이 필요**합니다.

→ **왜 배우나·현업 활용:** 명령 판단과 실행을 분리하여, 새로운 PC 기능을 추가할 때 라우터를 대폭 수정하지 않고 도구를 교체·검증하기 위해 배웁니다.

### D. 호출어와 음성 입력 구현 (16:35~)

`C:\Jarvis-server\local_runtime\voice\`에 구성 요소를 추가했습니다.

| 파일 | 역할 |
|---|---|
| `wake.py` | Vosk 기반 로컬 호출어 “자비스” 감지 |
| `mic.py` | 마이크 녹음, 발화 끝 감지 |
| `stt.py` | Google STT V1을 이용한 음성→문자 변환 |
| `config.py` | 음성 관련 설정 |
| `__main__.py` | 독립 테스트 실행 |

**예상 데이터 흐름:** 로컬 마이크의 상시 음성 → **Vosk로 호출어 판단(PC 내부)** → 호출 후 명령 구간 녹음 → **Google STT 전송 및 텍스트 변환** → 에이전트 명령 처리 → 도구 실행. 이 분리로 호출 전 원시 음성을 외부 STT에 지속 전송하는 것을 피하는 설계입니다. 실제 전송 범위와 보존 여부는 구현·설정 및 서비스 정책 확인이 필요합니다.

- 선택 설치 그룹 `voice`를 `pyproject.toml`에 추가했습니다.
- Google 인증 키, `.env` 경로와 WAV 경로를 점검했고, **WAV 변환 성공 및 호출어 모드 실행을 확인**했다고 기록했습니다.
- 향후 Google STT V1 결과에 맞춰 자주 발생하는 오인식 표현을 보정할 예정입니다.

→ **왜 배우나·현업 활용:** 호출어 감지와 외부 STT를 나누어, 비용·지연·음성 데이터 노출 범위를 설계하고 음성 인식 장애가 어느 단계에서 발생했는지 추적하기 위해 배웁니다.

### E. Windows 실제 명령 실행과 테스트 (17:40~)

- 로컬 전용 `.jaewoo/real_tools.py`에 **Chrome 등 앱 실행, URL 열기, 검색, 폴더 열기, 음소거**를 수행하는 도구를 만들었습니다.
- `.jaewoo/wav_test.py`로 **WAV → STT → 에이전트 → 실제 PC 실행**의 연결을 점검할 수 있게 했습니다.
- 테스트 명령 WAV를 만드는 PowerShell 스크립트도 준비했습니다.

여기서 **도구 목업 테스트**와 **PC에서 실제로 동작한 결과**를 구분하는 것이 중요합니다. 로컬 테스트 환경에서의 실동작은 확인했다고 기록했지만, 팀 전체 서비스의 FE·BE·클라우드까지 연결 완료된 것은 아닙니다.  
→ **왜 배우나·현업 활용:** 최종 실행 지점까지 추적하여, “AI가 실행했다고 답했지만 실제 OS 상태는 바뀌지 않은” 문제를 검출하기 위해 배웁니다.

### F. 팀 협업 및 배포 구조

- 팀 레포에서는 원칙적으로 **`modules/agent/` 및 `local_runtime/voice/` 담당 영역**을 중심으로 작업하고, 공유 코드 수정·커밋에는 사전 허락을 받기로 했습니다.
- `CLAUDE.md`, `AGENTS.md`, `.jaewoo/`의 지침·일지·포트폴리오·팀 공유 자료·설명 스크립트 등을 작성하고, `.git/info/exclude`로 로컬 Git 추적 대상에서 제외했습니다. 이는 **해당 개발 PC에서만 적용되는 제외 설정**으로, 다른 팀원에게 자동 전파되지 않습니다.
- Windows 제어 담당자 변경(신혜지님 → 김규연님)을 문서에 반영했으며, 이후 main의 공동 담당 표기(신혜지님·김규연님)도 확인했습니다.
- `feat/agent-core`에서 **`feat: 에이전트 규칙 라우터와 명령 처리 함수 추가` 커밋을 직접 수행**했습니다.
- `feat/voice-input`의 **`feat: 호출어 감지와 음성 텍스트 변환 추가` 커밋 메시지**를 준비했습니다. **실제 커밋 및 푸시는 아직 확인되지 않았습니다.**
- **FE/BE 구분:** 에이전트·음성 관련 코드는 BE 레포에 두고, FE에는 응답 형식과 음성 상태 이벤트 규격을 전달합니다.
- **클라우드 배포 시 PC 제어:** 서버에서 사용자의 로컬 OS를 직접 조작할 수 없으므로, 클라우드 서버가 **WebSocket**으로 로컬 실행기에게 작업을 요청하는 구성을 제안했습니다. 이 경우 인증, 명령 허용 목록, 실행 결과 회신, 재연결 처리 등이 필요합니다.
- Electron 연동은 미완료이며, Electron에서 Web Speech API 지원은 환경·버전·설정에 따라 별도 확인해야 합니다. 현재 계획은 **Google STT 경로를 중심으로 통합**하는 것입니다.

→ **왜 배우나·현업 활용:** 모듈 소유권·인터페이스·로컬 실행 경계를 구분하여, 다인 개발에서 충돌을 줄이고 클라우드 서버가 로컬 PC를 직접 제어하지 못하는 아키텍처 문제를 해결하기 위해 배웁니다.

## 4. 남은 작업과 권장 순서

- [ ] **P0 | 음성 입력 정량 검증:** 같은 조건에서 호출어 **10회** 말해 성공 횟수를 기록하고, 배경 소음·다른 말에 대한 오탐도 별도로 검사합니다. 단 10회 결과는 예비 점검이며 일반적인 인식률을 확정하는 통계는 아닙니다.
- [ ] **P0 | 음성→에이전트 통합:** 호출어→녹음→STT→`handle_command`→실제 도구 실행을 하나의 사용자 시나리오로 연결하고 단계별 로그·실패 지점을 남깁니다.
- [ ] **P0 | 안전성 점검:** 실행 가능한 명령 목록, 승인 필요 행위, 잘못 인식된 명령 처리, 인증·권한을 정의합니다.
- [ ] **P0 | 음성 브랜치 커밋/푸시:** `feat/voice-input` 변경 파일과 Git 제외 상태를 먼저 검토하고 PowerShell에서 커밋·푸시합니다.
- [ ] **P1 | `tzdata` 근본 수정:** 파일 수정 권한을 받은 후 Windows에서 시간대 데이터가 없어도 안정적으로 동작하도록 처리합니다.
- [ ] **P1 | TTS 연결:** Google TTS를 기본, Windows TTS를 예비 후보로 비교하고 응답 지연·설치·비용 조건을 확인합니다.
- [ ] **P1 | 라우팅 정확도 재측정:** 69개 평가 문장에 재채점해 초기 **58/69**와 비교하고, 분류 오류와 실제 도구 실행 오류를 나눕니다.
- [ ] **P1 | 팀 인터페이스 합의:** 한재윤님과 API·`pyproject.toml`·WebSocket, 도윤혁님과 응답 스키마·음성 상태 이벤트, 김규연님·신혜지님과 `os_control` 함수 규격을 정합니다.
- [ ] **P2 | Electron·백그라운드 연동:** 최소 통합 시나리오가 안정적으로 실행된 뒤 진행합니다.

### 바로 실행할 수 있는 검증 시나리오

**Windows PowerShell / 프로젝트 환경에서 실행할 테스트 흐름** (정확한 명령은 레포의 실행 스크립트와 의존성을 확인한 다음 적용):

1. **사전 확인:** 마이크 인식, Vosk 모델 경로, Google 인증 키·`.env`, `voice` 의존성을 점검합니다. 이 단계를 먼저 하는 이유는 STT 실패와 OS 실행 실패를 구별하기 위해서입니다.
2. **입력 확인:** 호출어 10회 검출 여부와 각 시도 실패 사유를 기록합니다. 다음 단계로 넘겨지는 명령 구간을 실제로 녹음하는지 확인합니다.
3. **텍스트 확인:** 녹음 또는 테스트 WAV를 STT에 넣어 변환 텍스트와 원래 명령을 비교합니다.
4. **명령 확인:** 변환된 텍스트가 규칙 라우터에서 처리됐는지, LLM으로 넘어갔는지, 어떤 도구가 선택됐는지 기록합니다.
5. **실행 확인:** 안전한 명령(예: 지정된 웹 페이지 열기)을 수행하고 **OS의 실제 상태**로 성공 여부를 확인합니다. 목업이면 `[시뮬레이션]`을 표시하고 실제 성공으로 집계하지 않습니다.

## 5. 복습과 예습

### 오늘 반드시 설명할 수 있어야 할 개념

- **규칙 라우터와 LLM 라우터의 차이:** 규칙은 빠르고 예측 가능하지만 표현 변형에 취약하고, LLM은 유연하지만 비용·지연·오분류 가능성이 있습니다.
- **도구 호출과 실행 결과 검증:** 모델이 도구를 *선택*하는 것과 실제 OS 명령이 *성공*하는 것은 별개의 단계입니다.
- **Wake word / STT / TTS:** 호출어 감지, 음성을 텍스트로 변환, 텍스트를 음성으로 합성이 각각 무엇인지 구분해야 합니다.
- **클라우드 서버와 PC 제어 경계:** 서버가 로컬 장치에서 실행할 수 없는 명령을 로컬 런타임에 요청해야 하는 이유를 설명해야 합니다.
- **Git 로컬 제외와 협업 공유 정책:** `.git/info/exclude`는 개인 저장소의 로컬 설정이며 브랜치로 공유되지 않습니다.

### 스스로 확인할 질문

1. “크롬 켜줘”가 들어왔을 때 규칙 라우터부터 실제 Chrome 실행까지 어느 함수와 단계가 연결되나요?
2. Vosk는 어떤 데이터를 PC 내부에서 처리하고, Google STT에는 어떤 구간의 음성이 전송되나요?
3. 에이전트가 “열었습니다”라고 응답했는데 앱이 열리지 않았다면 어느 로그부터 확인하겠습니까?
4. 클라우드 서버가 사용자 PC 프로그램을 직접 실행하면 안 되는 이유는 무엇이며, WebSocket 실행 요청을 어떻게 인증하겠습니까?

### 다음에 배우면 좋은 것 (우선순위 순)

1. **P0 | 파이프라인 통합 테스트:** 테스트 WAV 3개(정상 명령·인식 오류·지원하지 않는 명령)를 준비하고 단계별 입력·출력·실행 결과를 표로 기록합니다. **추천 이유:** 음성 인식과 명령 라우팅 오류를 분리할 수 있습니다.
2. **P1 | FastAPI–WebSocket–로컬 실행기 설계:** 요청·응답 JSON 예시, 인증 토큰, 명령 ID, 타임아웃, 허용 도구 목록을 문서화합니다. **추천 이유:** 팀의 BE와 로컬 PC 제어를 안전하게 연결하는 핵심 계약이기 때문입니다.
3. **P2 | TTS와 음성 상태 머신:** `대기 → 호출 감지 → 듣는 중 → 처리 중 → 말하는 중 → 대기` 상태를 구현·시각화합니다. **추천 이유:** 화면 오버레이, 마이크, 음성 출력 간 중복 실행과 상태 충돌을 예방하기 때문입니다.

## 6. 관련 현업 직무

**AI 에이전트 엔지니어:** LLM 명령 라우팅, 도구 함수 설계, 평가 데이터셋, 응답·오류 검증을 구현합니다. 오늘의 `handle_command`, 규칙/LLM 분리, 도구 등록 구조와 직접 연결됩니다. 추가 역량으로 FastAPI, 비동기 처리, 프롬프트 인젝션 방어, 테스트·관측성, 인증을 권장합니다.

**음성 AI / AI 백엔드 엔지니어:** 마이크 입력·VAD(음성 구간 판단)·STT·TTS를 연결하고, 지연·인식률·운영 비용·개인정보 범위를 관리합니다. 오늘의 Vosk→Google STT와 WAV 테스트 구조가 기초입니다. 추가로 스트리밍 처리, 오디오 포맷, WebSocket, 배포 및 개인정보 보호 설계가 필요합니다.

## 7. 신입 면접 예상 질문과 답변

**Q1. 규칙 기반 라우터와 LLM 라우터를 함께 쓰는 이유는 무엇인가요?**  
A. 자주 등장하고 구조가 명확한 명령은 규칙으로 빠르고 일관되게 처리할 수 있습니다. 규칙으로 분류하기 어려운 자연어 명령만 LLM에 맡기면 호출 비용과 지연을 줄일 수 있습니다. 다만 규칙의 우선순위와 오분류 여부는 평가 문장으로 확인해야 합니다.

**Q2. 함수 호출을 선택한 것과 실제 작업 성공은 어떻게 다른가요?**  
A. 에이전트의 도구 선택은 어떤 함수를 실행할지 결정한 상태일 뿐입니다. 실제 성공은 운영체제나 외부 서비스의 응답과 상태 변화를 확인해야 판단할 수 있습니다. 그래서 목업 응답에는 `[시뮬레이션]`을 표시하고 실제 실행 결과와 구별했습니다.

**Q3. 음성 비서에서 Vosk와 Google STT를 분리하면 어떤 장점이 있나요?**  
A. Vosk로 PC 내부에서 호출어를 감지하면 호출 전 소리를 지속적으로 외부에 보내지 않아도 됩니다. 호출 후 필요한 명령 구간만 STT에 전달하면 비용과 전송 범위를 줄이는 구조가 됩니다. 다만 인식 정확도와 실제 데이터 전송 범위는 별도로 측정·확인해야 합니다.

**Q4. 클라우드의 에이전트가 사용자의 Chrome을 실행하게 하려면 어떻게 설계하겠습니까?**  
A. 클라우드 서버는 사용자의 로컬 프로세스에 직접 접근할 수 없으므로 PC에 설치된 실행기가 요청을 받아야 합니다. WebSocket 등의 연결로 명령을 전달하되 사용자 인증, 도구 허용 목록, 명령 ID와 실행 결과 회신을 설계하겠습니다. 특히 위험한 명령은 서버가 텍스트로 요청했다는 이유만으로 무조건 실행하지 않도록 제한해야 합니다.

**Q5. 호출어 인식이 불안정하면 어디부터 문제를 확인하겠습니까?**  
A. 먼저 마이크 장치·입력 볼륨·샘플링 형식과 모델 경로를 확인하겠습니다. 그다음 조용한 환경과 소음 환경에서 호출어의 검출·미검출·오탐을 분리해 기록하겠습니다. 호출어 검출 이후에도 문제가 있으면 녹음 종료 판정과 STT 변환 결과를 단계별로 확인하겠습니다.
