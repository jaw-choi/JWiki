
오늘은 단순히 Python 코드를 작성하는 것보다 **DB → 웹 → OpenAI API → AI Agent까지 하나의 흐름으로 연결하는 방법**을 이해하는 데 초점이 있었다.

## 1. 오늘 한 내용

### Flask와 DB를 연결해서 웹 화면 만들기

먼저 SQLite에 저장된 데이터를 Python에서 읽고, Flask를 이용해 HTML 화면에 출력하는 구조를 확인했다.

```
사용자
 ↓
Flask(app.py)
 ↓
DB 조회
 ↓
Python에서 데이터 처리
 ↓
templates/*.html
 ↓
브라우저
```

Flask에서는 HTML을 `templates` 폴더에 넣고, `app.py`의 route를 통해 특정 화면과 연결한다는 흐름을 이해했다. DB에 있는 메뉴, 가격, 설명, 태그 같은 값을 가져와 HTML에서 반복해서 출력하는 방식도 확인했다.

여기서 느낀 것은 **HTML이 데이터를 가지고 있는 것이 아니라, Python이 DB에서 데이터를 가져와 HTML에 전달한다**는 점이다.

```
DB → Python → HTML
```

이 흐름을 알고 나니 Flask가 단순히 웹페이지를 띄우는 것이 아니라 **DB와 화면 사이를 연결하는 역할**이라는 것이 조금 더 명확해졌다.

---

## 2. SQLite `.db` 구조 이해

오늘 `shop.db`도 직접 확인하면서 SQLite가 어떻게 사용되는지 봤다.

CSV나 JSON처럼 사람이 파일을 직접 수정하는 방식보다는 DB 안에 여러 테이블을 만들어 데이터를 관리하고 SQL로 필요한 데이터를 조회한다.

예를 들어:

```
shop.db
├─ menus
└─ orders
```

그리고 Python에서는:

```
conn = sqlite3.connect("shop.db")
```

형태로 연결해서 사용한다.

오늘 실습에서는 DB 구조 확인, 결측값 확인, 매출 집계처럼 **DB에서 자주 할 수 있는 작업을 Python 함수로 만들어 놓고 호출하는 방식**까지 이어졌다.

---

## 3. OpenAI API 연결

OpenAI API를 Python에서 호출하는 기본 구조도 배웠다.

중요했던 부분은 API Key를 Python 코드에 직접 작성하지 않고 `.env`에서 관리하는 것이다. 수업에서도 `.env`에는 API Key나 계정 관련 정보처럼 외부에 노출되면 안 되는 값을 넣고, GitHub에 올리지 않도록 주의해야 한다고 강조했다.

구조는 다음과 같이 이해했다.

```
.env
 ├─ OPENAI_API_KEY
 └─ OPENAI_MODEL

       ↓

load_dotenv()

       ↓

os.getenv()

       ↓

OpenAI()
```

즉:

```
client = OpenAI(
    api_key=os.getenv("OPENAI_API_KEY")
)

model = os.getenv("OPENAI_MODEL")
```

처럼 사용한다.

`.env`는 프로그램 설정을 분리하기 위한 파일이기도 하지만, 특히 **API Key를 코드와 분리해서 관리하는 목적이 중요하다**고 이해했다.

---

## 4. Prompt와 Few-shot

API를 단순 호출하는 것에서 끝나지 않고, GPT에게 어떤 방식으로 대답하게 할지도 직접 구성했다.

Python의 f-string을 이용하면:

```
query = "SQLite가 뭐야?"

template = f"""
사용자 질문:
{query}
"""
```

처럼 사용자가 입력한 값을 Prompt 안에 넣을 수 있다.

그리고 Few-shot도 사용했다.

```
질문 → 예시 답변
질문 → 예시 답변
질문 → 실제 사용자 질문
```

Few-shot을 넣는 이유는 단순히 정답을 알려주는 것이 아니라 **AI에게 원하는 답변 형태와 수준의 예시를 보여주는 것**이라고 이해했다. 수업에서도 출력 예시를 Prompt 안에 넣는 방식으로 설명했다.

---

## 5. Streamlit으로 AI 화면 만들기

터미널에서 질문하고 답변을 받는 것보다 사용자가 직접 사용할 수 있도록 Streamlit 화면으로 변경했다.

직접 만들어본 화면에서는:

```
왼쪽 사이드바

Model
Temperature
Max Tokens
Few-shot 설정

----------------

메인 화면

질문 입력
[AI에게 질문]

AI 답변
```

형태로 구성했다.

수업에서도 Streamlit은 AI나 데이터 관련 프로토타입을 빠르게 화면으로 확인할 때 활용할 수 있고, 입력값이나 Temperature, Max Token 같은 옵션을 사이드바에서 조절하도록 구성하는 방법을 다뤘다.

여기서 한 번 헷갈렸던 부분은 Flask와 Streamlit을 같은 `app.py`에서 동시에 실행했던 것이다.

```
app.run(...)
```

이 들어간 Flask 프로그램을

```
streamlit run app.py
```

로 실행하면서 충돌이 발생했다.

이를 통해 **Flask 서버와 Streamlit 앱은 실행 방식이 다르다**는 것도 실제 오류를 통해 이해했다.

# 6. AI Agent

오늘 가장 중요하게 이해한 부분 중 하나였다.

처음에는 AI Agent가 굉장히 복잡한 기능이라고 생각했는데, 오늘 만든 간단한 구조를 보면 기본 개념은:

> **사용자의 자연어 요청을 이해해서 적절한 작업을 선택하고 실행하는 것**

이었다.

예를 들어 다음 함수를 만들어 두었다.

```
[schema_check]
DB 구조 확인

[null_check]
결측값 확인

[sales_check]
주문수 / 총매출 / 평균매출 확인
```

사용자가:

```
"여기 뭐뭐 들어있어?"
```

라고 하면:

```
schema_check
```

사용자가:

```
"돈 안 적힌 주문 있어?"
```

라고 하면:

```
null_check
```

사용자가:

```
"그래서 얼마 벌었어?"
```

라고 하면:

```
sales_check
```

를 Agent가 선택하도록 했다.

수업에서도 자연어를 받아 함수의 설명과 비교한 뒤 가장 적합한 함수를 선택하게 하고, 그 함수의 실제 DB 조회 결과를 다시 GPT가 설명하도록 만드는 흐름을 실습했다.

전체 구조는:

```
사용자 자연어
      ↓
GPT가 의도 파악
      ↓
함수 선택
      ↓
Python 함수 실행
      ↓
SQLite 조회
      ↓
실제 Result
      ↓
GPT가 Result 해석
      ↓
사용자 답변
```

이다.

---

## 7. Agent에서 Description이 중요한 이유

오늘 Agent를 만들면서 가장 기억에 남은 부분이다.

Agent에게:

```
[null_check]
매출금액 amount의 결측값을 확인한다.
```

라고만 설명하면 사용자가 정확하게:

```
결측값 확인해줘
```

라고 질문했을 때는 잘 선택한다.

하지만 실제 사용자는:

```
돈 안 적힌 거 있어?
뭔가 빠진 거 같은데?
금액이 비어 있는 주문 있어?
```

처럼 말한다.

그래서 Agent의 함수 설명을 단순한 기술 용어만으로 작성하면 일반 사용자 질문에 잘 대응하지 못할 수 있다.

수업에서도 `구조`, `항목`, `내용`, `결측`, `이상한 값`처럼 표현이 달라졌을 때 Agent가 다른 함수를 선택할 수도 있기 때문에 **함수의 Description을 어떻게 설계하는지가 중요하다**고 다뤘다.

내가 이해한 것은:

```
좋은 Agent
=
좋은 함수
+
좋은 Description
+
사용자의 의도를 잘 이해하는 Prompt
```

라는 것이다.

# 8. 규칙 기반과 AI Agent의 차이

이 부분도 프로젝트를 기획하면서 이해하게 됐다.

Agent가 없다면:

```
if reason == "발볼 좁음":
    ...
elif reason == "사이즈 작음":
    ...
```

처럼 개발자가 모든 규칙을 미리 만들어야 한다.

```
사용자 입력
 ↓
if / elif
 ↓
정해진 함수
 ↓
결과
```

AI Agent를 사용하면:

```
사용자 자연어
 ↓
AI가 의미 판단
 ↓
적절한 Tool 선택
 ↓
결과
```

가 된다.

즉 Agent의 장점은 단순히 "AI가 대답한다"가 아니라 **자연어를 실제 프로그램의 기능과 연결할 수 있다는 점**으로 이해했다.

---

# 9. Text-to-SQL까지 확장

기존에는 미리 만들어둔 세 개의 함수에서만 선택했지만, 모든 질문을 미리 함수로 만들어 둘 수는 없다.

그래서 추가로:

```
[text_to_sql]
```

을 만들어 자연어 질문을 SQL로 변환하는 방향까지 생각했다.

예를 들어:

```
"가장 많이 팔린 메뉴가 뭐야?"
```

라는 질문을 하면:

```
자연어
 ↓
SQL 생성
 ↓
SQLite 실행
 ↓
결과
 ↓
GPT 설명
```

방식으로 처리할 수 있다.

여기서 앞으로는 **미리 정의된 Tool을 사용하는 Agent와 Text-to-SQL 방식의 차이**도 더 공부할 필요가 있다고 느꼈다.

# 11. 앞으로 진행할 초미니 프로젝트

오늘 배운 내용을 활용해서 팀 프로젝트는 **운동화 반품과 AI Agent**를 주제로 진행할 예정이다.

단순 운동화 추천 자체보다 이번 프로젝트에서 중요한 것은 **AI Agent 사용 과정의 자원 관리**이다.

### 서비스 흐름

```
운동화 선택
 ↓
구매
 ↓
반품
 ↓
반품 사유 선택

예:
- 사이즈 작음
- 사이즈 큼
- 발볼 좁음
- 착화감 불편

 ↓

[AI 적합도 분석]

 ↓

AI Agent
 ↓
반품 이유 분석
 ↓
대체 운동화 추천
```

그리고 관리자 화면에서는:

```
CPU
RAM
처리시간
LLM 호출 횟수
Tool 호출 횟수
Token 사용량
```

등을 확인할 예정이다.

# 12. 프로젝트에서 비교할 내용

Agent를 사용하지 않는 경우에는 Python의 정해진 규칙을 이용한다.

```
반품 사유
 ↓
if / elif
 ↓
정해진 조건
 ↓
DB 조회
 ↓
추천
```

Agent 방식에서는:

```
사용자 자연어
 ↓
AI Agent
 ↓
의도 판단
 ↓
Tool 선택
 ↓
DB 조회
 ↓
추천 + 설명
```

으로 처리한다.

두 방식의:

```
CPU
RAM
처리시간
AI 호출 수
Tool 호출 수
Token
```

차이를 확인하는 것이 프로젝트의 자원관리 측면에서 중요한 부분이다.

# 13. 팀원 3명 역할

현재는 다음과 같이 나누는 방향으로 생각하고 있다.

**1번 — 데이터 및 사용자 화면**

```
SQLite DB
회원 데이터
운동화 데이터
구매/반품 데이터
상품 목록
상품 상세 화면
```

**2번 — AI Agent 및 자원관리**

```
반품 분석 Agent

CPU/RAM 측정
처리시간
Token

```

```

5분 발표 정리
```

업로드한 메모에서도 앞으로 할 일로 DB, 상품 목록·상세, AI Agent 제작, 발표 등이 정리되어 있다.

# 오늘 핵심적으로 이해한 내용

오늘 내용을 한 문장씩 정리하면 다음과 같다.

```
DB
→ 데이터를 구조적으로 저장하는 곳

Flask
→ DB와 HTML을 연결해 웹 서비스를 만드는 역할

Streamlit
→ AI/데이터 프로그램을 빠르게 화면으로 확인하는 도구

.env
→ API Key 같은 중요한 설정을 코드와 분리해서 관리

OpenAI API
→ Python 프로그램에서 GPT 기능을 호출

Prompt
→ AI가 어떤 방식으로 작업할지 지시

Few-shot
→ 원하는 출력 형태를 예시로 보여주는 방법

AI Agent
→ 자연어 의도를 파악해 필요한 작업을 선택하고 실행

Tool
→ Agent가 실제로 실행할 Python/DB 기능

Text-to-SQL
→ 자연어를 SQL로 바꾸어 DB를 직접 조회

자원관리
→ CPU/RAM뿐 아니라 처리시간, 호출 횟수,
   Token 등도 관리 대상으로 볼 수 있음
```

## 오늘 가장 크게 이해한 점

**AI Agent가 모든 것을 알아서 해주는 마법 같은 프로그램이 아니라, 개발자가 준비한 데이터와 함수, 설명을 바탕으로 사용자의 의도를 판단하고 적절한 작업을 연결해주는 구조라는 점을 이해했다.**

그리고 앞으로는 단순히 AI 기능을 붙이는 것에서 끝나는 것이 아니라,

> **“이 AI 기능을 사용하기 위해 어떤 자원을 사용했고, 그만큼 사용할 가치가 있었는가?”**

까지 생각해보는 것이 이번 초미니 프로젝트에서 가장 중요한 부분이라고 정리할 수 있다.
