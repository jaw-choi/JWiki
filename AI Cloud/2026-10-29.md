## 2. 토큰화와 어휘 사전

### 2.1 토큰, 토큰 ID, 임베딩의 차이

- **토큰(Token):** 모델이 처리하도록 분리한 텍스트 단위. 한 글자, 부분 단어 또는 단어일 수 있습니다.
- **토크나이저(Tokenizer):** 입력을 토큰으로 분할하고 모델의 어휘 사전에 따라 정수 ID로 변환하는 도구입니다.
- **토큰 ID:** 토큰을 가리키는 번호일 뿐, 숫자가 비슷하다고 의미가 비슷한 것은 아닙니다.
- **임베딩(Embedding):** 토큰 ID에 대응하는 학습된 벡터 또는 문맥을 고려한 벡터 표현입니다.

예를 들어 `나는 파이썬을 공부한다`를 모델에 넣으면, 해당 모델의 토크나이저가 부분 단어로 나누고 ID를 반환합니다. 실제 분할과 ID는 **사용한 모델마다 다르며**, 수업에서 설명한 빈도순 번호 부여는 원리 이해용 예시이지 모든 사전학습 모델의 규칙은 아닙니다. **[수업+보충]**

→ 왜 배우나·현업 활용: 모델별 토큰 ID와 입력 길이가 다른 이유를 이해하여, 임베딩 모델을 교체할 때 기존 벡터·토크나이저의 호환성 문제를 점검하기 위해 배웁니다.

### 2.2 WordPiece, BPE, 미등록 단어

녹취에서는 **WordPiece**, **BPE(Byte Pair Encoding)**, **부분 단어(Subword)**, **OOV(Out-of-Vocabulary, 어휘 사전에 없는 항목)**를 다뤘습니다. WordPiece는 BERT 계열에서, BPE는 RoBERTa/GPT 계열의 다양한 형태에서 사용합니다. 부분 단어 방식은 미등록 단어를 더 작은 조각으로 처리해 OOV 문제를 완화합니다. 다만 제품명·사내 약어·의학 용어가 의도치 않게 쪼개져 검색 품질에 영향을 줄 수 있습니다. **[수업+보충]**

> [보충] 녹취에서 N-gram 빈도 세기, 불용어(stopword) 처리, 서브워드 어휘 생성이 섞여 설명된 부분이 있습니다. 이들은 **서로 다른 기법**입니다. BPE는 빈번한 기호 쌍의 병합으로 어휘를 구성하고, 불용어 처리는 특정 단어를 제거하는 전처리입니다. 또한 기존에 학습된 토크나이저의 어휘 사전은 운영 중 임의로 바꾸면 모델과 불일치할 수 있습니다.

→ 왜 배우나·현업 활용: 특수 용어가 검색에서 누락되는 이유를 추적하여, 의료·법률·사내 제품 문서 검색 시 용어집과 동의어 정규화 규칙을 설계하기 위해 배웁니다.

### 2.3 Padding, Truncation, Attention Mask

여러 문장을 한 배치로 처리할 때 입력 길이를 맞추기 위해 짧은 문장에는 **패딩(Padding)**을 넣고 긴 문장은 **잘라내기(Truncation)**를 적용합니다. **Attention Mask**는 보통 유효한 토큰에 `1`, 패딩 위치에 `0`을 지정해 모델에 구분 정보를 줍니다. 패딩 토큰의 ID 자체는 모델마다 다를 수 있습니다. **[수업]**

```python
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("klue/bert-base")
texts = ["배송 문의", "배송이 언제 도착하는지 궁금합니다"]
encoded = tokenizer(texts, padding=True, truncation=True, return_tensors="pt")
print(encoded["input_ids"])
print(encoded["attention_mask"])
```

**실행 환경:** Windows의 VS Code Jupyter Notebook 또는 Python 인터프리터. **목적:** 서로 다른 길이의 입력이 패딩·마스크로 어떻게 배치되는지 확인. `padding=True`는 배치 내 최장 입력에 길이를 맞추고, `truncation=True`는 모델 허용 길이를 넘는 입력을 자릅니다. **예상 결과:** 두 텐서의 행별 길이가 일치하며 짧은 문장의 패딩 위치에서 마스크 0이 보입니다. 실제 숫자 ID는 실행 시 확인합니다. **[보충 실습]**

→ 왜 배우나·현업 활용: 긴 문서 입력이 잘리거나 패딩을 잘못 집계하는 문제를 이해하여, RAG 인덱싱 및 배치 추론에서 누락된 문장과 검색 품질 저하를 진단하기 위해 배웁니다.

## 3. Transformer의 핵심 원리

### 3.1 위치 정보와 Self-Attention

Transformer는 토큰 임베딩만으로는 단어 순서를 충분히 표현하기 어렵기 때문에 **위치 정보(Positional Encoding/Embedding)**를 함께 사용합니다. **Self-Attention**은 같은 입력 시퀀스 안의 토큰들이 다른 토큰을 얼마나 참조할지 계산합니다. 수업에서는 `오늘 파이썬을 공부했다`에서 단어의 관계를 살피는 예를 들었습니다. **[수업]**

Self-Attention의 주요 계산은 다음과 같습니다.

\[
\operatorname{Attention}(Q,K,V)=\operatorname{softmax}\left(\frac{QK^{T}}{\sqrt{d_k}}\right)V
\]

`Q(Query)`는 어떤 정보를 찾는지, `K(Key)`는 무엇과 비교하는지, `V(Value)`는 가중합할 정보가 무엇인지에 해당하는 **학습된 벡터 변환 결과**입니다. `softmax`는 주어진 점수를 합이 1인 가중치로 변환하며, 항상 가장 큰 값 하나만 반환하는 함수는 아닙니다. **Multi-Head Attention**은 서로 다른 투영 공간에서 어텐션을 병렬 계산해 다양한 관계를 포착합니다. **[수업+보충]**

> [보충] 녹취에는 Self-Attention을 “내 파일”, 일반 Attention을 “외부 자료”로 구분하는 비유가 등장합니다. 더 정확히는 **Self-Attention**은 Q·K·V가 같은 입력에서, **Cross-Attention**은 Q와 K/V가 다른 입력 표현에서 생성되는 구조입니다. 판매 데이터와 날씨 데이터를 결합한다고 자동으로 Cross-Attention이 되는 것은 아닙니다.

→ 왜 배우나·현업 활용: 모델이 문맥을 반영해 토큰 표현을 바꾸는 원리를 이해하여, 같은 키워드가 다른 의미로 사용되는 고객 질문을 분류하는 모델의 동작을 설명하기 위해 배웁니다.

### 3.2 Add & Norm, Feed-Forward, 자원 비용

Transformer 블록에는 어텐션 외에도 **잔차 연결(Add)**, **정규화(Norm, 보통 Layer Normalization)**, **Feed-Forward Network(FFN)**가 들어갑니다. 잔차 연결은 이전 표현을 더해 정보 전달을 돕고, LayerNorm은 계산 안정성을 높이며, FFN은 토큰 표현에 비선형 변환을 적용합니다. 이 처리와 여러 헤드·계층이 반복되므로 모델 크기와 입력 길이에 따른 메모리·추론 비용을 고려해야 합니다. **[수업+보충]**

> [보충] 녹취에서 `Norm`을 벡터 거리의 노름이나 Batch Normalization과 연결해 설명하는 부분이 있지만, Transformer의 **Add & Norm**은 일반적으로 **잔차 연결 + Layer Normalization**을 가리킵니다. Feed-Forward 역시 역전파 자체가 아니라 블록 내부의 순전파 신경망입니다.

→ 왜 배우나·현업 활용: 계층·헤드·입력 길이가 연산 비용에 영향을 주는 이유를 이해하여, CPU 추론이 느린 상황에서 모델 경량화와 배치 크기를 검토하기 위해 배웁니다.

### 3.3 BERT와 GPT의 역할 구분

| 구분 | BERT 계열 | GPT 계열 |
|---|---|---|
| 주된 구조 | 인코더 중심 | 디코더 중심 |
| 대표 학습 방향 | 가려진 토큰 예측 등 | 다음 토큰 예측 |
| 대표 활용 | 문장 분류, 개체명 인식, 특징 추출 | 글 생성, 답변·요약 생성 |
| 이번 수업과의 연결 | 질문·문서 표현 및 분류 | 검색 근거를 바탕으로 답변 생성 |

수업의 핵심은 **문서를 찾는 검색용 표현과 답변을 생성하는 모델의 역할을 구분**하는 것입니다. BERT가 반드시 문장당 하나의 정답만 낼 수 있는 것은 아니며, GPT 역시 분류 등 다양한 작업에 사용할 수 있습니다. **[수업+보충]**

→ 왜 배우나·현업 활용: 검색·분류와 생성의 역할을 구분하여, FAQ 검색에 불필요하게 대형 생성 모델을 사용하는 비용 낭비를 피하기 위해 배웁니다.

## 4. Hugging Face 모델을 학습 없이 활용

### 4.1 모델 카드와 config 확인

수업에서는 Hugging Face 모델을 다운로드하고 `config.json`에서 **`model_type`, `id2label`, `label2id`, `problem_type`**을 확인하는 흐름을 소개했습니다. `id2label`은 숫자 예측 ID가 어떤 범주인지 알려 줍니다. 금융 감정 모델의 긍정·중립·부정과 일반 감정 모델의 범주는 같아 보여도 학습 분야가 다르므로 동일하게 취급하면 안 됩니다. 모델은 최초 다운로드 이후 캐시에서 재사용할 수 있습니다. **[수업]**

```python
from transformers import AutoConfig

name = "klue/bert-base"
config = AutoConfig.from_pretrained(name)
print("모델 유형:", config.model_type)
print("레이블:", config.id2label)
```

**실행 위치:** Jupyter Notebook 셀. **목적:** 모델을 추론하기 전에 설정과 레이블 정의를 확인. **예상 결과:** 모델 유형 및 레이블 사전이 출력됩니다. 다만 `klue/bert-base`는 기반 모델이므로 표시된 레이블을 실제 학습 완료된 감정 분류 레이블로 오해하면 안 됩니다. **[보충 실습]**

→ 왜 배우나·현업 활용: 학습 데이터와 출력 레이블을 확인하여, 금융 특화 감정 모델을 일반 쇼핑몰 리뷰에 잘못 적용하는 오류를 막기 위해 배웁니다.

### 4.2 Pipeline, Zero-shot, 임베딩 추출

- **`pipeline("text-classification")`:** 분류 작업에 맞춰 미세조정된 모델을 간편히 호출.
- **`pipeline("zero-shot-classification")`:** 자연어 추론(NLI) 모델과 후보 레이블을 사용해 별도 도메인 학습 없이 새로운 분류 기준 시험.
- **`pipeline("feature-extraction")`:** 토큰별 모델 특징 표현을 얻는 용도. 문장 벡터가 반드시 바로 반환되는 것은 아닙니다.
- **`SentenceTransformer.encode()`:** 문장 임베딩에 특화된 모델로 문장 단위 벡터를 간편하게 얻는 방법.

수업에서는 한국어 전용·영어 전용·금융 특화 등 **모델의 용도와 언어를 함께 고려**할 것을 강조했습니다. 특히 Zero-shot으로 질문 카테고리를 먼저 예측해 메타데이터 필터에 사용하는 방식을 실습 주제로 연결했습니다. **[수업]**

→ 왜 배우나·현업 활용: 처음부터 모델을 학습하지 않고 적합한 사전학습 모델을 선정하여, 교육 과정 검색이나 고객 문의 분류의 프로토타입을 빠르게 검증하기 위해 배웁니다.

## 5. 벡터 DB 없이 의미 검색 구현하기

### 5.1 검색 단계와 RAG의 차이

`문서 준비 → 텍스트 정제 → 임베딩 → 코사인 유사도 → Top-K 문서`까지는 **검색(Retrieval)**입니다. 이 결과를 **생성 모델(Generator)**에 근거로 제공해 답변을 생성하면 **RAG(Retrieval-Augmented Generation)**가 됩니다. 벡터 DB는 대량 벡터의 저장·검색·색인에 유용하지만, 소량의 문서를 실습하는 데 필수 조건은 아닙니다. **[수업+보충]**

> [보충] RAG의 `A`는 **Augmented(증강)**, `G`는 **Generation(생성)**입니다. 생성 모델로 반드시 GPT API를 사용해야 하는 것은 아닙니다. 또한 생성 없이 가장 가까운 FAQ 답변을 반환하는 구조는 검색 기반 FAQ 시스템으로 표현하는 편이 정확합니다.

→ 왜 배우나·현업 활용: 검색과 생성의 경계를 이해하여, FAQ 정답 조회만 필요한 경우 불필요한 LLM API 비용을 줄이기 위해 배웁니다.

### 5.2 코사인 유사도와 임베딩

질문 벡터 `q`, 문서 벡터 `d`에 대해 다음을 계산합니다.

\[
\operatorname{cosine}(q,d)=\frac{q\cdot d}{\lVert q\rVert\lVert d\rVert}
\]

가까운 방향을 가진 벡터일수록 일반적으로 높은 코사인 유사도를 갖습니다. 다만 점수가 높다고 **정답이 보장되지는 않으며**, 사용한 임베딩 모델의 성격에 따라 순위가 달라집니다. 수업에서는 KLUE BERT의 768차원 표현과 문장 벡터를 만들어 비교하는 구조를 다뤘습니다. **[수업+보충]**

**직접 해볼 단일 셀 실습 (벡터 DB 및 LLM API 불필요):**

```python
# Notebook: 먼저 %pip install sentence-transformers
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("jhgan/ko-sroberta-multitask")
faq = {
    "도커란 무엇인가요?": "애플리케이션을 컨테이너로 패키징하고 실행하는 플랫폼입니다.",
    "쿠버네티스란 무엇인가요?": "컨테이너화된 애플리케이션의 배포·운영을 관리합니다.",
    "AWS란 무엇인가요?": "클라우드 컴퓨팅 서비스를 제공하는 플랫폼입니다."
}
query = "도커가 뭐야?"
questions = list(faq)
question_vectors = model.encode(questions)
query_vector = model.encode([query])
scores = model.similarity(query_vector, question_vectors)[0]
index = int(scores.argmax().item())
print("검색 질문:", questions[index])
print("유사도:", round(float(scores[index]), 4))
print("답변:", faq[questions[index]])
```

**실행 위치:** Windows VS Code의 `.ipynb` 셀. **명령 목적:** `encode()`로 문장 벡터 생성, `similarity()`로 질문과 FAQ를 비교. **예상 결과:** 가장 가까운 질문과 등록된 답변, 유사도 숫자가 출력됩니다. **해석:** 정답이 다른 질문으로 나오면 임베딩 모델·질문 표현·문서 구성을 점검합니다. 샘플 코드를 제시한 것이며 실제 실행 성공 여부는 확인되지 않았습니다. **[보충 실습]**

→ 왜 배우나·현업 활용: 별도 검색 서버를 두지 않고 임베딩의 효과를 비교하여, 소규모 사내 FAQ 서비스에서 검색 모델 교체 전 성능을 검증하기 위해 배웁니다.

### 5.3 Zero-shot 메타데이터 필터링과 검색 실패 위험

수업 흐름과 연계한 예시 질문은 “데브옵스나 시스템 엔지니어에게 필요한 과정은?”입니다. Zero-shot 분류 모델에 `AI, 클라우드, 콘텐츠크리에이터, 데이터분석` 범주를 주고 `클라우드`를 선택했다면 그 범주의 문서만 검색하도록 제한할 수 있습니다. **다만 예측이 잘못되면 정답 문서를 검색 전에 제외할 수 있으므로**, 상위 여러 범주 탐색 또는 분류 불확실 시 전체 검색을 비교해야 합니다. **[수업 맥락+보충]**

→ 왜 배우나·현업 활용: 검색량 감소와 정답 누락 위험의 균형을 이해하여, 교육 추천 RAG에서 잘못된 카테고리 예측 때문에 관련 교육 과정이 사라지는 장애를 예방하기 위해 배웁니다.

## 6. 데이터 정제와 RAG 평가

쇼핑몰의 `3만 원`/`30000원`, `35kg`/`35 kg`, 여러 형태의 연락처·직무명처럼 같은 사실을 다양한 형식으로 표현하면 검색 결과가 흔들릴 수 있습니다. 수업에서는 **표기 표준화, 불필요한 태그와 공백 정리, 전각·반각 문자 처리, 개인정보 마스킹, 업무별 용어집 관리**를 강조했습니다. 반면 무조건 모든 숫자나 문장 표기를 하나로 바꾸면 원래의 의미를 손상할 수 있으므로 원본은 유지하고 정제본을 따로 검증하는 방식이 안전합니다. **[수업+보충]**

→ 왜 배우나·현업 활용: 회사별 데이터 표현 차이를 이해하여, 배송비·전화번호·사내 상품명이 제각각인 FAQ를 정제하고 개인정보가 검색 결과에 노출되는 사고를 막기 위해 배웁니다.

**평가 원칙:** 먼저 질문 목록과 정답 문서(또는 허용 가능한 답변)를 준비하고, 정답이 Top-K에 들어오는지 확인합니다. 비슷한 검색 품질이면 **지연시간·메모리·라이선스·배포 조건**까지 비교합니다. 실패 사례에서는 토큰화, 특수 용어, 청킹, 검색 범위, 리랭킹을 점검합니다. 녹취에는 이러한 평가·선정 기준이 제시되었으나, 실제 성능 숫자나 성공률은 확인되지 않습니다. **[수업]**

→ 왜 배우나·현업 활용: 모델 점수 한 번에 의존하지 않고 실패 질문을 재현하여, RAG 모델 교체 후 특정 고객 문의가 검색되지 않는 회귀 오류를 발견하기 위해 배웁니다.

## 7. LLMOps: 새 FAQ가 올라올 때 필요한 운영 파이프라인

수업 후반부에는 **데이터가 바뀔 때마다 사람이 수작업으로 바꾸는 구조를 피하고**, 검증을 통과한 새 버전만 운영에 적용하는 것을 강조했습니다. 다음 흐름이 핵심입니다.

`새 FAQ 수신 → 기존 버전과 차이 확인 → 형식/금지 데이터/개인정보 검증 → 담당자 및 전화번호 검증 → 정제·임베딩 재생성 → 테스트 질문 검색 평가 → 승인/배포 → 운영 감시`

새 데이터의 금지 범주, 개인 정보 취급 기준, 담당자 확인 책임은 개발자가 임의 결정할 수 없으므로 현업 담당자와 협의해야 합니다. 문제 발견 시 직전 검증 버전으로 되돌릴 수 있는 버전 관리 역시 실무 설계에 포함할 수 있습니다. **[수업+보충]**

→ 왜 배우나·현업 활용: 데이터 갱신이 AI 검색 품질에 영향을 미치는 원리를 이해하여, 오래된 담당자 전화번호나 민감 정보가 포함된 FAQ가 검증 없이 운영에 배포되는 사고를 방지하기 위해 배웁니다.

## 12. 신입 면접 예상 질문과 답변

**Q1. 토큰화와 임베딩은 무엇이 다른가요?**  
토큰화는 입력 문장을 모델이 처리할 단위와 ID로 변환하는 과정입니다. 임베딩은 해당 토큰이나 문장을 연속적인 숫자 벡터로 표현하는 과정이며, 유사도 검색은 그 벡터를 비교합니다.

**Q2. BERT와 GPT는 어떤 차이가 있나요?**  
BERT 계열은 인코더 중심 구조로 문맥을 반영한 표현을 만들고 분류·정보 추출 등에 많이 활용합니다. GPT 계열은 디코더 중심의 다음 토큰 예측으로 문장을 생성합니다. 다만 각각의 활용은 이 대표 사례보다 넓습니다.

**Q3. 문장 유사도 검색에 원본 KLUE BERT보다 SentenceTransformer를 고려하는 이유는 무엇인가요?**  
원본 BERT의 토큰 특징을 단순 평균하면 문장 검색용으로 최적화된 표현이 아닐 수 있습니다. SentenceTransformer는 문장 간 관련성을 반영하도록 학습된 모델을 제공하므로 FAQ 검색에서 우선 비교할 가치가 있습니다. 실제 우열은 우리 데이터의 정답 질문으로 평가해야 합니다.

**Q4. Zero-shot으로 검색 범주를 좁혔는데 정답을 못 찾는다면 어떻게 대응하겠습니까?**  
먼저 분류 결과가 올바른지 확인하고, 관련 문서가 메타데이터 필터 때문에 제외됐는지 살펴보겠습니다. 상위 2개 범주 또는 전체 검색과 결과를 비교하고, 실패 질문을 평가 세트에 추가해 변경 전후를 측정하겠습니다.

**Q5. FAQ 업데이트 자동화에서 가장 중요한 검증은 무엇인가요?**  
데이터 형식과 개인정보, 금지 정보, 연락처·담당자 정확성을 우선 확인해야 합니다. 그다음 새 버전이 기존 테스트 질문의 검색 품질을 악화시키지 않는지 평가하고, 통과한 버전만 배포하며 문제가 생기면 되돌릴 수 있도록 관리하겠습니다.
