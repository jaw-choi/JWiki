# 2026-09-22 네트워크 수업 정리

## 오늘 수업의 핵심 흐름

오늘 수업은 네트워크 용어를 외우는 것보다, **내 PC에서 보낸 데이터가 실제로 어떤 과정을 거쳐 목적지까지 가는지**를 이해하는 데 초점이 있었다.

전체 흐름은 다음처럼 보면 된다.

```text
내 PC
→ 랜카드 / Wi-Fi 같은 물리적 연결 확인
→ 같은 네트워크 안에서 MAC 주소를 이용해 전달
→ IP 주소를 기준으로 다른 네트워크까지 경로 결정
→ 게이트웨이/NAT를 거쳐 외부 인터넷으로 이동
→ 여러 라우터(Hop)를 지나 목적지 도착
```

즉 네트워크 장애가 발생했을 때도 단순히 "인터넷이 안 된다"라고 보는 것이 아니라,

```text
장치가 살아 있는가?
→ 링크가 연결되어 있는가?
→ 같은 네트워크와 통신되는가?
→ 게이트웨이까지 가는가?
→ 외부 인터넷으로 나가는가?
→ 목적지까지 어느 구간에서 막히는가?
```

순서로 문제를 좁혀 가는 것이 중요하다.

# 1. OSI 7계층을 배우는 이유

OSI 7계층은 통신 과정을 역할별로 나눈 모델이다.

오늘은 전체 7계층을 모두 깊게 다루기보다는, 실제 네트워크를 이해할 때 가장 먼저 연결되는 **1계층(물리), 2계층(데이터 링크), 3계층(네트워크)**을 중심으로 봤다.

| 계층 | 핵심 역할 | 오늘 중요하게 본 것 |
|---|---|---|
| 1계층 물리 | 비트를 실제 신호로 전달 | 케이블, Wi-Fi, 랜카드 PHY, 신호, 속도 |
| 2계층 데이터 링크 | 같은 네트워크 안에서 장치 구분 | MAC 주소, 프레임, 스위치 |
| 3계층 네트워크 | 다른 네트워크까지 경로 결정 | IPv4, 서브넷, CIDR, 라우터 |

중요한 점은 이 계층들이 따로 움직이는 것이 아니라는 것이다.

예를 들어 `google.com`으로 데이터를 보낸다고 하면,

1. 실제 신호를 보낼 수 있는 물리 연결이 있어야 하고,
2. 로컬 네트워크에서는 MAC 주소를 이용해 다음 장치로 전달하고,
3. IP 주소를 이용해 최종 목적지까지 경로를 찾아간다.

따라서 어느 한 계층에 문제가 생겨도 최종적으로는 "인터넷이 안 되는 것"처럼 보일 수 있다.

# 2. 데이터가 전송될 때 주소가 여러 개 필요한 이유

네트워크에서는 주소가 하나만 사용되는 것이 아니다.

대표적으로 오늘 본 것은 다음 두 가지다.

### MAC 주소

랜카드에 연결된 장치를 식별하기 위한 주소다.

주로 **같은 로컬 네트워크에서 다음 장치로 데이터를 전달할 때** 사용한다.

### IP 주소

네트워크 상에서 목적지를 찾기 위한 논리적인 주소다.

다른 네트워크를 지나 최종 목적지까지 찾아갈 때 사용한다.

정리하면,

```text
MAC 주소
→ 가까운 구간에서 "다음 장치가 누구인가?"

IP 주소
→ 전체 네트워크에서 "최종 목적지가 어디인가?"
```

라는 차이로 이해하면 된다.

---

# 3. 프레임과 패킷

실제로 보낼 데이터만 그대로 전송하는 것이 아니라, 앞뒤에 여러 제어 정보를 붙여서 전달한다.

개념적으로 보면 다음과 같다.

```text
[각 계층의 제어 정보] + [실제 데이터]
```

네트워크 계층에서는 보통 **패킷**, 데이터 링크 계층에서는 **프레임**이라는 단위를 사용한다.

Wireshark 같은 프로그램을 사용하면 실제로 오가는 패킷과 프레임 내부의 헤더 정보를 확인할 수 있다.

중요한 것은 용어 자체보다,

> 실제 데이터 앞뒤에 주소와 제어 정보가 계속 추가되면서 네트워크를 이동한다.

는 구조를 이해하는 것이다.

# 4. MTU

네트워크에서 한 번에 보낼 수 있는 데이터 크기에는 한계가 있다.

오늘 수업에서는 일반적인 Ethernet 환경의 MTU 예시로 **1500 bytes**를 확인했다.

즉 데이터가 매우 크다면 한 번에 전부 보내는 것이 아니라 네트워크 규칙에 맞게 여러 단위로 나누어 전송될 수 있다.

Linux에서는 인터페이스 정보에서 `MTU` 값을 확인할 수 있다.

# 5. IPv4 주소 구조

IPv4 주소는 총 **32bit**다.

이를 8bit씩 네 부분으로 나누어 사람이 보기 쉽게 표현한다.

```text
192.168.1.10

192 | 168 | 1 | 10
 8bit 8bit 8bit 8bit
```

8bit로 표현 가능한 값은 다음과 같다.

```text
00000000 = 0
11111111 = 255
```

그래서 IPv4 한 구역의 값은 `0 ~ 255` 범위를 가진다.

핵심은 IP 주소만 보고는 "어디까지가 네트워크 부분이고 어디부터 장치 주소인가"를 완전히 알 수 없다는 것이다.

이를 구분하기 위해 **서브넷 마스크와 CIDR**이 필요하다.

---

# 6. 서브넷 마스크와 AND 연산

서브넷 마스크는 IP 주소에서

```text
어디까지가 네트워크 영역이고
어디부터가 호스트 영역인지
```

구분하는 역할을 한다.

기본 원리는 IP 주소와 서브넷 마스크를 **AND 연산**하는 것이다.

AND 연산은 다음처럼 이해하면 된다.

```text
1 AND 1 = 1
1 AND 0 = 0
0 AND 1 = 0
0 AND 0 = 0
```

즉 서브넷 마스크에서 `1`로 지정된 비트는 네트워크를 구분하는 부분이고, `0`인 부분이 호스트 주소로 사용될 수 있는 영역이 된다.

---

# 7. CIDR

CIDR은 IP 뒤에 `/숫자`를 붙여 네트워크 비트 수를 표현하는 방법이다.

예:

```text
192.168.1.0/24
```

`/24`라는 것은 IPv4의 32bit 중 **앞의 24bit가 네트워크 영역**이라는 뜻이다.

따라서 남는 비트는

```text
32 - 24 = 8bit
```

이다.

즉 마지막 8bit가 호스트 영역이 된다.

### 예시

| CIDR | 네트워크 비트 | 남은 호스트 비트 | 전체 주소 규모 |
|---|---:|---:|---:|
| /24 | 24 | 8 | 2^8 = 256 |
| /25 | 25 | 7 | 2^7 = 128 |
| /26 | 26 | 6 | 2^6 = 64 |

따라서 `/` 뒤 숫자가 커질수록 네트워크 부분이 커지고, 한 서브넷에서 사용할 수 있는 호스트 주소 공간은 작아진다.

```text
/24 → 비교적 큰 호스트 영역
/25 → /24의 절반 규모
/26 → /25의 절반 규모
```

강의에서는 `.1`을 게이트웨이로 사용하는 형태를 예로 많이 들었는데, 핵심은 특정 숫자를 외우는 것이 아니라 **CIDR을 보고 네트워크 범위와 호스트 범위를 계산할 수 있어야 한다는 것**이다.

# 8. 사설 IP와 공인 IP

내 PC나 VM에 표시되는 IP가 그대로 인터넷에서 사용되는 공인 IP인 것은 아니다.

오늘 Multipass 환경에서도 가상 머신이 별도의 사설 주소를 사용하고, 외부 인터넷으로 나갈 때 다른 네트워크 장치를 거치는 구조를 확인했다.

### 사설 IP

내부 네트워크에서 사용하는 주소다.

여러 회사나 가정에서 같은 사설 IP 대역을 반복해서 사용할 수 있다.

사설 IPv4 주소 사용은 RFC 1918과 관련된 규칙을 따른다.

### 공인 IP

인터넷에서 실제로 식별 가능한 주소다.

외부 인터넷과 통신할 때는 사설 IP가 그대로 인터넷 전체에서 사용되는 것이 아니라 **NAT(Network Address Translation)** 등을 거쳐 공인 IP를 통해 통신하게 된다.

흐름은 다음처럼 이해하면 된다.

```text
내 VM의 사설 IP
→ Windows/가상 네트워크
→ 게이트웨이
→ NAT
→ 공인 IP
→ 인터넷
```

# 9. Gateway

게이트웨이는 쉽게 말해 **내 네트워크 밖으로 나가는 출구**다.

내가 통신하려는 대상이 같은 네트워크 안에 없으면 데이터를 기본 게이트웨이로 전달하고, 이후 라우터들이 목적지까지 경로를 이어 준다.

Linux에서는 다음 명령으로 라우팅 정보를 확인할 수 있다.

```bash
ip route
```

기본 경로만 보고 싶다면 `default` 항목을 확인하면 된다.

Windows에서는 다음 명령으로 IP 주소와 기본 게이트웨이를 확인할 수 있다.

```powershell
ipconfig
```

# 10. Multipass에서 본 네트워크 구조

Multipass의 Ubuntu에서 보이는 IP는 실제 Wi-Fi 공유기가 직접 준 주소와 다를 수 있다.

가상 머신은 Windows 안에 만들어진 **가상 네트워크**를 사용하기 때문이다.

대략적인 구조는 다음처럼 이해하면 된다.

```text
Ubuntu VM
    ↓
가상 네트워크 인터페이스
    ↓
Windows Host
    ↓
Windows의 실제 Wi-Fi / Ethernet
    ↓
공유기 / 게이트웨이
    ↓
인터넷
```

그래서 VM에서 `ip route`를 실행하면 VM 기준 게이트웨이가 나오고, Windows에서 `ipconfig`를 실행하면 실제 PC 기준 네트워크 정보가 나온다.

이 구조는 이후 AWS 같은 클라우드의 가상 네트워크를 이해하는 데도 도움이 된다.

# 11. traceroute와 Hop

`traceroute`는 내 컴퓨터에서 목적지까지 데이터가 어떤 중간 장비를 거쳐 가는지 확인하는 명령어다.

예:

```bash
traceroute 8.8.8.8
```

각 중간 단계 하나를 **Hop**이라고 한다.

```text
내 VM
→ VM Gateway
→ Windows/로컬 네트워크
→ ISP 네트워크
→ 여러 라우터
→ 목적지
```

처럼 여러 Hop을 거쳐 최종 목적지에 도착한다.

따라서 traceroute를 보는 이유는 단순히 경로를 구경하기 위해서가 아니라,

> 통신 장애가 발생했을 때 어느 구간까지 정상이고 어느 지점 이후부터 문제가 생기는지 범위를 좁히기 위해서다.

라는 것이 핵심이다.

# 12. ping은 무엇을 보는가

`ping`은 상대 장비까지 기본적인 IP 통신이 가능한지 확인하는 가장 간단한 도구다.

예:

```bash
ping 8.8.8.8
```

Linux에서는 보통 횟수를 지정해서 사용할 수 있다.

```bash
ping -c 10 8.8.8.8
```

Windows에서는 다음처럼 사용한다.

```powershell
ping 8.8.8.8 -n 10
```

ping 결과에서는 주로 다음을 본다.

- 응답 여부
- 왕복 지연시간
- 패킷 손실

하지만 ping이 실패했다고 해서 원인이 무조건 인터넷 회선이라고 단정할 수는 없다.

방화벽, 라우팅, 장비 상태, 상대 장비의 ICMP 차단 등 여러 원인이 있을 수 있으므로 다른 정보와 함께 봐야 한다.

# 13. 네트워크 장애를 볼 때의 사고방식

오늘 수업에서 가장 실무적으로 중요한 부분은 이 흐름이다.

```text
"인터넷이 안 된다"
```

라는 결과만 보고 끝내는 것이 아니라 원인을 계층별로 좁혀야 한다.

### 1단계: 물리 연결

- 랜카드가 활성화되어 있는가?
- Wi-Fi가 연결되어 있는가?
- 링크가 살아 있는가?
- 케이블이나 장비 문제가 없는가?

### 2단계: 내 주소

- IP 주소가 정상인가?
- DHCP로 주소를 제대로 받았는가?
- 서브넷이 맞는가?

### 3단계: 로컬 통신

- 같은 네트워크의 다른 장비와 ping이 되는가?
- 게이트웨이까지 ping이 되는가?

### 4단계: 외부 통신

- 공인 IP까지 나가는가?
- `8.8.8.8` 같은 외부 IP에 도달하는가?

### 5단계: 경로 확인

- traceroute에서 어느 Hop부터 응답이 없어지는가?

이런 식으로 확인하면 "안 된다"를 구체적인 장애 지점으로 바꿀 수 있다.

# 14. 1계층: 물리 계층

물리 계층은 실제 신호를 전달하는 가장 아래 계층이다.

여기서는 목적지 IP를 판단하거나 패킷 경로를 계산하지 않는다.

핵심 역할은

```text
0과 1의 비트
→ 전기/무선/광 신호
→ 실제 매체를 통해 전달
```

하는 것이다.

따라서 물리계층 문제는 다음과 관련된다.

- 케이블
- 랜카드
- Wi-Fi 신호
- 대역폭
- 신호 감쇄
- 잡음
- 누화
- 링크 상태

# 15. 대역폭, 처리량, 지연시간

네트워크 속도를 볼 때 단순히 "몇 Mbps"만 보면 안 된다.

### 대역폭(Bandwidth)

이론적으로 한 번에 얼마나 많은 데이터를 보낼 수 있는지 나타내는 통로의 크기다.

### 처리량(Throughput)

실제로 일정 시간 동안 성공적으로 전달된 데이터 양이다.

대역폭이 1Gbps라고 해서 항상 실제 처리량도 1Gbps가 나오는 것은 아니다.

### 지연시간(Latency)

데이터가 목적지까지 갔다가 응답이 돌아오는 데 걸리는 시간과 관련된 값이다.

따라서 네트워크 성능은 대략 다음 세 가지를 함께 봐야 한다.

```text
대역폭은 충분한가?
실제 처리량은 얼마나 나오는가?
응답 지연은 얼마나 발생하는가?
```

# 16. bit와 Byte를 혼동하면 안 되는 이유

네트워크 속도는 보통 `bit/s` 단위로 표현된다.

하지만 파일 크기는 보통 `Byte` 단위로 표현한다.

```text
1 Byte = 8 bit
```

따라서 단순 계산에서는

```text
1 Gbps ÷ 8
≈ 125 MB/s
```

처럼 bit를 Byte로 변환해야 한다.

즉 "1Gbps 인터넷이면 초당 1GB 파일을 보낸다"라고 이해하면 안 된다.

---

# 17. iperf3를 사용하는 이유

인터넷 속도 측정 사이트는 외부 인터넷 전체 경로의 영향을 받는다.

반면 `iperf3`는 서버와 클라이언트를 직접 두고 **두 장치 사이의 실제 TCP/UDP 처리량**을 측정하는 데 사용할 수 있다.

기본 구조는 다음과 같다.

서버:

```bash
iperf3 -s
```

클라이언트:

```bash
iperf3 -c <서버 IP>
```

따라서 같은 로컬 네트워크의 두 장비 사이에서 테스트하면 인터넷 회선 전체가 아니라 **해당 네트워크 구간의 실제 처리 성능**을 보는 데 유용하다.

---

# 18. 전이중, 반이중, 단방향

두 장치가 통신할 때 데이터가 흐르는 방향도 중요하다.

### 단방향(Simplex)

한 방향으로만 통신한다.

```text
A → B
```

### 반이중(Half Duplex)

양쪽 모두 보낼 수 있지만 동시에 보내지는 못한다.

```text
A → B
잠시 후
A ← B
```

### 전이중(Full Duplex)

양쪽이 동시에 송수신할 수 있다.

```text
A ↔ B
```

현재 일반적인 Ethernet 환경에서는 전이중 방식이 많이 사용된다.

---

# 19. 랜선이 꼬여 있는 이유

일반적인 Ethernet 케이블 내부에는 여러 가닥의 선이 있고, 두 가닥씩 꼬여 있는 **Twisted Pair** 구조를 사용한다.

중요한 목적은 외부 잡음과 선 사이의 간섭 영향을 줄이는 것이다.

따라서 물리계층에서는 단순히 "케이블이 연결되어 있는가"뿐 아니라 케이블 규격과 품질도 실제 통신 품질에 영향을 줄 수 있다.

---

# 20. Wi-Fi도 1계층이다

Wi-Fi는 선이 없지만 결국 데이터를 **무선 신호**로 전달하므로 물리계층의 영향을 받는다.

확인할 수 있는 대표 정보는 다음과 같다.

- 주파수 대역
- 채널
- 신호 세기
- 연결 속도
- 무선 규격
- 사용 중인 프로토콜

수업에서는 Windows 네트워크 속성에서 `802.11ax` 같은 Wi-Fi 규격을 확인했다.

중요한 것은

> Wi-Fi도 아무 규칙 없이 동작하는 것이 아니라 IEEE 표준에 정의된 규칙을 따라 통신한다.

는 점이다.

---

# 21. 가상머신에서는 물리 Wi-Fi 정보를 직접 보기 어려운 이유

Multipass VM 안에서는 실제 노트북의 Wi-Fi 장치를 직접 사용하는 것이 아니라 **가상 네트워크 인터페이스**를 사용한다.

따라서 VM 내부에서는 실제 Wi-Fi의

- 주파수
- 채널
- 실제 무선 신호 세기

같은 정보를 직접 확인하기 어렵다.

AWS도 비슷한 개념이다.

클라우드 사용자는 AWS가 관리하는 실제 물리 네트워크 위에 만들어진 가상 네트워크를 사용하므로, 실제 케이블이나 물리 스위치를 직접 제어하지 않는다.

---

# 22. 랜카드는 1계층과 2계층에 모두 관련된다

랜카드 내부를 개념적으로 나누면 다음처럼 볼 수 있다.

### PHY

실제 전기/무선 신호를 처리한다.

→ 1계층

### MAC Controller

MAC 주소와 프레임 처리를 담당한다.

→ 2계층

그래서 랜카드는 단순히 선을 연결하는 부품이 아니라,

```text
물리 신호 처리
+
MAC 기반 데이터 전달
```

두 역할을 연결해 주는 장치라고 이해할 수 있다.

---

# 23. Hub와 Switch

두 장비는 겉보기에는 여러 랜선을 연결한다는 점이 비슷하지만 동작 방식이 다르다.

### Hub

한 포트로 들어온 신호를 다른 포트들에 그대로 전달한다.

```text
A가 전송
→ B, C, D 모두에게 전달
```

물리계층에 가까운 장비다.

### Switch

필요한 목적지 포트를 판단하여 해당 장치 쪽으로 전달한다.

```text
A가 B에게 전송
→ B가 연결된 포트로 전달
```

특히 L2 Switch는 MAC 주소를 이용하여 프레임을 전달한다.

따라서 실무 네트워크에서는 단순히 신호를 복제하는 Hub보다 Switch가 훨씬 중요하다.

---

# 24. Ethernet과 IEEE 표준

Ethernet은 유선 LAN에서 사용하는 대표적인 네트워크 기술이다.

서로 다른 회사가 만든 장비라도 통신할 수 있는 이유는 공통된 표준을 따르기 때문이다.

대표적으로 오늘 본 것은 다음과 같다.

```text
IEEE 802.3
→ Ethernet 관련 표준

IEEE 802.11 계열
→ Wi-Fi 관련 표준
```

즉 네트워크는 장비 회사가 각자 임의로 만든 방식으로 통신하는 것이 아니라, 표준 문서를 기반으로 구현된다.

---

# 25. RFC와 표준 문서를 보는 이유

오늘 수업에서 RFC 1918, CIDR 관련 표준 등 문서를 계속 확인한 이유는 단순히 이론을 외우기 위해서가 아니다.

실무에서는

```text
현재 설정 확인
→ 어떤 표준/규칙을 따라야 하는지 확인
→ 현재 설정과 표준 비교
→ 이상 여부 판단
```

과정이 중요하다.

즉 AI에게도 단순히

```text
"내 네트워크 알려줘"
```

라고 하는 것보다,

```text
"현재 설정을 확인하고
관련 표준과 비교해서
문제가 있는 부분을 설명해줘"
```

라고 요청하는 방식이 더 실무적이다.

---

# 26. DHCP와 자동 IP 할당

Windows IPv4 속성에서

```text
자동으로 IP 주소 받기
```

로 설정되어 있다면 일반적으로 DHCP를 통해 IP 주소를 자동으로 할당받는 구조다.

사용자가 직접 IP를 고정할 수도 있지만, 같은 네트워크 안에서 이미 사용 중인 주소를 중복으로 설정하면 통신 문제가 발생할 수 있다.

따라서 네트워크 자동화에서는 현재 IP가

- DHCP로 받은 주소인지
- 고정 IP인지
- 다른 장비와 충돌 가능성이 있는지

같은 정보도 확인할 수 있다.

# 27. 오늘 수업과 AI Agent가 연결되는 부분

오늘 수업의 목적은 명령어만 외우는 것이 아니었다.

명령어로 네트워크 상태를 수집한 뒤, 그 결과를 바탕으로 **자동 진단 Agent**까지 만들 수 있다는 흐름을 봤다.

예를 들어 다음 정보를 주기적으로 수집할 수 있다.

```text
ping 결과
traceroute 결과
IP / Gateway
Wi-Fi 신호
처리량
대역폭
패킷 손실
```

그리고 Agent가 이를 분석해서

```text
정상
↓
지연시간 증가
↓
게이트웨이는 정상
↓
외부 구간에서 손실 발생
↓
관리자에게 알림
```

처럼 판단하도록 만들 수 있다.

더 발전시키면 일정 조건에 따라

- 네트워크 상태 기록
- 관리자 알림
- Wi-Fi 재연결
- 특정 서비스 재시작
- 정기 리포트 생성

같은 자동화도 가능하다.

# 29. 명령어를 외우는 것보다 중요한 것

오늘 내용에서 명령어보다 더 중요한 것은 **각 명령을 언제 사용하는가**다.

```text
내 주소가 궁금하다
→ ipconfig / ip addr

어디로 나가는지 궁금하다
→ ip route / 기본 게이트웨이

상대 장비까지 연결되는지 궁금하다
→ ping

어느 경로에서 문제가 생기는지 궁금하다
→ traceroute

실제 데이터 전송 성능이 궁금하다
→ iperf3
```

즉 명령어를 외워서 입력하는 것이 목적이 아니라,

> 문제를 확인하기 위해 필요한 정보를 어떤 도구로 얻을지 판단할 수 있어야 한다.

는 것이 핵심이다.

# 30. 오늘 수업의 최종 정리

오늘 네트워크 수업을 하나의 그림으로 정리하면 다음과 같다.

```text
[1계층]
케이블 / Wi-Fi / 랜카드 / 신호
        ↓
장치가 실제로 통신 가능한 상태인가?
        ↓

[2계층]
MAC 주소 / Frame / Switch
        ↓
같은 네트워크 안에서 어디로 전달할 것인가?
        ↓

[3계층]
IPv4 / Subnet / CIDR / Gateway / Router
        ↓
다른 네트워크의 목적지까지 어떤 경로로 갈 것인가?
        ↓

[NAT / Internet]
사설 IP → 공인 IP
        ↓

[진단]
ping / traceroute / iperf3
        ↓

[자동화]
수집 → 분석 → 이상 탐지 → 알림/복구
```

결국 오늘 배운 핵심은 **네트워크를 단순한 IP 주소 모음으로 보는 것이 아니라, 물리 연결부터 주소 체계·경로·성능까지 단계적으로 연결해서 보는 사고방식**이다.

앞으로 AWS나 클라우드 네트워크를 다룰 때도 실제 케이블은 직접 보지 않지만,

```text
IP
Subnet
CIDR
Gateway
Route
NAT
```

같은 개념은 그대로 사용된다.

그래서 오늘 배운 로컬 PC와 Multipass의 네트워크 구조를 이해하는 것이 이후 클라우드 네트워크를 이해하는 기초가 된다.
