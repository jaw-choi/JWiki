## 먼저 짚는 전사 품질과 확인 필요 사항

특히 다음은 그대로 암기하지 말고 보정해야 한다.

- **[기술적 보정]** `ping`은 목적지까지의 도달 가능성과 왕복 시간, 패킷 손실을 보는 도구다. 중간에 거치는 경로를 확인하는 명령은 Windows의 `tracert` 또는 Linux/macOS의 `traceroute`다.
- **[기술적 보정]** `TTL`은 패킷이 네트워크를 무한 순환하지 않도록 홉마다 감소하는 수명 값이다. timeout 자체를 뜻하지 않는다.
- **[기술적 보정]** Wi-Fi라고 해서 항상 IP가 바뀌고 유선이라고 고정되는 것은 아니다. 동적/고정 여부는 DHCP 및 네트워크 정책에 달려 있다. 가정·교육장 네트워크에서는 보통 DHCP로 사설 IP를 동적 할당한다.
- **[기술적 보정]** DNS는 “IP를 DNS로 바꾸는 것”이 아니라, 보통 사람이 읽는 도메인 이름을 IP 주소로 해석(resolve)한다.
- **[기술적 보정]** IP 주소를 개인이 절대 구매할 수 없는 것은 아니다. 일반 사용자는 ISP나 클라우드 사업자에게 할당·임대받는 경우가 대부분이며, 조직은 인터넷 레지스트리 정책에 따라 주소 자원을 할당받을 수도 있다.
- **[기술적 보정]** 목업(mockup)은 화면이나 제품의 시각적 모형이고, 다이어그램은 관계·구조·흐름을 표현한다. 겹칠 수 있지만 동의어는 아니다.
- **[기술적 보정]** 브라우저 캐시는 성능을 높이지만 비밀번호가 반드시 평문 캐시 파일로 저장된다는 뜻은 아니다. 쿠키, 세션 토큰, 브라우저 저장소, 자격 증명 저장소는 구분해야 한다.
- **[확인 필요]** “2018년부터 일반인이 AI를 사용”이라는 전사 구간은 음성 인식이 크게 훼손되어 정확한 강의 주장과 근거를 복원하기 어렵다.

1. **[수업]** 신입에게 완성된 전문가 수준을 기대하기보다, 기초 지식과 장애 상황의 여러 가능성을 이해하고 설명하는 역량을 중요하게 본다.
2. **[수업]** 클라우드 엔지니어는 관리형 서비스를 단순히 클릭하는 사람이 아니라, 네트워크·서버·비용·보안·장애 대응을 이해한 상태에서 서비스를 연결해야 한다.
3. **[수업]** 온프레미스와 클라우드는 편의성만으로 선택하지 않고 보안, 비용, 구축 속도, 운영 능력, 규제 요구를 함께 판단해야 한다.
4. **[수업]** AWS·GCP·Azure는 제공 기능이 겹치지만 각 서비스의 결합 방식, 강점, 비용 구조, 조직의 기존 환경이 다르므로 요구사항에 맞춰 선택한다.
5. **[수업]** 여러 서비스·서버·컨테이너·작업을 목적에 맞게 연결하고 운영하는 관점을 오케스트레이션이라고 이해할 수 있다.
6. **[수업]** 네트워크 장애는 내 PC, 어댑터, 공유기/게이트웨이, DNS, ISP, 원격 서버 등 여러 지점에서 생길 수 있어 단계적으로 범위를 좁혀야 한다.
7. **[수업]** PowerShell이나 CMD 명령을 사용하면 네트워크 상태 확인과 어댑터 재시작 같은 작업을 규칙적으로 자동화할 수 있다.
8. **[수업]** LLM에게 모든 판단을 맡기기보다 IP 범위 검사처럼 규칙이 명확한 부분은 코드로 처리해야 환각과 비용을 줄일 수 있다.
9. **[멘토 보충]** 오늘의 네트워크 자동복구 예제는 `관찰 → 분류 → 도구 선택 → 실행 → 검증 → 기록`이라는 Agentic Design의 축소판이다.

# 2. 수업 내용 상세 정리

## 2.1 신입 엔지니어의 경쟁력과 직무 탐색

### 개념과 사용 목적

**[수업]** 짧은 도구 사용 경험보다 기본 이론, 문제 발생 가능성, 장애 대응 사고가 중요하다. 채용 공고의 직무명은 회사마다 통일되어 있지 않으므로 “AI 엔지니어”, “클라우드 엔지니어”, “MSP 엔지니어”, “AI PM”이라는 제목만 보지 말고 실제 업무와 요구 기술을 읽어야 한다.

### 동작 원리: 문제 해결형 엔지니어의 사고

```text
정상 동작 확인
→ 실패 증상 구체화
→ 가능한 원인 계층화
→ 관측 가능한 데이터 수집
→ 가장 저렴하고 안전한 검사부터 실행
→ 복구 조치
→ 재검증
→ 원인·조치·재발 방지 기록
``` 

### 예시

“네트워크가 안 된다”를 바로 “Wi-Fi를 껐다 켜자”로 결론 내리지 않는다. 로컬 어댑터 상태, IP 할당, 게이트웨이 도달, 외부 IP 도달, DNS 해석, 특정 서비스 상태 순으로 좁힌다.

### 주의할 점

- 포트폴리오에 “성공했다”만 쓰지 말고 문제, 제약, 장애, 측정값, 대안, 선택 이유를 남긴다.
- 공고의 긴 기술 목록을 모두 즉시 갖춰야 한다는 뜻으로 해석하지 말고, 필수/우대/도메인 지식을 나눈다.
- **[멘토 보충]** 본인의 프로젝트는 “언리얼에서 AI를 호출했다”보다 “실시간 게임 상태를 안전하게 도구 입력으로 변환하고, 실패 시 복구하며, 품질·지연·비용을 측정했다”가 훨씬 강한 서술이다.

## 2.2 온프레미스, 클라우드, 하이브리드, MSP

### 한 문장 정의

- **온프레미스:** 조직이 통제하는 자체 데이터센터나 시설에 서버와 네트워크를 구축·운영하는 방식이다.
- **클라우드:** 사업자가 제공하는 컴퓨팅·저장소·네트워크·관리형 서비스를 필요에 따라 임대해 쓰는 방식이다.
- **하이브리드 클라우드:** 온프레미스와 퍼블릭 클라우드를 연결해 데이터·업무 특성에 따라 나누어 운영하는 구조다.
- **MSP(Managed Service Provider):** 고객 대신 클라우드 및 IT 시스템의 설계·구축·운영·최적화·장애 대응을 수행하는 사업자다.

### 비교

| 판단 항목 | 온프레미스 | 퍼블릭 클라우드 | 하이브리드 |
|---|---|---|---|
| 초기 구축 | 느리고 자본 지출이 큼 | 빠른 시작 가능 | 연결·거버넌스 설계 필요 |
| 확장 | 장비 조달 필요 | 탄력 확장 가능 | 워크로드별로 다름 |
| 통제 | 물리·네트워크 통제가 큼 | 공동 책임 모델 | 경계와 책임이 복잡 |
| 비용 | 장기·고정 워크로드에 유리할 수 있음 | 사용량 기반이나 방치 시 급증 | 최적화 가능하나 운영 복잡도 증가 |
| 보안/규제 | 폐쇄망 요구 대응 용이 | 적절한 통제 구성 필요 | 민감 데이터 분리 가능 |

### 사용 목적과 주의점

**[수업]** 클라우드는 이미 만들어진 기능을 빠르게 사용할 수 있지만 비용과 보안이 선택의 핵심 이슈다. 금융·공공 등의 폐쇄망은 외부 클라우드 접속이 제한될 수 있다.

**[멘토 보충]** “클라우드는 보안이 약하다”가 아니라 책임 분담과 설정 오류 위험을 이해해야 한다. 조직의 규제, 데이터 위치, IAM, 암호화, 감사 요구에 따라 설계한다.

## 2.3 AWS, Google Cloud, Microsoft Azure

### 수업에서 다룬 관점

**[수업]** 세 플랫폼은 컴퓨팅, 데이터 처리, AI, 네트워크, 저장소 등 유사한 기능을 제공하지만 역사적 강점과 서비스 구성 방식이 다르다. 기업은 하나만 쓰기도 하고 멀티클라우드 또는 하이브리드로 조합하기도 한다.

### 프로젝트 관점의 대응 예시 — 멘토 보충

| 필요 기능 | AWS 예시 | 프로젝트에서의 역할 |
|---|---|---|
| 컨테이너 실행 | ECS/EKS | FastAPI·Agent 서비스 배포 |
| 객체 저장 | S3 | 게임 지식 원문·평가 데이터셋 저장 |
| 모델/API | Bedrock 또는 외부 LLM API | Agent 추론 |
| 벡터 검색 | OpenSearch, RDS pgvector 등 | RAG 검색 |
| 관측 | CloudWatch, X-Ray 계열 | latency/error/cost 추적 |
| 비밀 관리 | Secrets Manager | API 키·DB 자격 증명 |

### 주의할 점

- “AWS는 데이터, GCP는 AI, Azure는 사내 서버”라는 단순 구분은 입문용 비유일 뿐 절대적인 기술 분류가 아니다.
- 서비스 이름과 기능은 자주 바뀌므로 공식 문서를 기준으로 검증한다.
- 처음부터 멀티클라우드를 목표로 하면 학습·운영 복잡도가 급격히 커진다. 최종 프로젝트는 우선 한 클라우드에서 완성한 뒤 이식 가능 경계를 문서화하는 편이 좋다.

## 2.4 오케스트레이션과 워크플로우

### 개념

**오케스트레이션:** 여러 작업·서비스·컨테이너의 실행 순서, 상태, 재시도, 확장, 실패 처리를 중앙 규칙으로 조정하는 것이다.

### 수업 예시

**[수업]** 제조 공정에서 데이터베이스, 컴퓨터 비전, 자연어 처리 등 서로 다른 서버나 컨테이너를 유기적으로 연결해야 한다. 어떤 서비스를 한 번에 제공받을지, 여러 서비스를 결합할지는 비용과 기능 요구에 따라 달라진다.

### 프로젝트에서 구분해야 할 세 층 — 멘토 보충

1. **Agent orchestration:** LangGraph가 의도 분류, RAG, tool call, 검증, 응답 합성 순서를 관리한다.
2. **Application orchestration:** FastAPI, worker, queue, vector DB 사이의 요청 흐름과 재시도를 관리한다.
3. **Infrastructure orchestration:** Kubernetes가 컨테이너 배치, health check, 재시작, 확장을 관리한다.

세 가지를 모두 “오케스트레이션”이라고 부르지만 해결하는 문제가 다르다.

## 2.5 네트워크 기본 구조: IP, DNS, ISP, 게이트웨이

### 핵심 용어

- **IP 주소:** 네트워크에서 장치 또는 인터페이스를 식별하고 패킷을 전달하는 논리 주소다.
- **도메인 이름:** 사람이 기억하기 쉬운 서비스 이름이다.
- **DNS:** 도메인 이름을 IP 주소 등 DNS 레코드로 해석하는 분산 시스템이다.
- **ISP:** 인터넷 접속 회선과 관련 서비스를 제공하는 사업자다.
- **게이트웨이:** 서로 다른 네트워크로 나가는 출입점 역할을 하는 장치 또는 주소다.
- **DHCP:** 장치에 IP, 게이트웨이, DNS 등의 네트워크 설정을 자동 할당하는 프로토콜이다.

### 요청·응답 동작 원리

```text
사용자가 game-ai.example.com 입력
→ DNS가 이름을 IP로 해석
→ 클라이언트가 게이트웨이·ISP·인터넷 경로를 통해 서버로 요청
→ 서버/FastAPI가 요청 검증 및 처리
→ 응답 패킷이 클라이언트로 반환
→ Unreal Engine이 응답을 게임 상태에 반영
```

### 장애 범위 좁히기

| 단계 | 확인 대상 | 대표 검사 |
|---|---|---|
| 1 | 로컬 인터페이스 | 어댑터 enabled/connected 여부 |
| 2 | IP 설정 | `ipconfig /all` |
| 3 | 로컬 게이트웨이 | 게이트웨이에 `ping` |
| 4 | 외부 IP | `ping 8.8.8.8` 등, 단 ICMP 차단 가능 |
| 5 | DNS | `nslookup example.com` 또는 `Resolve-DnsName` |
| 6 | 경로 | `tracert example.com` |
| 7 | 애플리케이션 | HTTP 상태 코드, TCP 포트, 서버 로그 |

`ping` 실패만으로 인터넷 장애를 확정하면 안 된다. 서버나 방화벽이 ICMP를 차단해도 HTTPS는 정상일 수 있다.

| 명령/조작 | 목적 | 주요 옵션·주의 |
|---|---|---|
| `Win + R` → `ncpa.cpl` | 네트워크 연결 제어판 열기 | 어댑터 목록·속성 확인 |
| `ipconfig` | 기본 IP 구성 확인 | 상세 정보는 `ipconfig /all` |
| `ping 8.8.8.8` | 외부 IP 도달 가능성과 왕복 응답 확인 | ICMP 차단 가능, DNS 검사는 아님 |
| `Get-NetAdapter` | PowerShell에서 네트워크 어댑터 조회 | 관리자 권한이 필요한 후속 작업이 있음 |
| `Disable-NetAdapter` | 어댑터 비활성화 | 현재 원격 접속을 끊을 수 있어 주의 |
| `Enable-NetAdapter` | 어댑터 활성화 | 정확한 어댑터 이름 필요 |
| `Start-Sleep -Seconds 10` | 스크립트 실행을 10초 대기 | 고정 대기는 느리고 불안정할 수 있음 |
| `Export-Csv` | 구조화된 결과를 CSV로 저장 | `-NoTypeInformation`을 자주 함께 사용 |

### 전사 내용을 복원한 PowerShell 예시 — 멘토 보충

아래는 수업의 의도를 안전하게 이해하기 위한 예시이며, 강사가 제시한 원본 코드와 동일하다고 볼 수 없다.

```powershell
$adapterName = "Wi-Fi"

Disable-NetAdapter -Name $adapterName -Confirm:$false
Start-Sleep -Seconds 10
Enable-NetAdapter -Name $adapterName -Confirm:$false

$adapter = Get-NetAdapter -Name $adapterName
$ipv4 = Get-NetIPAddress -InterfaceAlias $adapterName -AddressFamily IPv4 `
  -ErrorAction SilentlyContinue
$reachable = Test-Connection -TargetName "8.8.8.8" -Count 2 -Quiet

[pscustomobject]@{
    Timestamp = Get-Date
    Adapter   = $adapter.Name
    Status    = $adapter.Status
    IPv4      = ($ipv4.IPAddress -join ",")
    Reachable = $reachable
} | Export-Csv -Path ".\network-report.csv" -NoTypeInformation
```

### 실행 흐름

1. 대상 어댑터 이름을 정한다.
2. 어댑터를 비활성화한다.
3. 10초 대기 후 다시 활성화한다.
4. 어댑터 상태와 IPv4 주소를 수집한다.
5. 외부 IP에 간단한 도달 테스트를 한다.
6. 사람이 읽고 프로그램이 재사용할 수 있는 CSV로 기록한다.

### 주의점

- 관리자 권한이 필요할 수 있다.
- 원격 PC에서 실행하면 자기 자신의 관리 연결을 끊을 수 있다.
- 어댑터 이름은 PC마다 `Wi-Fi`, `Wi-Fi 2`, 로컬 언어 이름 등으로 다르다. 하드코딩보다 조회·선택 로직이 필요하다.
- 단순 재시작은 원인 분석이 아니다. 재발 시 로그와 네트워크 계층별 검사 결과를 남긴다.
- 외부 공개 IP 하나에 대한 ping만으로 서비스 정상 여부를 판단하지 않는다.

## 2.7 네트워크 자가진단·자동복구 에이전트

### 개념

**[수업]** 사용자가 “인터넷이 안 돼요”라고 말하면 AI가 네트워크 문제로 분류하고, 여러 도구 중 적절한 도구를 불러 상태를 확인하고, 복구를 실행하고, 결과 보고서까지 작성하는 흐름을 에이전트 사례로 설명했다.

### 동작 원리

```text
사용자 자연어/이벤트
→ 의도 분류
→ 안전한 진단 도구 호출
→ 구조화 결과 수집
→ 규칙 기반 판단
→ 허용된 복구 도구 호출
→ 복구 후 재검증
→ 결과 및 증거 보고
```

### 하나의 에이전트인가 여러 에이전트인가

**[수업]** 진단, 복구, 보고를 한 에이전트에 넣을지 여러 에이전트로 나눌지는 설계 문제라고 설명했다.

**[멘토 보충]** 이 규모에서는 여러 LLM 에이전트보다 **한 개의 상태 그래프 + 여러 결정적 도구**가 더 단순하고 검증하기 쉽다. 역할을 노드로 나누되 모든 노드가 LLM일 필요는 없다.

### 안전 설계

- 조회 도구와 변경 도구를 분리한다.
- 어댑터 비활성화 같은 변경에는 정책 검사와 사용자 확인 단계를 둔다.
- 도구 입력은 JSON Schema/Pydantic으로 제한한다.
- 실행 timeout, 재시도 횟수, 허용 명령 목록을 둔다.
- 명령 원문, 결과, exit code, latency를 감사 로그로 남긴다.

## 2.8 LLM 판단과 결정적 코드의 경계

### 수업의 가장 중요한 구현 원리

**[수업]** 회사가 허용하는 IP 범위가 명확하다면 LLM에게 “문제가 있는지 보고서를 써 달라”고 맡길 것이 아니라 코드로 범위를 검사해야 한다. 이렇게 해야 토큰 사용과 환각을 줄일 수 있다.

### 구분 기준 — 멘토 보충

| 문제 유형 | 권장 방식 | 예시 |
|---|---|---|
| 규칙이 정확하고 검증 가능 | 일반 코드 | IP CIDR 포함 여부, 숫자 범위, 권한 검사 |
| 자연어가 모호함 | LLM 보조 | 사용자 장애 설명 의도 분류 |
| 외부 상태 확인 필요 | 도구/API | 게임 상태, DB 조회, 네트워크 진단 |
| 결과가 위험한 변경 | 코드 정책 + 승인 | 서버 재시작, 네트워크 차단 |
| 설명 생성 | LLM + 근거 데이터 | 진단 결과를 사용자용 문장으로 변환 |

이 원리는 최종 프로젝트에서도 그대로 적용된다. HP, 골드, 퀘스트 상태 같은 숫자·불리언 규칙은 코드가 판단하고, 자연어 대화와 계획 생성만 LLM이 담당해야 한다.

## 2.9 CSV 보고서와 구조화 데이터

### 개념과 목적

**CSV:** 행과 열을 쉼표로 구분하는 단순한 텍스트 표 형식이다.

**[수업]** `ipconfig` 등의 결과를 정해진 열에 넣어 CSV 보고서로 만들면 결과를 반복적으로 비교하고 다른 프로그램에서 처리할 수 있다고 설명했다.

### 프로젝트 보충

운영 이벤트는 CSV보다 JSON 로그나 시계열/관측 플랫폼이 더 적합할 수 있다. 최소 필드는 다음처럼 정한다.

```json
{
  "trace_id": "uuid",
  "session_id": "game-session-42",
  "event": "tool_call",
  "tool": "get_quest_state",
  "success": true,
  "latency_ms": 83,
  "cost_usd": 0.0021,
  "timestamp": "ISO-8601"
}
```

## 2.10 HTTP 요청·응답과 브라우저 캐시

### 동작 원리

**[수업]** 브라우저에서 사이트를 입력하면 HTML·이미지 등의 자료를 요청(request)하고 서버가 응답(response)한다. 한 번 받은 정적 자료는 캐시에서 재사용될 수 있어 다음 접속이 빨라질 수 있다.

### 프로젝트 연결

- Unreal Engine은 FastAPI에 JSON 요청을 보내고 JSON 또는 스트리밍 이벤트를 응답받는다.
- 동일한 게임 지식 검색이나 변하지 않는 설정을 캐시하면 latency와 LLM/검색 비용을 줄일 수 있다.
- 그러나 게임 상태는 빠르게 변하므로 무조건 캐시하면 오래된 상태(stale state)를 사용하게 된다.

### 주의점

- HTTP 캐시는 `Cache-Control`, `ETag`, 만료 시간 등 정책에 따라 동작한다.
- 인증 토큰, 개인 정보, 세션 데이터는 민감 정보로 취급한다.
- AI 응답 캐시는 프롬프트뿐 아니라 사용자, 게임 버전, 월드 상태, 지식베이스 버전까지 키에 포함할지 설계해야 한다.

## 2.11 AI 생성 결과, 프롬프트, HTML 실습

### 수업 내용

**[수업]** AI에게 자료와 예시를 첨부하고 문서를 정리시키거나, 네트워크 구성을 HTML 시각화로 만들고, 후속 프롬프트로 인터랙티브 요소를 추가하는 방식을 소개했다. 한 번에 모든 요구를 넣기보다 기본 결과를 만든 뒤 단계적으로 개선하고, 생성 결과를 꼼꼼히 검수하라고 강조했다.

### 핵심 원리

- 입력 자료, 목적, 대상 독자, 출력 형식을 명시한다.
- 큰 작업은 초안 → 기능 추가 → 검증으로 나눈다.
- 앞선 결과가 사라지지 않도록 변경 범위를 구체적으로 지정한다.
- AI의 자기검수만 믿지 말고 실행 테스트와 사람 검토를 함께한다.

# 4. 내 관심 분야와의 연결

## AI Agent — 직접 관련 있음

네트워크 자동복구 사례는 자연어 입력을 분류하고 로컬 도구를 선택해 실행한 뒤 결과를 검증·보고하는 단순 에이전트다. 핵심은 LLM 자체보다 **도구 권한, 상태, 분기, 실패 처리, 재검증**이다.

## LangGraph — 개념적으로 직접 관련 있음, 수업에서 프레임워크 자체는 다루지 않음

수업의 흐름을 LangGraph로 옮기면 `intake → diagnose → policy_check → repair → verify → report` 노드가 된다. “한 에이전트냐 여러 에이전트냐”보다 먼저 하나의 상태 그래프로 명시적으로 설계하는 것이 적절하다.

## RAG — 오늘 수업과 직접적인 관련 없음

전사에는 문서 검색형 RAG의 chunking, embedding, retrieval, reranking 구현이 나오지 않았다. 다만 “기존 데이터베이스와 연결해 답한다”는 넓은 아이디어와 LLM 의존을 줄이라는 원칙은 RAG 설계에도 유효하다.

## Tool Calling / MCP — Tool Calling은 직접 관련, MCP는 직접 다루지 않음

PowerShell·`ipconfig`·`ping`을 호출하는 아이디어가 Tool Calling에 해당한다. MCP 프로토콜, 서버·클라이언트, transport, capability negotiation은 수업에서 다루지 않았다. 최종 프로젝트에서는 Game API를 직접 function tool로 감싼 뒤 필요하면 MCP 서버로 노출하는 순서가 좋다.

## FastAPI — 오늘 수업과 직접적인 관련 없음

HTTP request/response와 URL의 기초만 연결된다. FastAPI route, Pydantic model, async, dependency injection, WebSocket 구현은 수업에서 나오지 않았다.

## Unreal Engine 연동 — 오늘 수업과 직접적인 관련 없음

다만 네트워크 연결과 요청/응답의 원리는 기반 지식이다. UE에서 HTTP/WebSocket 실패를 `DNS 실패`, `connect timeout`, `read timeout`, `4xx`, `5xx`, `schema 오류`로 구분해야 한다.

## Docker / AWS / Kubernetes — AWS·클라우드·오케스트레이션 개념은 관련, Docker/Kubernetes 실습은 없음

AWS/GCP/Azure와 컨테이너 조합을 언급했지만 Dockerfile, image, pod, deployment, service 등의 실제 명령·리소스는 다루지 않았다.

## Evaluation / Monitoring — 원리상 직접 관련 있음

자가진단 결과를 보고서로 남기고 성공 여부를 재검증한다는 점이 Agent Evaluation의 시작이다. 다만 hallucination, latency, cost, tool success rate의 구체적 계산법은 수업에 없었다.

# 5. 최종 프로젝트 적용 방법

## 제안 기능: 게임 운영관/동료 NPC 에이전트

플레이어의 자연어 요청과 현재 게임 상태를 받아, 게임 지식 RAG를 참고하고, 허용된 Game API 도구를 호출한 뒤, 결과를 검증하여 자연어 또는 구조화된 행동 명령으로 반환한다.

## 시스템 흐름도

```text
Unreal Engine
  │  REST: 단발 요청 / WebSocket: 토큰·이벤트 스트리밍
  ▼
FastAPI Gateway
  │  인증, 스키마 검증, timeout, trace_id
  ▼
LangGraph Agent
  ├─ Intent / Safety Router
  ├─ RAG Retriever ──> Vector DB + Game Knowledge
  ├─ Memory ─────────> Session / Long-term Memory
  ├─ Tool Policy
  └─ Tool Executor ──> Game State Service / Game API
                         │
                         └─ 결과 및 버전 반환
  ▼
Verifier / Response Composer
  ▼
FastAPI → Unreal Engine 응답 반환

공통 관측: trace, node latency, token/cost, retrieval evidence,
tool success, task success, error code
```

```json
  "game_state_version": 1842,
  "context": {
    "map_id": "forest_01",
    "position": {"x": 10.2, "y": 5.1, "z": 1.0},
    "hp": 27,
    "active_quest_ids": ["q-19"]
  }
}
```

### 2. Agent 응답

```json
{
  "run_id": "run-uuid",
  "trace_id": "trace-uuid",
  "reply": "북동쪽 야영지로 이동하세요.",

    {"type": "SET_NAV_TARGET", "target_id": "camp-3"}

```

### 3. 도구 계약 예시

```json
{
  "name": "set_navigation_target",
  "input": {
    "player_id": "player-7",
    "target_id": "camp-3",
    "expected_state_version": 1842,
    "idempotency_key": "run-uuid:tool-1"
  }
}
```

`expected_state_version`은 AI가 판단하는 동안 상태가 바뀌었는지 확인하고, `idempotency_key`는 재시도 때문에 같은 행동이 두 번 실행되는 것을 막는다.

## 예상 구현 순서

1. 게임 유스케이스 하나만 선택한다. 예: NPC 힌트 또는 내비게이션 타깃 설정.
2. UE↔FastAPI의 REST request/response 스키마와 오류 코드를 먼저 고정한다.
3. 실제 게임 없이 동작하는 Mock Game State API를 만든다.
4. LangGraph state와 노드, 종료 조건을 구현한다.
5. 읽기 전용 tool부터 연결하고, 이후 변경 tool에 정책·승인·멱등성을 추가한다.
6. 작은 Game Knowledge 문서셋으로 RAG baseline을 만든다.
7. 정상·실패·경계 사례 평가셋을 작성한다.
8. UE 클라이언트를 연결하고 timeout·재연결·취소를 구현한다.
9. Docker Compose로 API, vector DB, 관측 스택을 묶는다.
10. AWS에 작은 환경으로 배포한 뒤 필요할 때만 Kubernetes/EKS로 확장한다.

## 정답 핵심

1. 초기 비용·운영 통제·확장 속도·규제의 trade-off다.
2. 관리형 서비스를 연결해도 패킷 경로와 장애 지점을 이해해야 원인 분리가 가능하다.
3. 서비스 이름을 접속 가능한 IP 레코드로 해석한다.
4. `ping`은 도달성과 왕복 응답, `tracert`는 중간 홉 경로를 본다.
5. DNS, 방화벽, TCP 포트, TLS, 서버 오류, 스키마 오류 등이 있다.
6. 규칙 검사는 결정적이고 저렴하며 테스트 가능하고 환각 위험이 없다.
7. 최소 권한과 실수·공격에 의한 변경 방지를 위해서다.
8. 전자는 Agent 상태·분기, 후자는 컨테이너 배치·복구·확장을 다룬다.
9. 짧은 TTL, 이벤트 기반 무효화, 상태 버전 검사를 사용한다.
10. 도구가 모두 성공해도 잘못된 계획이면 최종 목표는 실패할 수 있다.

## 실습 과제 3개

### 과제 1: 결정적 네트워크 진단기

Python으로 `ipconfig`, DNS 조회, HTTP health check 결과를 구조화 JSON으로 만들고 규칙 기반으로 장애 계층을 분류한다. LLM은 사용하지 않는다.

### 과제 2: LangGraph 자동복구 시뮬레이터

실제 네트워크를 끊지 말고 mock tool을 사용해 `diagnose → policy_check → repair → verify → report` 그래프를 구현한다. 실패·timeout·재시도 경로를 테스트한다.

### 과제 3: Unreal↔FastAPI 최소 연결

UE에서 `POST /v1/agent/runs`를 비동기로 호출하고, FastAPI는 고정 응답과 `trace_id`를 반환한다. timeout, 422, 500을 UE 화면 또는 로그에 서로 다르게 표시한다.

## 오늘 작성해 볼 아키텍처 1개

**Game Network & Agent Diagnostic Graph**

```text
START
 → validate_request
 → get_game_state
 → check_api_health
 → [healthy?]
      ├─ yes → retrieve_game_knowledge → plan → tool_policy
      │          → execute_game_tool → verify_state → answer → END
      └─ no  → classify_failure → safe_retry

```

LangGraph state에는 `trace_id`, `session_id`, `game_state`, `state_version`, `messages`, `retrieved_docs`, `tool_calls`, `errors`, `step_count`, `cost`를 둔다.

- MCP의 실제 프로토콜과 보안 모델은 별도 학습 필요
- LangGraph checkpoint, interrupt, retry 구현은 별도 학습 필요
- RAG chunking/embedding/reranking/evaluation은 오늘 수업 범위 밖
