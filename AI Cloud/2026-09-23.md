# 2026-09-23 네트워크 수업 정리

## 오늘 수업의 한 문장

**IP는 “어느 네트워크의 어느 목적지인가”를 판단하고, MAC 주소는 “지금 이 링크에서 어느 랜카드로 프레임을 보낼 것인가”를 결정한다.** ARP, 스위치, 게이트웨이, 패킷 캡처 실습은 이 문장을 실제 통신 과정에서 확인하는 내용이었다.

---

## 1. CIDR과 서브넷: 먼저 “같은 동네인가?”를 판단한다

IPv4 주소만 보고 통신 경로를 정하지 않는다. IP 주소와 **프리픽스 길이(CIDR)** 를 함께 보아 네트워크 범위를 계산한다.

- 예: `172.16.8.5/24`
  - 네트워크 주소: `172.16.8.0`
  - 브로드캐스트 주소: `172.16.8.255`
  - 일반적으로 사용 가능한 호스트 범위: `172.16.8.1 ~ 172.16.8.254`
  - 이 범위의 호스트는 같은 서브넷에 있다고 본다.

`/24`는 앞 24비트가 네트워크 부분이라는 뜻이며, 서브넷 마스크는 `255.255.255.0`이다. 따라서 마지막 옥텟만 호스트를 구분한다. 네트워크 주소(`.0`)와 브로드캐스트 주소(`.255`)는 일반 호스트에 할당하지 않는다.

### 통신에서 서브넷 판단이 중요한 이유

송신 PC는 목적지 IP가 자신의 서브넷에 속하는지 먼저 판단한다.

1. **같은 서브넷**이면 목적지 장치의 MAC 주소를 알아내어 직접 보낸다.
2. **다른 서브넷**이면 목적지 서버의 MAC 주소를 찾지 않는다. 대신 **기본 게이트웨이의 MAC 주소**를 알아내어, 그 게이트웨이로 프레임을 보낸다.

즉 인터넷의 구글 서버로 보낼 때도, 내 PC의 첫 프레임 목적지 MAC은 보통 구글 서버의 MAC이 아니라 **우리 네트워크의 라우터(기본 게이트웨이) MAC**이다.

> 게이트웨이 주소를 `.1`이나 `.254`로 쓰는 관습은 흔하지만, 기술적으로 반드시 그 주소여야 하는 것은 아니다. 네트워크 관리자가 정한다.

## 2. IP와 MAC은 경쟁 관계가 아니라 역할 분담이다

| 구분 | IP 주소 | MAC 주소 |
|---|---|---|
| 주된 역할 | 네트워크 간 논리적 목적지/경로 판단 | 현재 링크에서 실제 NIC 식별 및 프레임 전달 |
| 계층 | 네트워크 계층(L3) | 데이터 링크 계층(L2) |
| 범위 | 라우터를 넘어 종단까지 의미 있음 | 보통 현재 LAN 구간에서만 직접 사용 |
| 예시 | `172.16.8.5` | `00-11-22-33-44-55` |

MAC 주소는 보통 48비트이며 16진수로 표시한다. PC에 Wi-Fi와 Ethernet 어댑터가 모두 있다면 각각 별도의 MAC 주소가 있을 수 있다.

핵심은 **IP로 최종 목적지를 판단하지만, 실제 이더넷/Wi-Fi 프레임은 MAC 주소를 목적지로 삼아 현재 구간을 이동한다**는 것이다.

---

## 3. ARP: IP 주소를 MAC 주소로 바꾸는 과정

같은 서브넷의 `172.16.8.10`에 ping을 보낸다고 하자.

1. PC는 목적지 IP가 같은 서브넷임을 확인한다.
2. PC는 ARP 캐시에서 `172.16.8.10`의 MAC 주소를 찾는다.
3. 없다면 LAN에 ARP Request를 브로드캐스트한다. “`172.16.8.10`은 누구인가?”라고 묻는 과정이다.
4. 해당 IP를 가진 장치가 자신의 MAC 주소를 담아 ARP Reply를 보낸다.
5. 송신 PC는 이 IP–MAC 대응을 ARP 캐시에 잠시 저장하고, 목적지 MAC으로 이더넷 프레임을 만들어 전송한다.

다른 서브넷의 주소라면 위 2~5단계의 대상이 목적지 서버가 아니라 **기본 게이트웨이**가 된다.

### ARP 테이블에서 볼 수 있는 것

Linux에서는 `ip neigh`, Windows에서는 `arp -a` 등으로 이웃/ARP 캐시를 볼 수 있다. 여기에는 보통 **내 PC가 최근 통신한 이웃 장치의 IP와 MAC 대응**이 담긴다. 내 IP와 내 MAC이 모두 반드시 표시되는 목록은 아니다.

### 꼭 구분할 것: ARP 캐시와 스위치 MAC 주소 테이블

- **ARP 캐시(호스트/라우터)**: `IP 주소 → MAC 주소`를 기억한다.
- **MAC 주소 테이블(CAM table, L2 스위치)**: `MAC 주소 → 스위치 포트`를 기억한다.

둘 다 “어디로 보내야 하나”에 쓰이지만 저장하는 정보와 주체가 다르다. 이 구분이 오늘 수업의 중요한 포인트다.

## 4. 데이터 링크 계층(L2)과 프레임

데이터 링크 계층은 같은 링크에서 데이터를 안전하게 전달할 수 있는 **프레임**을 만든다. 이더넷 프레임에는 대표적으로 다음이 포함된다.

- 목적지 MAC 주소
- 출발지 MAC 주소
- 상위 계층 정보(EtherType 등)
- Payload: 실제 전달하려는 상위 계층 데이터
- FCS: 전송 중 오류 검출에 사용하는 값

이더넷의 일반적인 MTU는 1500바이트다. IP 데이터가 이 한계를 넘으면 전송 방식과 설정에 따라 여러 단위로 나뉘어 전달될 수 있다. 여기서 “프레임”, “IP 패킷”, “TCP 세그먼트/UDP 데이터그램”은 엄밀히는 다른 계층의 단위라는 점도 기억한다.

---

## 5. 캡슐화와 역캡슐화: 데이터가 가는 길

애플리케이션 데이터는 전송될수록 각 계층의 제어 정보가 덧붙는다.

```text
보낼 때
애플리케이션 데이터
  → [TCP/UDP 헤더 | 데이터]
  → [IP 헤더 | TCP/UDP 헤더 | 데이터]
  → [Ethernet 헤더 | IP 헤더 | TCP/UDP 헤더 | 데이터 | FCS]

받을 때
Ethernet 확인/제거 → IP 확인/제거 → TCP/UDP 확인/제거 → 애플리케이션에 데이터 전달
```

이 과정을 **캡슐화(encapsulation)**, 수신 측의 반대 과정을 **역캡슐화(decapsulation)** 라고 한다. 라우터를 지날 때마다 L2 프레임은 다음 링크에 맞게 새로 만들어질 수 있으므로 MAC 주소는 홉마다 바뀔 수 있지만, 보통 IP의 종단 목적지는 유지된다.

---

## 6. 스위치와 게이트웨이가 하는 일

### L2 스위치: 같은 LAN 안에서 MAC 기준으로 전달

L2 스위치는 들어온 프레임의 출발지 MAC과 유입 포트를 학습한다. 이후 목적지 MAC을 알고 있으면 해당 포트로만 전달한다.

- **Learning**: 출발지 MAC이 어느 포트에 있는지 학습
- **Forwarding**: 목적지 MAC이 알려졌을 때 해당 포트로 전달
- **Flooding**: 목적지 MAC을 모르거나 브로드캐스트 프레임일 때, 들어온 포트를 제외한 여러 포트로 전송
- **Filtering**: 같은 포트에 있는 것으로 판단되는 경우 불필요한 전달을 막음
- **Aging**: 오래 사용되지 않은 MAC–포트 항목을 삭제

### 라우터/게이트웨이: 다른 네트워크로 전달

서브넷이 다르면 L2 스위치만으로는 충분하지 않다. 기본 게이트웨이(대개 라우터)가 목적지 IP를 기준으로 다음 경로를 선택한다. `traceroute`/`tracert`에서 보이는 hop들은 이와 같은 라우팅 경유 지점을 관찰하는 도구다.

## 7. TCP와 UDP: “보낸다”의 의미가 다르다

| 구분 | TCP | UDP |
|---|---|---|
| 연결 | 연결 설정 후 통신 | 연결 설정 없이 전송 |
| 신뢰성 | 순서, 수신 확인, 재전송 등을 제공 | 기본적으로 수신 확인/재전송 없음 |
| 특성 | 상대적으로 복잡하지만 신뢰성 높음 | 단순하고 지연이 작아 실시간성에 유리 |
| 대표 사용 | 웹, 파일 전송 등 | 음성·영상 스트리밍, 일부 실시간 서비스 등 |

TCP에서 포트 번호는 한 PC 안에서 어느 애플리케이션/서비스가 데이터를 받아야 하는지 구분한다. IP가 “어느 장비”, 포트가 “그 장비의 어느 서비스”인지에 해당한다.

UDP도 데이터를 일정 크기로 나누어 보낼 수 있지만, TCP처럼 수신 확인과 자동 재전송을 보장하지 않는다. 그래서 패킷 손실을 애플리케이션이 감수하거나 별도로 처리해야 한다.

## 8. 패킷 캡처 실습의 목적

실습은 Python/Scapy로 UDP 패킷을 만들고, 다른 Ubuntu 환경에서 `tcpdump`로 이를 관찰하는 흐름이었다. 목적은 “코드가 보냈다”가 아니라 **실제 네트워크에서 헤더와 Payload가 어떤 모양으로 나타나는지 확인하는 것**이다.

### 흐름

1. 수신 측에서 특정 인터페이스와 조건으로 `tcpdump`를 실행한다.
2. 송신 측에서 Scapy로 IP, UDP, Payload를 조합해 전송한다.
3. 캡처 결과에서 출발지/목적지 IP, 포트, Payload를 확인한다.
4. 필요하면 이더넷 헤더까지 표시하여 MAC 주소도 확인한다.
5. PCAP 파일로 저장하여 Wireshark 등에서 더 편하게 분석한다.

예시 명령의 의미:

```bash
sudo tcpdump -i eth0 -nn 'src host 172.24.240.113 and icmp'
ip neigh | grep 172.24.240.113
ping -c 2 172.24.240.113
curl -v http://172.24.240.113:8000
```

- `-i eth0`: 캡처할 인터페이스 지정. 환경에 따라 이름은 다르므로 확인이 필요하다.
- `-nn`: 이름 해석을 하지 않고 IP와 포트를 숫자로 그대로 표시한다.
- 필터 표현식: 특정 출발지 호스트와 ICMP 조건에 맞는 패킷만 본다.
- `ip neigh`: ARP/이웃 캐시를 확인한다.
- `ping`: ICMP 왕복 통신을 확인한다.
- `curl -v`: HTTP 요청 과정과 응답을 자세히 확인한다.

### Payload와 인코딩

Payload는 헤더를 제외한 “실제로 전달하려는 내용”이다. 바이트열로 보낼 때 ASCII만 허용하는 방식이면 한글은 인코딩 오류가 날 수 있다. 한글을 보내려면 예를 들어 UTF-8로 명시적으로 인코딩해야 하며, UTF-8에서 한글 한 글자는 일반적으로 3바이트를 사용한다.

```python
payload = "안녕".encode("utf-8")  # 보통 6바이트
```

캡처에서 Payload 길이와 전체 프레임 길이를 비교하면, 데이터 외에 Ethernet/IP/UDP 헤더가 붙어 전송된다는 사실을 직접 확인할 수 있다.

## 9. PCAP 저장과 분석

`tcpdump -w 파일명.pcap ...`처럼 `-w` 옵션을 사용하면 패킷을 PCAP 형식으로 저장할 수 있다. PCAP은 Wireshark 같은 분석 도구에서 열어 계층별 헤더를 펼쳐 볼 수 있다.

분석할 때는 다음 순서가 좋다.

1. Ethernet 헤더: 출발지/목적지 MAC은 무엇인가?
2. IPv4 헤더: 출발지/목적지 IP는 무엇인가?
3. TCP/UDP 헤더: 출발지/목적지 포트와 프로토콜은 무엇인가?
4. Payload: 실제 데이터는 무엇이며, 인코딩과 길이는 맞는가?
5. 여러 패킷 비교: 바뀐 것은 Payload뿐인지, 포트·길이·체크섬도 함께 바뀌었는지 확인한다.

## 10. 장애 진단과 보안 관점

“내 PC에서는 보냈는데 상대가 못 받는다”는 현상만으로 원인을 단정할 수 없다. 계층별로 좁혀 가야 한다.

| 확인 지점 | 점검 예시 |
|---|---|
| L1/L2 | 링크 상태, Wi-Fi 신호, NIC, MAC 주소, ARP 이웃 정보 |
| L3 | IP/서브넷/기본 게이트웨이, 라우팅, ping/traceroute |
| L4 | TCP/UDP, 포트 사용 여부, 방화벽, 연결 상태 |
| L7 | URL·서비스 설정·인증·애플리케이션 로그 |

ARP 관점에서는 다음을 의심해 볼 수 있다.

- **IP 충돌**: 같은 IP를 둘 이상의 장치가 사용해 통신이 불안정해지는 상황
- **ARP 스푸핑(ARP spoofing)**: 공격자 등이 거짓 IP–MAC 대응을 알려 트래픽을 가로채거나 방해하는 상황

ARP 스푸핑은 “현재 테이블 한 번 보기”만으로 확정하기 어렵다. 신뢰 가능한 기준값과 비교하거나, 시간에 따른 MAC 변경을 지속적으로 감시해야 한다. 특히 기본 게이트웨이 IP에 대응하는 MAC이 예고 없이 바뀌었는지, 여러 IP가 같은 MAC으로 비정상적으로 매핑되는지를 확인한다.

## 11. 실습을 다시 할 때의 체크리스트

- [ ] 각 VM/PC의 IP, CIDR, 기본 게이트웨이를 확인했다.
- [ ] 두 장치가 같은 서브넷인지 계산했다.
- [ ] 같은 서브넷이라면 목적지의 ARP 항목을, 다른 서브넷이라면 게이트웨이의 ARP 항목을 확인했다.
- [ ] 캡처 인터페이스 이름(`eth0`, `ens...` 등)을 실제 환경에 맞게 확인했다.
- [ ] 송신 IP, 수신 IP, 목적지 포트(예: 9999)를 양쪽에서 일치시켰다.
- [ ] Payload의 문자 인코딩을 명시했다.
- [ ] `tcpdump` 출력 또는 PCAP에서 Ethernet → IP → UDP/TCP → Payload 순으로 해석했다.

## 최종 정리

오늘 수업은 CIDR 계산 자체가 목적이 아니라, **CIDR로 같은 서브넷 여부를 판단한 결과가 ARP의 대상과 게이트웨이 사용 여부를 결정하고, 그 결과가 실제 Ethernet 프레임의 목적지 MAC에 반영된다**는 연결을 이해하는 시간이었다.

따라서 패킷을 볼 때는 “IP만 맞는가?”가 아니라 다음 질문을 순서대로 던지면 된다.

> 같은 서브넷인가? → 누구의 MAC을 ARP로 찾아야 하나? → 프레임은 어느 MAC으로 나갔나? → 라우터를 넘어야 하나? → 목적지 서비스의 포트와 프로토콜은 맞나? → Payload는 의도한 바이트열로 도착했나?

이 흐름을 잡으면 ARP, 스위치, 게이트웨이, TCP/UDP, tcpdump/Wireshark가 각각 따로인 지식이 아니라 하나의 통신 과정으로 이해된다.
