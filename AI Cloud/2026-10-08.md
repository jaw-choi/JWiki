## 2. 먼저 작은 기능을 정하고 기능 명세서를 작성하는 이유

### 문제·배경

요구사항 없이 바로 코드를 작성하면 무엇을 구현해야 하는지, 성공 기준은 무엇인지, 프론트엔드와 백엔드가 어떤 데이터를 교환하는지 쉽게 달라집니다. 강사는 **상품·재고 관리 시스템 전체 대신 상품 등록 하나만 구현해도 된다**고 강조했습니다. 오늘은 결과물의 크기보다 기능별로 쪼개어 명세화하는 방식이 중요합니다.

→ 왜 배우나·현업 활용: 과도한 개발 범위를 막고, 짧은 프로젝트 일정에서 최소 기능을 실제로 검증하기 위해 배웁니다.

### 개념: 기능 명세서란?

기능 명세서(functional specification)는 프로그램이 **무엇을 입력받고, 무엇을 검사하고, 어떻게 처리하며, 어떤 결과를 돌려줘야 하는지** 명확하게 기록하는 문서입니다. 회사 표준 양식이 있으면 그 양식을 사용하고, 없으면 Markdown 또는 HTML로 정리해도 됩니다. 화면, 데이터베이스, API, 오류 처리를 기능과 연결해서 작성합니다.

→ 왜 배우나·현업 활용: 개발자·기획자·테스터가 동일한 성공 기준을 공유하여, 작업 요청과 테스트 케이스를 명확하게 만들기 위해 배웁니다.

### 상품 등록 기능의 최소 명세 예시

| 항목 | 최소 정의 |
|---|---|
| 기능 | 상품 등록 |
| 사용자 입력 | 상품명, 가격, 재고, 카테고리 |
| 입력 검증 | 상품명 필수, 가격은 0 이상의 숫자, 재고는 0 이상의 정수 등 |
| 처리 절차 | 화면 입력 → 검증 → 백엔드 API → DB 저장 → 결과 반환 |
| 화면 | 입력 폼, 등록 버튼, 성공·실패 메시지 |
| 데이터베이스 | 상품 테이블과 각 컬럼 정의 |
| 성공 기준 | 정상 입력이 저장되고 등록 결과를 확인할 수 있음 |
| 실패 기준 | 잘못된 입력이나 DB 오류가 적절한 오류로 표시됨 |

위 표는 **녹취의 강의 방향을 기반으로 구성한 학습용 예시**입니다. 실제 테이블 이름·API URL·코드가 확정되었다는 뜻은 아닙니다.

→ 왜 배우나·현업 활용: 기능 요구를 입력값·출력값·검증 규칙으로 변환하여, 프론트/백엔드 연동과 QA 테스트를 빠르게 시작하기 위해 배웁니다.

## 3. 개발 파트를 나누고 작업 이력을 기록하는 이유

### 개발 순서

강사는 여러 작은 단계를 그대로 늘어놓기보다 **3~4개의 큰 작업 묶음**으로 정리하는 것도 권장했습니다. 예를 들어 다음처럼 순차적으로 진행할 수 있습니다.

1. **환경과 데이터:** Python 프로젝트·가상환경 준비, DB 연결, 테이블 정의
2. **백엔드 기능:** 데이터 모델과 검증, 상품 등록 로직, API 구현
3. **프론트 연결:** 등록 화면 생성, 입력·응답 표시, API 연동
4. **검증과 기록:** 정상/오류 테스트, 발견한 문제·수정 내용 정리

모든 개발을 한 번에 AI에게 요구하지 말고, 각 작업 묶음이 완료될 때 **무엇을 했는가 / 왜 했는가 / 어떤 오류가 났는가 / 어떻게 해결했는가 / 아직 안 된 것은 무엇인가**를 문서로 남깁니다. 녹취에서는 AI의 컨텍스트 한계 때문에 작업을 분할하고 중간 기록을 남길 필요성도 설명했습니다. 정확한 용어는 **컨텍스트 윈도(context window)**입니다.

→ 왜 배우나·현업 활용: 장시간 AI 보조 개발에서 이전 합의와 장애 원인을 잃지 않고, 개발자 교체나 후속 세션에서도 동일한 맥락으로 작업을 이어가기 위해 배웁니다.

### 실습 결과물과 완료 판정

오늘 오전 과제의 최소 결과물은 **기능 명세서 1개, 해당 기능의 화면·DB·검증 규칙, 단계별 구현 계획, 가능하면 동작하는 최소 기능, 오류·해결 기록**입니다. 녹취에는 학생이 실제로 모든 기능을 완성했다는 증거는 없습니다. 특히 **K3s는 VM 내부에서 DB·서비스를 연결하는 경로가 Windows에서 VM DB에 접근하는 경로와 다르므로 실행 환경을 구분**해야 한다고 언급했습니다. 오늘 실습에서 K3s 배포가 성공했는지는 **확인 필요**입니다.

→ 왜 배우나·현업 활용: 프로젝트 완료를 막연한 코드 분량이 아니라 검증 가능한 산출물로 판단하고, Windows·VM·K3s 사이의 접속 장애를 구별하기 위해 배웁니다.

### 바로 재사용할 프로젝트 작업 기록 템플릿

```md
## PART 02 — 상품 등록 API
- 목표: 상품 정보를 검증해 DB에 저장한다.
- 선행 조건: DB 접속 확인, 테이블 정의 완료
- 구현 파일/변경 내용:
- 테스트 입력과 기대 결과:
- 실제 실행 결과: (확인 후 기재)
- 발생 오류/원인/해결:
- 다른 구현 방법과 선택 이유:
- 사용자 승인·권한 필요 여부:
- 다음 단계:
```

→ 왜 배우나·현업 활용: Git 커밋·이슈 관리·AI 에이전트 작업 로그를 연결하여, 원인 추적과 재현이 가능한 개발 기록을 남기기 위해 배웁니다.

## 4. MCP는 무엇을 해결하는가?

### 문제·개념

기존에는 사용자가 특정 웹사이트나 프로그램을 열고 직접 버튼을 클릭해야 했습니다. **MCP(Model Context Protocol)**는 AI 애플리케이션이 외부 시스템에서 제공하는 기능과 데이터를 일정한 방식으로 찾아 사용하도록 하는 프로토콜입니다. 단순히 자연어를 이해하는 기능이 아니라 **외부 서버가 허용한 도구를 실제로 호출할 수 있게 연결하는 구조**가 핵심입니다.

→ 왜 배우나·현업 활용: 여러 사내 시스템의 조회·등록 기능을 채팅형 AI에서 연결하여, 반복적인 프로그램 전환과 수동 입력을 줄이기 위해 배웁니다.

### 전체 동작 구조

```text
사용자 자연어 요청
    ↓
AI Host (예: Codex·Claude Code)
    ↓
MCP Client (연결·프로토콜 처리)
    ↓
MCP Server (제공 가능한 기능과 자료 선언)
    ├─ Tool: 동작 실행 (검색·API 호출·파일 저장)
    ├─ Resource: 읽을 자료 (회사 규정·CSV 등)
    └─ Prompt: 재사용할 작업 지시문
    ↓
서버의 실행 결과 → AI Host → 사용자에게 설명·정리
```

중요한 구분: **MCP 서버는 사용자의 모든 요청을 혼자 계획하는 주체가 아닙니다.** 기능의 설명과 인터페이스를 제공하며, 어떤 도구를 선택하고 어떤 순서로 사용할지는 Host/모델과 사용자의 승인 정책에 달려 있습니다. 외부 도구가 항상 자동 실행되는 것도 아닙니다.

→ 왜 배우나·현업 활용: 도구 호출 문제인지, 서버 구현 문제인지, AI의 도구 선택 문제인지 나누어 진단하기 위해 배웁니다.

### Tool·Resource·Prompt 비교 — [보충: HTML 교안 STEP 7~9]

| 구성 | 하는 일 | 예시 |
|---|---|---|
| Tool | 기능 실행 | 웹 검색, 날씨 API 호출, DB 조회, 보고서 저장 |
| Resource | 읽을 데이터 제공 | 업무 규정 문서, 직원 CSV, DB 스키마 |
| Prompt | 반복 가능한 지시문 제공 | 뉴스 요약, 회의록 작성, 코드 리뷰 형식 |

예를 들어 “규정에 따라 위험 교육생 보고서를 저장해줘”라는 요청이라면 **규정을 Resource에서 읽고 → 교육생을 Tool로 조회하고 → Prompt 형식에 맞춰 정리한 뒤 → 저장 Tool을 실행**하는 조합이 가능합니다. 실제 순서는 Host와 구현에 따라 달라집니다.

→ 왜 배우나·현업 활용: 조회 데이터를 무조건 실행 도구로 만들지 않고 책임별로 분리하여, 유지보수와 접근 권한 관리를 쉽게 하기 위해 배웁니다.

## 5. 브라우저 UI 제어 데모와 사용 조건

강사는 컴퓨터 화면을 확인하고 **마우스 이동·클릭·키보드 입력·스크롤을 수행하는 MCP 도구**를 활용한 예시를 설명했습니다. 검색 페이지를 열어 날씨를 검색하고, 정보 일부를 표로 요약하는 흐름을 보여주었습니다. 쇼핑 사이트의 텀블러 검색·가격 정렬·10개 비교도 시도했으나 인증/화면 처리 문제가 언급되어 **정상적으로 결과 10개를 수집했는지는 확인되지 않습니다.** 실제 검색 데이터나 가격은 녹취에 없어 기재하지 않았습니다.

→ 왜 배우나·현업 활용: 기존 사이트에 API가 없을 때 사용자 승인 아래 브라우저를 통한 반복 작업을 자동화하거나, 화면 동작을 검증하기 위해 배웁니다.

### UI 자동화의 한계

- **좌표 기반 클릭**은 창 크기와 화면 배치가 바뀌면 실패할 수 있습니다. 따라서 가능하면 요소 선택자, 접근성 정보 또는 제공된 공식 API를 우선 검토해야 합니다.
- 로그인·CAPTCHA·추가 인증은 자동 실행이 막힐 수 있고 사용자의 개입이 필요할 수 있습니다.
- 강사는 한글 검색어를 시간차로 입력하는 방법을 시연했습니다. 그러나 **사람 입력을 흉내 내어 사이트의 자동화·봇 탐지나 보안 제한을 회피하려 해서는 안 됩니다.** 합법적·승인된 테스트에서는 서비스 이용 조건과 테스트 허용 범위를 따르고, 사이트가 제공하는 API나 테스트 환경을 사용합니다.
- 단순 화면 캡처 후 OCR은 가능할 수 있으나, 이미지의 숫자·텍스트 오인식 여부를 별도로 검증해야 합니다.

→ 왜 배우나·현업 활용: UI 자동화의 실패 원인을 화면 좌표·인증·접근 정책으로 구분하고, 운영 서비스에 피해를 주지 않는 테스트 방식을 선택하기 위해 배웁니다.

## 6. 검색 결과를 가져오는 것과 의미 있는 분석을 만드는 것

강의에서는 **날씨 조회 → 필요한 수치만 표로 정리**, **뉴스 검색 → 기사 3개 → 제목·요약·키워드 추출**, **상품 검색 → 가격·특징 비교 → 인사이트 작성**이라는 예시가 등장했습니다. 이 흐름에서 도구는 정보를 가져오는 역할을 하고, 모델은 결과를 분류·요약·비교할 수 있습니다. 다만 최신 사실을 보증하려면 원문 URL·조회 시점·데이터 출처를 함께 남겨야 합니다.

→ 왜 배우나·현업 활용: 단순 데이터 조회를 보고서나 의사결정 자료로 전환하되, 출처가 없는 요약이나 잘못된 추정을 걸러내기 위해 배웁니다.

또한 강사는 MCP 기반 검색과 RAG(Retrieval-Augmented Generation, 검색 증강 생성)를 비교해 볼 필요성을 언급했습니다. **MCP는 도구·데이터에 접근하는 연결 규약이고, RAG는 외부 정보를 검색해 모델 응답에 반영하는 설계 방식**입니다. MCP로 RAG 검색 도구를 제공할 수도 있으므로 둘은 무조건 대체 관계가 아닙니다.

→ 왜 배우나·현업 활용: 사내 규정 질문 응답 시스템을 설계할 때, 문서 검색 전략과 AI-서버 연결 전략을 각각 선택하기 위해 배웁니다.

## 7. Codex에 MCP 서버 등록·조회·검증하기

강의 후반에는 **OpenAI 개발 문서 검색용 MCP 서버**를 Codex에 연결하는 방법을 설명했습니다. 핵심은 **등록 → 목록 확인 → 서버 상세 확인 → 실제 도구 호출 테스트** 순서입니다. 단지 목록에 보인다고 실제 기능을 쓸 수 있는 것은 아닙니다.

→ 왜 배우나·현업 활용: 서버 연결 문제와 도구 자체 오류를 분리하고, 사내 MCP를 IDE나 에이전트에 안정적으로 제공하기 위해 배웁니다.

### Codex CLI 실습 — Windows PowerShell / VS Code 터미널

> **주의:** 다음 예시는 일반적인 Codex CLI 명령 형태를 보여줍니다. 수업 녹취에는 실제 서버 URL이 정확하게 남아 있지 않습니다. 서버 주소·지원 옵션은 **현재 공식 문서로 확인 필요**이며, 임의의 URL을 실제 값으로 가정하지 않습니다.

```powershell
# Codex CLI가 설치된 터미널에서
codex mcp list

# 공식 주소를 확인한 뒤 등록 (자리표시자 교체 필요)
codex mcp add openai-developer-docs --url <확인한_MCP_서버_URL>

# 등록 목록 및 개별 설정 확인
codex mcp list
codex mcp get openai-developer-docs
```

- `list`: 등록된 MCP 서버 목록 확인. 실행 가능 여부까지 보증하지는 않습니다.
- `add`: 서버를 설정에 등록. `--url`에는 해당 서버가 공개한 MCP 주소가 필요합니다.
- `get`: 개별 서버의 설정을 확인. 이후 Codex에서 **실제 문서 검색 요청**으로 성공 여부를 확인합니다.
- 일부 환경에서는 설정 변경 뒤 CLI/IDE 세션을 다시 열어야 반영됩니다.
- **Codex 웹에서 쓰는 MCP 설정과 로컬 CLI/VS Code의 설정은 같은 것으로 단정하면 안 됩니다.** 각각의 환경과 권한을 따로 확인합니다.

→ 왜 배우나·현업 활용: MCP 도구가 보이지 않거나 호출에 실패했을 때 URL 오타, 인증, 등록 범위, 세션 갱신 문제를 단계적으로 확인하기 위해 배웁니다.

### 서버 이름과 메타데이터의 의미

MCP 도구에는 이름, 설명(description), 입력 형태(schema/type) 같은 정보가 제공됩니다. AI는 이를 이용하여 **어떤 기능을 언제 어떤 인수와 함께 호출할지** 판단합니다. 따라서 `search_docs(query: str)`처럼 이름과 설명이 명확한 도구를 작성해야 합니다. **JSON-RPC**는 MCP 메시지 교환에 사용되는 통신 형식이며, 개발자는 Python의 함수와 스키마를 SDK로 노출할 수 있습니다.

→ 왜 배우나·현업 활용: AI가 잘못된 도구를 고르거나 잘못된 인수를 전달하는 상황을 줄이도록 MCP 도구의 인터페이스를 설계하기 위해 배웁니다.

## 8. TOML, JSON과 구성 파일의 역할

녹취에서는 Codex CLI/VS Code 쪽에서 설정을 다룰 때 **TOML**을 언급했습니다. TOML은 사람이 읽기 쉬운 설정 파일 형식으로 기본적으로 `key = value` 형태를 사용합니다. JSON은 구조화된 데이터 교환에 자주 사용됩니다. `config.toml`은 구성을 저장하는 파일이고, MCP 요청 메시지와 동일한 것은 아닙니다.

```toml
name = "sample-mcp"
version = "1.0"
port = 8000
```

이 TOML 코드는 **문법 소개용**이며 실제 Codex MCP 설정 파일에 그대로 넣으면 동작한다는 뜻이 아닙니다. 실제 설정의 섹션·필드 이름은 사용 중인 Codex 버전의 문서를 따릅니다.

→ 왜 배우나·현업 활용: 로컬 개발 환경을 공유하거나 CI에서 MCP 서버 구성을 재현할 때, 설정 파일과 런타임 메시지의 역할을 혼동하지 않기 위해 배웁니다.

### 짧은 Python FastMCP 구조 예시

**실행 환경:** Windows PowerShell, Python 가상환경. 실제로 실행하려면 `mcp[cli]`를 설치해야 합니다.

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install "mcp[cli]"
```

`server.py`:

```python
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("Sample Server")

@mcp.tool()
def add(a: int, b: int) -> int:
    """두 정수를 더합니다."""
    return a + b

if __name__ == "__main__":
    mcp.run(transport="stdio")
```

```powershell
mcp dev server.py
```

- `python -m venv .venv`: 프로젝트 전용 Python 패키지 환경 생성
- `Activate.ps1`: Windows PowerShell에서 가상환경 활성화
- `pip install`: MCP SDK 설치
- `mcp dev server.py`: MCP Inspector 기반 개발 테스트(설치된 도구 및 실행 환경 확인 필요)
- 예상 확인: `add` Tool이 목록에 나타나고, 정수 입력으로 계산 결과를 반환하는지 점검. **실제 테스트 성공 기록은 없음**

→ 왜 배우나·현업 활용: 복잡한 외부 서비스 연결 전 가장 단순한 함수부터 MCP 호출 경로가 정상적인지 검증하기 위해 배웁니다.

### 데이터베이스와 보안 — [보충: STEP 11, 13, 14]

DB를 연결할 때 `run_sql(sql)`처럼 임의 SQL을 실행하도록 만들면 데이터 유출이나 변경 위험이 커집니다. 교안에서는 **읽기 전용 연결, 미리 정의된 SELECT, 매개변수 바인딩, 결과 건수 제한, 오류 정보 비노출**을 강조했습니다. 원격 MCP는 HTTPS, 사용자 인증, 역할별 권한, 감사 로그, 비밀키 관리까지 필요합니다. OAuth에서 인증(Authentication)은 '누구인가', 인가(Authorization)는 '무엇을 할 수 있는가'를 뜻합니다.

→ 왜 배우나·현업 활용: AI가 자연어 요청을 받더라도 허용된 데이터만 조회하도록 제한하고, 운영 환경에서 누가 어떤 Tool을 호출했는지 추적하기 위해 배웁니다.

## 10. 오늘의 실습을 다시 수행하는 순서

1. **범위를 축소합니다.** 상품·재고 관리 전체가 아니라 상품 등록 하나를 선정하고, 입력·검증·DB·화면·오류·성공 기준을 작성합니다.
2. **작업 계획을 3~4파트로 나눕니다.** 환경·DB → 백엔드 → 프론트 → 테스트·기록의 순서로 정리합니다.
3. **최소 기능을 실행합니다.** 입력값을 저장하고 다시 확인할 수 있는지 검증합니다. DB 초기화·삭제 명령은 기존 데이터 손실에 주의합니다.
4. **이슈 로그를 기록합니다.** 실제 발생한 오류 원문, 사용한 명령, 실행 위치(Windows/VM/K3s), 해결 여부를 함께 적습니다.
5. **Codex에서 MCP를 확인합니다.** 이미 등록된 서버 목록을 확인하고, 공식 URL을 검증한 뒤 개발 문서 MCP를 등록하며 실제 검색까지 시험합니다.
6. **확장 과제를 선택합니다.** 필요하다면 FastMCP로 로컬 Tool을 하나 만들고 Inspector에서 개별 기능을 확인합니다.

→ 왜 배우나·현업 활용: 프로젝트 산출물과 MCP 연결을 서로 독립적으로 검증하여, 자동화가 실패해도 어느 단계에서 문제가 생겼는지 찾기 위해 배웁니다.

## 11. 자주 발생할 수 있는 문제와 확인 순서

| 상황 | 가능한 원인 | 먼저 확인할 내용 |
|---|---|---|
| 서버가 `list`에만 보이고 호출되지 않음 | 잘못된 URL·설정 미반영·인증 | `get`, 실행 로그, 새 세션에서 Tool 테스트 |
| 브라우저 클릭이 엉뚱한 곳에서 실행됨 | 창 크기·좌표 불일치 | 화면 해상도, 요소 위치, 선택자 지원 여부 |
| 검색 결과가 비어 있음 | 권한·사이트 제한·검색 조건 문제 | 원본 사이트·공식 API·로그 확인 |
| VM DB 접속 실패 | IP·포트·바인딩·방화벽·네트워크 위치 | 호출 주체가 Windows인지 VM/Pod인지부터 확인 |
| AI가 이전 작업 내용을 잊음 | 컨텍스트 한계·불충분한 기록 | PART별 완료 문서와 현재 작업 상태 재제공 |
| 원격 MCP 접근 거부 | 토큰 누락·만료·scope 부족 | 401/403, 인증 서버, 토큰 대상·권한 확인 |

위 표는 **녹취의 실패 가능성과 교안의 운영 원칙을 바탕으로 한 장애 대응 가이드**로, 오늘 모두 발생한 오류라는 의미는 아닙니다.

→ 왜 배우나·현업 활용: 장애를 무작정 재시도하지 않고 설정·네트워크·권한·코드 오류로 분류하여 복구 시간을 줄이기 위해 배웁니다.

**주의:** 오늘 수업만으로 해당 직무 준비가 끝나는 것은 아니며, 실제 구현과 테스트 근거가 있는 포트폴리오가 필요합니다.

## 15. 신입 면접 예상 질문과 답변

### Q1. 기능 명세서를 작성하고 개발을 시작해야 하는 이유는 무엇인가요?

**답변:** 기능 명세서는 입력·출력·검증 규칙과 성공 조건을 개발 전에 합의하는 문서입니다. 이를 바탕으로 프론트엔드·백엔드·테스트 담당자의 작업 경계를 구분할 수 있습니다. 요구사항 변경 시에도 어떤 기능과 테스트가 영향을 받는지 확인하기 쉽습니다.

### Q2. MCP에서 Host, Client, Server의 역할은 어떻게 다른가요?

**답변:** Host는 사용자가 대화하는 AI 애플리케이션이며 도구 사용 흐름을 조율합니다. Client는 MCP Server와 통신하는 연결 단위이고, Server는 Tool·Resource·Prompt 같은 기능을 제공합니다. 모델이 직접 데이터베이스에 무제한 접근하는 것이 아니라 서버가 허용한 기능을 통해 작업한다는 점이 중요합니다.

### Q3. MCP의 Tool과 Resource는 어떻게 구분하나요?

**답변:** Tool은 API 호출이나 보고서 저장처럼 작업을 실행하는 데 사용합니다. Resource는 회사 규정이나 CSV처럼 참고할 데이터를 URI 기반으로 제공합니다. 단순 문서 열람은 Resource가 자연스럽지만 조건 검색이나 권한 확인이 필요한 경우에는 Tool도 고려할 수 있습니다.

### Q4. MCP 서버가 등록되었는데 AI가 도구를 사용하지 못하면 어떻게 대응하나요?

**답변:** 먼저 서버 주소와 설정이 맞는지, 클라이언트에서 서버가 활성 상태인지 확인하겠습니다. 다음으로 실제 도구 목록 조회와 단독 호출 테스트로 연결 문제와 도구 실행 문제를 구분하겠습니다. 인증과 실행 로그도 확인하고, 설정이 변경되었다면 세션 재시작 여부를 점검하겠습니다.

### Q5. AI가 자연어로 DB를 조회하도록 만들 때 보안상 무엇을 고려해야 하나요?

**답변:** 모델이 만든 임의 SQL을 그대로 실행하는 방식은 피하겠습니다. 미리 정의한 읽기 전용 쿼리와 매개변수 바인딩을 사용하고, 노출 컬럼과 반환 행 수를 제한하겠습니다. 원격 서비스라면 인증·권한 검사와 감사 로그를 추가해 사용자별 접근 범위를 통제하겠습니다.
