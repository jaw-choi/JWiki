## 1. 오늘의 목표와 전체 흐름

**[오늘 작업]** 노트북용 Windows AI 비서에서 음성 명령이 실제 앱 실행으로 이어지도록 하고, 팀원 모듈 및 Electron 프론트엔드와 연결 가능한 인터페이스를 준비했습니다. 오전에는 음성·에이전트 통합, 점심 무렵에는 팀 코드 연동, 오후에는 MVP 명세 및 Local IPC, 저녁에는 LLM 라우팅 평가와 시연 준비를 진행했습니다.

`사용자 발화 → 호출어 감지 → STT(음성→문자) → 에이전트/도구 선택 → OS 제어 또는 서버 명령 → 결과 → TTS(문자→음성)`

Electron을 통한 흐름에서는 호출어 감지 이후 UI 상태 이벤트를 전달하고, 녹음 및 음성 출력은 정해진 IPC 계약에 맞춰 협업해야 합니다. 모든 과정이 항상 동일한 단일 코드 경로로 동작한다고 단정할 수는 없으며, 모드와 통합 상태에 따라 달라집니다.

→ 왜 배우나·현업 활용: 비서 기능의 시작부터 실행 결과까지 책임 경계를 이해하여, 음성은 인식되지만 앱이 열리지 않는 장애를 단계별로 추적하기 위해 배웁니다.

## 2. 오전 09:15~11:00 | 공유 준비와 음성 기능 완성

→ 왜 배우나·현업 활용: 운영체제별 실행 환경 차이를 이해하여, 개발 PC와 배포 환경 간 시간 표시 오류를 줄이기 위해 배웁니다.

### 2.2 음성 인식에서 에이전트 실행, 음성 응답까지

**[오늘 작업]** `--agent` 옵션으로 음성 인식과 에이전트의 도구 실행을 연결했습니다. 호출어 검출이 약한 원인을 진단 스크립트로 찾아 마이크 입력 크기를 조절하는 `MIC_GAIN` 설정을 추가했습니다. Google TTS를 기본 음성 출력으로 사용하고 실패하면 Windows 음성 출력으로 전환했습니다. TTS 출력 중 자신의 음성이 마이크로 다시 들어온 경우를 걸러내도록 했고, Google 인증·제한 관련 403 문제를 해결한 뒤 실제 음성 응답을 확인했습니다.

**[이해 보충]** STT(Speech-to-Text)는 소리를 텍스트로 바꾸고, TTS(Text-to-Speech)는 텍스트를 소리로 바꿉니다. 마이크 게인을 무작정 높이면 잡음까지 증폭될 수 있으므로 인식 성공률과 오탐률을 함께 측정해야 합니다. HTTP 403은 서버가 요청을 거절했다는 뜻이며, 원인은 API 권한·사용 설정·키 제한·할당 정책 등으로 다양하므로 실제 원인을 로그로 확인해야 합니다.

→ 왜 배우나·현업 활용: 입·출력 음성 파이프라인을 이해하여, 호출어 미인식이나 TTS 실패가 발생했을 때 해당 단계만 분리해 검사하기 위해 배웁니다.

### 2.3 협업 규칙

**[오늘 작업]** 커밋과 PR(Pull Request: 코드 변경을 검토·병합하도록 요청하는 절차) 작성법을 정리하고, **병합은 GitHub PR에서만 수행**하도록 지침을 보완했습니다.

## 3. 오전~점심 11:00~13:00 | 팀원 기능과 연결

### 3.1 `os_bridge`: 다른 팀원의 기능을 수정하지 않고 사용하기

**[오늘 작업]** 김규연님의 실제 `os_control` 구현과 한재윤님의 `/agent/commands` API를 확인했습니다. `os_bridge` 어댑터를 작성해 OS 제어 코드 자체를 수정하지 않고 결과를 에이전트 도구 규격으로 변환했습니다. 크롬, VS Code, 메모장, 유튜브, 구글 실행을 확인했습니다.

**[이해 보충]** 어댑터(Adapter)는 서로 다른 두 모듈 사이에서 요청·응답의 **형식**을 바꿔 주는 연결층입니다. 예컨대 OS 제어 모듈이 반환하는 실행 결과를 에이전트가 해석하는 `success/failed/rejected` 같은 공통 상태로 정규화할 수 있습니다. 이는 두 코드의 내부 구현을 서로 모르게 만드는 장점이 있습니다.

→ 왜 배우나·현업 활용: 모듈 간 의존성을 줄여, OS 제어 구현이 변경되더라도 에이전트 코드의 수정 범위를 어댑터로 제한하기 위해 배웁니다.

### 3.2 서버 API 인증과 테스트

**[오늘 작업]** 개발 계정 로그인, 계정 미존재 시 자동 가입, 토큰 만료 시 재로그인을 지원하는 명령 API 클라이언트를 만들었습니다. 팀원의 API를 해당 작업 공간에서 띄워 확인했고, 서버 WebSocket 음성 경로가 `stt.py`를 사용하도록 연결된 PR #3도 확인했습니다. `main` 위에서 자신의 변경을 검증해 팀 테스트 **47개 통과**를 확인했습니다. PR #4는 CI의 줄 길이 오류를 고친 뒤 **Squash 병합**했습니다.

**[이해 보충]** WebSocket은 연결을 유지하며 양방향 메시지를 주고받는 통신 방식이고, CI(Continuous Integration)는 코드 변경 때 테스트·스타일 검사를 자동 수행하는 작업입니다. Squash 병합은 여러 커밋을 하나로 합쳐 병합 이력을 간결하게 만듭니다. 자동 가입은 개발 환경에 적합할 수 있지만 운영 환경에서는 가입 정책과 보안 검토가 필요합니다.

→ 왜 배우나·현업 활용: 인증·통신·자동 검증의 역할을 이해하여, 프론트와 서버의 연동 중 토큰 만료 또는 배포 전 테스트 실패를 대응하기 위해 배웁니다.

### 4.2 공통 계약: 추적 ID·출처·실행 상태

**[오늘 작업]** 담당 범위 F-01~F-04, F-12를 정리했습니다. `request_id`와 `source(voice/ui)`가 `os_control`까지 전달되도록 했고, 도구 결과는 `success`, `failed`, `rejected` 중 하나로 표현했습니다. 이미 실행 중인 앱은 다시 열기보다 기존 창을 앞으로 가져오도록 했습니다. 역할은 1번 음성, 2번 Windows, 3번 데이터, 4번 프론트, 5번 백엔드로 정리했습니다.

**[이해 보충]** `request_id`는 하나의 요청을 여러 모듈의 로그에서 같은 작업으로 식별하도록 돕는 식별자입니다. `source`는 음성 호출과 버튼 클릭을 구분합니다. `failed`는 실행 실패, `rejected`는 정책 또는 확인 절차 등에 의해 실행을 거부했음을 뜻하도록 계약을 명확히 해야 혼동이 줄어듭니다.

→ 왜 배우나·현업 활용: 모듈 사이에 동일한 메타데이터와 결과 규격을 유지하여, 특정 사용자의 음성 명령이 어느 구간에서 실패했는지 로그를 연결해 분석하기 위해 배웁니다.

### 4.3 Electron 중심 구조

**[오늘 작업]** 노션 API 명세를 분석해 Electron을 프론트 중심으로 사용하고, 로컬 음성 모듈은 Local IPC(Inter-Process Communication: 같은 PC 안의 프로세스 간 통신)로 연결하기로 했습니다. IPC와 녹음 방식은 4번 담당자의 구현에 맞추고, 경로는 명세 기준으로 정했습니다. AI 답변과 실제 실행 결과가 불일치하는 문제는 보류했습니다.

→ 왜 배우나·현업 활용: UI 프로세스와 Python 실행 프로세스의 책임을 구분하여, 화면 상태 갱신이나 마이크 점유 충돌을 방지하기 위해 배웁니다.

## 5. 오후 15:30~17:00 | Local IPC와 서버 데이터 연동

### 5.1 이벤트로 프론트엔드와 협업

**[오늘 작업]** `--ipc` 모드를 추가해 `wake_word.detected`, `ui.state.update` 이벤트를 전송하고 `tts.speak` 메시지를 수신하도록 했습니다. 메시지 규격과 실제 전송 방식은 분리했습니다. PC에서 호출어 인식이 동작했으며 해당 확인 과정에서 확신도 **0.915**가 기록되었습니다. 호출 뒤 응답 전까지 호출어 감지를 중지해 Electron 녹음과 충돌하지 않게 했습니다.

→ 왜 배우나·현업 활용: 비동기 이벤트와 상태 전환을 이해하여, 음성 응답 중 재호출되거나 여러 녹음 작업이 겹치는 오류를 예방하기 위해 배웁니다.

## 6. 저녁 17:00 이후 | 하이브리드 에이전트 평가

**[오늘 작업]** gpt-4o-mini를 이용한 69개 문장 평가에서 다음 결과를 기록했습니다.

| 라우팅 방식 | 정확도 | 시간 | 토큰 |
|---|---:|---:|---:|
| 규칙만 | 78% | 0초 | 0 |
| LLM만 | 88% | 2.15초 | 2,420 |
| **Hybrid** | **91%** | **0.85초** | **959** |

하이브리드 방식은 LLM만 사용하는 경우와 비교해 **정확도 약 +3%p**, 처리 시간 약 **60.5% 감소**, 토큰 사용량 약 **60.4% 감소**했습니다. 표의 정확도는 반올림된 값이며, 시간과 토큰이 총합인지 평균인지는 **확인 필요**입니다. `규칙만 0초` 역시 측정 해상도나 표시 방식에 따른 값으로 해석해야 하며 실제 연산이 전혀 없다는 뜻은 아닙니다.

**[이해 보충]** 규칙 기반 라우터는 명확한 표현을 빠르게 분류하고, LLM(Large Language Model: 대규모 언어 모델)은 규칙만으로 처리하기 어려운 자연어를 유연하게 해석합니다. 하이브리드 라우팅은 쉬운 요청은 규칙으로 처리하고 애매한 요청만 LLM으로 보내는 방식입니다. 정확도와 응답 시간, 비용의 균형이 개선될 수 있지만 위험한 작업에는 별도의 권한 확인이 필요합니다.

→ 왜 배우나·현업 활용: 모델 호출을 반드시 모든 요청에 사용하지 않아도 되는 이유를 이해하여, 서비스 응답 지연과 토큰 비용을 줄이면서 명령 분류 성능을 유지하기 위해 배웁니다.

**[오늘 작업]** 포트폴리오 근거(⭐1 성능 수치, ⭐7 호출어, ⭐8 연동 설계), 팀 공유 자료, 설명 스크립트, 작업 기록과 다음 날 시연 절차도 정리했습니다.

## 7. 실제 시연 명령과 점검 순서

```powershell
python -m local_runtime.voice --agent --speak
```

- **실행 위치:** 프로젝트 코드와 패키지를 인식할 수 있는 Windows PowerShell의 프로젝트 루트, 올바른 Python 환경을 활성화한 상태.
- **목적:** 로컬 음성 입력 → 에이전트 처리 → 음성 답변을 시연.
- **옵션:** `-m`은 Python 모듈 실행, `--agent`는 에이전트 연동 모드, `--speak`는 응답 음성 출력 모드입니다(오늘 기록 기준).
- **확인할 것:** “자비스, 크롬 실행해 줘”를 말한 뒤 호출어 감지, STT 결과, 도구 실행, 실제 Chrome 창 반응, TTS 순서가 이어지는지 점검합니다.
- **문제 발생 시:** 마이크 장치와 `MIC_GAIN` → 호출어 진단(`wake_debug.py`) → STT 출력 → 에이전트 라우팅 → `os_bridge`와 OS 실행 결과 → TTS 및 인증 로그 순으로 범위를 좁힙니다.
- **주의:** 명령 실행으로 브라우저 같은 실제 앱이 열릴 수 있습니다. `--ipc` 기반 Electron 전체 시연은 별도 통합 테스트가 필요하며, 위 명령 하나로 Electron 통합까지 검증되는 것은 아닙니다.

→ 왜 배우나·현업 활용: 재현 가능한 최소 시연과 장애 진단 순서를 확보하여, 발표 현장에서 음성 입력 실패와 외부 API 실패를 빠르게 구분하기 위해 배웁니다.

## 12. 신입 면접 예상 질문과 답변

**Q1. 음성 비서에서 STT와 호출어 감지를 왜 구분하나요?**  
A. 호출어 감지는 비서가 입력을 처리하기 시작할지 결정하고, STT는 실제 명령 문장을 텍스트로 바꿉니다. 두 단계를 구분하면 평소 불필요한 명령 처리를 줄이고, 문제가 생겼을 때 호출 실패인지 문자 변환 실패인지 따로 진단할 수 있습니다.

**Q2. 어댑터 패턴을 적용한 이유는 무엇인가요?**  
A. 팀원의 OS 제어 모듈과 에이전트가 기대하는 입력·출력 형식이 다를 수 있어서 중간에 `os_bridge`를 뒀습니다. 원래 모듈을 직접 변경하지 않고 공통 결과 형식으로 바꾸므로 협업 충돌과 결합도를 줄일 수 있습니다.

**Q3. IPC와 WebSocket은 어떻게 다른가요?**  
A. IPC는 같은 기기에서 서로 다른 프로세스가 통신하는 개념이고, WebSocket은 네트워크 연결에서 양방향 메시지를 지속적으로 주고받는 프로토콜입니다. 이 프로젝트에서는 Electron과 로컬 Python 모듈에는 IPC 계약을, 서버 음성 기능에는 WebSocket을 활용하는 구조를 확인했습니다.

**Q4. 하이브리드 라우팅을 사용한 이유와 근거는 무엇인가요?**  
A. 모든 요청에 LLM을 사용하면 응답 시간과 토큰 비용이 증가할 수 있어 명확한 명령은 규칙으로, 애매한 문장은 LLM으로 분류하도록 접근했습니다. 제공된 69문장 평가에서 하이브리드 방식은 정확도 91%, 0.85초, 959토큰으로 LLM 단독보다 높은 정확도와 낮은 측정 시간·토큰 사용량을 보였습니다.

**Q5. '자비스'라고 말했는데 앱이 실행되지 않으면 어떻게 진단하겠습니까?**  
A. 먼저 마이크 입력과 호출어 감지 로그를 확인하고, STT 문장이 정상 전달됐는지 봅니다. 이후 동일한 `request_id`를 기준으로 에이전트 판단, OS 제어 결과, UI 상태 반영까지 순서대로 추적해 실패 단계를 좁히겠습니다. 실행이 거부된 것인지 실패한 것인지도 구분해 사용자에게 적절히 안내하겠습니다.
